# v1.2.0 — Machine & Multiblock Kernel


> 平台：Minecraft 1.20.1 / Forge / Java 17
> 版本策略：实现、审核和人工批准分离
> 适用规约：`AGENTS.md`、`docs/05-MASTER-TEST-PLAN.md`、`docs/06-RELEASE-AND-ACCEPTANCE-GATES.md`、`docs/14-PARALLEL-DEVELOPMENT-AND-WORKTREE-COORDINATION.md`、`docs/17-V1PLUS-QUALITY-BUDGETS.md`


## 1. 版本目标

从已验证的电解机垂直切片中提取轻量、可测试的过程机器与多方块基础设施，为批量恢复旧机器铺路，同时避免重建庞大的 LibVulpes。

### 玩家可见结果

- 获得至少三种结构和输入输出差异明显的可靠机器。
- 多方块成型失败会显示可读原因。
- 机器在区块卸载、重启和结构破坏后保持资源守恒。

## 3. 本版范围

- 通用 `ProcessMachineLogic`、状态、进度与配方执行。
- Item/Fluid/Energy port 契约。
- 多方块 pattern、旋转、镜像、标签/精确方块匹配。
- Controller/part 绑定、成型、解体和重验证。
- 可读 formation diagnostics。
- 至少三台代表机器迁移。
- 通用菜单同步和 JEI 适配点。
- v1.0/1.1 电解机数据兼容。

## 4. 明确不做

- 不复刻 LibVulpes 全部 GUI 模块、网络实体或抽象层。
- 不一次迁移所有旧机器。
- 不在框架中硬编码具体机器配方。
- 不允许多方块强制加载未加载区块。

任何非目标若要提前，必须单独 ADR，明确存档、网络、兼容、安全和回退影响。

## 5. 本版待冻结契约

- 过程逻辑与 BlockEntity/GUI 分离。
- 能力端口有明确 side/方向规则。
- 多方块验证返回结构化结果，而不是布尔值。
- 所有机器资源变更是原子步骤并可在保存点恢复。
- 框架只包含至少被两种实现复用的能力。

契约冻结后，下游任务只能通过变更提案请求调整，不能在各自 worktree 中自行改变公共语义。

## 6. 详细实施顺序

1. 审计电解机重复逻辑并形成提取清单。
2. 实现纯 Java `ProcessState` 和 recipe simulation。
3. 实现 capability port facade 与 side policy。
4. 选择三台代表机器：单方块、普通多方块、多输入输出复杂多方块。
5. 实现 pattern schema、旋转/镜像和诊断。
6. 实现 controller/part 生命周期、区块卸载与解体。
7. 先迁移第二台机器验证框架，再迁移电解机，避免为旧实现量身定制。
8. 迁移第三台复杂机器验证端口组合。
9. 实现 DataGen/recipe/JEI 公共支持。
10. 建立机器 schema migration 和代表世界 fixture。
11. 压力测试大量 idle/active machine 和结构重验证。

## 7. 可并行工作流

| 工作流 | 允许写入 | 依赖/说明 |
|---|---|---|
| Process core | `machine/process/**` | 纯 Java优先 |
| Ports/capabilities | `machine/port/**` | 与 process 并行 |
| Multiblock pattern | `machine/multiblock/pattern/**` | 先冻结 schema |
| Representative machines | 各自独立包 | 等待框架 contracts |
| JEI/DataGen | 集成目录 | 等待 recipe contracts |
| Migration/tests | fixtures/tests | 独立审核 |

中央注册、版本、网络总入口、Gradle、`mods.toml` 和状态文件由集成任务独占。

## 8. 存档、网络与数据迁移

- 旧电解机 NBT 无损读取。
- 迁移不能重复产出配方结果。
- controller/part UUID/位置变更有 schema。
- 结构未加载完整时保持 `UNKNOWN/WAITING`，不误解体。
- 旧能力 side 配置有明确映射。

## 11. 人工与视觉测试

- [ ] 三种 GUI 在 GUI scale 2/3/4。
- [ ] 多方块缺失部件的定位反馈。
- [ ] 成型/解体模型与碰撞一致。
- [ ] JEI 配方显示与实际执行一致。
- [ ] 长配方名称、不同语言和超出范围数值。

Xvfb/LLVMpipe 只形成 `V0` 视觉冒烟证据。涉及 GUI、天空、模型、粒子或客户端性能时，必须在真实 GPU 客户端形成 `V1`；涉及多人时形成 `V2`。

## 12. 安全与滥用测试

- [ ] 客户端不能提交完成进度或产出。
- [ ] 远程 GUI/无权限玩家操作被拒绝。
- [ ] 伪造 controller/part 坐标不加载区块。
- [ ] 超大 pattern/配方输入受限。
- [ ] 重复 packet 不重复产出。

## 13. 性能与资源预算

- [ ] idle 机器近零或低 tick 成本。
- [ ] active machine 不每 tick 重扫整个结构。
- [ ] 结构变更通过 dirty/event 驱动。
- [ ] 大量 capability 查询有缓存但失效正确。
- [ ] 参考压力满足质量预算。

## 14. 通过确认

- [ ] 三种差异明显的机器共享框架且无大段生命周期复制。
- [ ] 电解机世界无损升级。
- [ ] 多方块旋转/镜像/卸载/重启全部通过。
- [ ] 没有无界扫描或资源复制。
- [ ] 框架公共 API 有文档和最小样例。
- [ ] 零 Critical/High。

## 17. 失败与回退

- 旧电解机 decoder 在支持周期内保留。
- 框架接入按机器逐台进行，可回退单台适配。
- 结构状态不确定时停止处理并保留资源。
- 若抽象只服务单台机器，回退并删除无效层，而非继续扩大。
