## Context

Gate G4's general dedicated-server matrix includes player-state
synchronization, two-player consistency, chunk-unload behavior, configuration
mismatch handling, and proof that an optional client mod can be absent without
affecting the server. The v0.0.2 bootstrap registers no gameplay, project
packet, shared player or world state, ticking object, permission, inventory, or
interaction. Its only project config value controls lifecycle logging, and it
declares no optional runtime or client-only dependency.

The matching packaged-client join, disconnect, same-world restart, reconnect,
and missing-project-mod observation remain mandatory. This decision does not
replace those tests and does not make G4 pass.

## Decision

For v0.0.2 only, classify these five cases as `NOT_APPLICABLE`:

1. **Project-state synchronization:** there is no project packet, synchronized
   project capability, or server-owned gameplay state to transfer on join. The
   normal Forge mod/version handshake and a real matching-client join remain
   mandatory.
2. **Two-player consistency:** there is no project-owned multiplayer state in
   this milestone whose consistency can be compared.
3. **Chunk-unload behavior:** there is no project block, entity, ticking
   service, persistent world state, or chunk lifecycle callback whose behavior
   can be observed across an unload.
4. **Configuration mismatch:** the only project config value toggles diagnostic
   lifecycle logging. v0.0.2 has no compatibility-bearing config, project
   protocol, or defined config-mismatch rejection behavior to exercise.
5. **Optional client dependency absence:** there is no optional client
   dependency to remove for a distinct test case. A clean packaged client with
   Forge and the project JAR remains required for the matching-client test.

Repository owner `sunthemoon` accepted all five classifications on 2026-08-30.
The decision is version-scoped and does not by itself make G4 pass: the required
matching-client, restart/reconnect, and missing-project-mod observations still
need mechanically complete evidence and final human Gate review.

## Risk and user impact

- A bootstrap-only side or connection fault could be missed if the required
  matching-client and missing-project-mod cases are not completed.
- No synchronization, chunk lifecycle, configuration compatibility, or
  gameplay consistency claim is made because v0.0.2 exposes no corresponding
  project behavior.
- The decision must not be carried into v0.1.0 or later, where new registered
  content or dependencies may create testable multiplayer behavior.

## Temporary mitigation

- Require the packaged server smoke test and client-class boundary scan.
- Require a physical client/server JAR hash match, first join, disconnect,
  same-world restart, reconnect, and combined log review.
- Require the Forge-only missing-project-mod observation without pre-filling
  whether Forge accepts or rejects the connection.
- Make evidence readiness fail while any applicability review is absent or
  requests an additional test.
- Treat `REQUIRE_ADDITIONAL_TEST` as a blocking review request, not a final
  disposition. Before executing that request, amend this ADR and the evidence
  schema with the reviewer-defined protocol and acceptance evidence. Do not
  relabel a completed applicable test as `NOT_APPLICABLE` merely to satisfy the
  current strict checker.

## Alternatives

### A. Run two packaged clients

This remains available if the reviewer rejects the first classification. It is
not selected automatically because there is no project state to compare.

### B. Invent an optional dependency for the test

Rejected. Adding an unused dependency would expand the milestone solely to
manufacture a test condition and would violate the vertical-slice scope.

### C. Invent project state or a compatibility-bearing config

Rejected. Adding packets, persistent state, ticking content, or a new
compatibility contract solely to manufacture synchronization, unload, or
config-mismatch cases would implement later-version behavior in the bootstrap
milestone. If a reviewer finds existing v0.0.2 behavior that makes one of these
cases applicable, that real behavior must be tested instead.
