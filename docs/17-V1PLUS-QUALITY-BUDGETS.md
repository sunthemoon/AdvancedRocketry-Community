# v1.0+ 质量预算与验收等级

## 1. 目的

测试数量不能替代质量判断。本文件为 `v1.0+` 定义统一的：

- 环境可信等级；
- 缺陷阻断规则；
- 性能预算；
- 数据、网络和扫描上限；
- 真实视觉 Gate；
- 迁移与恢复要求。

具体阈值可通过 ADR 调整，但不得在失败后无记录地降低门槛。

## 2. 验证环境等级

| ID | 环境 | 用途 | 可放行 Gate |
|---|---|---|---|
| `A0` | Pure Java | 算法、状态机、Codec、迁移单元 | G3 部分 |
| `A1` | Forge GameTest | 世界/方块/实体行为 | G3 |
| `S1` | 打包专服 | sidedness、保存、网络、运行 | G4–G7 |
| `S2` | 强制停止/恢复专服 | 事务和崩溃恢复 | G5–G6 |
| `V0` | Xvfb + LLVMpipe | 客户端视觉冒烟 | 仅补充证据 |
| `V1` | 单真实 GPU 客户端 | 正式视觉和基础性能 | G8 |
| `V2` | 两真实客户端 | 多人、乘客、权限、同步 | G6/G8 |
| `R1` | 干净 release 重建 | 制品可重现 | G9 |

## 3. 缺陷等级

### Critical

- 可稳定复制物品、流体、方块、火箭或卫星奖励；
- 存档损坏且没有恢复路径；
- 火箭/乘客永久消失；
- 任意代码执行、凭据泄漏或远程管理绕过；
- 客户端包使服务器加载任意区块或造成无限资源消耗；
- 主流程无法完成。

**任何 Critical 阻断发布。**

### High

- 常规操作导致崩服/崩客户端；
- 跨维度事务重复或丢失；
- 非所有者可操作空间站/轨道武器；
- 迁移后关键状态错误；
- 无上限扫描、NBT、packet 或任务队列；
- Dedicated Server 加载客户端类。

**任何未修复 High 阻断发布。**

### Medium

- 有明确规避方法但影响核心体验；
- 一部分受支持配置无法工作；
- 明显性能回退；
- UI 状态不同步但不破坏数据；
- 低概率恢复错误但能人工修复。

候选版不应带未审核 Medium。必须修复，或由维护者在 `KNOWN-ISSUES` 中签署有限豁免、受影响范围和修复版本。

### Low

- 轻微视觉、文本或交互问题；
- 不影响数据和流程的小问题。

可带入发布，但必须公开记录。

## 4. 参考服务器预算

参考节点：4 vCPU / 8 GiB / Debian 12。初始目标：

| 项目 | 默认预算 |
|---|---|
| Forge server Java heap | `Xmx4G` 以内 |
| 测试常态 RSS | 不持续超过 5.5 GiB |
| 平均 MSPT | ≤ 25 ms（定义的参考负载） |
| P95 MSPT | ≤ 50 ms |
| P99 MSPT | ≤ 100 ms |
| 单次非启动/保存尖峰 | 不应持续超过 500 ms |
| Watchdog/OOM | 0 |
| 非预期强制加载区块 | 0 |
| 4 小时 soak 后单调内存增长 | 不允许 |

这些值必须和“参考负载”一起记录；空服数据不能证明大型火箭或大气压力场景。

### 参考负载最少包含

- 2 名真实或可验证行为等价的玩家连接；
- 16 个氧气设备/密闭体；
- 10 个空间站记录；
- 100 个卫星/任务；
- 2 枚活动火箭；
- 至少一次 2048 方块火箭组装/拆解；
- 至少一次维度转移；
- 周期性保存和重启。

`v1.9` 应升级到更高并发和 8–12 小时 soak。

## 5. 扫描和队列预算

每个系统必须有可配置硬上限，并在超限时给玩家可读失败原因。

| 系统 | 必须限制 |
|---|---|
| 火箭扫描 | 方块数、包围盒、BlockEntity NBT 总量、扫描时长 |
| 大气扫描 | 体积、节点/tick、活动任务数、等待区块数 |
| 多方块结构 | 最大尺寸、匹配耗时、重验证频率 |
| 卫星任务 | 每玩家数、全局数、每 tick 完成数、离线补算上限 |
| 星图/路线 | 节点数、路径搜索预算、缓存大小 |
| 轨道武器 | 目标范围、区块可见性、权限、调用频率 |
| 数据包重载 | 定义总数、文件大小、错误聚合上限 |

超限不得：

- 强制加载无限区块；
- 在主线程一次性完成无界工作；
- 静默截断导致资源丢失；
- 继续相信客户端提交的数据。

## 6. 网络预算

所有 C2S packet：

- 有方向声明；
- 在主线程验证；
- 验证 sender、距离、权限、状态和区块加载；
- 有频率限制；
- 不接受最终资源计算结果；
- 不接受任意 NBT 或无限集合；
- 有协议版本或兼容策略。

建议初始预算：

```text
单常规 packet：尽量 < 64 KiB
结构快照：分段、压缩并有 1 MiB 级总上限
每玩家高频 UI 同步：只发送差量/摘要
服务器拒绝超限包：记录一次审计日志，不回显巨大内容
```

实际值由测试和 ADR 冻结。

这些建议不放宽现有更严格上限。v0.9 基线的 `RocketLimits` 已限制视觉快照
总量 524288 bytes、分块 32768 bytes、BlockEntity NBT 总量 1048576 bytes，
v1.0 稳定化保留这些边界；改动需原有基准和批准 ADR。

## 7. 存档预算

每个持久化对象必须具备：

- schema/version；
- 明确默认值；
- 非法/缺失字段处理；
- 最大集合/字符串/NBT 大小；
- 旧版迁移；
- round-trip 测试；
- 崩溃恢复或事务语义；
- 失败时不覆盖原存档副本。

版本发布前至少验证：

```text
上一个 stable → 当前 candidate
上一个 beta/rc → 当前 candidate
当前 candidate 保存 → 重启
当前 candidate 事务中断 → 恢复
当前 candidate 重复迁移 → 安全拒绝或幂等
```

## 8. 真实客户端视觉预算

绝对 FPS 依赖硬件，因此正式判断使用“基线对比 + 不可接受尖峰 + 正确性”。

每个候选版本记录：

- CPU、GPU、驱动、分辨率、GUI scale；
- Vanilla/Forge 空场景基线；
- 64、512、2048 方块火箭；
- 单火箭和多火箭；
- 天空、粒子、OBJ、GUI；
- 平均 FPS、1% low、首次出现卡顿；
- 客户端内存和结构缓存；
- 资源重载后缓存释放；
- 跨维度后旧缓存释放。

最低正确性：

- 无缺失纹理紫黑块；
- 无模型跨格、穿插或明显偏移；
- GUI 在测试缩放下无关键按钮越界；
- 天体/天空与服务端环境一致；
- 火箭乘客位置稳定；
- 重新连接后实体和视觉一致；
- 日志无持续 OpenGL 错误风暴。

Xvfb/LLVMpipe 结果只能标记 `V0`，不能产生 `V1/V2 PASS`。

## 9. 发布制品预算

- 审核前从干净候选 commit 构建；批准且证据完整后创建 tag，再验证相同制品；
- JAR、sources、LICENSE、NOTICE 和 provenance 完整；
- 不含测试世界、密钥、token、开发日志或个人路径；
- 不含重复资源；
- 所有上游导入有来源 ledger；
- JAR SHA-256 固定；
- GitHub Release、tag、manifest 和 mods.toml 版本一致；
- 完整安装步骤由未参与开发的人执行一次。

## 10. Gate 降级规则

任何门槛改变必须：

1. 新建 ADR；
2. 说明原门槛、失败原因和真实风险；
3. 提供新门槛及验证数据；
4. 指定是否临时；
5. 指定恢复原门槛的版本；
6. 由非原实现会话审核。

禁止为了让候选版“通过”而直接删除测试、缩小压力场景或把失败项改为非目标。
