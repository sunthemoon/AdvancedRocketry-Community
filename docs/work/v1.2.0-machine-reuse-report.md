## Deliberately separate responsibilities

Electrolyzer retains its old schema-1 machine root, single-block storage,
legacy-progress adoption and status mapping. Rolling retains physical Item,
Fluid and Energy storage in four ports. Its pattern is 5/3/2 in x/y/z and does
not enable mirroring. Precision uses five fixed inputs, two outputs and one
Energy port in a 3/3/4 pattern with mirroring; ADR-019 central Item ownership,
two-barrier migration, retained shadows/markers and pending-removal policy
are Precision-specific.

The Rolling and Precision managers still have similar event queue, reindex,
validation and process scheduling adapters. Shared algorithms do not mean
zero duplicated lifecycle orchestration. There is no claim that a general
machine manager or universal migration framework has been delivered.

Likewise, the common transaction executor orders calls to adapter stores; it
does not make separately saved chunks atomic. Precision's central Item
guarantee must not be extrapolated to Rolling's physical ports, external FE
transfers, Item entities or hardware power loss. Artifact-specific coverage
and limits remain in the [migration report](v1.2.0-migration/REPRESENTATIVE-MACHINE-MIGRATION.md)
and [Precision persistence report](v1.2.0-precision-assembler/PREC04B-VERIFICATION.md).

## Size review

Source inspection counted the following production classes above 500 lines:

| Class | Lines | Responsibilities inspected |
|---|---:|---|
| ElectrolyzerProcessController | 656 | Process orchestration, old schema adoption, recovery and display-state mapping |
| PrecisionAssemblerBlockEntity | 516 | Forge lifecycle bridge, controller Item ownership and migration/persistence coordination |
| PrecisionAssemblerPortBlockEntity | 508 | Binding, legacy shadow/marker preservation and capability lifetime |

Process algorithms and persistence helpers are separate. No production class
over 800 lines was found in the inspected process/port/multiblock/three-machine
scope. This is not a claim about the whole repository or a waiver of the
500-line review rule.

The original size review found `RollingMachineGameTests` at 819 lines (11 cases
plus fixtures), without a class-size ADR. The later
[V120-TST-02 extraction](v1.2.0-rolling-test-fixtures/VERIFICATION.md) resolves
that specific gap: the unchanged eleven scenarios occupy a 763-line container,
with five constants and seven helpers in an 85-line fixture class. The >500-line
responsibility review is recorded there; no production refactoring or size
waiver was introduced.

## Verification boundary

The guide changes no Java, schema, recipe or generated resource. Its examples
point to the actual process unit tests and runtime JSON included in the U
checkpoint's clean build (600 JUnit / 121 Required GameTests). Source references,
dimensions, mirroring, amounts and ownership are checked against the implementation.
Independent documentation review and repository/link validation are recorded in
the canonical [implementation log](v1.2.0-implementation-log.md).

The later [JEI client check](v1.2.0-jei-integration/CLIENT-VERIFICATION.md)
verifies default recipe display, catalysts and menu click areas at one scale
and language. Version status and G0–G9 are unchanged; neither this comparison
nor the short automated run establishes
full visual, multiplayer, reference-load or whole-content acceptance.
