### L1 — casing label depends on resource namespace iteration

Location: original `src/main/java/io/github/sunthemoon/advancedrocketrycommunity/datagen/V180LanguageProvider.java:49–50`,
with existing `datagen/V170LanguageProvider.java:27`.

The v1.8 provider emits `block.advancedrocketrycommunity.endgame_casing` in
`advancedrocketrycommunity_v180`, but v1.7 still emits the same key with its old
label in `advancedrocketrycommunity_v170`. The actual Forge 47.4.10 mapped
Minecraft classes load language entries by resource-manager namespace iteration:
`MultiPackResourceManager` stores namespaces in a `HashMap` and returns its
`keySet`; `ClientLanguage.loadFrom` iterates that set and overwrites map entries.
Version order does not establish precedence.

The independent Java 17 probe reads the actual packaged namespace set. With
the current 17 namespaces the resulting order happens to select the v1.8
label. Adding eight distinct namespaces grows the map to the next capacity;
the `_v170` entry then follows `_v180` and the modeled English result is
`Endgame Casing`. This violates ADR-064 §4's display-label requirement for an
otherwise harmless mod/resource combination. Saved IDs and gameplay remain
unaffected, hence Low under the repository's text/visual severity definition.

Evidence: [mapped client loader bytecode](ClientLanguage.javap.txt),
[mapped namespace manager bytecode](MultiPackResourceManager.javap.txt),
[independent namespace/label probe](NamespaceOrder.java),
[probe output](namespace-order-02.txt). This is a static platform-code and
Java-container observation, **not** a real-client resource-reload run.
Use an unambiguous description key or a single authoritative translation entry;
verify actual block/item description IDs and bilingual generated resources.
Root has proposed a correction; its separate source freeze must be reviewed
before treating L1 as resolved.

## Design/security/provenance observations

Motors are inert blocks/items, not ticking adapters or global world state;
there is no new packet, capability inventory, schema or world scan. Two small
pure generators define bounded JSON/art, with four DeferredRegister entries
of each type. Shapeless crafting is an explicitly documented encoding of the
accepted quantities, not an inferred recipe-number change. Vanilla crafting
recipe data needs no custom JEI category; actual JEI/client presentation has
not been tested here.

MotorArt constructs original pixels without reading upstream or official
bitmap files; the NEW declaration precedes generation in repository metadata.
No LibVulpes code/art was read or copied by this reviewer. This supports the
NEW scope but is not by itself full G0 approval; content screening, the broader
provenance manifest and release audit remain separate evidence.
