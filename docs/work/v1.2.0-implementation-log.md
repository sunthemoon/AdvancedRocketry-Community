# v1.2.0 implementation log

## Goal

建立轻量、服务端权威、可迁移且有硬边界的过程机器与多方块内核，并以
三台结构和输入输出差异明显的机器证明复用价值，不复刻 LibVulpes。

```yaml
version: v1.2.0
status: IN_PROGRESS
phase: INTEGRATING
branch: codex/v1.2.0-precision-assembler
base_commit: 660cfc95c1dff7901a25ad937cc3c0e3242e51ef
prerequisite: v1.1.0 PASSED
prerequisite_observed: not_satisfied
runtime_implementation_allowed: true
accepted_adrs: [ADR-016, ADR-017, ADR-018, ADR-019]
test_scheduling_adr: ADR-018
last_updated: 2026-09-26
```

## Scope and non-goals

ADR-016/017 已于 2026-09-06 接受，允许从固定基线开展 v1.2.0 生产实现。
开发顺序例外不创建候选、不放行 G0–G9，也不改变 `v1.1.0` 的实际状态。

明确不做：LibVulpes 复刻、全部旧机器迁移、动态 GUI DSL、任意区块强制
加载、v1.3 公共 API、长期压力执行和发布 Gate 判定。

## Decision log

1. 代表机器暂定为 Electrolyzer、Rolling Machine、Precision Assembler。
   三者分别覆盖单方块、普通多方块和复杂多输入结构；Item 与 Energy 被三者
   使用，Fluid 被前两者使用，满足“至少两种实现再抽取”的约束。
2. 实现顺序暂定 Rolling Machine → Electrolyzer → Precision Assembler。
   先用新机器验证框架，再迁移已存在机器，避免为 v0.2 实现量身定制。
3. `advancedrocketrycommunity:electrolyzer`、`electrolyzing` 和
   `arce_machine` schema 1 是兼容输入，不在本阶段更名或删除。
4. pattern 不读取未加载区块；结果为 `WAITING_UNLOADED`，不是结构损坏。
5. ADR-016 中的限制值已由维护者冻结；修改须回到契约评审并记录迁移影响。
6. Pattern cell 与可绑定 part 分开：普通 casing 可参与结构而无需 BlockEntity；
   只有发现到的 binding target 进入 controller 的持久化 part 集合。
7. `QUEUE_FULL` 要求调用者停止继续入队并稍后重试；队列不静默丢弃 dirty 事件。
8. 生命周期核心不等同于机器集成；`V120-LIFE` 在 Rolling Machine 的实际
   controller/part 与方块事件接入完成前保持 `in_progress`。
9. Rolling Machine 使用一份社区原创 2×3×5 结构和四种明确 port block ID；只沿用
   已审计的尺寸与行为类别，不转换上游 cell 布局、资源或 recipe JSON。
10. 长期负载与完整视觉/多人矩阵按 ADR-018 延后，但每个 Rolling 叶任务仍执行
    定向单测、build、DataGen 和 Required GameTest，失败不得以延期策略豁免。
11. 维护者于 2026-09-10、2026-09-11、2026-09-25、2026-09-26 再次确认：须先完成原有机械与维度清单，
    再启动完整的长时负载、专服、真实 GPU、双客户端及全机械/全维度集成测试；
    单个切片完成不触发完整测试，开发期间的短周期 Required 检查仍照常执行。
12. Rolling port 资源使用机器私有稳定根 `arce_rolling_port` schema 1，根与单个
    Item 数据分别限制为 64 KiB/16 KiB；未来或无效 schema 原样保留并停止形成与
    Capability 访问。后续格式变化只能通过显式迁移，不能静默重写。
13. `rolling` 配方只接受有界 vanilla Item/Tag ingredient、water 与无 NBT Item
    结果；单定义限制 64 KiB、ingredient 文本 4096 字符、解析变体 32 个，服务端
    单次 lookup 最多接受 1024 份 Rolling 配方，歧义或超量均 fail closed。
14. Item/Fluid 在完成点通过 `arce_process_journal` 事务提交，Energy 按 ADR-016
    逐 tick 扣除；若重载数据只有满进度而没有 journal，控制器进入
    `RECOVERY_REQUIRED`，不进行第二次无能耗结算。journal 阶段写入目前调用
    BlockEntity `setChanged()`，不宣称每阶段强制 fsync；打包专服中断证据留给
    `V120-ROLL-05`。
15. 服务停止时继续清空 Rolling 索引与静态 runtime bridge，并在下一次
    `ServerAboutToStartEvent` 重新安装同一受生命周期约束的 manager，避免集成客户端
    返回标题后开启第二个世界时 bridge 永久为空；连续两次启动的打包证据仍留给
    `V120-ROLL-05`。
16. Rolling 菜单不增加自定义 C2S 包；打开位置由服务端写入 vanilla menu buffer，
    `stillValid` 同时校验 controller 方块与玩家距离，资源槽每次只解析当前已加载、
    已形成且 generation 一致的端口。结构失效或过期 view 均 fail closed。
17. vanilla `ContainerData` 在网络上只传 16-bit 字段，因此世界坐标与最高 72,000 tick
    的进度使用显式 low/high halves；enum 使用固定 wire ID 而非 ordinal，未知值映射为
    无权限或无动作的安全状态。
18. v1.2 DataGen 独占 `src/generated/v1.2/resources` 的 35 个非缓存输出；当前 provider
    生成 Rolling 的模型、语言、配方、战利品和合并后的挖掘标签，历史 v0.1/v0.8 标签
    副本只在资源打包时排除，既有来源文件不被改写。
19. `V120-ROLL-05` 的打包强制中断场景先执行 `save-all flush`、观察保存完成并记录
    region hash，再直接终止进程而不发送 `stop`。该证据证明已持久化的活动进度可在
    非优雅终止后恢复并 exact-once 完成；它不声称每个 journal phase 都会同步 fsync。
20. Electrolyzer 保留 `advancedrocketrycommunity:electrolyzer`、`electrolyzing` 和
    `arce_machine` schema 1 兼容入口，以窄 adapter 使用共享 process/port 契约；不抽取
    公共 BlockEntity 基类，也不改变现有批次、菜单和方向策略。
21. legacy 活动状态迁移只建立可验证的 `arce_process` 快照，不查找配方、不消耗资源、
    不产生输出且二次读取幂等。future、invalid 或超过 64 KiB 的 legacy/process/journal
    根原样保留并阻止执行与外部资源访问。
22. Electrolyzer 恢复只接受机器 ID、完成进度、配方签名和 transaction plan 全部匹配的
    journal；孤立或不匹配 journal fail closed。失效 capability view 永久不可恢复，菜单
    合并、直接替换与 quick-move 均经过同一服务端 storage 锁。
23. v0.2 打包迁移 fixture 以单次 `setblock` 原子写入完整 legacy BlockEntity NBT；旧的
    `setblock` 后 `data merge` 会混合初始化后的新 process root 与旧状态，不能作为纯
    legacy 迁移输入。
24. Precision Assembler 的五个同型 Item 输入端口与两个同型输出端口在原创 3×3×4
    pattern 中占据固定本地 cell；对应 channel 由本地 cell 分配，不由方块放置顺序、
    世界朝向或镜像决定。配方只匹配已声明输入槽，未声明槽非空时不选择短配方。
25. Precision Assembler 配方使用与 Rolling 共享的有界 vanilla Item/Tag ingredient
    codec；不接受带 NBT 的输入，因为当前 process 快照只以 Item ID 计量。两台机器
    的定向回归均覆盖该共享解码器。
26. v1.2 新机器的 JEI 分类只从可执行 `ProcessDefinition` 生成 Item/Fluid/能耗
    展示，不维护第二套客户端配方数值；适配仅位于 client compat，保留旧
    Electrolyzer 的兼容日志标记，不把 JEI 类型暴露给 common/server。
