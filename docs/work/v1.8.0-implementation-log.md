# v1.8.0 implementation log

## Goal and scope

Deliver [Classic Content Completion](../versions/V1.8.0-CLASSIC-CONTENT-COMPLETION.md):
restore the classic machines, materials, items, armor, components, recipes,
models, sounds and progression in source batches, with provenance, hashes,
licenses and conversion records for every imported file, until the porting
matrix has no `UNKNOWN` and no in-scope `MISSING`. Development evidence does not
approve a release or remove inherited Required Gates.

```yaml
version: v1.8.0
status: IN_PROGRESS
phase: CONTRACT_REVIEW
execution_state: ACTIVE
branch: codex/v1.8.0-classic-content
proposed_development_baseline: 55da6a58842762c382edce0a5a842d06bb76ff6e
runtime_implementation_allowed: false    # until ADR-060..062 are ACCEPTED
runtime_build: 1.20.1-1.7.0-dev          # unchanged in C14
last_updated: 2026-10-02
```

The v1.7 handoff is a development baseline, not a passed prerequisite. ADR-060
must separately authorize this version before any runtime change. Root is the
sole tracked writer. Independent review uses read-only repository access and
fresh Temp outputs. The untracked user documentation bundle stays excluded from
reads and writes. No upstream code or asset is imported in C14.

## C14 — porting matrix audit and batch plan

Planned outputs:

- Branch from the v1.7 handoff commit `55da6a5`.
- A read-only [content audit](v1.8.0-content-audit.md) of the pinned upstream
  commit `c5cd5af`, fetched as an archive into Temp and hash-checked against
  `legacy-manifest` (510 Java files, 898 assets, all equal).
- A deterministic [legacy inventory](v1.8.0-legacy-inventory.json) of 653
  units, generated by `tools/audit/inventory_v180_content.py`.
- The [content ledger](v1.8.0-content-ledger.csv) (one disposition per unit) and
  the [asset plan](v1.8.0-asset-plan.csv) (one handling per legacy asset), both
  checked by `scripts/validate_v180_content_ledger.py` and its unit tests (46
  after review round 2, plus 4 calibration tests of the derivation check).
- Contracts: ADR-060 (development baseline exception), ADR-061 (identity,
  import pipeline and sources, validation, recipe graph), ADR-062 (dispositions
  with player impact, earlier deferrals resolved, batch plan).
- The [coverage table](v1.8.0-contract-coverage.md) and porting-matrix rows per
  system.
- Independent contract review rounds until acceptance, then the evidence packet.

Explicit C14 non-goals: any change to production Java, resources, build
scripts or generated data; the runtime version; world migration; new items or
blocks; asset imports; candidate, tag or Gate changes; remote, long-load or
real-client tests.

Progress:

- Revision 1: three ADRs, the audit, the inventory (609 units), the ledger, the
  asset plan, the validator with 18 tests, the coverage table, porting-matrix
  rows and a CI step. A preliminary full Gradle run on this tree passed:
  1,376 JUnit tests and all 337 required GameTests, an empty DataGen diff, and
  all three JARs byte-identical to the v1.7 handoff build (`4326d3d…`,
  `824813c…`, `79116f6…`). The evidence packet follows the acceptance.

- Review round 1 of revision 1: 0 Critical, 2 High, 12 Medium, 7 Low, 6 Info;
  every ADR accepted with required changes. H1 (vanilla-derived art judged by
  name) led to the measured derivation check; H2 removed LibVulpes as a
  source. Every finding is answered in its own commit
  ([review-01-dispositions](v1.8.0-preparation/review-01-dispositions.md));
  revision 2 of ADR-060..062 goes to round 2 with the C15 batch contract
  (ADR-063).
- The full Python test suite (970 tests) shows the same 9 failures and 117
  errors on the clean v1.7 handoff export as on this branch (v0.0.2 manual
  evidence and Markdown-link tests that need a Linux host); none is new.

Decisions made while auditing:

- LibVulpes 1.12 (`c2ca79d`, MIT) was first proposed as an approved
  third-party source; review round 1 (H2) showed that its casing, hatch and
  battery textures came from an unmerged third-party pull request, so
  revision 2 does not approve it and the batches draw that art new.
- Presumed vanilla-derived files are excluded by name match; one model JSON is
  byte-identical to a vanilla file.
- The two language files already used in v0.1.0 are handled as `IMPORTED`;
  later batches extract their own keys under their own records.
