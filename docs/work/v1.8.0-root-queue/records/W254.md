## The S2 finding

On every ticking connection `ServerGamePacketListenerImpl.tick()` runs `player.doTick()` and then
`absMoveTo(firstGood...)`. `doTick()` applies gravity to an airborne server player, because `Entity.isEffectiveAi()` is
`!isClientSide` with no player override (checked with `javap -c` in the pinned mapped Forge 47.4.10 jar). Forge posts
`PlayerTickEvent` END inside `doTick()`, so the exit service's END sample sees the rider 0.0784 blocks lower; its next
sample, at server END, sees the restored position, and `Continuity.observe` rejects that as an upward move. The offer
ends at the first tick with a non-zero velocity. In every failing case the fixture's trace shows the same end, at
`point=SERVER_END` with authority and lease true and the tracker step accepted, for example X5:
`last=152:8.5000:51.0716:… now=152:8.5000:51.1500:…`.

Consequences: a descent that takes longer than about one tick is not protected on a real server, and X2, X4, X5 and X7
cannot pass. The W242 GameTests could not see it, because their embedded players' connections are never ticked. Only
a landing in the exit's own tick or the next one is protected; X9 and X10 use exactly that (W242's first-tick landing)
to show the packaged observers. The analysis and three options for Root are in `FINDING-S2-PLAYER-TICK.md` in the W254
folder; nothing in S2 was changed.

## How the native evidence is made

**The held exit.** A rider can only be aboard a held rocket if it boarded before the hold: during a hold the existing
held-login routing keeps a reconnecting passenger waiting and never remounts it. So every case makes its exit in the
first start, in the same session as the launch:

1. `arce satellite release-test registry-writer arm STAGED PAUSE` (the registry writer's cuts need an empty server).
2. `arce bay release-test exit fixture 8 2 8`: a facility-owned survival test player, `W254Rider`
   (`00000000-0000-4000-8000-000000254001`), is assigned seat 0 and boards the bay forced-stop fixture rocket; the
   fixture then launches as before. It is crew, not the owner.
3. The rocket ascends with its rider. The coordinator claims it, writes and acknowledges the data bay's INTENT, and D2's
   registry write pauses at STAGED: an INTENT hold with the claim waiting on `BAY_REGISTRY_PROOF`, stable for as long
   as the server runs. `exit ready` waits until the rider has a checked exit: the claim, an acknowledged T with its
   guard digest, the exit lease, and both mapped observers.
4. `save-all flush` puts the held rocket (at 48 blocks) and the seated rider on disk.
5. The case drives one exit to its phase and the harness kills the server there.
6. Two restarts with `bayRegistryBlocked=true` turn the durable INTENT into B10's REPAIR hold (the same rows as
   `B10_BLOCKED`), so T stays PREPARED with the rider's seat and the rocket stays locked at altitude. The first restart
   also logs the rider in again.

**Acting like a client.** The fixture uses only what a player's client causes: `stopRiding` (vanilla dismount), the
riding sneak input packet (`ServerboundPlayerInputPacket`, detached by `Player.rideTick` in the same tick), and the
held menu LEAVE through `RocketRuntime.requestFlightIntent`. After an exit it accepts the newest teleport with
`ServerboundAcceptTeleportationPacket`, then descends with one `ServerboundMovePlayerPacket.Pos` per tick, three blocks
apart, through vanilla's `handleMovePlayer`, and lands with an on-ground packet, so the landing runs vanilla's own
`doCheckFallDamage` path. The packets go to the rider's real `ServerGamePacketListenerImpl`; the existing
`ReleaseTestPlayers.pump` ticks its connection every tick as for any test player.

**Measurements.** Each exit command measures, immediately before and after the synchronous exit, the overworld's
loaded-chunk count, the complete ticket map (`DistanceManager.tickets`, read through
`ObfuscationReflectionHelper.findField(..., "f_140761_")` so it resolves in the packaged namespace), and an authority
snapshot: T by identity, the guard digest, the rocket snapshot by identity, the rocket's fuel and manifest, the bay
receipts naming L and the pending charge. The landing packet is measured the same way. The sneak input exit happens
in the next tick's passenger tick, so its measurement spans a whole tick and is recorded, not asserted.

**Trace.** After an exit the fixture logs, read-only and after the exit service's own samples, the rider's sample at
each of the service's observation points (`PlayerTickEvent` START and END, server-tick END) for six ticks, and the
observation that ends the offer, with the authority, lease, counter, correction window and the last and current
samples. Cases that end an offer require exactly one end, at or after their own stimulus or deadline.

## Choices where R279 or the design left room

- **The gate.** Every new command calls `EscrowTestEndpoints.requireEnabled` first, the same complete gate as the bay
  fixture: hooks on, a dedicated server without RCON, and only facility-owned players. The drive's event listeners are
  added only by a command that passed that gate, so an ordinary server never gets them.
- **The freeze.** To kill the server inside the correction window, `exit leave ... freeze` logs its state and then
  holds the server thread for at most 30 seconds; the harness kills the process within about a second. It is the only
  way to cut between the exit's own correction and vanilla's tracker correction, which follows in the next tick's
  Level tick. It changes nothing and is reachable only through the gate.
- **In-tick stimuli.** A dedicated server runs console commands after the Level tick, so the END of the exit's own
  tick comes before vanilla's tracker correction and before the server-side player tick first moves the rider. X6, X9
  and X10 apply their stimulus there. This follows W242's first-tick landing test and keeps those cases independent of
  the S2 finding.
- **The hold.** The registry-writer pause gives a held exit with an acknowledged INTENT, the case W230 section 6
  names. A clean stop is not used at the cut: the paused registry write cannot be released while a test player is
  online (the writer's cuts require an empty server), so the stop would wait on it. Every cut is therefore a kill.
- **The landing heights.** X4 and X7 land ten blocks under the exit, so an unprotected landing hurts (seven points)
  without killing the rider. X9 and X10 fall 3.1 blocks, more than the three-block threshold and within the four-block
  per-tick limit, so a protected landing keeps 20 health and an unprotected one loses one point.
- **The control.** `X0_CONTROL` makes no exit. Every exit case must restart to exactly its durable outcome.

## Known risks

- **The S2 finding** above: the fall safeguard does not survive a real descent on a ticking connection. Until Root
  decides, the safeguard protects only a landing in the first tick or two, and V2 section 3 will record that.
- **The freeze** holds the server thread for up to 30 seconds by design; it exists only behind the gate and only for
  X3. A server that is not killed resumes and logs `ARCE_RELEASE_BAY_EXIT_THAWED`.
- **Timing of X1.** The input exit's offer is live at the cut only because the harness's state query runs before the
  offer's second tick; after the S2 finding is fixed it no longer depends on that.
- **Stimuli at the exit tick's END** rely on a dedicated server running console commands after the Level tick
  (`DedicatedServer.tickChildren`, checked with `javap`); the harness asserts the same tick number for the exit and
  its stimulus, so a change there fails the case rather than passing it.
- **Class sizes:** `BayPassengerExitReleaseDrive` has 377 lines and `BayPassengerExitReleaseTest` 271, both below 500;
  `BayReleaseTestCommands` has 291.
