## What was built

**Root.** `arce_rocket_item_cargo`, schema 1, 32 KiB, depth 20 and 2,048 nodes, with C-A's fields and D-P's `buffer` in
place of the tank. The field set is closed at the root, at the buffer frame (`slots` only, exactly four compound
slots) and in each stack (D-K's `id`, `Count` and `tag`). An empty slot is written as `{}`. A slot is checked by D-K's
structural rule first, then the registry, then the native round trip, so a missing mod reads as `UNREGISTERED_ITEM`
rather than as invalid data. An unknown, future, invalid, mismatched, oversized or unregistered-item root is kept raw
(by reference when it exceeds the envelope) and protects the device, exactly as C-A's root does.

**W118-R6.** The codec closes the field set and writes an empty slot as `{}`. D-P's fixtures already match: both
`EscrowItemCargoEligibilityTest.candidate` and `EscrowItemCargoGameTests.unbound` build `schema_version`, `owner`,
`device`, `role`, `buffer` (the `EscrowItemBuffer` form with `{}` slots) and `resource_escrow`, and
`dpFixtureFormDecodesUnchanged` decodes that form and re-encodes it byte for byte. D-P's size-padding fixtures that add
an `extra` field to a device root test the eligibility envelope only; such a root is a refusal fixture and would also
be invalid under this codec.

**Port.** One `ITEM_HANDLER` instance on every side, bound to a capability epoch. The loader only inserts and the
unloader only extracts. Every call needs the exact loaded instance on the server thread, a claimed and supported
root, no duplicate and no escrow lock, and takes the device's non-reentrant lock before it reads the caller's stack.
Simulation writes nothing. A stale, off-thread or reentrant call moves nothing and shows nothing. `isItemValid`
applies section 5.3's stack bounds; an insert also needs the whole root to fit after the change. Merging needs the
same item and tags under D-K's digest rule; a display name never decides.

**Menu.** Four vanilla slots and the player inventory, opened only by the owner within 8 blocks, usable both ways in
either role (W11CD Q8). On the server, every slot change goes through a guarded container: `mayPlace` and `mayPickup`
take the device lock and check section 5.3's bounds and the root envelope, and the container hands out copies only,
so vanilla never mutates a live stack. Shift-click is the menu's own: out of the device it takes only what the player
inventory can hold; into the device it offers matching slots, then empty ones. Eight scalar values (status, binding,
role, cursor x, y, z and slot) synchronize as shorts; with admission unwired the cursor is absent and its slot is -1.
The client screen is drawn in code and registered from `client/` only. *Superseded in part by W120F (W120-R1, below):
vanilla's item click overrides do change the copies, so the menu now handles device-slot clicks itself.*

**Drops.** The device item carries nothing, so the placer owns a placed device and its placement UUID is always
fresh; a placement by anything but a connected player is unclaimed. Breaking or exploding an unprotected device drops
the plain item through its loot table and spills the buffer once through `Containers.dropItemStack`, as vanilla
containers do; after the spill the block entity shows and exposes nothing. A protected device refuses player removal
before loot, leaves the explosion list, drops and spills nothing and refuses extraction; `/setblock` and `/fill`
remain the recorded residual (one WARN, nothing spilled). `onlyOpCanSetNbt()` is true and the item refuses a
`BlockEntityTag` for every player, operators included.

**Linker and status.** `RocketItemCargoLinker` repeats C-A's linker roles for the item block entity with W11B3's
binding and selection codecs and the linker's 10-tick cooldown; `LinkerItem` dispatches to it. The status comes from
the shared `RocketCargoStatus`; a valid bound device shows `ADMISSION_DISABLED`.

**Native saves.** Section 7 exactly as C-A: the bounded bay preflight; only an observed native incompatibility
records a `GuardedChunkSaves` denial; a lossless root or one over the work budget is saved unchanged; the
serialized-root hook also scans unloaded block entities.

**Resources.** Two original 16x16 textures drawn in code: a bevelled frame, a four-cell parcel hatch and a roller band
whose chevron points into the hatch for the loader and out of it for the unloader, with a side lamp high or low, and
olive and rose tints, distinct from each other and from the fluid devices' couplings. Models, blockstates, loot, the
two shaped recipes of section 5.5 (`" H "` over `"IMC"` and the reverse, with H `minecraft:hopper`, I `item_io_board`,
M `machine_casing` and C `control_board`), unlock advancements, and seven new keys per language (two names, the
placement message and four screen labels). No upstream, LibVulpes, Minecraft or Forge asset.

## Choices where the design or the TASK was open

1. **Shared code instead of copies.** The binding checks gained an owner-and-binding overload rather than a second
   copy, and the fluid index now holds either kind. The linker is a mirror of C-A's for the item block entity, so
   C-A's fluid block entity (which W117 rewrites) is untouched.
2. **Escrow unit.** Item operations name the device endpoint with unit `CONTAINER` (`EscrowOperation`), so the
   read-only hold looks the item device up with `CONTAINER`. The fluid lookup is unchanged.
3. **"An oversized-NBT stack left unchanged in the buffer."** Read both ways and tested both ways: an offered stack
   outside section 5.3's bounds stays where it is (the caller's stack, the carried stack and the buffer are
   unchanged), and a root that already holds an oversized stack is kept raw, protects the device and spills nothing.
4. **Root envelope versus four valid stacks.** Four stacks at the 512-node stack bound exceed the 2,048-node root
   bound. A change that would overflow the root is refused before it is written (the port returns the stack; the menu
   keeps it carried), and the A0 test pins the root at 2,047, 2,048 and 2,049 nodes built from valid stacks. Valid
   content cannot reach the root's byte or depth bounds; those predicates are pinned with padding, as C-A's are.
   *Superseded by W120F (W120-R2, below): a change must also leave room to bind and mark the device.*
5. **Status text.** The item devices reuse W109's shared status keys. Three of them are fluid-worded
   (`DEVICE_EMPTY` and `DEVICE_FULL` say "tank", `INCOMPATIBLE_CARGO` says "fluids"); none is reachable while admission
   is unwired, so this leaf did not change C-A's text. D-E or D-D should word them for items when they become reachable.
6. **Stack size.** The device item carries nothing, so it stacks to 64.
7. **`/setblock` on an unprotected device** spills its buffer (the block entity is not `Clearable`); vanilla chests are
   cleared instead. This keeps items rather than deleting them and needs operator rights.

off-thread event cannot satisfy it, and the assertion message prints the values. Because the test now has a
connected owner, it waits for entity sections with the 80-tick timeout of C-A's player tests (it was 40). No assertion
was dropped and no production code changed. The unit suite at `34705454` still applies, because `10aca023` changes
only that GameTest class.

### W120-R1: device-slot clicks go through the device first

On the server, `RocketItemCargoMenu.clicked` now handles pickup (both buttons), number-key and offhand swap, and throw on
a device slot itself. This is the review's first suggestion, which R47 prefers.

- Under the device's lock it decides and writes the device's part first, through the same `RocketItemCargoLocal`
  operations as the port and shift-click, so section 5.3's stack bounds and the root envelope apply. Only then does it
  change the cursor or the player's slot, so whatever the device refuses leaves both sides as they were.
- An empty cursor takes the stack, or half of it rounded up with the right button. A carried stack goes in whole, or one
  item with the right button, when the slot is empty or holds the same item and tags. Otherwise the two swap, and only
  when the whole carried stack fits the slot. These are vanilla's outcomes without the item overrides.
- No item's `overrideOtherStackedOnMe` or `overrideStackedOnOther`, and no `ItemStackedOnOtherEvent`, ever sees a device
  stack. A bundle in the device, or carried onto it, moves whole like any other item.
- Swap accepts only hotbar keys 0 to 8 and the offhand (40), which is all that vanilla's client sends; any other key
  changes nothing. Throw takes from the device first and then drops what it took: one item with button 0 and the whole
  stack otherwise, as vanilla does.
- `canDragTo` is false for device slots, so a drag never places into one and cannot reach vanilla's single-slot drag
  click, which calls the click code directly rather than through `clicked`. `canTakeItemForPickAll` is false for device
  slots, so a double-click gathers from the player inventory only. Both also hold on the client, so its prediction agrees.
- Shift-click keeps the menu's own `quickMoveStack`. For other clicks the client still predicts vanilla's outcome, and
  the server's state replaces it, as before.

**W120-R3.** No click path calls the container's `setItem` any more, so the residual that the review described (a refused
`setItem` after the cursor or the inventory had already changed, which loses or duplicates one stack) cannot occur.
`setItem` stays a guarded write for any other caller. The W120 menu paragraph and its "Menu residual" item are
superseded here.

### W120-R2: room to bind a filled device, and a clean refusal

- `RocketItemCargoRoot.leavesRoomToBindAndMark()` measures the root with an owner, the largest binding a linker can
  write (a station and a 128-character level ID, as in A0's `full()` fixture) and one escrow marker with a ledger and the
  largest counters in place of its own. `RocketItemCargoBlockEntity.slotFits`, which the port, the menu and shift-click
  all use, now accepts a change only when that measure fits. The reserve is 15 nodes (9 for the binding and 6 for the
  marker), so the four stacks may hold 2,022 of the 2,048 nodes rather than 2,037. Valid stacks cannot reach the byte or
  depth bounds. This is an admission rule inside the existing bounds: decoding, the bounds and the saved form are
  unchanged. A root loaded fuller than the reserve still loads, saves and can be emptied, but takes nothing in until it
  leaves room again.
- `bind` now returns why it refused instead of throwing. A bound root over the envelope, which only such a fuller root
  can reach, is refused as `CARGO_TOO_LARGE` ("Cargo data exceeds the transfer limit; no cargo moved."). For that refusal
  the linker starts its 10-tick cooldown, so a held use does not repeat it with every packet. The lock refusal keeps its
  `ESCROW_PENDING` text and starts no cooldown, as before. Clearing a binding cannot grow the root.
- W120's choice 4 is superseded: a change that would leave no room to bind and mark the device is refused, as well as one
  that would overflow the root.
