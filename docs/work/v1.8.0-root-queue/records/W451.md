## What the mode does

`scripts/run_v180_crash_replay.py --observe-passive` is accepted only together with `--triage-run followup-<name>` and
only for the cases X01-05, X01-06, X01-07, X01-09 and X01-11. For each case it:

1. records the case again with the unchanged runner (one JVM start, the same kill point as S3) and plans the state
   table as S3 did;
2. checks that the named state (`07-LATE-LOSS`, `07-LATE-LOSS`, `01-LATE-LOSS`, `07-LATE-LOSS`, `12-LATE-LOSS`) has the
   same id, the same derivations and the same present or absent seam files as the sealed `states.json`, and refuses
   otherwise;
3. materializes a fresh copy of that state for each of two variants and starts it twice. `hooks` is S3's JVM command
   without `escrowScenario` and `escrowCase`, so no probe is constructed. `plain` also drops `releaseTestHooks`, which
   is the configuration of an ordinary server. Each start waits for `Done`, runs for 20 seconds (about 400 ticks),
   sends `save-all flush`, waits for `Saved the game`, and stops in order;
4. keeps, before the first start and after each stop, the runner's own independent raw decode (ledger, journal,
   endpoint payloads, identities, markers) and a lossless archive of the native files (`level.dat`, `data/*`, region
   and entity files), plus the full logs;
5. compares the typed totals with the kill image, and separately the ledger's sequence, accounts, receipts and
   tombstones, and reports one of `QUANTITIES_CONSERVED_AUTHORITY_OR_HISTORY_LOST`,
   `QUANTITIES_CONSERVED_AUTHORITY_INTACT`, `QUANTITY_LOST_OR_CREATED` (with amounts) or `UNDECIDABLE` (with what is
   missing).

The mode writes no `results.jsonl` row, selects no oracle and reports `OBSERVED`, never `PASS`. Without the flag the
runner behaves as before: no default, oracle, outcome, marker, count or timeout changed, and the existing 44 campaign
tests pass unchanged. The new code is in `scripts/v180_passive_observation.py` (new) and 34 added lines in
`scripts/run_v180_crash_replay.py`. Nothing under `src/` changed.

Markers and locks on disk:

- **X01-05, X01-06, X01-07 and X01-09.** Both endpoints stay at resource epoch 1, each with its one marker of
  sequence 1, and stay bound to the ledger id. The rewound ledger has `issued_through` 0 and no record, so these
  markers name a sequence the ledger no longer knows. Neither start prunes them, in either variant.
- **X01-11.** The endpoints are already normalized at the kill: epoch 0, no marker, the rocket still bound to the
  ledger id and the unloader unbound. Nothing names the lost settlement any more. The receipt that would prove it is
  gone and is not written again.
- No ledger record, armed flight, floor or journal transfer exists in any snapshot, so nothing on disk locks an
  endpoint.

The servers do not react to the loss. In all 20 passive starts the ledger file and the rocket journal are
byte-identical before the first start and after both stops. Each start reached `Done`, saved, and exited with code 0
with no `ERROR` or `FATAL` line. The only `WARN` is the usual `ARCE_FIRST_EVENT_HELD ... SOURCE_UNCONFIRMED`. No
escrow, cargo, transfer, repair or fence marker was logged. The decoded raw files differ between snapshots only in
the chunk's `LastUpdate` (and its compressed length); X01-11's three decodes are identical. Unrelated files changed as on any start: `raids.dat`, and the
satellite registry's baseline write.

## What this does not show

- **No next operation was attempted.** The observation is passive, and C6's cargo admission is off in production
  (`EscrowCargoSwitches.production` returns false for every kind) unless a gated probe opens it for a session. What a later load, unload, disassembly or launch does with endpoints that still carry sequence-1 markers
  under a ledger whose next sequence is again 1 was not exercised. C6 has a guard for this case
  (`EscrowReconciliationPruning` refuses a marker beyond `issued_through` with `LEDGER_BEHIND`), but these runs did not
  reach it, so whether the endpoints end held, repaired or usable is still open. That is an availability question
  and, until tested, also the place where a conservation fault could still hide.
- In-memory locks are not visible from disk or from these logs. The record states only what the files show.
- The comparison uses decoded JSON values, so NBT tag types (byte or int) are not compared. The archived native
  files keep them.
- The decoders read the fixture chunk and its entity slots. Nothing moved, so this is sufficient here.
- Twenty seconds per start is a bounded dwell, not proof that no later tick would act.
- All of W448's residual limits remain: no real power cut, no intermediate late-loss generation, R7 files held at the
  kill image.

## Choices made where the TASK was open

- **Two variants.** "Without the probe" can mean S3's command minus the probe selection, or an ordinary server. Both
  are cheap, so both were run. They agree everywhere.
- **Dwell.** The recovery probe asserted after 100 ticks, and a comment in C6's release probe names a 200-tick
  retry, so each passive start runs about 400 ticks before the save. The option `--observe-dwell` is new and affects only this mode.
- **Fuel** is reported as its own typed total and never added to cargo.
- **A failed start** would still be followed by the second start and reported as `UNDECIDABLE`. None occurred.
- **Rebuilding** by a new recording, as explained above.
