## How the rules are implemented

Choices where W62 and ADR-061 section 4.7 leave room are marked "Choice".

- **Records.** A record is a JSON file in `docs/provenance`. A naming is one target path with one SHA-256 from:
  - `entries` (schema 1 and 2);
  - `related_entries`, which take the status of the cited record's naming (a citation of a record that does not
    name the target fails rule 4);
  - `files` (the v0.3.0 XML fixture) and `local_assets` (v0.0.2);
  - the `targets` of a generated-resource inventory.

  Choice: v0.0.2's bootstrap `targets` are left out, because `validate_bootstrap_provenance.py` owns them and
  `build.gradle` has changed since. The Markdown records are listed in the index but not parsed.
- **Rule 1.** A JAR entry comes from each allowed root that holds its path with the same bytes. None or more than
  one fails. The allowed roots are `src/main/resources`, `src/generated/resources`, every `src/generated/v<x>.<y>/resources`
  and `src/imported/v1.8/resources`. Choice: `src/generated/resources` counts as part of the v0.1.0 managed root,
  as in `validate_v010_asset_baseline.py`. Today 36 paths exist in more than one root (the superseded copies), and
  none of them has identical bytes. Other entries (classes, `META-INF`, `pack.mcmeta`, the logo, 3,003 in all) are
  counted but not placed.
- **Rule 2.** The tree is `git ls-files --cached --others --exclude-standard`, or a directory walk without git.
  Each file and each packaged entry with a legacy-manifest SHA-256 must be named by a record. Choice: its latest
  record must also give it `UPSTREAM_AR_MIT` (or a blocked status, which rule 3 handles). A NEW or GENERATED claim
  on upstream bytes fails.
- **Rule 3.** It fails when a packaged file's latest record is `QUARANTINED` or `REJECTED`, and also when a packaged
  entry has the bytes of such a target under another name. Not checked: the asset plan's REVIEW and EXCLUDE handling
  of legacy files, which the ledger validator and the importer own.
- **Rule 4, the latest record.**
  - A naming listed by another naming of the same target in `supersedes_target_sha256` or
    `supersedes.target_sha256` is superseded, whatever the order.
  - Otherwise, when the remaining namings disagree, the record file added last in HEAD's topological history wins.
    Choice: records added in the same commit must agree, and without git history disagreeing records fail.
  - Among namings with the same SHA-256, a blocked status wins.
- **Rule 5.** The shared files are `src/generated/v1.8/resources/assets/*/lang/<locale>.json`.
  - A naming's recorded version is the version in HEAD's history with its SHA-256.
  - It vouches for its `new_keys` (4 records list them). Otherwise it vouches for the keys that the ordinary commit
    producing that version added or changed (5 records, 1 or 2 keys each). Choice: a version that only a merge
    produced needs `new_keys`, because a merge's diff also holds the other side's changes.
  - For each vouched key, the latest record that vouches for it gives the value, and the current file must still
    have that key with that value. Keys that no record vouches for are not checked.
  - Why not compare whole snapshots: `message.advancedrocketrycommunity.vent.scrubber_recovery_refused` changed
    after the laser-gun record's version. That key belongs to another slice, so a snapshot comparison would fail on
    a legitimate edit.
- **Output.** `--output-dir` writes both files. The exit code is 1 on any failure. Without `--jar`, rules 1 and 3
  are `NOT_RUN` and rule 2 covers the tree only. The JSON names the commit, whether the work tree is clean, the JAR's
  file name and SHA-256, and the tool's own SHA-256. It holds no absolute paths and no timestamps.
- **Limits.**
  - Records: up to 1,024, each up to 4 MiB. The legacy manifest: up to 16 MiB.
  - The tree: up to 200,000 files, each up to 256 MiB.
  - The JAR: up to 256 MiB and 100,000 entries. Each entry is streamed and stops at 64 MiB inflated.
  - Language history: up to 2,000 versions, each up to 8 MiB.
  - Each git call times out after 300 seconds.

## Not done and known risks

- REG fails rule 5 until its checkout fetches the full history (line 1 above). Running the audit without
  `fetch-depth: 0` would be a false failure, not a finding.
- The `supersedes` and `related_entries` fields are read as W53 used them. A later record that re-pins a target at a
  hash that an earlier naming listed as superseded would itself count as superseded. No record does that today.
- The record order uses the commit that added each record file. A record that gains an entry later, as
  `v1.8.0-c16d-acquisition.json` did in `b9a0141d`, keeps its first date. Explicit supersession covers that case
  today.
- The audit checks file identity and record coverage, not origin review. All 12 v1.8 JSON records stay
  `PENDING_HUMAN_REVIEW`, and the REVIEW batches and human approval are outside this task (W62 9.7, class C).
- The 9.7 item 4 gap (seven records without a Java test of their targets) is now covered by rule 4 for every
  target, but only where Root wires the audit in.
- The full Python suite was not run here; it takes over 30 minutes on this machine. GOV runs it.
