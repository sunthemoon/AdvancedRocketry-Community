## Part 1: cause

A launch is governed exactly when the rocket's escrow section has a ledger binding
(`RocketGovernedAdmission.check`: `rocket.escrowSection().ledger() != null`). Its record then carries
`nativeTransfer`.

- `RocketTransferService.tick` (line 310) skips `tickLive` for a record with `nativeTransfer`. The governed flight is
  driven by `RocketGovernedSourceDispatcher.tick` instead.
- The bay's D0 enqueue is one call, `recovery.bays().checkpoint(...)` in `RocketTransferService.tickSource` (line 623),
  at the ASCENT to TRANSIT change. It reaches `BayTransferRecovery.ascentComplete`, which starts the claim.
  `RocketGovernedSourceDispatcher.dispatchLoaded` makes the same state change through
  `EscrowGovernedSourceFlight.tick` and never called the hook.
- So a governed flight skipped D0 only. Every later bay step (D1 to D7) is driven by the coordinator's own queue from
  a claim, and no claim existed, so none of them ran. The gate itself is consulted on governed flights:
  `RocketGovernedSourceDispatcher.tick` and `RocketGovernedLaunchBoundary.allows` call `bays.before(...)`.

**A bay on a governed flight cannot deploy, by the existing design.**

- The source is never neutral. `RocketEscrowGate.bayNeutral` refuses a section with a ledger binding, and a governed
  record exists only for such a section; the ledger's ARMED entry for the rocket is a second refusal.
- `RocketGovernedLaunchBoundary.allows` accepts only an UNCLAIMED bay boundary and refuses a bay permit ("Credited
  bay-source consumption is W27f, not an escrow exemption for a bay permit"). A held claim would only pause the flight.

The designed D0 outcome for such a source is therefore always the refusal `BAY_SOURCE_PROTECTED`. On a governed
flight nobody recorded it, so the menu reason stayed NONE.

## Part 1: fix (`7aeef1e86`)

The proposal was committed first (`a09df105b`) and implemented as proposed.

1. `RocketTransferBayRecoveryGate` has one new default no-op method, `governedAscentComplete`.
   `RocketTransferBayDispatch.governedCheckpoint` forwards to it.
2. `RocketGovernedSourceDispatcher.dispatchLoaded` calls it once, where it already observes the source's change to
   TRANSIT (beside the `transitStarted` feedback).
3. `BayTransferRecovery.governedAscentComplete` applies D0's admission conditions unchanged (not stopping, the gated
   `session.admissionEnabled()`, no claim on the rocket) and D0's own neutral check. For a non-neutral source it
   records `BAY_SOURCE_PROTECTED` in the session's runtime rejection map for each packaged bay of the source snapshot
   and logs one INFO line, `ARCE_BAY_GOVERNED_REFUSED`. The bay menu reads that map (`BayReceipts.deploymentStatus`).
   It starts no claim, writes no receipt, registers nothing, loads nothing and does not pause the flight. For a
   neutral source, which is not reachable, it does nothing: no reason and no deployment.

Why it is minimal: one call at the one missing place, 38 added lines in four files, reusing the existing reason,
rejection map and admission gate. It starts no claim because a legacy claim exists only to hold the transfer while
D0's checks run over several steps. Here the one applicable check is decided at once; a claim would pause a governed
flight and end in a READY_SOURCE handoff that puts a governed transfer into the legacy live set. No saved form,
network packet or public ID changes. With admission off, as in production today, the method returns at its first
line, as D0 does.

Conservative choices: the refusal is recorded only at the dispatcher's own ASCENT to TRANSIT change. A server that
restarts in mid-flight and restores the source directly in TRANSIT records nothing, as a legacy flight's restart rows
record no runtime refusal either.

## Part 2: the seam (`4ff047929`) and B17.3

`ReleaseTestBayEndHold` follows W332's `ReleaseTestLoadFailure`. With the start property
`advancedrocketrycommunity.bayEndUnready=<logical rocket>`, the release-test hooks, a dedicated server and the open
release-test gate, R2's END_LOADING wait of that rocket's restart group does not end in that session
(`BaySourceResume.resume`, asked only after the real readiness check passed; one INFO line
`ARCE_RELEASE_BAY_END_HELD` per rocket). It changes no ticket and no other group's readiness. Without the property it
returns at its first line, before it touches the server; it has no static state. The next start without the
property releases the group, so no release command is needed.

Two new tranches of `run_v180_bay_uncovered.py` use it. Both first run the existing `B3_MOVED` cut, which leaves a
REGISTERED group U on disk after a hard stop.

- `W363_B17_UNLOADED`: restart 1 holds U and launches a healthy fixture flight H from a second origin. H must deploy
  and land while every sample of U shows RESUME, END_LOADING and unchanged receipts. Restart 2 has no hold: U resumes
  and deploys, and H is unchanged. This follows the pattern of B17.1 and B17.2 (waiting work ahead of an in-session
  flight). **PASS.**
- `W363_B17_UNLOADED_RESTART`: a second hard stop first leaves H as a REGISTERED group too, behind U in receipt
  order. Then restart 1 holds U, and H, now a restart group, must resume and land. **FAILED: H never left RESUME.**

No disabled-protection control was run for B17.3: the protection under test is scheduling, and the second case
already shows the oracle failing when progress stops.

### Finding: a waiting restart group starves the restart groups behind it

`BaySourceResume.resume` allows one group per tick: it returns NEXT_TICK when `stepTick == now` and sets `stepTick`
before its waits (lines 84 and 85). A group that waits (TRANSFER_JOURNAL_PENDING, END_UNAVAILABLE, END_LOADING or
RELEASE_FENCED) also returns NEXT_TICK. `BayStepQueue.run` offers NEXT_TICK keys again in the order they ran. So the
first waiting group takes the tick's one R2 slot on every tick, and every restart group behind it is answered
NEXT_TICK without a check for as long as the first one waits.

In the native run H stayed at `claim=RESUME reason=BAY_RESTART`, its initial reason, for the whole 300-second
limit, so R2 never ran one checked step for it. `BayRegisteredGameTests` line 48 already notes that "a second restart
claim in the batch could take the slot until the first one's end had loaded".

Reach: only restart groups in RESUME are affected; in-session flights are not, as the first case shows. In production
END_LOADING normally ends within ticks, because the coordinator tickets the ends. END_UNAVAILABLE is a wait at the
same place with no end (a missing Level or an inadmissible column set), and an end that cannot load never leaves
END_LOADING. I read these two from the code and did not reproduce them. Bay admission is off in production today.

Proposed fix, not made: let only a group that passes its waits take the tick's slot, by setting `stepTick` after
the RELEASE_FENCED wait and before the copy census. The waits are bounded reads (at most 16 columns per end). This
changes production pacing, so it needs its own task.
