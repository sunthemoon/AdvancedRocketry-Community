# W363: the bay on a governed flight, and a gated control for B17.3

Status: IN PROGRESS. This first version holds the cause and the proposed fix, written before the implementation as
the TASK requires. Results are added below as they exist.

## Part 1: cause

A launch is governed exactly when the rocket's escrow section has a ledger binding
(`RocketGovernedAdmission.check`: `rocket.escrowSection().ledger() != null`). Its record then carries
`nativeTransfer`.

- `RocketTransferService.tick` (line 310) skips `tickLive` for a record with `nativeTransfer`. The governed flight is
  driven by `RocketGovernedSourceDispatcher.tick` instead.
- The bay's D0 enqueue is one call, `recovery.bays().checkpoint(...)` in `RocketTransferService.tickSource` (line 623),
  at the ASCENT to TRANSIT change. It reaches `BayTransferRecovery.ascentComplete`, which starts the claim.
  `RocketGovernedSourceDispatcher.dispatchLoaded` makes the same state change through
  `EscrowGovernedSourceFlight.tick` and never calls the hook.
- So a governed flight skips D0 only. Every later bay step (D1 to D7) is driven by the coordinator's own queue from a
  claim, and no claim exists, so none of them runs. The gate itself is consulted on governed flights:
  `RocketGovernedSourceDispatcher.tick` and `RocketGovernedLaunchBoundary.allows` call `bays.before(...)`.

**A bay on a governed flight cannot deploy, by the existing design.**

- The source is never neutral. `RocketEscrowGate.bayNeutral` refuses a section with a ledger binding, and a governed
  record exists only for such a section; the ledger's ARMED entry for the rocket is a second refusal.
- `RocketGovernedLaunchBoundary.allows` accepts only an UNCLAIMED bay boundary and refuses a bay permit ("Credited
  bay-source consumption is W27f, not an escrow exemption for a bay permit"). A held claim would only pause the flight.

The designed D0 outcome for such a source is therefore always the refusal `BAY_SOURCE_PROTECTED`. On a governed
flight nobody recorded it, so the menu reason stayed NONE.

## Part 1: proposed fix

1. `RocketTransferBayRecoveryGate` gets one default no-op method, `governedAscentComplete(server, journal, record,
   source)`. `RocketTransferBayDispatch.governedCheckpoint` forwards to it.
2. `RocketGovernedSourceDispatcher.dispatchLoaded` calls it once, where it already observes the source's change to
   TRANSIT (the `transitStarted` feedback).
3. `BayTransferRecovery.governedAscentComplete` applies D0's admission conditions unchanged (not stopping, the gated
   `session.admissionEnabled()`, no claim on the rocket) and D0's own neutral check `RocketEscrowGate.bayNeutral`.
   For a non-neutral source it records `BAY_SOURCE_PROTECTED` in the session's runtime rejection map for each bay of
   the source snapshot that holds a package, and logs one INFO line `ARCE_BAY_GOVERNED_REFUSED`. That map is what
   the bay menu reads (`BayReceipts.deploymentStatus`). It starts no claim, writes no receipt, registers nothing,
   loads nothing and does not pause the flight. If the source were neutral (not reachable, see above), it does
   nothing: no reason and no deployment.

Why this is minimal: it adds one call at the one missing place and reuses the existing reason, the existing rejection
map and the existing admission gate. It does not start a claim, because on a legacy flight the claim exists only to
hold the transfer while D0's checks run over several steps; here the one applicable check is decided at once, and a
claim would pause a governed flight and end in a READY_SOURCE handoff that puts a governed transfer into the legacy
live set. No saved form, network packet or public ID changes: the rejection map is RAM only, the reason and its
translation exist already. With admission off (production today) the new method returns at its first line, as D0 does.

One conflict with the TASK is known before implementing. The runtime rejection map is RAM only by W128's design
("cleared when the session ends"), on legacy flights too. W358's `forced-W358-B6-BOUND` oracle requires the reason
`BAY_SOURCE_PROTECTED` in the first session **and after both restarts**. The reason can be shown after a restart only
if it is saved, which is a saved-form change this task must stop for. The oracle is left unchanged; the native result
below says which part passes.
