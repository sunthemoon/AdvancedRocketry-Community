## The fix

`GameTestStationCleanup`, in the `gametest` package, is a `GameTestListener`. Each test installs it right after it
creates its station. When the test ends, whether it passed, failed or timed out, the cleanup removes the station the
way `StationWarpGameTests.Fixture.close` does:

- it deletes the station from the registry, drops its notice summary and removes its unchanged platform template, then
  flushes the registry;
- before that, it runs the test's own restore actions, drops any landing-pad index entry still filed under the
  station, and discards rockets left in the station's region (only a failed test can leave one).

Removal waits until nothing the test started still names the station:

- no transfer record has its source or destination in the station's region, or a plan that targets the station
  (the same region rule as `StationManager.delete`);
- no landing pad of the station holds a claim whose transfer is not yet acknowledged absent;
- no live warm-up lies in the station's region;
- the test's own rockets hold no transfer record, ARMED tuple, warm-up or terrain allocation
  (`EscrowWarmupFixtures.rocketHolds`).

A passing test has settled all of these before it succeeds, so its station goes in the same call. After a failure or
timeout, the check repeats every 20 ticks for at most 6,000 ticks. The cleanup never throws into the GameTest listener
chain. These cases log a WARN, so the run's log check fails instead of a later test meeting the station:

- `ARCE_GAMETEST_STATION_LEFT`: the station is still held at the bound; the line names every hold.
- `ARCE_GAMETEST_STATION_CLEANUP_FAILED`: the removal threw.
- `ARCE_GAMETEST_STATION_LEFT_AT_STOP`: the server stopped before the station was removed.

The last case is the task's end-of-run check. Each cleanup listens for the server stop until it has removed its
station. A station that these tests created and that is still in the registry when the server stops is therefore
reported before "Game test server shutting down". A successful removal logs `ARCE_GAMETEST_STATION_REMOVED` at INFO.

Per test:

- The three monitor tests install the cleanup in step 0, right after the station is created and before
  `addMember`. Their held condition is the flight's own rocket.
- The named-pad test installs it in `setup`. Its concrete strip and landing-pad block in Space were never removed
  before. The test now records each block's previous state when it places it, and the cleanup restores those states.
  Breaking the pad block drops its index entry through `LandingPadBlock.onRemove`. The held condition covers the
  launching rocket and the rival.
- The capacity test installs it in `setup`, held by all ten of its rockets.

Removal frees the cell, so later stations reuse (0, 0) and its neighbours instead of moving outward. In both the
focused and the full after-run, every one of the five stations was created in (0, 0) and removed again. So the
restored dock and the removed template leave the platform footprint free for the next station.

Vanilla's batch runner is the first listener on each test. It starts the next batch, with its structures and any
`@BeforeBatch` function, in the same call, just before the cleanup runs. That is why each `REMOVED` line follows the
next batch's start line. No test function of the next batch runs before the removal. None of the repository's
`@BeforeBatch` functions reads stations: they handle Earth return pads, discovery progress, satellite registries,
switches, escrow areas and torches.

## Choices where the task was open

- The wait bound after a failure, 6,000 ticks checked every 20 ticks, is ten 600-tick warm-up lifetimes. A failed
  test's flight or warm-up can end on its own within it.
- The "settled" rule is the strictest that a test can check without production changes. It is the station deletion
  guard's region rule, plus pad claims, warm-ups and the test's own records.
- The end-of-run check is per station and costs nothing until the server stops. A scan of the whole registry would
  also report stations that other tests own, which is outside this task.

## Not done and risks

- Not changed: the two GameTests that remove their station only on success, the two escrow tests that leave
  pseudo-station pad entries, and the four native fixtures (all above).
- Not run: `runData`, because no generator or resource changed. No packaged server, real client or visual test was
  run either. Root still runs the hosted sharded regression and merges. Nothing here approves a version or a Gate.
- Observation (production, not changed): `StationManager.delete` leaves the deleted station's landing-pad index
  entries in place. They are inert, because `LandingPadService.registered` needs the station, but they count toward
  the index's station limit. The test cleanup removes them itself.
- Not exercised: the failure path. Every run here passed, so the deferred retry, the bound and the three WARN lines
  were not triggered. They are covered by review only.
- Risk: after a failure, the cleanup waits for the test's flight or warm-up to end on its own. If a record never
  settles within 6,000 ticks, the station stays, and the run logs `ARCE_GAMETEST_STATION_LEFT` with the holds. A run
  with a failed test fails anyway, and the WARN names what kept the station.
- Risk: after a failure, rockets in the station's region are discarded only when their chunks are loaded. A rocket
  saved in an unloaded chunk of the region would reappear when a later station reuses the cell. A passing test leaves
  no rocket there.
- Risk: freed cells change which cells later stations use in a full run. All 1,761 tests passed with the new
  placement, and tests that use positions relative to their own station's cell do not notice.
