## Completed scope and design decisions

- The [design note](W249-design.md) was committed first. Both mono motors use
  ordinary `forge:obj` block models, inherited by their block items. Placed
  blocks and assembled rockets use the same baked geometry. No block entity,
  renderer, state property, protocol, persistence field or gameplay rule changed.
- Six files were imported through the [plan](../../../../tools/import/v180-w249-plan.json)
  and [coverage table](W249-asset-coverage.csv): two block OBJ/MTL pairs and
  two byte-identical upstream PNG copies. The OBJ bytes and relative `mtllib`
  names stay unchanged. The two `map_Kd` references become namespaced
  `block/combustion_classic` and `block/advcombustion_classic` sprites, whose
  PNGs are under `textures/block/`. Every rewrite is in the
  [pending provenance record](../../../provenance/v1.8.0-w249-motor-models.json).
  It records 912 budget vertices and 27,686 bytes; review remains
  `PENDING_HUMAN_REVIEW`.
- Both legacy `facing=down` variants have the identity placement transform.
  No fitted scale or rotation was added. Bounds remain `[-0.0005, 0.005,
  -0.0005]` to `[1.0005, 1, 1.0005]`; the tiny horizontal rim overhang is
  documented rather than modifying the upstream geometry. Item camera
  transforms are explicit, as listed in the design note. V1 must judge UVs,
  lighting, adjacent seams, both hands, item contexts, reload and assembled rockets.
- The atlas check follows each baked OBJ to its MTL and every material map,
  including unused materials. Missing files, unstitched sprites, unsupported
  loaders, material overrides and item overrides fail closed. No runtime
  fallback was introduced. The old formed-hull rendering route is unchanged.
- Repository validation also needed a small resource-reader update: the old
  auditor treated loader IDs and OBJ locations as PNGs. It now distinguishes
  top-level OBJ metadata from texture slots, checks the actual OBJ file and
  continues checking texture existence and case. Unknown loaders fail.
  Importer/Java checks retain responsibility for OBJ/MTL syntax and atlas dependencies.

### W249-R2: the motors no longer occlude

Before the change, every server-side use was checked against the Forge
47.4.10 mapped bytecode (`javap`). `noOcclusion()` only clears `canOcclude`.
As a result, `isSolidRender` becomes false and `getLightBlock` drops from 15
to 1. It stays 1 rather than 0 because `propagatesSkylightDown` is still false
for the full-cube shape. Everything else that the server reads comes from the
collision or support shape and does not change. That covers `isSolid`,
`blocksMotion`, `isFaceSturdy`, the default suffocation, view-blocking,
redstone-conductor and spawn predicates, and the motion-blocking heightmaps.

| Server use | What it reads | Result |
|---|---|---|
| Rocket scan, transaction, sealed terrain and disassembly (`ServerLevelRocketScanWorld`, `ServerLevelRocketTransactionWorld`, `SealedTerrain`, `SealedTargetPreparation`) | `isAir` and the `rocket_movable` and `rocket_propulsion` tags | Unchanged |
| Atmosphere sealing (`ServerLevelVolumeWorldView`) and the atmosphere detector | Tags (the motors are in neither atmosphere tag), the boundary catalog, `isAir`, the `MOTION_BLOCKING_NO_LEAVES` heightmap, then the full collision shape | Unchanged: still `SEALED` |
| Landing and arrival (`RocketLandingPadSelector`, `NamedLandingPadStaging`, `RocketRejoinWorld`, `SafetyReturnArrival`, `SafeCelestialTravel`, `SealedCarrierPlacement`) | Heightmaps, `isFaceSturdy(UP)` and `isAir` | Unchanged |
| Placement | The motors are plain `Block`s, with no `canSurvive` or placement override | Unchanged |
| Sky checks (`PlayerEnvironmentalService`, `SolarExposure`, `ResearchService`, `ResearchReleaseCommands`) | `canSeeSky`, which needs sky light 15 | Unchanged: a motor still attenuates sky light by one, so the cell beneath it, and the motor's own cell, stay below 15 |
| Other server code | Nothing reads `canOcclude`, `isSolidRender`, `getLightBlock` or occlusion shapes outside GameTests; the only mixin (`IOWorkerPendingReadMixin`) is unrelated | Not applicable |

No mod gameplay result changes, so the fix went ahead. Vanilla behaviour that
reads light does change, as intended. Block light, and sky light reduced by
one level, now reach the cells beneath and beside a motor, which affects
spawn light levels. Grass beneath a motor no longer dies
(`SpreadingSnowyDirtBlock.canBeGrass` reads `getLightBlock`). A beacon beam
passes through a motor (`BeaconBlockEntity.tick` stops only at
`getLightBlock` ≥ 15). These match an ordinary non-occluding block, and, by my
reading of 1.12 (not verified here), upstream's non-opaque motors.

The new GameTest is `MonoMotorOcclusionGameTests`, in its own batch,
`motor_occlusion`. It builds three enclosed columns: each motor, and an iron
block as the control. In each column, glowstone sits above the tested block,
and an air cell beneath it has stone on its other five faces. On both
registered motors, the test asserts the following:

- `canOcclude` and `isSolidRender` are false, `getLightBlock` is 1, and
  `propagatesSkylightDown` is false;
- the collision, `isSolid`, `blocksMotion`, sturdy top face, redstone and
  suffocation properties are unchanged;
- the sealing view still reports `SEALED`;
- block light 13 reaches the enclosed cell beneath, while the control's cell
  stays at 0.

It waits for the light wave with one tick driver, and its deadline is tick 99.
On the old registrations it failed with "rocket_motor still occludes as an
opaque cube". The server reported 678 batches with the new one, counting split
batches separately, so the batch-name map stays below its 768-entry resize
threshold.
