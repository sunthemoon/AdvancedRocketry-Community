# W280: Electrolyzer slot synchronization

## Scope and implementation

This implements [TASK W280](../TASK-W280-ELECTROLYZER-SLOT-SYNC.md) on
`codex/v1.8.0-w280`, from shared head `2070f94ee072221a212287f3ddf8e898e47fe03e`.
The implementation is limited to the electrolyzer's client menu storage, its
synchronization regression tests, and this record. Nothing was pushed or merged.

The server menu already reads current machine storage. The problem was at the
receiving end: the client constructor reused `machine.menuInventory()`. Vanilla
`initializeContents` and `setItem` both call the menu slot's `set` method, which
therefore attempted resource operations through the client's restricted machine
ports. Those operations cannot remove redstone from the charge slot or insert
machine-produced canisters into output slots. Closing the screen did not clear
the client's block entity inventory, so reopening could retain the stale items.

The client-only constructor now allocates an independent four-slot
`ItemStackHandler`. Initial contents and incremental updates replace display
stacks directly. The server constructor, revisioned ports, charge/input locks,
recipe processing, output restrictions, distance checks and inventory authority
are unchanged. There are no save-format, recipe, scalar, opening-frame or
network-protocol changes, and no new ADR decision or exemption was needed.

## Regression coverage and reproduction

The new GameTests use actual server and client menu constructors, separate mock
players and separate block entities. A loopback `ContainerSynchronizer` copies
the values emitted by vanilla menu synchronization and delivers them through
`initializeContents`, `setItem`, carried-stack updates and data updates, matching
the client packet listener's entry points without requiring a socket or GPU.
Only the authoritative machine is ticked during each synchronous fixture.

On test-only commit `882179c8f07aaa08a60032b2c95cefb3571bb917`, with the original
production constructor, both tests failed:

- `consumedChargeSynchronizesAndReopeningClearsStaleSlots`: After the first
  conversion, client slot 1 still contained two redstone while the server stored
  one.
- `producedOutputsSynchronizeInitiallyIncrementallyAndAfterPickup`: After
  production, client slot 2 contained air while the server stored one hydrogen
  canister.

The tests also cover empty-charge updates, reopening on the same client block
entity, initial synchronization of existing outputs, normal pickup, shift-click,
carried-stack synchronization, refused output reinsertion and repeated empty
extraction. Conservation checks require exactly two input canisters to become
one carried hydrogen canister and one oxygen canister in the player's inventory,
with exactly 1,000 mB water and 2,000 FE consumed. Clicking consumed charge must
not create an item; two redstone without processing must yield exactly 4,000 FE.

## Related-menu audit

The search covered every `*Menu.java` under `machine/` and the corresponding
client constructor and slot storage choices. No other audited machine menu
shares this cause:

- `RollingMachineMenu` and `PrecisionAssemblerMenu` already construct separate
  client `ItemStackHandler` storage and retain restricted handlers on the server.
- `CombustionGeneratorMenu` uses a local `SimpleContainer` for its client fuel
  slot, with its authoritative fuel-bank operations on the server.
- `ClassicControllerMenu`, `ResearchControllerMenu`, `SolarGeneratorMenu` and
  `SolarArrayMenu` expose scalar data rather than machine inventory slots.

No other machine was changed.
