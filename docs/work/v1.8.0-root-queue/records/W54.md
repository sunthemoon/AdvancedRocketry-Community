# W54: three escrow writer tests made independent of machine load

Implementer: a headless Claude session. Branch `codex/v1.8.0-w54-escrow-timing`, based on the shared branch at
`66be7b71`. Root reviews and merges.

## Cause

- `EscrowAdmissionAuthorityTest`, `EscrowFloorsTest` and `RocketEscrowAuditTest` each drove a real
  `EscrowLedgerWriter`, whose IO runs on its own thread. They looped `coordinator.tick(tick++)` with
  `Thread.sleep(2)` or `Thread.sleep(5)` until a five-second `System.nanoTime()` deadline.
- Reaching "unavailable" needs three UNKNOWN outcomes, and the writer waits 200 owner ticks after each one
  (`retryAt = tick + 200`). The loop therefore needs about 403 ticks. That is at least 0.8 s or 2.0 s of sleeping,
  plus three turns of the IO thread. Recovery needs about 200 more ticks.
- On a loaded machine each sleep and each IO turn takes longer, and the loop ran out of wall-clock time before the
  writer reached the state. In the W52 XML each failing test took 6.3 to 6.5 s: the whole 5 s loop, then the
  recovery loop.
- The production writer is correct. The tests measured logical progress with a wall clock.
- The W52 record says the `EscrowFloorsTest` failure at line 105 was the journal not acknowledging. Line 105 is
  `assertEquals(fail, writer.unavailable())`: the ledger writer in the `fail = true` case, with the same cause. The
  journal wait (lines 94 to 99) had the same pattern but passed in that run.

### How the tests wait now

- **Ledger writer.** `AwaitedLedgerIo` (test sources, package `resourceescrow`) is the writer's IO executor.
  - Each write still runs on a real daemon thread, `ARCE-escrow-ledger-test`. So IO stays off the owner thread, as
    in production, and the latch-gated tests still interleave.
  - It keeps the `Future` of every submitted write. `awaitWrites()` returns once every write submitted so far has
    finished, and so has queued its completion. A write task that throws now fails the test; with the production
    executor, the exception would only be printed.
  - `tickUntil(owner, tick, done)` repeats two steps, "await the submitted writes" and "run one owner tick", until
    `done` holds, for at most 2,000 ticks. It returns the next unused tick.
  - So each tick sees every write started before it. The writer's own 200-tick backoff and 10-tick cadence decide
    how many ticks pass. There is no sleep and no wall-clock deadline.
- **Journal writer.** `EscrowFloorsTest` awaits the journal through `RocketJournalTestAccess.awaitWriter`.
  - It is a public class in the test sources, in the journal's package. It calls the existing package-private
    `drainForTests()`, which pumps the journal writer until its submitted generation completes.
  - `RocketJournalWriterTest` and `RocketJournalContinuationTest` already wait this way. No journal production code
    changed.
- **What stays the same.**
  - Every assertion is unchanged. `"Autosave must not wait for the journal writer"` still runs before the journal is
    awaited.
  - The owner tick values passed to the writer are unchanged, except for one one-tick shift (see Choices).
  - In `unknownOutcomeRetains...`, the per-tick check (`outcomes.size() == 3` implies unavailable and no successor
    capture) stays inside the tick step.

## Choices

- **A real, awaited IO thread rather than a direct executor.** Running writes inline on the owner thread would also
  be deterministic. But it would hide an IO task that touched owner-only state, and it would deadlock the
  latch-gated tests.
- **The tick bound is 2,000 owner ticks for every wait.**
  - That is ten 200-tick backoffs, and the same as the existing 2,000-tick loop. The longest wait needs about 620
    ticks.
  - The bound only matters when the writer never reaches the state; the test then fails at its original assertion.
- **The journal uses the existing `drainForTests()`** instead of a second production seam in
  `RocketTransferSavedData` and `RocketJournalWriter`.
- **No hang guard was added.** The waits on IO completion have no wall-clock limit. The original tests could hang
  just the same: after their loop timed out, `close()` would drain without a limit. The existing `@Timeout(60)`
  annotations in `EscrowLedgerWriterTest` remain.
- **One tick shift.** In `anAmbiguousRetirementWhoseProofIsLaterInvalidated...`, the final non-retiring autosave
  runs at the old tick plus one, because `tickUntil` returns the next unused tick. Both values pass the coordinator's
  and writer's 10-tick cadence, and no assertion depends on the value.

## Known risks

- **Remaining wall-clock limits.**
  - The latch gates (5 s and 10 s) wait for the IO thread to reach a checkpoint that a test controls. Under extreme
    load, that could take more than 5 s. None failed in W52 or here.
  - The three drain elapsed-time assertions measure production `drain()`, which sleeps 1 ms per tick through up to
    about 600 ticks of backoff. If one of them fails under load, that is a separate question about the production
    drain; it is not this kind of test-timing problem.
- **Every write completes within one owner tick.** With `AwaitedLedgerIo`, every write finishes before the next tick.
  These tests no longer exercise a write that stays in flight over several ticks; before, that happened only by
  chance. The latch-gated tests in `EscrowLedgerWriterTest` and the escrow GameTests still hold writes in flight on
  purpose.
