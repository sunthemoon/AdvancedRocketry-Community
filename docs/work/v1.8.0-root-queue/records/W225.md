## Design decisions

D18 is the authority, through the [owner decision record](OWNER-DECISIONS-20261031.md).
There are four shards. A batch belongs to the unsigned big-endian first four bytes of
SHA-256(UTF-8 batch name), modulo four. Every test in a batch, including numbered vanilla
sub-batches, stays together. New safe batch names are assigned by this rule; invalid names,
missing or duplicate membership and non-unique test identities fail. HashMap iteration is
not used to decide ownership.

The CI-only observer reads the actual complete registered `TestFunction` inventory, including
generators, before the existing `GameTestBatchFilter`. It sets that filter's existing
`advancedrocketrycommunity.gameTestBatches` property at HIGHEST event priority. Each shard
runs its own `runGameTestServer`, fresh world and unchanged test functions. A delegating
vanilla `LogTestReporter` wrapper records every terminal test identity and original
timeout/setup/attempt metadata, without changing the test scheduler or failure logging.

The single build job retains clean build/unit tests, artifact/provenance audits and both
original deterministic DataGen invocations. It builds and seals one development-runtime
`main.jar`, the existing adapter fixture JAR, the observer JAR and the already-audited release
JAR, with source SHA and individual SHA-256 values. All shards download that exact bundle.
ForgeGradle userdev needs official-mapped development bytes: shards run verified exploded
contents of the same built runtime JAR, **not the SRG-mapped distribution JAR directly**.
All six Java/resource compilation tasks are excluded; exact runtime contents are checked
before and after execution. Installed/release-JAR qualification remains a separate Gate.

The original `regression` job name becomes the aggregate, with `needs: [build, gametest]`
and `if: always()`. It requires successful build and matrix results, four native-success
receipts, complete callback reports, identical full inventories/bundle identities, exact
per-shard execution and exact named union coverage, with no missing or duplicate test.
Failures, timeouts, cancellations, missing artifacts and incomplete logs fail closed.

Each raw log is checked with the unchanged `check_gametest_log.py` against its generated
manifest slice, then rechecked by the aggregate. Patterns, exact per-batch counts and
maximum values are unchanged. Startup-only warnings and the documented once-per-start
W44 baseline warning retain per-process limits. Other unscoped ceilings additionally apply
to the whole matrix; host-lag remains eight, not 32. An expectation naming an absent full
inventory batch fails rather than being silently omitted.

Job guards are build 35 minutes, each shard 45 minutes, aggregate 10 minutes. The target is
under 30 minutes per shard including setup, without changing any per-test timeout.

### Completed scope and design decisions

1. [EndgameDestructionGameTests](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/gametest/EndgameDestructionGameTests.java)
   now captures and discards only new item entities joined synchronously during

   uses existing `EntitySections.loadNow` to progress the server-owned entity
   deserialization queue, within one normal 50 ms tick per readiness attempt.
   Chunk-source task polling alone does not progress that queue, as documented
   by W122. All 40 readiness attempts and the outer 600-tick timeout remain.
   Local isolated runs also exposed `hasChunkAt == false` before the original
   block entity was removed. Diagnostics showed the index unchanged and clean,
   but `removed=false`. The same 300-attempt unload wait now awaits removal,
   paces waiting ticks, and calls the existing `GameTestChunkUnloadPump`.
   Vanilla's ready unload callbacks can otherwise be starved by its spare-time
   predicate. The unchanged helper runs at most 64 ready callbacks per waiting
   tick, retaining native save, Forge-event and block-entity removal semantics;
   it does not fabricate an unload or advance ticket time. The original index,
   marker, finder-does-not-load and removal assertions remain.
3. [RocketPropulsionGameTests](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/gametest/RocketPropulsionGameTests.java)
   cleans up its own transfer's timed flight tickets after its existing journal
   removal and checked acknowledgement. Removing a journal record stops refreshes
   but does not delete tickets already issued. The shared landing helper covers

   Hosted transfer `d325b0aa-184e-4404-bd17-6f0ab6aa62db` begins in
