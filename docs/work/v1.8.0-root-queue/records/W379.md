### The injector

The property is `advancedrocketrycommunity.storageFault=<store>:<fault>:<count>`. The store is a
`ManagedSavedDataType` name, and the count is 1 to 16. The injector acts on that store only. One write is one staging
open with the operations that follow it. The fault is used on the first `count` writes after the installation, once
for each write, and every other operation goes to `DIRECT`.

| Fault | Design row | Where it acts |
|---|---|---|
| `WRITE_ERROR` | F1 | The first `write` call throws `IOException`; nothing reaches the staging file. |
| `DISK_FULL` | F2 | The first `write` call stores half of its bytes and then throws "not enough space". |
| `DISK_FULL_OPEN` | F2 | `open` throws "not enough space"; no staging file is created. |
| `FLUSH_ERROR` | F3 | `force` throws; the staging data is not forced. |
| `MOVE_ERROR` | F4 | `move` throws before the rename. |
| `MOVE_DENIED` | F4 | `move` throws `AccessDeniedException` before the rename (the Windows sharing violation). |
| `MOVE_AFTER` | F4 | `move` renames and then throws. |
| `CLOSE_ERROR` | F5 | `close` releases the channel after a successful force and then throws. |
| `LOST_WRITE` | F6 | Every `write` call of the attempt reports success and stores nothing. |
| `DELETE_ERROR` | F8 | As `WRITE_ERROR`, and the staging cleanup of that attempt throws without deleting. |
| `READ_ERROR` | F9 | As `MOVE_AFTER`, and the next readback of the store through `CheckedSavedDataPolicy.read` throws. |
| `READ_CORRUPT` | F9 | As `MOVE_AFTER`, and the next readback returns a root with one added tag. |

The task's seven faults are `WRITE_ERROR`, `LOST_WRITE`, `FLUSH_ERROR`, `MOVE_ERROR`, `CLOSE_ERROR`, `DISK_FULL` and
`READ_ERROR`; the others are the design's variants and F8.

The injector reports what it did as INFO lines that start with `ARCE_RELEASE_STORAGE_FAULT`:

- `installed store= fault= count=`, once;
- `injected store= fault= operation= attempt= remaining=`, for each injection;
- `attempt store= attempt= result= moved= faulted= bytes= sha256=`, at the end of each of the store's first 64
  writes. The result is `moved`, `failed` (the staging cleanup ran) or `open-failed`. The digest covers the bytes the
  writer handed over, so a retry of the same candidate shows the same digest;
- `unseen ... operation=move`, when a write that lost its bytes passed the staging readback and reached the move;
- `closed store= fault= injected= attempts=`, at the restore.

### Gating

`installAtStartup` first restores what an earlier injector of this class replaced. It installs only when all of
these hold, as section 6 says for the recorder:

- `advancedrocketrycommunity.releaseTestHooks` is true;
- `server.isDedicatedServer()` is true;
- `advancedrocketrycommunity.storageFault` is set;
- `EscrowTestEndpoints.requireEnabled(server)` passes (the call site passes it as a parameter, as for the recorder).

A malformed property, or a server on which the recorder is already installed, logs
`ARCE_RELEASE_STORAGE_FAULT_INVALID reason=...` once at ERROR and installs nothing. One `ServerStoppedEvent` listener
at LOWEST priority restores `DIRECT` and the unwrapped readers. The restore only removes this class's own injector,
so it never removes the recorder. There is no command, network message, configuration key or saved field.

### The X02 runner

`python -B scripts/run_v180_storage_faults.py --list` prints the 72 cases of the default campaign: 52 live cases and
20 offline cases on the four stores of R461.

- **A live case** runs one existing native cut through its existing runner, with the property on the first start
  only, and then the runner's own two restarts.
- **An offline case** (F7 and F10) records the cut with the storage trace, as slice S2 does, damages one store file
  in a copy of the kill image, and runs the runner's two restarts on it. The kinds are `STALE` (the content before
  the last completed recorded write), `ZERO_LENGTH`, `ZEROED_TAIL`, `BIT_FLIP` and `TRUNCATED`. The store file is
  hashed after each server process has ended.
- **Classification.** A completed case gets exactly one of `SEEN_HELD`, `CAUGHT_LATER` and `NOT_CAUGHT`, with its
  reasons and evidence lines in `cases/<case>/classification.json`.
  - `SEEN_HELD` needs all of these: every faulted write ended as a failure inside the faulted session; no move
    followed a lost write; a readback fault was followed by a retry with the same digest; the first start and both
    restarts met the existing runner's checks.
  - A live case whose existing oracle fails is never `SEEN_HELD`. When a restart fails its oracle, the case is
    `CAUGHT_LATER` only if the session missed the fault and a later start logged an error; otherwise it is
    `NOT_CAUGHT`.
  - `NEEDS_REVIEW` is not a class. It marks a live case in which the session saw the fault and both restarts met the
    existing oracle, but an existing check of the faulted start failed (see the journal smoke).
  - An offline case is `CAUGHT_LATER` when a start logged an error and the file is byte-identical after both starts,
    or when the file changed and the existing oracle passed on both starts. Otherwise it is `NOT_CAUGHT`.
  - A run without an outcome has no class: `NOT_RUN` (the fault was not installed or not injected), `INCOMPLETE` (the
    native case did not reach two restarts, or not all faults were used) or `NOT_APPLICABLE` (the recording cannot
    carry the offline fault). With a `NOT_RUN`, `INCOMPLETE` or `NEEDS_REVIEW` case the campaign's status is
    `INCOMPLETE`, never `COMPLETE`.
- **Evidence.** `MANIFEST.json`, `results.jsonl`, `SUMMARY.md` (class counts, one row for each case, the residuals and
  the uncovered scope of section 5), `SHA256SUMS.txt`, and for each case the compressed logs, the commands, the
  observation and the classification. Server copies are deleted by the existing runners; the campaign's scratch
  directory is deleted in its `finally`. The campaign stops with `OVER_BOUND` above 100 MiB or 50 MiB for one file.
- **Lock and disk.** The runner takes `locks/heavy-jvm` once for each live case and once for each group of offline
  cases that share a recording, releases it in the same `finally`, waits 90 seconds between two holds (a smaller
  `--cooldown` is refused), and checks 10 GiB on C: and D: before each hold.
- **How it reaches the existing runners.** They are not edited. While a case runs, the runner replaces two names
  that the existing runners look up at call time and puts them back afterwards: `v180_crash_replay.trace_command`
  (to add the property to the first start's command) and `run_dedicated_server_smoke.CapturedProcess` (to observe
  the end of each server process).

## Choices where the design was open

1. **The count is a number of writes.** Each of the first `count` writes of the store gets the fault once. A count
   of 4 therefore passes the writers' three-failure limit only when the store retries the same generation.
2. **`LOST_WRITE` drops the bytes.** The staging file stays empty, so the staging readback fails. The design also
   allows a zeroed file; I did not add that variant.
3. **`FLUSH_ERROR` does not force.** The conservative reading of "a failed flush" is that the data was not forced.
4. **`CLOSE_ERROR` closes first.** A leaked handle would block every later move on Windows and would test the
   harness, not the writer.
5. **`READ_ERROR` and `READ_CORRUPT` include the faulted move.** The writers read back only after an attempt that
   entered the committer, so the read fault needs the move that fails after the rename.
6. **The injector and the recorder exclude each other.** The injector refuses to install over another
   `CheckedFileOps`. A fault run has no trace.
7. **A seen fault whose restart fails an oracle is `NOT_CAUGHT`.** The task asks for one of three classes and for no
   relaxed oracle. The tool cannot show "held as designed" when the durable outcome fails an existing oracle, so it
   reports the worst class and keeps the evidence. When only a check of the faulted start fails, the case gets no
   class (`NEEDS_REVIEW`): calling it held would relax that check, and calling it a residual would be false.
8. **"A later start caught it" is read from ERROR and FATAL lines.** The lines are kept as evidence. An unrelated
   ERROR line would count; slice S5 has to read the kept lines of each `CAUGHT_LATER` case.
9. **Offline cases use the kill image of a cut**, not a cleanly stopped world, because the existing runners have a
   capture and restart API for exactly that image (slice S2). `STALE` rewinds to the content before the last
   completed recorded write.
10. **The default campaign** has every live fault with count 1, `WRITE_ERROR` also with count 4, and the five
    offline kinds, on four stores: 72 cases. The design estimated about 60.

## The first smoke, and what it changed

Smoke 1 ran `BAY_RECEIPTS:WRITE_ERROR:1` on the cut `B1_MOVED`. The injection happened where the design says
(thread `ARCE-bay-receipts`, the first write, `attempt=1 result=failed moved=false bytes=0`). The bay receipt writer
then ended that generation: the deployment was cancelled (`ARCE_BAY_CLAIM ... state=READY_SOURCE`) and the rocket flew
on and landed with its satellite. The cut was never reached, the runner timed out, and the case was `INCOMPLETE`.
I stopped that run while it waited for the lock before its second case.

A bay write that fails before the move therefore cannot use a cut case. The existing case `B12_FAILED` checks
exactly this outcome (landed, nothing consumed, no receipt, on the first start and both restarts); it causes the
failure with a directory at the staging path. `X02_D1_FAILED` is `B12_FAILED` without that directory, so that the
injector is the cause. Its expectations are `B12_FAILED`'s, unchanged, and a unit test pins that the two differ only
in the `staging` flag. The seven bay faults that fail before the move use it; the five that enter the committer
(`MOVE_*`, `READ_*`) use `B1_MOVED`, where the writer retries the exact candidate and then reaches the cut.

### Two questions that slice S5 needs answered

1. **Hold lines at ERROR in the faulted start.** The journal and the registry log their hold at ERROR
   (`ARCE_TRANSFER_JOURNAL_UNACKNOWLEDGED`, `ARCE_SATELLITE_REGISTRY_UNACKNOWLEDGED`), and runner S refused the
   journal's line as it refuses any ERROR or FATAL line of a start. Should the X02 runner accept a list of named hold
   lines for each store, declared in the manifest before the run, as the design's section 3 does for X01?
   *My recommendation: yes, for exactly these two markers, and only for the faulted start.* Until then such cases
   stay `NEEDS_REVIEW`.
2. **A registry case whose first write may fail.** `R3` cannot carry a fault on the first registry write. The choices
   are a sibling case for runner R, as `X02_D1_FAILED` is for runner B (runner R has no `extra_cases` argument, so
   this needs a small additive change to it), or a fourth field in the property that skips the first N writes of the
   store (this changes the property's form, which the task fixed). *My recommendation: the skip field*, because it
   also lets a fault reach a later write (D4, D7, L2) that no first-write fault can reach.
