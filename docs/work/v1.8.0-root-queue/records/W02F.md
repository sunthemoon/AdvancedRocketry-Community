## Implementation boundaries and recovery design

The write scope is the rocket transfer/resource adapters, their JUnit and GameTests,
the exchange refusal translations and generated language files, and this record.
No state file, content ledger, build configuration, other worktree or upstream asset
is changed. No push, integration or delegation is performed.

F1 retains the existing destination entity as authority by its owner, logical rocket
identity and relocated snapshot binding, independently of fuel balance or flight
state. ASSEMBLED, FUELED and LANDED arrivals share reservation settlement/release;
recovery does not install the historical arrival resource vector over that entity.
Successful disassembly retires the retained reservation.

F2 refuses external resource mutations until the lifecycle-owned transfer service
has reconciled the journal. A retained PREPARED passenger-wait record is not a settled
resource authority even when it is in the transient settled set. A blocked journal,
an unclassified record or a non-authoritative entity also refuses mutation. Passenger
reconnect continues to use the existing durable manifest and removes the source
record only when all passengers are online. No persistence schema, checksum or save
veto is introduced. This is a clean-restart correction, not a new torn-save guarantee.

F4 applies current catalog and captured allowlist admission only to incoming Fluid.
Draining uses the registered stored identity and the existing lossless whole-container
planner, so tags, unsupported containers and nonrepresentable remainders remain intact.

F3 remains a limitation: whole-unit containers cannot refill or unload a sub-container
balance; C17a's mB-precise loader follow-up must address it without rounding the remainder.
