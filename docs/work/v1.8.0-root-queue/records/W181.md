## Findings for Root

**F1. On a dedicated-server client, JEI loses or breaks every machine recipe that uses an item tag.**
At JEI's second start (01:08:31), `BoundedItemIngredientCodec.resolveAlternatives` found no bound
alternatives for any tag entry. `diagnosis-tag-recipe-counts.txt` (SHA-256 `088707c2…58ac`) counts the
shipped recipes. In each classic category, the client count equals the number of item-only recipes:

| Category | Shipped | With a tag | Client count |
|---|---|---|---|
| lathe | 7 | 7 | 0 |
| arc_furnace | 5 | 4 | 1 |
| cutting | 14 | 1 | 13 |
| crystallizing | 2 | 2 | 0 |
| chemical_reacting | 7 | 4 | 3 |
| laser_etching | 2 | 2 | 0 |
| centrifuging, electrolyzing | 1 each | 0 | 1 each |

The classic `definition()` filter drops those recipes silently. The 18 rolling and 8 precision-assembler
recipes are not filtered, so their counts match. Each of those 26 recipes logs a project ERROR,
`Disabling machine recipe … until tag reload: machine ingredient has no bound alternatives`, followed by
JEI's ERROR `Found a broken recipe`. That is 52 ERROR lines in the client log. The small plate press
(17 tag recipes) is not affected.

JEI did not start again after this point. The likely cause is that JEI registers on the recipe update,
before the client has bound the server's item tags. A single-player or GameTest run would not show this,
because the integrated server has already bound the shared registries. Gameplay on the server is not
affected; this is a client JEI display defect.

**F2. The v1.8 runner's one-receipt rule conflicts with how JEI 15.56 starts.** When the server has no
JEI, JEI starts twice after the connection:

1. It first starts with the client's default recipes. All 11 categories then log `recipes=0`, and JEI warns
   that the unknown server does not provide recipes.
2. It then stops and starts again with the server's recipes.

`audit_client` rejects every receipt after the connection that does not carry the expected count. So the
zero-count first pass fails the cell even after F1 is fixed. The v1.0 runner only required its last
receipt to follow the connection. Under R145, the runner was left unchanged.
