## Choices where the TASK or an ADR was open

- **Record layout.** The TASK asks to keep each old entry and add the new
  one. The four block faces had only markdown records, so each gained dated
  sections and kept its text and hashes.
  - The carbon brick's pre-authoring markdown is pinned by SHA-256 in
    `docs/work/v1.8.0-c16d-components-graph/ACQUISITION-ADOPTION-01.md`, so
    it stays byte-unchanged.
  - Its schema-2 JSON keeps the first entry and gains a second entry for the
    same target. That entry carries `supersedes_target_sha256` and
    `correction_record`. No tool rejects two entries for one target; I
    checked the importer and the ledger validator.
  - The new W53 record holds the four block-face entries and the screening
    evidence. It points to the C16d entry instead of duplicating it.
- **Tints and encoder.** Every texture keeps its tint and the shared encoder,
  so its colour identity matches its sibling textures. Only the grids change.
- **Pre-authoring order.** The pre-authoring declaration was committed before
  any replacement grid was written, following W49's practice.
- **Screen binding.** The provenance test checks the committed report of the
  187-file run and the five screened hashes. It does not re-screen the
  current root, so later PNG additions remain the governance workflow's job.

## Known risks

- The new drawings clear with their strongest rank between 0.44 and 0.52,
  well under 0.75. A new reference client or a stricter tool would need a
  fresh screen, as with every NEW texture.
- Any later change to these five PNG files fails
  `V180ArtRedrawProvenanceTest` until the screen is rerun and recorded. This
  is intended.
- The record entries' `source_sha256` values describe the providers at
  `1035fabf`. The tests do not pin the current provider sources, so
  unrelated later edits to these shared providers do not break them.
