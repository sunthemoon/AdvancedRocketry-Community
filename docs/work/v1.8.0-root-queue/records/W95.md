**The adapter (`EscrowLoaderEndpoint`).**
- It reads only the loader's own bounded root, from the live block entity or from a disk record. An unsupported root
  is refused and never projected.
- A pristine section is observed as epoch 0 with no markers for the current ledger.
- The C2 debit moves exactly the payload out of the tank. It binds the section to the ledger with the operation's
  SOURCE marker at the after epoch, and it checks the recorded after-signature.
- The observer, the disk observer, the reconciliation view, change, validation and action, the C6 readback validator,
  C8 pruning and O4 settlement pruning dispatch loader endpoints to the adapter without release-test hooks. The chest
  fixture keeps its gate.
- The driver treats loader sources as registered, so loader records get production reconciliation instead of
  `RECONCILIATION_UNIMPLEMENTED`.
- A loader's paced tick prunes an independently validated retired marker, which covers restart cleanup.

**Ledger creation (W11B3-DESIGN section 2, steps 1 to 4).**
- Step 1: `fillRefusal` runs against `EscrowLedger.empty(id)` with the ID the new ledger will carry. Then `tryReserve`
  runs while the delegate is NO_FILE. A refusal at either point creates nothing.
- Step 2: `createForFill` stores the ledger and binds it, so the delegate becomes LOADED. `enqueueCreated` queues the
  reserved operation. Nothing that can fail runs in between.
- Step 3: `commitPreparations` first writes the empty generation-1 root. L1 is captured only after that write's exact
  acknowledgement.
- Step 4: a definite baseline failure, or a failed readback when the coordinator binds, removes the uncaptured fill
  with one false callback, and with it the reservation. An UNKNOWN baseline keeps both until the writer's exact retry
  resolves.

**Admission (section 2, "One attempt").**
- A paced loader that would start a fill waits once in the runtime-owned `EscrowFillQueue`. The queue keeps arrival
  order, makes at most eight visits and one endpoint capture per tick, and holds 256 entries. Every visited entry
  leaves the queue.
- A visit repeats every device and eligibility check. Then `EscrowLoaderAdmission.admit` captures everything in one
  owner-thread action: the bank selected against the rocket projected through its unresolved prefix, both complete
  native envelopes, the identities, epochs, hashes, owner, snapshot and journal guard.
- It then calls `prepareFill`, or the creation order in a NO_FILE world.
- The queue drives the L1 commits of exactly the fills it queued.

## 6. Choices where the design was open

1. **Signature registration.** `EscrowSignatureKind` gains `FLUID_TANK_V1` as the last member; kinds persist by name.
   `EscrowAdapterIds.LOADER` is the block-entity type, and a loader endpoint must use unit TANK. The loader's
   observation invariant is the endpoint reference digest (identity, Level, type, position). The owner is not in it,
   because a held device cannot be rebound or reclaimed.
2. **Same-direction chains.** `RocketEscrowGate.idle` is false for a chain, and so is
   `RocketTransferService.resourceMutationAllowed`, which begins with it. For a chain, `LoaderEligibility.evaluate`
   uses three checks instead:
   - `EscrowLoaderAdmission.chainable`: the rocket's unresolved holds are only PREPARED, reason-free, unsettled loader
     fills into this exact endpoint; its wrapper is exactly their applied prefix; and no flight checkpoint, ARMED
     entry, READY head, receipt history, floor or frozen frontier names it;
   - `RocketRuntime.escrowReconciliationBoundary`, which has the same journal and assembly-recovery interlocks without
     the idle test, and a stricter journal requirement;
   - `resourceMutationUnproved`.

   Anything else refuses as ESCROW_PENDING. The capture then projects the rocket through the prefix and repeats the
   bank selection against the projected vector.
3. **Retired markers.** A rocket wrapper holding a retired, not yet pruned marker refuses with ESCROW_PENDING until
   pruning, as `captureCurrentTest` waits ("C0 waits for stale marker pruning"). A fill's beforeWrapper is therefore
   always the prefix that will exist when it applies.
4. **Status mapping and final visibility.** `prepareFill` stays package-private; `EscrowLoaderAdmission.admit` is its
   only caller, from the fair-queue visit.
   - QUEUED maps to PREPARING.
   - UNAVAILABLE and IDENTITY_CONFLICT map to LEDGER_UNAVAILABLE.
   - INVALID maps to INVALID_DATA.
   - STALE and ENDPOINT_BUSY map to ESCROW_PENDING (eligibility already refuses flight holds).
   - ROCKET_LIMIT, ESCROW_FULL, SERVER_FULL and ROCKET_FULL map to ESCROW_FULL.

   The device's progress is as follows:
   - PREPARING until its own debit is applied; this covers the creation baseline, L1 and an UNKNOWN L1;
   - TRANSFERRING through the proofs and L2;
   - ESCROW_PENDING for a stalled, manual, waiting or UNKNOWN-after-apply state, or a retired marker;
   - LEDGER_UNAVAILABLE when the coordinator is unavailable.

   READY means that the device is waiting in the fair queue. A progress status whose operation has resolved reads as
   READY until the next paced attempt.
5. **The gated switch.** Admission requires the release-test gate (`EscrowTestEndpoints.enabled`). On a GameTest
   server it opens per device through `EscrowRuntime.loaderAdmissionForTests`, for at most 64 devices. On a gated
   release dedicated server (hooks, no RCON, only test-owned players) it opens by the property
   `advancedrocketrycommunity.escrowLoaderAdmission`. `FluidFuelLoaderBlockEntity.admitFromQueue` is public so that
   gated GameTests can run one visit synchronously; it still enforces the gate.
6. **Creation details.** Any exact acknowledgement ends baseline mode, so an autosave that publishes the same empty
   root also counts. A definite baseline failure cancels every uncaptured queued fill. Its sequence is not reused, and
   the writer's next baseline is at generation 2, because generations never repeat. A failed readback when the
   coordinator binds leaves that coordinator unavailable for the session, under the writer's existing sticky rule.
7. **Device lock and eligibility.** The lock covers the section's marker and every durable, queued, captured or UNKNOWN
   operation naming the device's identity, a frozen proof and a settlement receipt. It is cached per tick and
   refreshed by an admission and by every root write. Eligibility requires the device's chunk to be FULL with the exact
   block entity loaded, and the rocket's locator chunk to be FULL with loaded entity sections. Reconciliation applies
   nothing until both slots are FULL, entity-loaded and ticking; the recovery GameTest relies on this.
8. **Ledger replacement in tests.** The runtime's scheduler is rebuilt when the bound coordinator changes. Production
   has one ledger per server, so its behaviour is unchanged.
9. **Settlement.** O4 settlement pruning gained the loader branch, so a settled loader is not locked forever. Operator
   settlement on loader endpoints is wired through the shared observers, but this slice does not exercise it (cut-O
   is B3-S6).
10. **Class size.** `FluidFuelLoaderBlockEntity` has 660 lines (it had 579) and `EscrowCoordinator` has 582 (it had 501).
    Each keeps one responsibility: the device's lifecycle bridge, and the ledger's queue and writer. Both stay under the
    800-line ADR threshold; the new admission, adapter and queue logic are separate classes.

## 8. Known risks

- Once enabled, the first fill creates a ledger file in a player world (R-035's scope change). This needs the
  independent review that the TASK names.
- The fair queue commits every queued preparation of the server ledger while it has any outstanding fill of its own.
  A gated fixture preparation queued at the same moment would be committed with it; this interplay is possible in tests
  only.
- Chain projection depends on the coordinator's unresolved set. It is tested with prefixes of two to five fills in
  GameTests; longer prefixes are bounded by the five-marker limit.
- If the creation GameTest failed midway, it could leave the shared GameTest ledger detached and its file set aside as
  `advancedrocketrycommunity_resource_escrow.dat.w95-backup`. It passed here and restored both.
- The status mapping sends STALE and a frozen frontier to ESCROW_PENDING. If W11b2 adds a new `prepareFill` refusal, it
  falls into the existing categories until it is mapped.
