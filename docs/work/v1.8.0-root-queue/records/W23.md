## Tests

`gametest/OperatorItemNbtGameTests` (batch `operator_item_nbt`):

- `everyRegisteredBlockEntityIsListedAndRootsRequireAnOperator` is the data-driven test.
  It lists 32 operator-only classes and 3 classes that save no root. It walks every
  `BlockEntityType` in the mod namespace and creates each one on a valid block's default
  state. Then it checks three things:
  - the class is in exactly one list;
  - `onlyOpCanSetNbt()` matches that list;
  - every listed class is created by some registered type.

  A new type therefore fails until someone classifies it. The assertion follows
  `ForceFieldGameTests` line 308.
- `nonOperatorScrubberItemNbtYieldsAFreshScrubber` places a scrubber item whose
  `BlockEntityTag` names another identity and a binding to the cell above. The test first
  shows that the forged root is a valid bound root by loading it into a detached block entity.
  Then it checks three placements:
  - a connected creative non-operator, through `ServerPlayerGameMode.useItemOn`, gets a fresh
    scrubber: a new identity, no binding and no protected data;
  - a placement without a player, as a dispenser does, also gets a fresh scrubber;
  - a creative operator still loads the forged root.

## Choices where the TASK was open

- **Operator-only scope.** The TASK names owners, identities, generations, bindings, and
  retained, guarded or unknown roots. I applied it to every class that saves any of these,
  including classes whose only such data is a refused or future root:
  - the rocket assembler;
  - the satellite builder;
  - the combustion generator;
  - the tank;
  - the suit workstation;
  - the atmosphere detector.

  This follows the existing solar generator, which is operator-only for the same reason.
  Only the three classes that save no root were left alone.
- **Dormant adapter classes.** `machine/classic/adapter` is not registered. Its two classes
  got the one-line override because they hold guarded owner state. The registry-driven
  test cannot reach them, because no registered type creates them.
- **Representative GameTest.** I chose the scrubber because a forged binding makes the block
  unbreakable, and because its item has no carried-root path of its own.

## Known risks and follow-ups for Root

- **Carried roots bypass this gate.** These four blocks deliberately reload a carried root
  from the item's `BlockEntityTag` in their own `setPlacedBy`, for every placer:
  - `SatelliteTerminalBlock` (ADR-029 and ADR-051 section 5);
  - `SatelliteBuilderBlock`;
  - `MicrowaveReceiverBlock`;
  - `FuelLoaderBlock`.

  For them, `onlyOpCanSetNbt()` closes only vanilla's merge. A creative non-operator can
  still craft an item that carries, for example, another player's `owner_id` or terminal ID
  for the terminal, or another owner for the fuel loader. This is a deliberate carry design,
  and changing it is a behaviour change outside W23. After the carried root loads, the
  terminal's `setOwner` and the fuel loader's `assignOwner` give the placer ownership only
  when no owner was loaded, so a carried owner is kept. I did not analyse what each block's
  other checks do with a forged ID. The fix needs an ADR decision, for example accepting a
  carried root only from a drop that the server recorded.
- **Player-visible change.** For the 18 newly covered registered types, creative non-operators
  no longer get block-entity data from vanilla's NBT pick-block copies. Survival placement
  is unchanged: vanilla already skipped the merge for players without `instabuild`, and the
  four carried-root blocks still reload their roots through `setPlacedBy`.
- Real-client checks and a hosted CI run were not performed here.
