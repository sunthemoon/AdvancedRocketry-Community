## Verdict

**Merge after one named fix (F1).** Candidate sessions are unchanged, the session and manifest refusals

## Findings

### F1 (medium, fix before merge): the Forge baseline does not check the `srg` client JAR

- Where: `scripts/campaign_client/baseline.py` lines 112 to 133 (`check_forge_outputs`), called from
  line 103.
- What: for the Forge profile the function checks seven files against the installer: `fmlcore`,
  `javafmllanguage`, `lowcodelanguage`, `mclanguage`, the Forge universal JAR, the patched client JAR
  and the client `extra` JAR. Forge's client launch handler also loads
  `net/minecraft/client/1.20.1-20230612.114412/client-1.20.1-20230612.114412-srg.jar` from the library
  directory. I confirmed this in `fmlloader-1.20.1-47.4.10.jar`: `CommonClientLaunchHandler.class`
  holds the strings `srg` and `extra` next to `findPathForMaven`. No harness file mentions `srg`.
- Input that gets through: a Forge baseline whose `libraries_root` holds any bytes at that path, or
  no file at all. My probe P1 ran `load_baseline` three times on the test fixture's Forge profile,
  with the JAR absent, present and then changed. All three passed with an identical
  `baseline_identity`. The existing test `test_empty_forge_identity_checks_installer_and_version`
  also passes with no such file on disk.
- Effect: a changed `srg` JAR would start a baseline with different Minecraft classes, and neither
  the READY receipt nor `dependency-inventory.json` (100 library files, none of them `srg`) would
  show it. A missing one is found only when the client fails after READY.
- On this machine the file is unchanged as far as I can tell: 18,842,082 bytes, SHA-256
  `e2e940fe7ca0a9fba5a5c11ad2cf3e2f7df91bbf51d12af22cdde7af18adc344` in
  `D:/GitHub/ARCE-Task-Evidence/root-queue/P3/runtime/libraries`. The candidate launch reads the same
  file, also unchecked; that path is older code and outside this review.
- Fix: check this file in `check_forge_outputs`, add it to `forge_runtime_files`, and add a test for a
  missing and a changed file. The installer carries no digest for it (`MC_SRG` has no `_SHA` entry), so
  the check needs a pinned SHA-256 in `baseline.py`. I measured the value above in one runtime only
  and did not check that the installer produces the same bytes on every install. Correct README
  lines 125 to 127 and the W498 record, which say the runtime-discovered Forge files are verified.

### F2 (low): asset objects are not checked at launch

- Where: `scripts/campaign_client/baseline.py` line 102.
- What: only the asset index is checked. The 3,575 objects it names (textures, sounds, language files)
  are not opened, and the receipt records nothing about them. Probe P3 confirms that `load_baseline`
  does not read the `objects` folder.
- Input that gets through: a changed file under `assets_root/objects/`.
- The README says this plainly (line 138 asks the operator to inventory the objects first), and the
  package's inventories list every object with its SHA-256. The gap is that nothing in the harness
  compares them on the night. A check of `dependency-inventory.json` in the capture procedure would
  close it without a harness change.

### F3 (low): the run directory may sit inside the profile directory

- Where: `scripts/campaign_client/session.py` lines 102 to 110.
- What: the overlap check covers `client_game_dir`, `runtime_root`, `libraries_root` and `assets_root`,
  but not the directory that holds `baseline.json`.
- Input that gets through: `run_dir` set to `<profile>/run-inside-profile`. Probe P2: the session
  reached READY, wrote its evidence beside `baseline.json`, and the profile still validated afterwards.
- Effect: no wrong launch. A run could write into a hashed evidence package. The candidate path has
  the same gap for the cell directory. The shipped example sessions use `authoring-w498/live-runs/`,
  which is outside both profiles but inside the package that `delivery-inputs.json` inventories.

## The six checks

1. **Candidate sessions are unchanged: confirmed.**
   - `cells.py`, `launch.py` and `scripts/v100_compatibility_runtime.py` have no diff.
   - In `protocol.py`, `session.py` and `cli.py` every new branch is behind
     `spec.get("launch_kind") == "baseline"`. A session without the field takes the old path at each
     of them.
   - `launch_kind: "candidate"` parses to the same session as no field (probe P4). Before this commit
     that field was refused as an unknown key, so this is a new accepted input, as the task intended.
   - One side effect: `session.py` now imports `scripts.v100_compatibility_runtime` when the module
     loads instead of at the first launch. It changes no behaviour.
2. **Baselines are pinned: confirmed except F1, with F2 and F3 as low gaps.**
   - Version files: the Vanilla JSON and JAR and the Forge JSON are compared with constants in
     `baseline.py`. The installer is checked against the pinned SHA-1 `66bfea99…` in the existing
     helper. A changed file is refused even when the manifest declares the new hash.
   - Libraries: every library in the two version files is checked by SHA-1 and size, at validation
     and again while the command is built.
   - Mods: the template must hold exactly five empty directories. The launched game directory is
     created new and its `mods` folder is never copied from anywhere.
   - Attach mode, multiplayer, two clients and unknown kinds are refused in `load_session`
     (`protocol.py` lines 175 to 178 and 185).
   - World: the run directory, the game directory and `saves/baseline` are each created with a call
     that fails if the path exists, and cleanup removes the game directory. No world is copied.
   - Baseline and candidate manifests are not interchangeable in either direction.
   - Links and junctions are refused in the template, the version tree and the library paths.
3. **Receipts: confirmed.**
   - `summary.json` keeps every candidate key and adds `launch_kind` and `baseline_identity`.
   - The client receipt adds `process` (`pid`, `name`, `created`, all integers or strings) and
     `game_dir` (a string after serialisation). Probe P5 read both back with `json.loads`.
   - The real Forge identity serialises to 2,978 characters and the Vanilla one to 765.
   - The Vanilla receipt gives `version_id` `1.20.1`, `candidate_sha256` null, `forge` null and `jei`
     false, which is what W491's `tools/test_w491_capture.py` line 95 expects.
4. **Profile: confirmed.**
   - `prepare_profiles.py` and `finalize_profiles.py` import no network or process module. They copy
     four files from the P3 runtime, and two from W496's Vanilla runtime.
   - The four Forge files hash the same as their P3 sources today, and the installer's SHA-1 is the
     pinned one.
   - All 28 files in `delivery-inputs.json` match their recorded SHA-256 and size, and no other file
     is in the package. `delivery-inputs.json` itself is `f3454ca8…3926`, as the record says.
   - The package holds no account or launcher file. The command plans carry `--accessToken 0`.
   - All ten template directories are empty, and neither `live-runs` directory exists yet.
5. **Tests: confirmed.**
   - 190 tests pass on `bfb6e4b7e`.
   - `git diff --stat 48de443ec bfb6e4b7e -- tests` lists only the new file, which has 30 tests, so
     no earlier test changed.
   - The new tests read as Linux-safe: no `os.name` or platform guard, no `ctypes`, no process flags,
     POSIX-style relative paths, and the two symlink tests skip when links are unavailable. I ran
     them on Windows only.
6. **README: matches the code, except for F1.** Lines 125 to 127 say the runtime-discovered Forge
   files are verified, and the `srg` JAR is not. The schema, the two profile names, the five
   directories, the world settings, the receipt fields and the test commands all match.
