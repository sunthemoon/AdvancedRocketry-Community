## Choices where the task left room

- **The warm-up also covers ready destinations when a slot is free** (section 7.2). This protects the multi-tick F1 and
  F2 window. It is open question 1.
- **Lifetime and cap.** The warm-up lifetime is 600 ticks and the cap is 8, both fixed constants like the other flight
  limits (open questions 6 and 7).
- **Release events.**
  - A warm-up is released at the handover right after T's first ACTIVE refresh, not at F1's start. Releasing at F1's
    start would demote the margin during F1's asynchronous store and write, and F1 and F2 repeat the census.
  - Refusals before the warm-up decision (rate limit, range, fuel) leave the warm-up running until its deadline.
  - A disconnect or the source rocket's removal releases only an unbound warm-up.
- **Named pads.** The selection claim is released at a loading refusal, so no saved claim survives the wait. The
  warm-up's in-memory region reservation keeps the pad (open question 3).
- **Source refusal.** It uses a new request code rather than a detail key, because detail keys are pad-only and print
  as "Landing pad refused". New keys go into the v1.8 language provider. The unused v0.6 provider is only extended to
  compile, so no historical generated root changes.
- **Post-F2 census conflicts** keep today's behaviour and are reported as `CENSUS` (open question 5).

## Not done and known risks

- **No code or tests.** The note's tests and JVM estimates are plans. The warm-up needs its own independent review
  before any code (R21 item 4).
- **Vanilla behaviour is read from bytecode, not measured.** The warm-up's non-renewal relies on
  `DistanceManager.addTicket` resetting a re-added ticket's age, which comes from revision 1's read. The quiet-machine
  re-read the review asked for is still open (open question 8).
- **Cost figures are upper bounds.** They assume disjoint margins and already-generated terrain. Cold-destination
  generation and the 1 × 16 case are not measured; R21 item 5's reference run must add them.
- **The lifetime can run out during a slow F1.** A relaunch near the end of the 600-tick lifetime, with a slow F1 store
  or write, can lose its warm-up before F2. The launch is then discarded by the existing checks, which is safe, and the
  player launches again.
- **A stale copy of L is reported misleadingly.** When the census refuses such a copy, the player still sees the
  misleading `TRANSFER_JOURNAL_BLOCKED` text. The note does not change it.
- **Dependency on continuation 53.** The design builds on its pending reservations (`453094c3`), which were not yet
  merged when this note was written. If continuation 53 changes, section 7.4 must follow it.
- **Length.** The note is longer than revision 1 because the task asked for the warm-up's full lifecycle, text, tests
  and the review answers.
