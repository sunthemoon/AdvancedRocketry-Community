# W168: ground-survey preflight

## Scope and design before implementation

Date: 2026-10-27. Implementer: the assigned Codex worker. Base:
`67cc6e01e5f7657c97bb0478a397ad65bb0c86fd`, branch `codex/v1.8.0-w168`, worktree
`D:/GitHub/arce-v180-w168`. The worktree was clean and no other worker process was
assigned to it. Other workers use separate worktrees. Root remains Claude.

The write scope is `satellite/mission/GroundSurveys.java`, the related `RecordSizer`
contract comment, ground-preflight tests and a standalone benchmark under
`src/test`, and this record. Runtime writers, saved formats, bounds, section budgets,
quotas, protocols, ADRs, risk entries, status files and the ledger are not changed.
No upstream code or assets are imported. The active development version is v1.8
under ADR-060; the unfinished release acceptance cursor is still v1.0. No Gate is
approved here.

The measurement comes first. The standalone benchmark uses the real codec sizer,
50 measured calls per case after warm-up, Xmx4G, and the machine-wide heavy-JVM lock.
Each measured call is a complete domain operation. Fixture construction is outside
the timed interval. It reports START, account creation through final analysis, and
an ordinary survey change on a restored near-byte-bound root. Additional
reservation-provable fixtures distinguish the optimized cases from the fallback.

The change will reuse the existing reservation proof. Its candidate bound adds
the new job and instance reservations for START and `RecordSizer.ACCOUNT_BYTES`
only for a newly created account. Existing records remain covered by their
lifecycle reservations. A failed proof still calls the unchanged encoding and
round-trip preflight. Validation, epoch overflow checks, publication and refusal
codes stay in their original order. Boundary tests will cover an exact fit, one
byte over, and restored over-budget roots, including refusal without mutation.

If the post-change measurements miss docs/17, implementation stops at this
behavior-preserving optimization. Numbers and options go to Root; this worker
does not choose a new admission policy or per-tick quota. Root arranges the fresh
read-only review before merge.

## Measured result and stop

Production and final test changes are committed as `1015644887b8f12682544fc05c91f8ee794b204c`.
The after benchmark ran on that clean commit. The before source is
`2a70693906181c94f5efe97b24c4baf4c93f0504`. Both runs completed normally but
reported `STOP_RULE`: the remaining fallback exceeds docs/17. No further
admission-policy implementation was made, and this slice is not cleared for merge.

Environment: Windows amd64, AMD Ryzen 5 5500 (6 cores / 12 logical processors),
Oracle Java 17.0.7+8-LTS-224, Forge 47.4.10, Xmx4G. The detached runner took the
atomic machine-wide lock and checked C: and D: above 10 GiB and available physical
memory above 6 GiB before each run. These are isolated owner-thread operation
measurements, not a reference Debian server or a whole-server performance PASS.
Each case has 5 warm-ups and 50 measured samples; percentiles use nearest rank,
so P99 equals the maximum at this sample count. Fixture setup is not timed.

| Case | Before P50 / P95 / P99 / max (ms) | After P50 / P95 / P99 / max (ms) | Whole-root calls before -> after |
|---|---|---|---|
| Near-bound START | 273.39 / 314.34 / 416.09 / 416.09 | 199.66 / 216.61 / 230.38 / 230.38 | 50 -> 50 |
| Near-bound new account | 265.68 / 289.76 / 296.91 / 296.91 | 198.74 / 218.59 / 232.04 / 232.04 | 50 -> 50 |
| Restored near-bound ordinary advance | 248.55 / 286.16 / 287.64 / 287.64 | 198.34 / 224.30 / 242.89 / 242.89 | 50 -> 50 |
| Section-fit START | 78.72 / 90.70 / 108.18 / 108.18 | 0.217 / 0.308 / 0.489 / 0.489 | 50 -> 0 |
| Section-fit new account | 74.44 / 88.18 / 99.67 / 99.67 | 0.100 / 0.154 / 0.224 / 0.224 | 50 -> 0 |

The near-bound fixtures contain 5,251 claimed missions, with encoded roots of
16,772,065, 16,773,174 and 16,773,130 bytes before the respective operations,
against 16,777,216 bytes. They leave less than 8 KiB to admit one candidate, as
in W128's byte-bound measurement pattern, rather than padding an invalid root.
Their reservation bounds are 18,482,493, 18,484,084 and 18,484,212 bytes. The
section-fit fixtures contain 1,641 missions, encode at about 5 MiB, and reserve
about 5.8 MB including framing. Every measured operation succeeded before and
after. The account case deliberately exercises the domain restore entry before
`finishRestore` repairs missing accounts; it does not claim that a normal loaded
healthy root has a missing account. The tests additionally exercise actual
encoded-byte refusals, leaving less than one account width below the root cap.

The unchanged fallback still runs on every eligible operation whose candidate
reservation proof fails, including every ordinary change on a restored
over-budget root; this patch adds no per-tick cap. The sample rates are 100% for
each near-bound case and 0% for each section-fit case after the patch, not an
estimate of the frequency in player worlds. Differences between the two runs'
unchanged slow-path timings are host/JVM variation, not an optimization claim.

Root's options, not selected or implemented here:

1. Refuse unprovable candidates with `STORAGE_BUDGET`. This removes those whole-root
   calls, but all 150 successful near-bound benchmark operations would instead be
   refused. The one-byte-over reservation tests also demonstrate that an
   unprovable candidate can genuinely fit. This changes behavior, can prevent
   already-paid survey/analysis progress, and requires Root's decision and a
   risk note before implementation.
2. Limit or schedule preflights per tick. A limit of one still leaves an individual
   operation with measured P95 216.61-224.30 ms and P99 230.38-242.89 ms, above
   50/100 ms. A rate limit alone bounds frequency, not the operation's latency;
   meeting the per-operation budget would require further work such as deferred
   validation with fresh-state revalidation, with its semantics separately decided.

No schema, saved bytes, bound, section quota, timeout, protocol or production
refusal rule changed. No ADR choice was made. The performance miss remains open
for Root to track in the central files, which are outside this worker's scope.
