## Summary

- The crystallizer, the chemical reactor and the precision laser etcher each have a mid-job restart GameTest.
  These tests are stronger than W62's "R" grade. They do not load the saved NBT back into the same objects. Each
  test saves every block entity of the multiblock and then installs fresh block entities decoded from that NBT,
  the way a chunk load does.
- Optional item done: the etcher also crosses a real chunk unload and reload, with the job paused mid-batch
  ("D" grade in W62's terms).
- The atmosphere detector has separate happy and failure GameTests, and a restart test that round-trips the mode
  root through a fresh block entity and then measures.
- No production code changed. No production defect was found.
- The first full GameTest run failed on the new unload test, a test-timing fault fixed in its own commit. The
  second run, on the fixed commit, passed all 1,084 required GameTests, and the log checker passed.

## The new GameTests

`C16cRestartGameTests` (each test has its own batch):

| GameTest | What it checks |
|---|---|
| `crystallizerMidJobRestartKeepsExactResourcesFeAndProgress` | `crystallizing_dilithium`, restart after 101 ticks. |
| `chemicalReactorMidJobRestartKeepsExactFluidsFeAndProgress` | `chemical_reacting_rocket_fuel` (two fluid inputs, one fluid output), restart after 41 ticks. |
| `etcherMidJobRestartKeepsExactResourcesLensFeAndProgress` | `laser_etching_basic_circuit_plate`, restart after 301 ticks. The lens carries a custom NBT marker. |
| `etcherJobCrossesARealChunkUnloadAndReloadWithExactAccounting` | The same etcher recipe across a real chunk unload and reload. |

The three restart tests share one method. Before the restart, it checks that the job is running mid-batch and
that the FE balances: consumed plus stored equals injected. The restart saves the controller and every hatch
with `saveWithFullMetadata`. For each one, it builds a new block entity with `BlockEntity.loadStatic` and
installs it with `Level.setBlockEntity`. That path runs the production `onLoad`, so the manager observes the new
controller with no test help. The method then asserts:

- every old block entity is removed, and every new one re-saves exactly the NBT it was loaded from;
- the new controller is a different object, needs no repair, and has the same job record, progress ticks,
  consumed FE, stored FE (in the new plugs), encoded resources and batch ordinal;
- after exactly `processingTicks - progress` more ticks, the batch completes once with exact FE, inputs and
  outputs (`C16cMachineFixture.assertCompleted`);
- the etcher's lens comes back with its NBT payload;
- five further ticks do not duplicate the batch.

The real-unload test:

1. It builds the etcher in a chunk at absolute X + 1,000,000, Z − 1,000,000 from the test, Y 200, with the whole
   pattern inside that one chunk. The beacon tests use Z + 1,000,000, so the two never share a chunk.
2. It seeds the recipe. Native server ticks then run the job on the seeded 20,000 FE until it pauses with
   `ClassicWait.ENERGY`, so the job is unpowered and mid-batch when the chunk unloads.
3. It records the job, the progress, the FE, the encoded resources and every hatch's NBT, then releases the
   fixture's tickets.
4. It waits until three things are true: a `ChunkEvent.Unload` for that chunk has fired, `hasChunkAt` is false,
   and the old controller is removed. While it waits it never looks up a block entity, because a lookup would
   load the chunk again.
5. It restores the tickets and loads the chunk from storage. It then asserts that the reloaded controller and
   hatches are new objects with the same job, progress, consumed FE, resources, instance ID and exact hatch NBT.
6. It waits for the production `onLoad` and manager to re-form the controller. It checks that the unpowered job
   did not move, then completes the batch with exact FE accounting and the lens payload intact.

The WARN totals differ because run 1 created fresh configuration files and logged 132 "Incorrect key ... corrected
from null" warnings, while run 2 reused them and logged 11. The manifest's generic budget admits both counts.

**The run-1 failure.** The unload test's 420 waiting ticks took 1.7 seconds of wall time. GameTest ticks are
unthrottled, but this chunk's neighbourhood had been generated about 0.2 seconds earlier and was still generating
and lighting on background threads. The chunk's unload save waits for that work. The fix in `361d16fb` gives each
waiting tick a server tick's 50 ms through the existing `GameTestTickPacer`, as `BeaconReloadGameTests` does for
its readiness wait. It also allows up to 600 waiting ticks (30 s) and raises the test's timeout from 600 to 900
ticks. No assertion changed. In run 2 the whole batch took about 3 seconds of wall time.

**Log manifest.** The new tests log no WARN or ERROR when they pass, so `scripts/gametest_expected_log.json` and
its pinned total are unchanged. No workflow line is needed: the hosted regression already runs every GameTest.

**The lock.** Twice I stopped my own waiting script and restarted it while it still waited, with the lock held
by another task. The first restart shortened its wait limit from three hours to 70 minutes, so that the wait and
the run fit the two-hour limit on background commands. The second shortened its poll from 60 seconds to half a
second, because `W69` re-took the lock between its back-to-back native runs. Both runs released the lock in a
`finally` block, at 15:53:09 and 16:34:18.

## Choices where the specification was open

- **What "restart" means here.** The TASK asks for "save mid-job, load and continue" as
  `ArcCuttingGameTests:189` and `C16cMachineGameTests:135` do. Those tests load the NBT back into the same
  objects. I replaced every block entity with a fresh one decoded from the saved NBT instead. This also covers
  the codec and the hatch-claim and binding resolution between new objects, which an in-place load does not.
- **Which machine gets the real unload.** I chose the etcher. Its 400 FE per tick drains the two seeded plugs in
  50 ticks, so the job is reliably paused mid-batch and unpowered when the chunk unloads. The comparison after
  the reload is therefore exact.
- **The controller after a disk reload.** The controller's saved formation state is not compared, because the
  unload sets it to WAITING_UNLOADED by design. The job, progress, FE, resources and instance ID are compared,
  and every hatch's NBT is compared exactly.
- **The detector restart** uses a fresh block entity in a loaded chunk, not a real unload. The TASK asks for "a
  mode-root round trip and a measurement".

## Not done

- No real chunk unload for the crystallizer or the chemical reactor. Their fresh-instance restarts run the same
  kernel code as the etcher.
- No packaged dedicated-server restart ("N" grade) for any of the four. W62 lists that as class B, for the final

- W62's other "weak restart" machines (arc furnace, cutting machine, lathe, centrifuge, solar generator, solar
  array, suit workstation) are outside S1 and unchanged.

## Known risks

- The real-unload test depends on wall-clock pacing. On a slow hosted runner, the far chunk's neighbourhood may
  take longer than the 30-second budget to finish generating. The failure would then be "Timed out waiting for
  the fixture chunk to unload", as in run 1.
- The restart tests require each fresh block entity to re-save exactly the NBT it loaded. A later codec change
  that writes an unordered collection would fail them. That failure would be correct: the save would then not
  be deterministic.
