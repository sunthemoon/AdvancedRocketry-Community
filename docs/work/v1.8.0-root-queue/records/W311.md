## Item 1: reopening the console from a high seat (finding 7-2)

### What vanilla checks

These were read from the Forge 47.4.10 bytecode (`javap`), not assumed.

- **Client pick.** `GameRenderer.pick` calls `ProjectileUtil.getEntityHitResult`, which selects an entity whose box
  contains the eye at distance 0. Otherwise, the view ray must clip the box within reach.
- **Server check.** `ServerGamePacketListenerImpl.handleInteract` calls `canReachRaw(entity, 3.0)`, which is
  `isCloseEnough`: the distance from the eye to the entity box, inflated by its pick radius, must be below the reach
  attribute plus 3. That is 6 blocks in both survival and creative, because the raw attribute is 3.
- **The reported failure.** The seat was the rocket's top block, 9 blocks above the origin, so the rider's eye was 10.77
  blocks above the origin. The old 1.5 by 4 box ended 6.77 blocks below the eye. The client pick missed, and the server
  check would have refused the interaction as well.

### Design

- **The box.** `RocketEntity.makeBoundingBox` returns the union of three boxes:
  - the type's fixed 1.5 by 4 box, so the box never becomes smaller than before;
  - every structure block;
  - each seat's block and the block above it (`RocketEntityExtent`, a pure Java class with a unit test).
- **Why the seats count.** A rider sits 0.15 above the seat block (W292). On a top seat, the rider's eye is 0.77 blocks
  and the head 0.95 blocks above the structure, so a box of the structure blocks alone does not contain the eye.
- **Sources.** The server reads its snapshot. The client reads the synced visual blocks and seat tags. These are the same
  sources and the same cache (`RocketPassengerPlacement`) that W292 uses to place riders. Until the visual blocks arrive,
  the client keeps the fixed box, and the rider sits at the fallback offset inside it.
- **Refresh.**
  - The server rebuilds the box on every snapshot change, at the end of `refreshSyncedData`.
  - The client checks the box each tick, because the visual blocks arrive after the entity without a position change.
  - Both refresh with `setBoundingBox`, never `setPos`. A box refresh is therefore not a position write and cannot
    invalidate a bay proof (W170-R22).
- **Unchanged.** The rocket stays not pushable and not a collision surface. `isPushable` and `canBeCollidedWith` are
  unchanged, and the new GameTest asserts both.
- **Guard 1: explosions.** `ignoreExplosion` returns true.
  - `Explosion.getSeenPercent` casts about (2w + 2)(2h + 2)(2d + 2) rays for each entity. That is about 1,500 rays for a
    3 by 11 by 3 rocket and about 287,000 for a 32-block cube, the bounding-volume limit.
  - The rocket takes no damage, and its motion is reset every tick, so explosions had no effect on it.
- **Guard 2: fluids.** `updateInWaterStateAndDoFluidPushing` no longer scans.
  - Vanilla reads every block of the box for fluids each tick on both sides, up to 32,768 blocks.
  - Nothing reads a rocket's fluid state, and the rocket never moves with fluids.
  - The only visible effect is that lava no longer sets a parked rocket on fire.

### Vanilla's entity-section margin (commit `870dea2ab`)

- **The margin.** `EntitySectionStorage.forEachAccessibleNonEmptySection` visits sections from 4 blocks below the
  searched box upward, and 2 blocks around it horizontally. A rocket is indexed in the section of its base. The pick
  searches the rider's box, inflated by 1 and extended along the view.
- **When it misses.** On a level or upward look from a seat h blocks above the origin, the rocket's section is searched
  only when the origin's height within its section, plus h, minus 5, is below 16.
  - The reported rocket's origin (y = 151) is 7 blocks into its section, and h = 9.15, so the rocket is found.
  - From an origin 12 to 15 blocks into its section, the rocket is not found.
  - Taller seats miss more often.
  - Looking down extends the search downward and usually finds the rocket.
- **Demonstrated.** With the box but without this fallback, the worst-case GameTest failed on a level look
  (`negative-no-seated-pick`).
- **The fallback.** `RocketSeatedPickClient` handles `InputEvent.InteractionKeyMappingTriggered`, which Forge fires
  before `Minecraft.startUseItem` reads the hit result.
  - It acts on the use key, when vanilla picked no entity, if the rider's eyes are inside its own rocket's box. The shared
    rule is `RocketSeatedPick.target`, in common code.
  - The hit result then becomes that rocket. Vanilla's own `interactAt`, `interact` and interaction packet follow.
  - No packet is added. The server still checks reach and every console rule.
- **For Root.** This goes beyond the letter of R359, which expected vanilla's pick alone to select the rocket. It is a
  separate commit that can be dropped without affecting the box.

### Other readers of the entity box

- **Vanilla's pick and the `handleInteract` reach check.** A seated rider targets its rocket in every direction. Tested.
- **Unmounted players.**
  - They can now target and reach the rocket near any part of its structure.
  - The console still requires 8 blocks from the origin (`RocketFlightService` access), so an unmounted player beside the
    top of a tall rocket gets OUT_OF_RANGE. Tested.
  - Disassembly and propulsion items keep their own server checks.
  - Blocks inside the structure's bounding box are harder to target, because the rocket is picked first.
- **W300's absence check (`RocketSeatInput`).** Unchanged: it compares `player.getVehicle()`, not the box.
- **Area queries.**
  - The readers are `StationManager` (station occupancy), W301's `SafetyReturnOverworldArrival` (rocket avoidance),
    `BayCopyCensus`, the recovery query in `ServerLevelRocketTransactionWorld`, `FuelLoaderBlockEntity` and
    `ClassicSoundClient`.
  - A rocket now matches when any part of its structure intersects the query, so station occupancy, rocket avoidance and
    the copy census include more rockets.
  - The recovery and fuel-loader queries still filter by assembly ID or origin distance, so their results do not change.
  - The client sound query gets more candidates and keeps its origin-based distances.
- **Landing and clearance.**
  - `RocketLandingPadSelector` first refuses for rockets whose entity box touches the arrival, then runs the structure
    discovery (`NamedLandingPadOccupancy`). The first check now catches most occupants.
  - Refusals and reasons are unchanged. Commit `373e3e274` makes the first check log `ARCE_PAD_OCCUPANCY_REFUSED` naming
    the occupant, as the discovery does (W13F review N3 and `CHANGELOG.md`).
  - More rockets can be visited, so the 64-inspection budget can be reached sooner in a crowded station.
- **Loaders, linkers, cargo devices and monitors.**
  - The readers are `LoaderEligibility`, `RocketCargoBindingChecks` and `RocketMonitorBinding` (6 blocks), and
    `LinkerItem`, `LinkerEndpoints`, `RocketItemCargoLinker` and `RocketFluidCargoLinker` (8 blocks).
  - Distance is now measured to the nearest part of the structure, not to the base. A device or a player beside the upper
    part of a tall rocket is therefore in range.
  - The duplicate-copy search covers a larger area, which is more conservative.
- **Bay passenger exit (`BayPassengerExitWorld.entitiesClear`).**
  - An exit candidate inside the rider's own rocket's structure box is unsafe. Before, only the 1.5 by 4 base box counted.
  - For a rocket wider than 3 blocks around its origin column, the ±2 candidates fall inside the box, and the anchor
    columns are used instead.
- **Rendering bounds.**
  - `RocketEntityRenderer.shouldRender` already used the visual structure bounds, so culling is unchanged.
  - The F3+B hitbox shows the new box.
  - F3's "Targeted Entity" line never lists the rocket, because vanilla fills it only for living entities and item frames.
- **Projectiles, fishing hooks and the laser trace.** They now hit the rocket over its whole structure, not only at the
  base. The rocket still takes no damage.
- **Pressure plates and tripwires.** Vanilla counts every entity whose box touches them, so a plate inside the rocket's
  structure box is now pressed. This is not changed.
- **Explosions and fluids.** Guarded, as described above.
- **GameTests.**
  - Five occupancy tests and one arrival-footprint test asserted that a wide occupant's entity box stays clear of the
    arrival. Their purpose (W13 R1) is to show that the structure-based check, not the small box, does the refusing.
    Under R359, that premise cannot hold.
  - The occupancy tests are two in `NamedLandingPadOccupancyGameTests` and three in
    `LegacyLandingPadOccupancyGameTests`. The sixth test is in `RocketArrivalFootprintGameTests`.
  - Commit `5ac290cee` now asserts two things: that the occupant's base box, which was its whole entity box before W311,
    stays clear of the arrival; and that the new box covers it. Every refusal assertion is unchanged.
  - **Root should confirm that this adaptation keeps W13 R1's intent.**

`RocketEntity` grows to 776 lines, under the 800-line limit. The extent calculation lives in `RocketEntityExtent` and
`RocketPassengerPlacement`; the entity only uses it.

## Item 2: the named pad's refusal on the console (finding 7-5)

- **Server (`RocketFlightFeedback.reply`).**
  - The client already receives the named pad's reason, in the chat line "Landing pad refused: %s".
  - A refused request that carries a pad reason (`detailKey`) now uses the same text, with the existing key, for its
    action-bar reply.
  - Every named-pad refusal names a reason (`NamedLandingPadStaging`). A fixed-pad refusal without a reason keeps "All
    fixed destination pads are occupied or unsafe". A governed fixed-pad refusal for the chunk budget now also shows its
    reason.
  - The chat line is unchanged. No language key, packet, menu data or protocol changes, so runData has nothing new to
    generate.
- **Client.**
  - `ScreenMessageState` gains one pinned slot. A pinned refusal outlives the 6-second lifetime. A newer timed notice is
    shown first, and the refusal returns after it.
  - `ScreenActionMessages` pins a message only when two conditions hold: the open screen is a `RefusalOwner` (only
    `RocketFlightScreen` is), and the message is a flight refusal (`RocketFlightFeedback.refusal`).
  - The console releases the refusal when the player uses any of its controls: the destination, station, body, map,
    launch, cancel, board and leave buttons, or a target on the star map.
  - It also releases the refusal when the plan a launch would send changes (`selection.target(LAUNCH, activePlan)`), for
    example when a station or pad is cleared.
  - Closing or switching screens clears it, as before.
- **Choice 1, all refusals.** The console keeps every refused flight request, not only the named pad's, so that refusals
  behave alike. Success and JOURNAL_PENDING progress are not refusals.
- **Choice 2, which plan.** "The flight plan" is the plan the console would launch, not the server's state. A refusal
  that arrives as a countdown ends therefore stays visible; using the server's state would clear it at once.
- **The timing in the report.** The mirror's lifetime has been 6 seconds since `927a5875d`. The report's "about 3
  seconds" was a screenshot interval or another notice. Either way, a refusal no longer expires on a timer.
