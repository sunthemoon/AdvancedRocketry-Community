## Recheck of R32 against `b5cdcdef`

- `RocketTransferService.spawnDestination` still has the PREPARED wait (origin entities loaded and entity-ticking)
  before it builds the `DESTINATION_SPAWNED` record, and W91's acknowledgement callback still rechecks the origin's
  readiness and the pad, and drops the transfer from live dispatch when either fails.
- Governed (record-3) flights never reach `spawnDestination`. Their dispatcher already requires both recorded ends'

  legacy flights. Item 2 still applies to governed flights at their F2 callback.
- W90a's `RocketDiscoveryColumns` gives the checked set. Its `releaseSet()` is "every column when admissible, else the
  origin", which is exactly R32's destination ticket set, and F8's `releaseMargins` already removes it in each end's
  own Level. A legacy flight has no explicit release today: its tickets expire 400 ticks after the last live refresh.

**Item 2, tickets.** `RocketTransferEntities.keepDestinationLoaded` replaces `keepLoaded` for the destination end at
the three places that ticket it: the legacy PREPARED acknowledgement, the governed F2 callback and the live refresh in
`tickLive`. It adds one flight ticket (level 2, the same type, key and timeout) on each column of
`destinationTicketSet`, which is `RocketDiscoveryColumns.of(destination).releaseSet()`: every column of an admissible
checked set (at most 16, origin included), otherwise the origin alone, as before. It then loads the origin as today.
The source end keeps `keepLoaded` (origin only); governed records keep W90a's margin refresh. Budget: at most 16
destination tickets per transfer instead of 1, so 1,024 at 64 transfers (a unit test pins the 1,024). Release: governed
F8 removes exactly the destination's release set in its own Level; legacy tickets still expire 400 ticks after the
last refresh. For an admissible governed destination, the F2 callback now adds the same columns that the first
ACTIVE refresh adds, a few ticks earlier.

**Item 1, the wait.** After today's origin check, `spawnDestination` asks `RocketArrivalFootprintWait.ready`, which
counts the columns of the same ticket set whose entity sections are loaded (`ServerLevel.areEntitiesLoaded`; it never
loads, tickets or forces a chunk). While any column is missing, the record stays PREPARED, nothing is written, and the
next live visit retries; the native probe records an owned wait with cause `DESTINATION_ENTITIES`, so the concurrency
harness does not count a missed step. A destination whose set is not admissible checks only its origin, which today's
check already covers, so its behaviour is unchanged. There is no new timeout. The wait keeps one RAM entry per waiting
transfer (at most 64, pruned to the live set, cleared with the service, never saved). When a wait starts it writes one
INFO line, `ARCE_ARRIVAL_ENTITIES_LOADING transfer=… logical=… level=… columns=k/n reason=entities_loading`, and sends
the passengers aboard one action-bar message, `message.advancedrocketrycommunity.pad.reason.entities_loading`
("Arrival waiting: the landing area's entities are still loading." / "到达等待中：着陆区域的实体仍在加载。"). When it
ends it writes `ARCE_ARRIVAL_ENTITIES_READY transfer=… waited=<ticks>`. The key is a pad reason, so a request result
would also accept it.

`RocketTransferService` grows by six lines (797 lines). The wait's state lives in the new 73-line
`RocketArrivalFootprintWait` so that the service stays under 800 lines; that class is the only file outside the
task's listed write scope, and it holds nothing but this wait.

**What a player sees.** In ordinary play the destination columns are ticketed from the countdown, about 160 ticks
before the arrival is due, so the wait rarely shows. It shows after a restart (no ticket until the first live refresh)
or when entity loading is slow: the rocket holds at flight altitude in the source Level with its passengers aboard,
they see the action-bar message once, and the arrival proceeds on the first visit after the columns load.

**Item 3, W91's placement callback (unchanged).** If, between the `DESTINATION_SPAWNED` acknowledgement and the
callback, the origin's entities unload or a rocket enters the footprint, the callback places nothing and drops the
transfer from live dispatch. The player sees the source rocket hold at flight altitude with its passengers aboard,
because passengers move only at `PASSENGERS_TRANSFERRED`. The in-session recovery pass, which visits one unclassified
record per tick once both recorded origins are loaded, then classifies the record as `KEEP_SOURCE`: the source returns
to its origin, stationary, with the fuel recorded before the flight, online passengers are remounted, the record is
removed and `ARCE_TRANSFER_RECOVERY … action=KEEP_SOURCE` is logged at WARN.

## Tests

- `RocketDestinationTicketsTest` (7, unit): a border-crossing destination tickets its 2 x 2 checked set in its own
  Level and release removes exactly that; over 2,000 random destinations the added set equals the destination's release
  set, stays within 16 columns and contains the origin, and an inadmissible one keeps only the origin; a one-column
  destination keeps a single ticket and refreshes are idempotent; an absent Level gets no call; 64 of the largest
  destinations hold exactly 1,024 tickets and a 17-column one keeps the origin ticket; W90a's governed refresh tickets
  the same destination columns; the loaded-column count reads each column once.
- `RocketArrivalFootprintWaitTest` (5, unit): one line when a wait starts and one when it ends, nothing in between or
  after; a ready first visit logs nothing and a later wait is a new transition; entries of transfers no longer live are
  pruned; at most 64 entries, and an unreported wait still waits; the reason key, its two translations and its
  acceptance as a request detail.
- `RocketArrivalFootprintGameTests`, new batch `arrival_footprint`:
  - `parkedRocketInAnUnloadedFootprintColumnHoldsThenRefusesTheArrival`: an arrival from x 24008 to 24052 on the Moon,
    columns 1500 to 1503. A rocket whose structure overlaps the arrival but whose entity box does not is parked in
    column 1503, then its column is unloaded (entities saved). With the origin ready and column 1503 still unloaded, the
    first due `tickLive` visit waits with one `entities_loading` line and tickets all four columns. The tickets load
    column 1503; the census then refuses the arrival naming that rocket, and the source returns undebited. Every visit
    asserts the record stayed PREPARED and no rocket with the arrival's identity exists in the area.
  - `readyFreeFootprintPlacesTheArrivalOnItsFirstDueVisit`: the same geometry with all four columns loaded and free
    reaches `DESTINATION_SPAWNED` on the first due visit, logs no wait, and is placed at its reserved origin.
  - `legacyStationFlightAcrossAChunkBorderLandsWithNoPlayerNearby`: a three-wide legacy rocket flies through the
    production runtime to a new station's pad, whose x is a multiple of 16, so the footprint spans two columns. With no
    player within 128 blocks of the pad, the acknowledged flight's tickets are exactly the source origin and the
    destination's four checked columns, and the rocket lands.
- `RocketDestinationReadinessGameTests` now also waits for the destination ticket set's entity sections before its
  blocked-pad step. That step calls `spawnDestination` directly and expects an immediate return; without this wait it
  could race a neighbour column's entity load and meet the new wait instead. Nothing is relaxed: the wait is stricter
  and its 80-attempt bound is unchanged.
- The log expectation `transfer-returned-to-source` gains `"arrival_footprint": 1` for the parked case's return WARN,
  and `test_named_pad_occupancy_return_has_its_own_exact_count` pins it. No ERROR expectation was added.

## Not done, residuals and risks

- TASK-W83 item 3, unchanged: a rocket whose entity stands in a chunk outside the destination's checked set while that
  chunk's entities are unloaded, but whose structure overlaps the footprint, can still be missed
  (`NamedLandingPadOccupancy.discoveryBox` reaches far beyond the footprint). W83b does not claim to detect every
  unloaded off-footprint rocket.
- The recovery rebuild path (`REBUILD_DESTINATION`, neither end present) still places a destination without a
  readiness or occupancy guard, as TASK-W83B item 3 requires to be left.
- An inadmissible destination (checked set over 16 columns, arithmetic overflow, or an origin outside its own set)
  keeps today's origin-only ticket and wait, so its footprint is not covered.
- The wait has no timeout of its own. If a destination column can never load its entities while the origin stays
  ready, the arrival waits indefinitely at PREPARED, as the origin wait already can.
