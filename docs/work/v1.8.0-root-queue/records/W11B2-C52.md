F8 journal/prune acknowledgements were eight because they include those
seven cancellations; they do not prove eight arrivals. The unchanged
4,000-tick deadline stopped the run at age 4,001, workload tick 3,831.
The harness deliberately fails rather than treating this as completion.

The product selects surface-pad reservations only from
`RocketTransferService.prepareLaunch`'s published `journal.entries()`.
Coalesced F1 requests can therefore select the same first free pad before
any F2 record exists. Once the first callback publishes F2,
`RocketTransferSavedData.validateNewRecord` refuses an overlapping second
reservation. `EscrowFlightCheckpoint` catches that admission refusal;
the checked pre-F2 cancellation subsequently retires the other arms.
This source-level diagnosis matches eight arms, one F2 and seven cancelled
flights. The retained native snapshot does not contain the seven discarded
destination envelopes, so it is not a direct coordinate trace of all eight.

The new diagnostic `EscrowFlightBenchmarkPadAdmissionTest` reproduces the
reservation conflict: eight distinct launches sharing one destination all
preflight and become ARMED while the journal is empty; publishing the first
F2 makes the other seven throw exactly `Transfer destination overlaps an
active reservation`. Their per-rocket no-T leases remain valid. Thus this
is separate from the old journal-wide lease defect and from the optional
two-slot F2 callback queue. This test pins the observed refusal, not a claim
that cancellation satisfies the benchmark. No production fix is attempted,
as continuation 51 item 4 requires retaining and reporting a newly exposed
functional failure. Neither explicit fixture-selected pads nor waiting for
one completed flight before launching another is substituted.
