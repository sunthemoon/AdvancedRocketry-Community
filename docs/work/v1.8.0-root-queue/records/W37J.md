# W37J: save-boundary feasibility and clone reconciliation

## Design (written before any production code, 2026-10-14)

The intended write scope is the sleep/respawn service and any small lifecycle helper, its related
tests, their exact log expectations and pinned totals, and this record. Status files, the ledger,
ADRs, the risk register, build scripts, other worktrees and other tasks are excluded. No upstream
code or assets will be copied. This session is an implementer, not Root; it will not push, merge,
delegate or change a shared branch.

F1 requires reconciliation before the saved player's native fields and Forge data are serialized.
The first copy may replace only the exact cleared tuple while a readable backup is pending. Later
copies may replace only the exact tuple previously copied by this service into that same old player,
for the same still-unadopted replacement and connection. A proposed service-owned identity map would
retain that last copied tuple and expire it on adoption, ownership mismatch, a foreign change to the
old tuple, completed disconnect saving or server stop. An abnormal stop would lose that map and any
unsaved updates; it would not provide crash-atomic durability. This is a design only, not implemented.

F2 would reconcile a pending backup against `Clone.getOriginal()` rather than treating a fresh
replacement's defaults as evidence of ownership. The original player's newer point must release
the shared envelope before replacement restoration, including setter cancellation and no-arrival
branches. Existing tuple-only foreign-clear behaviour, END/LOWEST decisions, the DISCARDED final
check and End-exit judgement must remain unchanged.

Before implementing either change, the requested `SaveToFile` boundary is checked against the
actual Forge 47.4.10 bytecode. TASK-W37J requires stopping if its correction needs a Mixin. No
production code has been written.

## Result: BLOCKED at F1's required save-boundary check

The task's premise that `PlayerDataStorage.save` posts `PlayerEvent.SaveToFile` before writing is
false on the pinned platform. With JDK 17.0.7, `javap -c -p` shows this order:

| Method | Bytecode offset and operation |
|---|---|
| `PlayerDataStorage.save` | 8: `Player.saveWithoutId`, producing the serialized compound. |
| Same method | 33: `NbtIo.writeCompressed`, writing that compound to the temporary file. |
| Same method | 85: `Util.safeReplaceFile`, replacing the player's `.dat`. |
| Same method | 97: `ForgeEventFactory.firePlayerSavingEvent`. |
| `ForgeEventFactory.firePlayerSavingEvent` | 3: construct `PlayerEvent.SaveToFile`; 13: post it. |
| `ServerGamePacketListenerImpl.onDisconnect` | 98: `PlayerList.remove(this.player)`. |
| `PlayerList.remove` | 1: logout event; 18: `PlayerList.save` on the supplied player. |
| `PlayerList.save` | 13: `PlayerDataStorage.save` on the supplied player. |
| `PlayerList.saveAll` | 29: `PlayerList.save` on each listed player. |

Thus both ordinary saves and disconnect saves use this post-write event. Changing fields or
removing the backup in that listener cannot change the compound or player file already written.
Changing event priority cannot move the event ahead of serialization. An END-tick retry cannot
cover a setter immediately followed by logout before another END. A logout listener is genuinely
before its save, but it is not a general player-file pre-save boundary.

No post-save `.dat` overwrite or recursive second save is attempted. Forge's
[SaveToFile API documentation](https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.x/src/main/java/net/minecraftforge/event/entity/player/PlayerEvent.java)
warns against overwriting the native player file from this event. The local pinned bytecode, not
the moving online branch, is the version-specific evidence.

An interception before `PlayerDataStorage.save` serializes the player (for example a separately
approved Mixin) would provide the requested boundary. This task does not authorize adding it, so
implementation stops instead of silently substituting a different save protocol. This is not a
claim that every possible non-Mixin design is impossible: `Entity.saveWithoutId` calls
`serializeCaps` at 455, before the ForgeData copy at 490 and `addAdditionalSaveData` at 499.
A side-effecting capability serializer is a different candidate mechanism, not the requested
`SaveToFile` listener; it has not been implemented, tested or accepted here. Root must revise the
boundary decision before runtime work resumes.

F1's three native regressions and F2's two clone regressions remain unimplemented. F2 was not
attempted after the task's stop condition. The reviewed data-loss and stale-backup risks remain
open, not fixed or waived.
