The reader retains the failing world-relative filename, file length, up to
8,192 original header bytes as hex, header length, slot and reason. If the
file cannot be read, unavailable fields stay null with the diagnostic error;
UNKNOWN never becomes absence. A zero-byte region has no allocated slots;
every nonempty header shorter than 8,192 bytes remains UNKNOWN, including a
complete location table with a missing timestamp table. Record decode failures
also retain diagnostics rather than escaping the reader.

Vanilla code citation: Minecraft 1.20.1's `RegionFile` (`dfd`) constructor in
the locally cached official server's extracted `output.jar`, SHA-256
`80db52b203ac5de6e5fc1c5082259df440fb2b5390b4c61d474e8fbc63cc41f5`.
The four-argument constructor's bytecode offsets 5–11 allocate the 8,192-byte
zeroed header, 201–218 read it and skip header processing on EOF (`-1`), and
221–240 warn on a nonempty truncated header. `getChunkDataInputStream`
(`a(ChunkPos)`) offsets 0–11 return null for a zero offset. Thus empty files
are legitimate, but a short nonempty file is not silently classified as empty.
This is behavior reference only, not copied Minecraft code or assets.
The exact `javap -p -c` output is retained at
`D:/GitHub/ARCE-Task-Evidence/root-queue/W221/r208/vanilla-RegionFile-javap.txt`,
SHA-256 `dae79c7b5cb4ab0fb0944488eeb8ba7a9e422fab6d49a06155d60c097c61bd8b`.

Before deleting any named-pad server copy, the runner archives byte-identical
read inputs, including the offending region on UNKNOWN, with hashes verified
from the archive. Successful reads also retain their inputs for replay.
Evidence limits are 128 inputs, 100,000,000 uncompressed bytes and 50,000,000
archive bytes. Evidence-copy failure keeps the owned server copy for recovery;
it never deletes the only remaining input. UNKNOWN ends the attempt before
another restart and stops the campaign for analysis. No remaining attempt is
automatically spent on an unexplained read.
