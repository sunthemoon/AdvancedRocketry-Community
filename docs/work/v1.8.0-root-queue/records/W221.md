# W221: governed named-pad crash windows

## Cut design (committed before native execution)

This task starts at `eb6bd6b26` on `codex/v1.8.0-w221`, in the assigned clean
worktree. Authority is [TASK W221](../TASK-W221-GOVERNED-NAMED-PAD.md), R207.
W211-R2 is coverage, not a demonstrated production defect. W204's ordinary
N2 evidence and W211's ordinary-form exclusions remain unchanged.

The fixture creates one real station and registers a physical named pad with
`LandingPadService.register`. A real fluid loader fills a mono rocket once:
5,000 mB initially, then 4,000 in the loader and 1,000 in its typed bank.
The installed `RocketTransferService.prepareLaunch` selects and claims the
named pad; it is not a synthetic journal, manually claimed pad, or direct
call to governed preparation. The flight authorizes one 500-mB typed debit.
The uncrewed destination is the Space Level. Fixture tickets cover only the
declared source and destination discovery columns.

The initial ordinary save persists the station, physical pad, empty bank and
loader. At F2 acknowledgement the fixture additionally saves **only the pad
index**, using its existing native SavedData save method, to put the actual
product claim on disk. This is a labelled fixture-owned persistence choice,
not a claim about production save timing. It does not save a rocket, advance
a journal acknowledgement, or supply a proof. Subsequent entity persistence
belongs to product F1/F6 and normal shutdown. Read-only observation files
are outside the world and never loaded into it.

There are seven mono selections, 21 planned starts including 14 restarts;
each has at most two attempts. Both restarts use the named selector without
the initial cut/fault, retain exact station/pad/physical identities and epoch,
and finish with one landed destination, 4,000 + 500 mB, one authorized debit,
no source, journal entry, armed tuple, markers or pad claim. Release counting
means one transition from the exact transfer claim to unclaimed, not the
number of idempotent `releaseTransfer` calls. An already released disk image
must show no further transition. Initial rows that retain a durable claim
must release it once on restart 1 and never again on restart 2.

The observer records the entire source/arrival NBT, typed fuel, pad index and
physical pad, journal and escrow root at preparation and selected boundaries.
The Python oracle reuses S6 normalization, canonical NBT and complete rocket
projections, checks raw native files separately from live observations, and
rejects UNKNOWN reads rather than interpreting them as absence. Mutations
of quantities, snapshots, markers, identity, epoch, claim, acknowledgements
and release ordering must fail. The observation interval has explicit
begin/end/count framing.

The new `EscrowLoaderS6PadJournalProbe` is observation-only: exact hooks,
`start` scenario, BEFORE/MOVED selector and the complete release gate are
required. Otherwise it returns the identical policy without accessing the
world or invoking callbacks. It wraps the existing committer without changing
bytes or outcomes. Its unit tests pin these conditions and commit ordering.
UNKNOWN reuses R52's existing failure mechanism, not this observer. All live
fixture entry points require the release gate and exact selector.

Write scope: this record; new named-pad S6 fixture/observer and server-side
test bridge; S6 probe dispatch and journal observer dispatch; the S6 runner,
new named-pad oracle/tests and pinned case inventory. Existing shared loader
and escrow runners are read-only imports. No production algorithm, schema,
admission, pad policy, budget, timeout, ADR, status, ledger, build, workflow,
generated resource or upstream asset is changed. W220 and all other workers'
files and processes are excluded.

Verification: failing-first new Python/JUnit tests, isolated new JUnit
classes, whole unit suite, loader S6/escrow/pad Python suites, station/pad/
governed GameTest batches, then committed-source native rows under the
machine lock. Native processes run detached with bounded waits and retain
commands, source/JAR hashes, logs and decoded images. R190/R201 permit one
test-side renewal only with failing-first tests and retained-image replay;
a production cause or unexplained image stops for Root. No gate is approved.
