# W295 — Reliable endgame switch instructions

## Scope and decision

The implementation is commit `16df47a14fa52526847d812eefbe51823c51f478`, based on
`87aeae6ea2916de2e0211075e66b8d99107615b6`, on `codex/v1.8.0-w295`.
The worktree was clean at entry. Only this task's files were changed. No other
agent was launched, and nothing was pushed or merged.

I chose the task's documentation-correction option. Operators must stop the
server, edit `config/advancedrocketrycommunity-common.toml`, and start it again.
Singleplayer requires fully exiting and restarting Minecraft. The guide names
`/arce endgame status` as the loaded-value check and explains that `/reload`
reloads data packs, not COMMON configuration. There is no existing ARCE
operator command that reloads this file.

Clearing the BooleanValue cache alone would not fix a missed file load. Making
arbitrary editor writes reliable would require changing the watcher or adding
explicit reload machinery. Neither is needed for the conservative, accurate
operator instructions permitted by this task. ADR-054 remains unchanged: after
a successful Forge reload, the settings still reach their consumers on use.

## Investigation and reproduction

- The round-four server debug log watches the same absolute COMMON path that
  the harness's `set_switch.py` edits. It tracks one COMMON registration for
  ARCE. This is not evidence of a second loaded config or an edited client file.
- Forge 47.4.10's installed `ConfigFileTypeHandler.ConfigWatcher` first loads the
  file, then calls the spec's `afterReload()`. `ForgeConfigSpec.ConfigValue.get()`
  caches values, and `afterReload()` clears those caches. ARCE's
  `serverSwitchValue` reads that loaded/cached value, not the file.
- The bundled NightConfig 3.6.4 `FileWatcher.WatcherThread` ignores events whose
  kind is not `ENTRY_MODIFY` **or whose count exceeds one**. Its subscription
  also omits create/delete events, so replacing a file by rename is not a
  portable reload mechanism either.
- The committed [native probe](../../../../scripts/java/ConfigWatcherProbe.java)
  uses the actual installed NightConfig watcher on Windows 11 / Java 17.0.7.
  A bounded latch holds its callback thread, modeling delayed polling while a
  callback runs. One normal truncate-and-write of the watched TOML then produces
  `ENTRY_MODIFY count=2`. A subsequent fence callback proves the watcher drained
  its queue, but the target callback count is zero. The loaded physical-mining
  value remains `false`; a fresh file load reads `true`. The scratch directory
  and files are deleted by the probe.
- An earlier exploratory probe additionally made eight positional writes; its
  native event count was ten and its result was identical. The committed probe
  needs only the single rewrite, not that burst.
- The [file-backed tests](../../../../src/test/java/io/github/sunthemoon/advancedrocketrycommunity/config/CommonConfigReloadTest.java)
  cover all six endgame switches. They demonstrate unchanged values after disk
  edits, unchanged values after cache invalidation without loading, the need for
  both loading and cache invalidation after a populated cache, and changed
  values after unloading and fresh startup loading. No test override is used.

This reproduces a concrete missed-notification mechanism on this machine. The
historical round-four run did not record raw WatchEvent counts, so it cannot
prove which native event was lost in that particular run. No new real-client
or packaged dedicated-server campaign was performed.

The portable watcher source has the same count filter on Linux; ordinary
modifications can reload when their notifications reach the callback, whereas
coalesced counts above one are discarded. Atomic replacements must not be
assumed to work. This is a source-based inference, not a Linux runtime result.
The primary source inspected was
`https://raw.githubusercontent.com/TheElectronWill/night-config/v3.6.4/core/src/main/java/com/electronwill/nightconfig/core/file/FileWatcher.java`.
Forge's current 1.20.x handler source was also consulted at
`https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.x/fmlcore/src/main/java/net/minecraftforge/fml/config/ConfigFileTypeHandler.java`;
the installed 47.4.10 bytecode, rather than the moving branch, confirmed the
load/invalidation sequence used here. Installed dependency hashes and bytecode
inspection outputs are retained with the external logs.
