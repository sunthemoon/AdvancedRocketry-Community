### The extension point

No special-recipe extension point existed: the etcher's retained lens is hard-coded by recipe
type. I added the narrowest point that W10's processing allows:

- A `chemical_reacting` recipe may carry `"special"`, one of five closed names. The codec refuses
  it on other types, refuses unknown names, and requires item row 0 (the subject) to have count 1
  and at most three other item outputs. The name is part of the signed canonical JSON, so a
  running job never resumes across a change of special.
- `ClassicSpecialRecipe` binds each name to its domain behaviour. In `ClassicBatch.prepare`, a
  stack is offered to the matcher only if the special admits it. The subject must have a
  transform, and no consumed tank may hold gas. A refused stack is never debited.
- The debited subject returns as its changed self in the same transaction and output plan, never
  as a fresh output Item. In the kernel definition it is a retained output, as the etcher lens is.
  A subject whose alternatives overlap another row disables the recipe with the existing bounded
  error log.
- If a match fails only because of eligibility, the controller shows `INELIGIBLE`, both during
  lookup and while a running job is paused. Missing inputs still show `INPUT`.

## Choices where the ADRs leave room

- **Recipe shape:**
  - The legacy reactor generated one recipe per registered `ItemArmor`.
  - Here there are four recipes, one per slot. Each takes its subject from the Forge tag
    `forge:armors/{helmets,chestplates,leggings,boots}`, which Forge 47.4.10 fills with the
    vanilla pieces.
  - The legacy `sheetTitaniumAluminide` maps to `advancedrocketrycommunity:sheets/titanium_aluminide`.
  - The named slot is checked on each stack, so a mis-tagged piece is refused rather than sealed
    without the chest tank.
- **Eligibility (ADR-066 section 5.1, W03's restrictions kept):**
  - The stack must be a native `ArmorItem` for that slot.
  - It must be one unstackable unit with bounded data (`EquipmentNbt.safe`).
  - It must not be a built-in space suit piece. The legacy recipe likewise excluded
    `ItemSpaceArmor`.
  - It must not be owned by a registered ADR-025 provider, whether that provider is enabled or not.
  - It must not already carry `space_breathing` at any level. The legacy reactor would have
    consumed the inputs as a no-op.
  - It must be in the enchantment's ARMOR category and compatible with its existing enchantments.
  - For a chest, it must not hold an unsupported `arce_enchanted_suit_oxygen` root.
  - The result must stay within the bounds.
  - Note: Forge routes `Enchantment.canEnchant` to the enchanting-table check, which W03's
    enchantment refuses. The recipe therefore checks the category directly. A unit test records
    that tables, books, trades, discovery and anvils still refuse the enchantment. The enchantment
    class itself is unchanged.
- **Output:** the result is the input stack with one enchantment entry added. Its damage, name,
  other enchantments and unknown tags are kept, and a valid oxygen root is not rewritten.
- **Tank:** the chest recipe consumes a tank only if it has a supported root storing 0 units,
  following W03's rule that a recipe never destroys a tank's gas. A drained tank that still names
  a gas is accepted. The legacy reactor consumed any tank.
- **Refresh:**
  - Only a fully spent cartridge (0 uses) is accepted, as the legacy exact data 32766 required.
    Partly used and unsupported cartridges are refused and preserved.
  - Only `uses` changes, to 32,766. The root, the name, unknown tags and the item stay exactly the
    same, so one cartridge goes in and one comes out.
  - The legacy charcoal output is kept.
- **Switches (ADR-066 section 2):** `equipment.classicEnabled` gates the four seal recipes, and
  `lifeSupport.classicDevicesEnabled` gates the refresh. A running job pauses with
  `CONFIG_DISABLED` and keeps its progress.
- **Recipe graph:** a seal recipe produces the node
  `enchantment:advancedrocketrycommunity:space_breathing`. Like the etcher lens, the armor piece
  and the cartridge are requirements, not outputs. The refresh yields only charcoal. The four
  armor recipes are the only producers of the enchantment, and it is unreachable without the
  chemical reactor.

## Known risks

- A modpack that puts more than 32 items into one Forge armor tag disables that slot's seal recipe
  until the next reload. The existing bounded error is logged; the other recipes keep working.
- If the subject is swapped during a job, the job pauses. FE already spent stays spent, as with
  the existing `INPUT` pause.
- The kernel's retained-subject balance uses the lens precedent: an output under the input's own
  key with the first alternative's ID. The exact stack and its data live only in the native plan.
- A grindstone can still remove the enchantment (vanilla behaviour). The oxygen root stays, and a
  later seal reuses it only if it is valid.
- Each refresh yields one charcoal, which is the legacy balance.
