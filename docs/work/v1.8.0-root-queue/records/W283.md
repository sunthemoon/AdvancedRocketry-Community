## Causes and design decisions

The reconnect setup checked entity ticking at the destination origin, but
`RocketTransferService.spawnDestination` also waits for every occupancy-census column.
The supplied hosted log reports `ARCE_ARRIVAL_ENTITIES_LOADING` immediately before
`Own spawn did not queue`. Setup now uses the product's destination ticket set and
readiness predicates, with separate test-owned tickets. It still demands a queued spawn
on the first fully ready visit, and retains every original publication, reconnect,
source-preservation, uniqueness, and zero-recovery-ticket assertion. Wait limits and
the original batch and timeout are unchanged.

The new sibling has a 44-block-wide snapshot and initially tickets only its remote
destination origin. It checks that another census column really starts unloaded.
With the original spawn assumption it fails with exactly `Own spawn did not queue`;
with the fix all ten tests in the batch pass. It uses actual asynchronous native entity
loading, not a changed readiness result, clock, production queue, or simulated proof.

The escrow failure is an observer assumption, not a lost production callback. The
hosted run records `failures=2`, one callback, and a deadline 400 ticks after that
callback. An earlier F6 proof retry legitimately survives capture replacement. The
observer now snapshots the existing count and requires the same history to advance
once, capped at three, with exactly one observed F7 failure and the exact backoff
from its callback tick. Its logger is still preserved and restored. Unit controls
cover an earlier proof failure, saturated history, incorrect callback-relative
deadlines, and duplicate observations, alongside the original delayed-observation,
wrong-history, proof-failure, and queue-refusal controls.

Neither machine failure reproduced: each unchanged batch passed one initial run
without added load, three initial loaded runs, twenty consecutive delivery loaded
runs, and the full regression. Thus **23 loaded runs were tried for each machine
test**, without reproducing either supplied failure. Their code is unchanged; no
speculative timeout, pacing, or production change was made.
The supplied full-run scale logs show that unloading consumed nearly the entire
global fixture deadline, but that observation alone does not prove its cause.
