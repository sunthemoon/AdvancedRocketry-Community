## Implementation and findings

Code commit: `45fef294a7b95d392d17f2ccda3032ba6ff838c5`.

`EscrowTerminalRetryCut.assertWriteFailure` now requires the same history
instance, exactly one observed definite F7 failure callback, one history
failure, and `nextTick == callbackTick + EscrowReason.backoff(1)`. The callback
tick is captured by temporarily wrapping that history's existing logging
consumer. The original consumer still receives every transition and is restored
in `finally`, before the fixture removes its writer cut. No retry history,
deadline, production scheduling, timeout, or other assertion is changed.

The history has no stored failure tick. Its `failed()` method updates the count
and deadline before invoking the consumer, on the owner thread. The observer
records the clock there; it does not derive a tick by subtracting 100 from the
deadline being checked. It only recognizes `F7_WRITE / LEDGER_WRITE_FAILED`.
The existing first backoff is still 100 ticks.

There is only one `assertWriteFailure` caller. The other helper uses are the
three F6 replacement failures, lease invalidation checks, and the relogin
precondition. None has another equality against `getTickCount() + 100`.
The existing F6 deadline-range and readiness-boundary assertions are unchanged.

### Reproduction and limits of the historical diagnosis

The uncommitted experiment ran the existing dismount cut, checked its original
assertions immediately, then deferred another invocation of the retry assertion
by one real server tick through the fixture's existing tick callback. It did
not schedule a callback from inside another callback.

- Original assertion: failure count 1, deadline 252, immediate observation 152;
  it passed immediately and failed at observation 153 with the hosted error text.
- Fixed assertion under the same delay: failure count 1, deadline 253, captured
  callback tick 153; observations at 153 and 154 both passed.
- Both experiment patches and logs are retained outside Git. The delay and
  diagnostic logging were removed before the code commit.

This proves the observation-dependent assertion defect, but does not establish
the precise cause of hosted job 122364090027. That log prints neither the
failure count nor the two ticks. At this source revision, the call to
`assertWriteFailure` follows `EscrowTerminalLeaseCut.exercise`, which pumps
`coordinator.tick()` until its writer is idle within the same owner-thread
call. Ordinary escrow completions are polled in `EscrowRuntime` at tick END;
the separate checked-root/journal writer polls at START. Thus a later-tick F7
callback/observation gap did not occur naturally in the local immediate case,
and the TASK's START description is not the escrow writer's implementation.
The new assertion includes the count, deadline, recorded/observed ticks, and
callback count if this hosted failure recurs. No production defect was found.
