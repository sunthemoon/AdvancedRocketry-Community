## Design note: flight intents after W182 (written before the code)

`RocketFlightIntentPacket` (unchanged format: action byte, rocket entity ID, travel target, request ID, optional landing
pad) carries four actions. Its handler queues `RocketRuntime.requestFlightIntent` on the server thread, which reaches
`RocketFlightService.request`. Only `RocketFlightScreen`, the flight menu's screen, calls `RocketFlightNetwork.sendIntent`;
no key binding, item or block interaction sends the packet.

| Action | Where the client sends it | Checks after W182, in order |
|---|---|---|
| `LAUNCH` | the flight screen's launch button (with a landing pad when a station pad is chosen) | the C2S boundary (below); rejoin protection; the per-player rate limiter; access (the rocket is loaded, operational and in the player's Level within 8 blocks); owner, creative or operator; the request ledger; then the launch's own checks (launch-ready, destination, station access, plan, journal) |
| `CANCEL` | the flight screen's cancel button | as `LAUNCH`, then the countdown and planned-target checks |
| `BOARD` | the flight screen's board button | the C2S boundary; rejoin protection; rate limiter; access; the request ledger; then the release fence, escrow idleness, a stationary state and a free seat |
| `LEAVE` | the flight screen's leave button | as `BOARD`, then the fence's retained-rider rule, a stationary state and an assigned seat |

The C2S boundary is the landing-pad path's check before W182, now for every intent: the logical server thread; a
connected (`connection.connection.isConnected()`), living, non-spectator player that is not a `FakePlayer`; and that
player's open `RocketFlightMenu` for this rocket entity, valid by `stillValid` (same player, alive, not a spectator,
rocket alive and operational, same Level, chunk loaded, within 8 blocks). Any failure answers `UNAUTHORIZED`. It stays
first, where the landing-pad check stood, so a refused intent spends no rate budget and leaves no ledger entry.
(Corrected under R147: the `UNAUTHORIZED` goes only to the caller. The packet handler discards it, so the player gets
no message and the server logs no line; see "Review fixes (R147)".)

All four actions are sent only from the flight menu, so every one needs the open menu. No intent reaches
`RocketFlightService.request` from outside the menu. Three server paths start or change a flight without it and keep
their own checks: the rocket monitoring station's launch (`ClassicControlIntentPacket` of kind `ROCKET_MONITOR`, which
goes through `RocketMonitorFlights` to `RocketFlightService.launch` behind the monitor menu's and the link's checks), the
operator and test entries (`requestAdminFlight`, `requestAdminStationFlight`, `requestAdminPadFlight`, server-only), and
the rocket's own use (open the menu, or with sneak, disassembly). No packet format changes.

## Choices where the TASK was open

- "Reuse their existing check": the spectator test went into each menu's own validity check (`stillValid`, or
  `openRefusal` for the endgame devices), not into a new shared guard. Opening needed one more line per holder,
  because vanilla's spectator path reaches only `createMenu`. Reusing the whole `stillValid` there was rejected: several
  existing GameTests call `createMenu` directly with mock players at the world origin (for example
  `BootstrapGameTests.twoMenusShareAuthorityAndQuickMoveUsesMachineBoundaries`), and the distance part would have
  refused them.
- The endgame refusal code for a spectator is `UNAUTHORIZED`; a spectator never reaches the blocks' `use`, so no player
  sees it there.
- F3 keeps the boundary's position and its single refusal code, so a refused intent spends no rate budget and leaves
  no ledger entry. A far player is now refused `UNAUTHORIZED` at the menu rather than `OUT_OF_RANGE` in `access`: the
  menu's reach and the service's are both 8 blocks. (Corrected under R147: the refusal is silent, with no message and
  no log line, and `access`'s `OUT_OF_RANGE` branch can no longer be reached through `request`. `openMenu` and the
  navigation paths still reach it.)
- The test fixtures open the menu through `RocketRuntime.openFlightMenu`, not `Player.interactOn`, so that an item in
  the hand (fuel exchange) or a sneak (disassembly) cannot change a test's state. The new GameTests and the matrix still
  open it through `interactOn`.
- Fake players became unjoined connected stand-ins rather than joined players, so that no login, logout, chunk ticket
  or player tick enters tests that never had one.
- The verification's "every rocket flight batch" is taken as the 26 batches listed above that run flight intents or
  flights, plus `menu_authority` and `flight_intent_authority`. The escrow, cargo-settlement and menu batches whose
  tests or helpers changed ran once more on their own.

## Known risks

- The boundary does not check that the player is in the server's player list; the TASK's list does not ask for it.
  The test stand-ins rely on that: they are connected but never join.
- The other 16 menus are unchanged. Those whose holders' `createMenu` does not refuse a spectator (for example the
  combustion generator and the classic controllers) still open a menu on vanilla's spectator path. Their `stillValid`
  refuses it, and the server closes it at the next tick, but the vanilla open packet, which has no Forge extra data,
  still goes to the client (W179-F1's related note). (Resolved under R147 by W182-R3: no holder builds a menu for a
  spectator now.)
- A player whose open flight menu becomes invalid (the rocket stops being operational, for example) is now refused
  silently. (Corrected under R147; this line first said that such a player "now gets `UNAUTHORIZED` where it got
  `ENTITY_UNAVAILABLE` before".) The boundary returns before `report`, and the packet handler discards the service's
  result, so the player gets no action-bar message and the server writes no `ARCE_FLIGHT_INTENT` line. Before W182 such
  an intent passed the rate limiter and was then reported `ENTITY_UNAVAILABLE`, with a message and an INFO audit line.
- The native probes above may need a follow-up when their cases next run. (Superseded under R147; see the native
  results there.)
