## Cause and design

`SealedDisassembly.tickRequest` rejects a live request older than 200 server ticks
before U retention, including while PREPARE is waiting for proof admission or retry.
PREPARE requires checked predecessor absence and current native entity/terrain proofs.
After retention, expiry instead enters recovery; it does not discard U or player data.
`RocketDisassemblyRequest.finishedRetained` answers a terminal REJECTED with
`region_busy`. A new player request is the designed response, not renewal of accepted
pending work. Existing `SealedRequestLifetimeTest` covers this refusal without mutation.

W271's four nearly simultaneous rejections match that pre-U request-lifetime boundary.
Its component fixture stopped calling `Submission.advance` after its first admission,
unlike the fault fixtures that noticed the terminal reply and requested again.
The historical log does not expose the individual native slot's refusal reason, so it
does not establish a particular failed capture or permanent region conflict.
No evidence was found requiring a production change.

The deterministic sibling supersedes the first request's PREPARE entity proof by
calling vanilla `entityManager.storeChunkSections` for its own rocket column every
tick. It makes 201 saves, then observes the age-201 rejection on the following GameTest
tick, 202 ticks after admission. It stops saving at that first terminal reply. It does
not change clocks, proof results, admission queues, player authority or production
constants. Two setup-only runs exposed the server-END versus GameTest observation
offset; the final fixture asserts the exact 202-tick observation, not a larger timeout.
An earlier launcher attempt failed before starting a JVM because of command quoting.
Those setup failures are retained separately.

With the original wait, this sibling timed out with exactly
`Original component block not yet published`. With the fix, both component and
inventory siblings observe one terminal rejection, receive a second pending admission
and reach SEALED. Their logs each contain exactly two pending admissions, one
`PENDING_REJECTED` observation and one SEALED result. The unchanged `Submission`
authority check also proves that the refused request did not change persisted D.

No ADR decision was changed or left open. All original assertion literals, conditions
and timeout calculations are preserved. Production, `AdapterAsyncFixture`, the
expected-log manifest, checker, status files, queue, ledger and build scripts are
unchanged. No upstream code or assets were imported.
