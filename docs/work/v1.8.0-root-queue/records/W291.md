# W291: named landing-pad selection

## Scope and implementation design

This task changes `/arcepad select`, the flight console's pad display and station cycling, their English and Chinese generators, and focused tests. The write scope is the landing-pad command/service, flight menu/selection/display/plan packet and channel revision, their tests and generated v1.8 language files, and this record. Landing and assignment rules, persistence schemas, chunk-ticket policy, build scripts, status files and the ledger are not changed. No upstream assets are imported.

ADR-065 section 6.1 keeps an unloaded pad unavailable for actual flight admission. A command choice is bounded, transient menu intent, not a reservation or authority to land. The command may therefore record a station-owned indexed reference without loading its chunk, reporting that the pad must be loaded before flight. `NamedLandingPadStaging.select` and `recheck` still require loaded physical identity and the existing geometry, occupancy and claim checks. Loaded but mismatched block entities remain refused. Station access remains `VISIT`, including members; selection does not acquire owner-only management rights.

The console keeps a pad only when station cycling leaves the station UUID unchanged. Moving to another station/body clears it. The S2C flight-plan packet gains one display-only UTF-8 name, at most 32 characters, only for a plan carrying a pad reference. Missing or removed index entries use an empty display value and a translated unavailable label. The flight-channel revision changes so old clients cannot misread the frame. C2S packets, coordinates, launch validation and saved flight plans are unchanged. The route prioritizes the pad name and provides its full text on hover. Root must independently review the network diff before integration.
