## Design before implementation

`applyEscrowCargo` installs a reconstructed immutable snapshot with the new content
hash, validates bindings and refreshes scalar entity data, but never notifies the
visual channel. That channel currently sends only on `StartTracking`. Both normal
cargo publication and reconciliation roll-forward use this same method. Operator
settlement normalization/pruning changes only the wrapper, not the snapshot.

After successful validation, emit a server-local notification only when the
content hash changed. The existing visual synchronizer sends one bounded chunk
set through Forge's tracking-entity distributor, encoding once per change. Network
failure must not unwind an already committed resource change. Initial tracking
continues to send the latest snapshot. No transient state is persisted, no world
scan or chunk load is added, and no client value becomes authority.

## 关键设计决定

Use a server-local event after successful `applyEscrowCargo` validation rather than
polling, caching another hash, or changing the protocol. Compare before/after
content hashes, including a change back to a previously seen hash. Encode once and
use Forge's actual tracking-entity distributor. A visual-send exception does not
undo resource publication. Operator normalization/pruning preserves the snapshot
and therefore adds no visual send. No saved format, client authority, upstream
asset or admission rule changed.
