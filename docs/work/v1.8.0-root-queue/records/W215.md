There are 68 distinct named classes (596 events), of which 55 belong to this
mod. The remaining 1,211 events are generated hidden lambda/method-handle
classes, not stable preload names. Preserve the exact named mod inventory in a
test resource derived from both W212 campaigns. ClassLoad is a load observation,
not proof of when initialization occurred; initialization is audited separately.

Add a Forge `ServerStartedEvent` subscriber that calls `Class.forName(name,
true, helperClassLoader)` for exactly those 55 mod classes. It never reads the
event's server, a Level, configuration, registry, saved data or networking,
and never constructs a flight, source, journal, proof or fake world. JVM class
initialization is once per defining loader, including repeated integrated-server
starts. Missing names/linkage errors propagate with the class identity; tests
resolve every entry and pin the measured inventory, rather than silently skipping.

Source audit: records/helpers have no static initializer. The exceptions are
compiler-generated enum constants/arrays; `EscrowAdapterIds` constructs two
identifier strings through the pure `ModIdentity.id`; `EscrowStoreFault` creates
only a `ChunkPos(4, 4)` value; `EscrowTransferProjection` creates three immutable
string collections. Constructors of the selected enums only call `Enum`;
`RocketTransferPhase` additionally assigns its final boolean authority flag.
Initializing nested classes does not initialize their enclosing service (notably
the retry logger, save monitor or checkpoint). The store-fault object's atomic
fields and all test-property reads are instance/method work, never run here.
Bytecode tests will pin the reachable initializer calls/field accesses and reject
new effects; repeated initialization will be tested without a server or world.

Cost moves to the server-start lifecycle before gameplay ticks: class metadata
and constant objects remain for the mod classloader lifetime, even if no player
uses governed flight. This is bounded by the explicit list, not a package scan.
Measure elapsed startup initialization, thread allocation and heap/metaspace
deltas in the diagnostic export, plus whole-process RSS. No forced GC is added;
deltas are observations, not retained-size estimates. Costs were pending at
this design commit; the measured results follow below.

This cannot remove JIT/cold-code cost, lazy generated call sites, or all vanilla,
Forge and library linkage. Do not exercise methods to warm them. No state,
authority, ordering, proof, acknowledgement, schema, timeout, quota or budget
changes are allowed. R-035 remains open and admission remains disabled.

Verification uses failing-first isolated tests, the whole unit suite, three
repetitions of W207's warm-up/pad/margin/launch batches, and W212's eight native
geometries plus restart, with four launches per flight process. Build before and
after JARs from committed source under the heavy-JVM lock; retain first and later
cohorts separately in both observer modes. Compare whole checkpoint ticks to
docs/17's unchanged 100 ms P99, without subtracting observations or calling a
small-sample maximum a robust percentile. Root supplies independent review and
hosted full regression; no version or Required Gate approval is claimed.

### Displaced startup cost and memory correction

Initialization runs on the Server thread during ServerStarted, before gameplay
ticks; it adds startup waiting, not an earlier dummy flight. Across the 28 main
after-campaign starts, its directly measured elapsed cost is 17.581-83.628 ms.
The three supplemental corrected-probe starts measure 24.492, 23.462 and
87.328 ms. All these wall-clock costs are retained, including the long samples;
no CPU-only or pause-subtracted cost is substituted.

Review found that the first diagnostic memory field,
`metadata_used_delta_bytes`, incorrectly added Compressed Class Space to the
already combined HotSpot Metaspace pool. **That field in the four-campaign
evidence is invalid as a unique-memory measurement and must not be used.**
The raw reports were not edited. A failing-first test observes 1,200 instead of
1,000 bytes for a 1,000-byte combined pool with a 200-byte subset.
Commit `099cbf290` reports the pools separately and passes that test. The pool
relationship was checked against OpenJDK 17's `memoryPool.cpp`:
`https://raw.githubusercontent.com/openjdk/jdk17u/master/src/hotspot/share/services/memoryPool.cpp`.

The supplemental run uses new contained and the same-world restart (three
successful JVM stages, two real relaunches). Its ordinary production JAR is
byte-identical to the main after-campaign JAR; only the diagnostic collector
changed. Each startup loads 55 classes. Corrected observations are:

- Owner-thread allocation: 5,473,936-5,478,808 bytes.
- Combined Metaspace used increase: 334,856-335,360 bytes.
- Compressed Class Space subset: 33,872-34,112 bytes, already included above.
- Whole-JVM heap-used delta: 4 MiB in each of the three samples.

These are allocation/pool observations, not post-GC retained-size estimates.
No forced GC was added. Class metadata and immutable constants live with the
mod classloader; temporary loading allocations can be reclaimed. The earlier
probe also observed negative heap deltas, demonstrating why a heap delta is
not a retained-size measurement. JVM queries and output are outside the inner
initialization timer; the outer INFO duration includes diagnostic overhead.

Whole-process peak RSS, including setup and shutdown, is 2.600 / 2.273 GiB
before (full / timing-only) and 2.442 / 2.698 GiB after. This does not establish
a precise retained-memory difference. Other-CPU mean ranges are
2.396-13.181% / 11.758-29.185% before and 2.103-14.999% / 2.524-18.231% after.
Early timing-only baseline work overlapped targeted test compilation.
The startup probe itself is after-only diagnostic work. These unequal host
conditions and instrumentation preclude a controlled percentage-speedup claim.
