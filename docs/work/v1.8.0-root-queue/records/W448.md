## Priority findings: X01-10 and X01-12

### E1: X01-10 is an absent-ledger recovery-probe mismatch

The original trace records ledger `open` sequence 7 with `pre="absent"`, and `move` sequence 12.
The five old-side states therefore have **no target ledger**, not an empty ledger file.
Their logs reach `Done (...)!` but never emit `ARCE_RELEASE_CARGO_CUT_RESULT`.
`EscrowCargoFlightCuts.recover`, lines 314 onward, decides why:

```java
if (data == null) { data = ResourceEscrowSavedData.existing(server); if (data == null) { return; } }
```

The next-attempt enablement is inside `created()`, after this return. The absent root cannot
reach it. This is a gated fixture/probe limitation, not evidence of an in-flight product crash
or loss. The first-creation state itself is allowed by W368-DESIGN section 3.

The additive Python old-side check starts without that fixture probe, performs `save-all flush`
and a normal stop twice, and independently requires: ledger absence; exact journal; one original
rocket with identical UUID, position and entire `RocketEntityData`; identical block-entity roots;
neutral/unbound endpoints; exactly 5,000 mB water and 1,000 mB fuel. A startup marker alone cannot
pass it. S-NEW still uses the unchanged FF_N1 recovery/admission oracle. No assertion or timeout
in the original runner was weakened. The old-side outcome and check are recorded before replay.

Limitation: the absent-root runs establish the specified before-creation state, including harmless
leftovers, not a subsequent enabled cargo admission from that state. C6's probe cannot exercise
that next admission. Native replacement of those particular leftover files on the next admission
remains unproved; it must not be inferred from the PASS entries.

### E2: X01-12 is a builder completion-model fault, not overlapping C6 writes

The original registry trace is sequential: operations 0--5 open/write/force/close/read/move the
empty baseline; sequence 13 opens the same registry again on `ARCE-satellite-registry`, with a
pre-image matching that baseline; operations 14--18 write/move the launch. The intervening
directory-force entry at sequence 12 is on `ARCE-rocket-journal`, not the registry thread.
The log also says `acknowledged=0 ... busy=false` before the terminal launch is requested.

`SatelliteRegistryCapture.write` only calls the directory-force callback when
`attributes.force() != null`. An ordinary completed registry write legitimately has no directory
force. The builder previously required that entry to call a write complete, producing
`Overlapping writes on a thread/store` at sequence 13. The recorder correctly recorded the calls.

A subsequent open on the **same thread, same store and same target**, after a recorded move,
now proves completion of the prior attempt, not directory durability. Unmoved attempts,
different-thread overlaps, bad pre-images, and inconsistent kill images still refuse. Such
completed nonforced writes remain eligible for R6 late loss; the state/byte/operation bounds remain.

### E3: X01-02 state 09 needs the already existing before-launch oracle

Its original state table rewinds the receipt and registry first creations to absence (open
sequences 21 and 28), while keeping the unconsumed original source rocket. Both original starts
report `claim=NONE hold=NONE ... receipts=[] transfer=NONE ... state=FUELED ... locked=false
consumed=-+- owned=0`. There is no INTENT to resume. B3_STAGED expects that INTENT and a completed
launch, so its timeout is a harness mismatch for this coherent all-old state.

Only B3 late loss with **both root hashes absent** selects the unchanged B1_STAGED oracle.
That oracle requires the original unconsumed packages, zero satellites, no receipts/transfer,
and the stationary original rocket; extra satellites or changed packages still fail. State 07,
where the registry survives, does not qualify. B8 states do not qualify. The new table selects
this oracle before either restart; no marker allowlist or existing oracle changed.

### Residual evidence and reach

These are realizable R6 rewinds of acknowledged checked-store generations, with independent
region/entity files held at the kill image by R7. They are not torn atomic target files or
unbounded cross products. Classification is based on the actual restored store contents and
dependent effects, not just the word LATE-LOSS. No ordinary in-flight product defect was established.

- **E4, X01-02/07:** `states.json` removes only the receipt root; the registry still contains the
  satellite. The quoted status in E3 instead ends `owned=1`. A registered satellite and an
  unconsumed source package survive without the receipt connecting them. Neither successful
  recovery nor a duplication exploit was established. The unchanged oracle still fails.
- **E5, X01-02/08 and X01-03/08:** the registry pre-image is absent. Original logs show
  `consumed=<operation UUID>+- owned=0`, with no REPAIR hold; X01-02 reaches `state=LANDED`.
  The runner reports `the fixture owner holds 0 satellites, expected 1`. The paid-for satellite
  registration is lost while its package remains consumed. The follow-up reproduces this loss.
- **E6, X01-03/07 and /09:** receipt pre-image 35 is INTENT, not REGISTERED. The log says
  `ARCE_BAY_CLAIM ... state=REPAIR reason=TRANSFER_AUTHORITY_CONFLICT`, followed by
  `locked=true ... state=TRANSIT y=50.0`; /07 retains `owned=1`, /09 has `owned=0`.
  This is retained, repair-held authority (and in /09 a lost registration), not a successful
  restart. An allowed marker was not added after observing it.
- **E7, X01-05/06/07/09:** ledger pre-image 14 is the generation-1 baseline: `issued_through=0`,
  no records, accounts, receipts or heads. The kill image already contains epoch-1 endpoint
  effects. Each log's actual error, before the misleading exit-code-0 tail, is
  `Exception caught during firing event: Restart violated cargo conservation, epoch, identity or pruning`.
  This comes from the release probe, whose combined predicate includes
  `data.ledger().issuedThrough() == ... epoch` and requires marker pruning. Rewinding L1 loses
  that history. The error is **not proof that production crashes without hooks, nor proof of
  fluid/item quantity loss**. The saved trace and pre-images establish the authority/history
  residual. The original pack discarded the post-failure raw files, so physical conservation
  after each restart cannot be decided from the combined assertion. To decide it, reconstruct
  these same states, start twice without the mutating/asserting recovery probe, and retain raw
  ledger, endpoint payloads, identities and marker/lock observations before and after each save;
  then compare typed totals and authority separately. Do not turn the existing failures into passes.
- **E8, X01-11/12:** the ledger is rewound to generation 1 with no intent, receipt or account,
  while the region/entity endpoints retain the settlement's normalized state. Its two deduplicated
  derivations rewind the ledger alone or ledger plus the already-equivalent journal.
  `EscrowCargoSettlementCuts.recover` returns while `!released(root)`; `released` requires a
  released tombstone. The log reaches startup but never emits the FS_O3J_BEFORE result, then
  the unchanged runner times out. This establishes loss of the accepted settlement/audit and
  absence of its completion proof, not a quantified loss or a measured protective lock. The same
  passive, raw two-start observation described in E7 would decide the resource/availability effect.

For C6-SWITCH-REPORT section 13 under R-035: **Windows directory-force omission permits loss of
