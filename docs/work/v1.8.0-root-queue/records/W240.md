## Result

The cause is a fixture defect, not a product defect in the adapter restore path. The restore callback was
never reached: B2 ended the mismatch trial's queued request `REJECTED` at its 200-tick request age, before
retention, and the trial never looked at the refusal. The fixture now observes that terminal refusal and
requests again, as `scanFailure` already does. The hosted signature was reproduced first on the unchanged
source by forcing that request age. Five natural baseline runs did not reproduce it. All 22 runs on the fix
pass, including the two forced cases.

## Cause

1. **Hosted facts.** In run 41261374700, shard 0 (job 124717797365, log
   `D:/GitHub/ARCE-Task-Evidence/root-queue/tools/job-124717797365.log`, SHA-256
   `f4bf62f8f801989677a73f24db994f1ae1d9679a6d18e1eaeb1647ea60c9747b`), the four restore trials were admitted
   as pending at test ticks 1 to 4. The mismatch trial's D, `b3024d10-…`, was admitted at tick 4 (line 4658).
   THROW, FALSE and SLOW reached their holds at ticks 109, 168 and 208. At 01:46:29.6, about tick 204, line
   4684 logs `ARCE_ROCKET_SEALED_DISASSEMBLY entity=b3024d10-… result=REJECTED`, and line 4685 logs
   `ARCE_DISASSEMBLY_DURABILITY_COMPLETE … reason=REJECTED`. No entity removal, carrier hold or restore
   callback followed for that D. The trial timed out at its unchanged limit of 3,201 ticks (01:48:59, line
   4874), and the strict check would also see only 3 of 4 `w164-adapter-r107-holds` warnings.
2. **Product behaviour.** The port's clock is the server tick count. [SealedDisassembly](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/sealed/SealedDisassembly.java)
   finishes a request `REJECTED` when its age exceeds 200 ticks before retention is submitted (`tickRequest`
   and `step`). [RocketDisassemblyRequest](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/RocketDisassemblyRequest.java)
   then sends `region_busy` to the requester. D and its saved authority are unchanged, and no U, carrier or
   restore exists. This is B2's request lifetime, the same terminal `REJECTED` that W164's `74d1f7775`
   handled for `scanFailure` ([W164 record](W164.md), "Integration result and changed files").
3. **Fixture defect.** [AdapterAsyncFixture.Submission](../../../../src/adapterTest/java/io/github/sunthemoon/arceadaptertest/AdapterAsyncFixture.java)
   already handles that reply. It logs `PENDING_REJECTED`, checks D's accepted authority, and requests again
   after the 20-tick intent window. But [AdapterFaultGameTests](../../../../src/adapterTest/java/io/github/sunthemoon/arceadaptertest/AdapterFaultGameTests.java)
   `RestoreTrial` called it only until the first admission. `DISASSEMBLY_PENDING` then waited only for the
   restore probe, so a terminal refusal left the trial waiting until its timeout. `HEALTHY_DISASSEMBLY` had
   the same gap.
4. **Why the fourth request runs out of time.** All four requests are created within four ticks. Each needs a
   PREPARE proof before retention, and proof turns are shared at about one per 20 ticks. A read-only trace
   (below) records each request's age at retention. In 22 of 25 natural local runs the four initial requests
   retained at ages 44 (45 in two runs), 65, 142 and 163 ticks, and in the other three at 44, 103, 121 and
   142. The last request therefore uses 142 to 163 of its 200 ticks, which leaves 37 to 58 ticks of margin.
   In the four other retained hosted logs of this batch, the last of the four trials reached its hold at tick
   268 or 288. In the failing hosted run the interleaving differed (THROW held at tick 109), and the fourth
   request did not retain within 200 ticks. That exact hosted interleaving was not reproduced locally.
5. **Second effect when the healthy request is refused.** Forcing the first healthy request (`forced-red-5`
   below) stalled THROW in `HEALTHY_DISASSEMBLY`, and also stalled the other three trials in
   `PREPARATION_HELD`. Their exit waits for `checkedAbsent`, which needs
   [RocketTransactionSavedData](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/persistence/RocketTransactionSavedData.java)
   `acknowledgedCurrent()`: the journal's latest mutation must have a committed checkpoint. THROW's healthy
   reassembly had just mutated the journal, and that query never requests a write. Only sealed work requests
   checkpoints, so with the refused request not retried, no writer remained. In the traced `forced-green-5`
   run the journal stood at mutation 63 with acknowledgement 53 at the refusal (tick 312). The retried
   request asked for a checkpoint at tick 335, the acknowledgement was current at tick 336, and all four
   trials passed. The same fix covers both effects.

## Change

In `RestoreTrial`, while D is present and no restore callback has run, `DISASSEMBLY_PENDING` now calls the
trial's existing `submission.advance(helper)`. While the healthy D is present, `HEALTHY_DISASSEMBLY` does the
same. `Submission.advance` returns at once for an accepted pending request, unless the reply is `region_busy`,
so a live operation is never refreshed. The change is 6 added lines in one file. The write scope was that test
class and this record.

No assertion was removed or weakened. The authority check before retirement, the exactly-once callback and
readback branch, the held-carrier identity and inventory checks, and every no-drop check are unchanged. The
timeout (`completionTicks(4, 2, true)`, 3,201 ticks) and every budget are unchanged, and no test moved to
another batch. No product code, expectation manifest, checker, status file, ledger, ADR or upstream content
changed. I did not change the product's request lifetime or proof order. That would be product behaviour
outside this task, and the restore path itself has no defect. I also did not make the fixture request
checkpoints itself, because retrying the refused request already restores a writer.
