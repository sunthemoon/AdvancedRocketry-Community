`javap -c -p` against the mapped Forge 47.4.10 jar confirms the mechanism, with two qualifications
to the task's analysis: `BaseRailBlock.onRemove` notifies neighbors for ascending or straight-only
rails when not moving, not every flat ordinary rail; `neighborChanged` calls `shouldBeRemoved`,
which checks support and then calls `dropResources` and `removeBlock`. `UPDATE_CLIENTS` does not
prevent those callbacks. The exact generated structure at the hosted coordinates was not inspected.

The deterministic reproduction uses a west-ascending rail and a supported upper rail in the
ceiling shell. X-first carving removes both supports before removing the lower rail, so its
callback drops the upper rail in the shell. The original helper fails with
`Room carving left terrain drops in the shell: [1 rail at 7, -55, 3]`. An earlier east-ascending
setup passed because the upper support had not yet been carved; it was corrected rather than
treated as a reproduction.

The fix expands only the setup cleanup box by one block, exactly covering the carved shell.
Every room-carving automation scenario uses this shared helper. Cleanup finishes synchronously
before `room()` returns; there is no deferred cleanup that could erase actual machine output.
`spilled()` retains its original interior bounds and counts every item type. The regression checks
the whole carved volume immediately and through tick 20. A second GameTest verifies the exact
reported item and position for an iron ingot created immediately after setup and a rail created
at tick 2, retaining spill detection through tick 20. Both use the ordinary rig lifecycle and a
single callback registered at test start.
