### The seam

- The channel is closed through a `Closeable` resource that calls `ops.close`, so the close still runs after the body
  and is still suppressed under a body failure, as the earlier try-with-resources did.
- `DIRECT.forceDirectory` keeps the Windows return. `DIRECT.delete` is `Files.deleteIfExists` with the result dropped,
  as before.
- No writer, committer or cut changed. Every existing cut still wraps the committer and reaches the move through
  `CheckedSavedDataFile.atomicMove`.

### The recorder

- **Lines.** Each line has `seq`, `thread`, `store`, `op`, `path` and `result`. `seq` comes from one counter under the
  recorder's lock and is assigned when the operation has returned, so file order is sequence order. `result` is `ok`
  or the class name of the exception, which is rethrown unchanged. `path` is relative to the world, with forward
  slashes. `store` is the `ManagedSavedDataType` whose file name matches the target, `UNKNOWN` otherwise, and `null`
  for a directory force.
- **Extra fields.** An open adds `target` and `pre`; a write adds `offset`, `length` and `sha256`; a move adds
  `target`.
- **One unbuffered call.** A line is one `FileChannel.write` of the whole line. A forced stop loses at most the line of
  the operation in flight.
- **Blobs.** The bytes of each write call are stored once as `blobs/<SHA-256>`, before the line is written.
- **Old target.** At each open the recorder copies the current target to `pre/<seq>` and puts its SHA-256 and length in
  the line, or creates the empty marker `pre/<seq>.absent` and writes `"pre":"absent"`.
- **Bounds.** At most 4,096 operations and 256 MiB of stored bytes. On the first operation over a bound, or on any
  failure to write the trace, the recorder logs `ARCE_RELEASE_STORAGE_TRACE_INVALID reason=<reason> operations=<n>`
  once at ERROR, closes `ops.jsonl` and from then on only delegates.
- **Outcome.** The recorder performs the operation first and records afterwards, inside a catch of `IOException` and
  `RuntimeException`. It holds its lock only while it records, never while `DIRECT` runs.

### Gating

`installAtStartup` first restores `DIRECT`. It installs a recorder only when all of these hold:

- `advancedrocketrycommunity.releaseTestHooks` is true;
- `server.isDedicatedServer()` is true (a `GameTestServer` is not a dedicated server, so GameTests never install it);
- `advancedrocketrycommunity.storageTrace` names a directory;
- `EscrowTestEndpoints.requireEnabled(server)` passes. Like the other gated seams, it throws on a server that is not a
  release-test server.

When the recorder is installed, one `ServerStoppedEvent` listener at LOWEST priority restores `DIRECT` and closes the
trace, so writers that drain in their own stop listeners are still recorded. There is no command, network message,
configuration key or saved field.

## Choices where the design was open

1. **The gate is a parameter.** `persistence.migration` does not import `resourceescrow` today, and `resourceescrow`
   imports `persistence.migration`. The call site passes `EscrowTestEndpoints::requireEnabled`, so no new package edge
   appears.
2. **Install point.** The recorder is installed at `ServerStartedEvent`, before the first-event seams. Checked writes
   earlier in start-up (migration, the pre-start validators) are not recorded.
3. **The trace directory must be new or empty, and outside the world.** Otherwise the installer logs the marker
   (`reason=directory-not-empty` or `reason=directory-inside-world`) and installs nothing. A restart therefore needs its
   own directory or no property. The smoke's restarts ran without the property.
4. **The 256 MiB bound counts the old-target copies as well as the blobs.** The design names only blobs; a copy of a
   large journal at every open would otherwise be unbounded.
5. **A failed write** records its offset and the bytes the buffer consumed, and stores no blob.
6. **The marker is logged at ERROR.** It can appear only on a release-test server with the property set.
7. **The failed-readback test** uses a payload with a `NaN` double. NBT compares doubles with `==`, so the staged root
   honestly differs from the candidate and the earlier code and `DIRECT` both throw "SavedData staging readback
   differs".

## Known risks

- The seam adds one volatile read and one interface call for each file operation of a checked write. I did not measure
  it; the ledger and journal benchmarks were not rerun.
- The relaunch inventory entry records static reachability only (see above).
- A trace of a large journal reaches the 256 MiB bound quickly, because each open copies the old target. The case is
  then discarded by its marker, not truncated silently.
- The seam changes the JAR's bytes, so X01 and X02 evidence has to come from a candidate cut after this merge
  (W368-DESIGN question Q4, decided in R461).
