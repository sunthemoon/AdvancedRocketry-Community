## Cause

The step did not fail at random: its result depended on the runner image's git version.

- Both failing jobs (`3a8893a0`, job 122185866189, and `6fc6cd9f`, job 122206261687) ran on the hosted image
  `ubuntu-24.04` `20261025.353.1`, which has git 2.56.0. The regression job of the same day (`51ecfded`, job
  122174865021) ran on the older image `20261012.334.1`, which has git 2.55.0. GitHub was rolling out the new image, so
  a run passed or failed according to the runner it got; the rerun of `3a8893a0` passed.
- `upstream_history` read each source's history with `git log --follow`. Git 2.56.0 contains upstream git commit
  `304812ed33dec7ea7e68928feab38199d796ea25` ("log: improve --follow following renames for non-linear history",
  Miklos Vajna, 2026-06-22; first tag `v2.56.0`). Until 2.55 `--follow` kept one followed path for the whole walk,
  so on non-linear history the answer depended on the walk order; git's own message says it "isn't really defined".
  From 2.56 each parent has its own followed path, and the follow's built-in copy detection also takes a file with the
  same bytes on a merge's side.
- The AR history of the K6 icons is non-linear. `b3b5f83a` ("fix resources, fluid handling") lower-cased the item
  textures; its parent held the same blob at two paths (for example `opticalSensor.png` and
  `satellitePrimaryFunction0.png`, blob `b318c138`). The merge `61d7b2b0` (first parent `205dacd2`, after the
  rename) joins the side parent `6854ab61`, which descends from `0631f3ab` ("Keep track of assets") and holds only
  `satellitePrimaryFunction0.png` with that blob. Against the side parent, the merge deletes that file and adds both
  `opticalsensor.png` and `satelliteprimaryfunction0.png` with its bytes. Git 2.56 takes it as the source of
  `opticalsensor.png` and walks the side, where `0631f3ab` added it, so four of the six entries
  (`opticalsensor`, `basiclens`, `microwavetransmitter`, `oremapper`) gain `0631f3ab`, the record's digest changes,
  and verify fails. Git 2.55 gives the committed histories.

Reproduced locally with Git for Windows 2.56.0 (`MinGit-2.56.0-64-bit.zip`, SHA-256
`064b440ff870ed5198527e8f3a92cdf5bd2fd0fedf5e718af95e3fdaddeff718`) against the system git 2.55.0.windows.5, on
the same clones: `scripts/k6_history.py` in the evidence directory reports `DIFF` for those four entries with 2.56
and `same` for all six with 2.55. Python version, `PYTHONHASHSEED`, fresh or cached clones and fresh or cached
vanilla JARs made no difference (see the runs below).

The committed record is not wrong. ADR-061 section 4.9 lists "the upstream commits that touched its source file",
and the tool documents "following renames". `0631f3ab` added `satellitePrimaryFunction0.png`, another file that still
exists separately at the pin as `satelliteprimaryfunction0.png`; it never touched `opticalSensor.png`. In
`satelliteidchip.png` and `satellite.png`, `0631f3ab` stays because it added those paths themselves.

## What was done

1. `5c842ee52` feat(import): name the first difference of a v1.8 record that does not reproduce. `verify` keeps the
   line `[FAIL] provenance record does not reproduce byte for byte from the plan, upstream and targets` and exit
   code 1, and prints one more `[FAIL]` line: the first differing JSON path in file order (the top-level `review` last,
   because a changed core also changes its digest), both values cut to 300 characters, and the number of differing
   values (counted up to 1,000). A record whose JSON values are equal names the first differing byte and line.
   With the old walk and git 2.56 it prints, for example, `[FAIL] provenance record first differs at
   $.entries[0].upstream_history[3]: recorded <absent>, regenerated {"author": "zmaster587", ...
   "commit": "0631f3aba16f43463d10851d6b75a1b922807348", ...}`.
2. `205344593` fix(import): walk the upstream history without git log --follow. `upstream_history` walks the commit
   graph itself (`rev-list --topo-order --parents`, children before parents), keeps the followed paths per commit and
   passes them to every parent (only the first parent in the first-parent pass), so the walk order no longer matters.
   - A parent without the file gets the rename source. That is a path the commit deletes with the same bytes, paired
     by the same path ignoring case, then the same file name ignoring case, then as the only pair left. A choice
     between several fails with "the rename source is ambiguous".
   - Only when no unpaired deleted path has the same bytes does git's own `-M` pairing (default similarity,
     `-l1000`) name a rename that changed the bytes; an exact `R100` from git is ignored there.
   - A copy (a file with the same bytes that the commit keeps) is not followed.
   - Pass one lists non-merge commits that changed the file on any line; pass two adds the first-parent merges that
     changed it against their first parent, as before. Commits are ordered by commit date (newest first, then commit
     ID); git's `--follow` output for K6 had the same order.
   - Blob IDs come from one `git cat-file --batch-check` session. New bounds: 100,000 commits, 64 followed paths.
3. This record.

ADR choice where the ADR is open: section 4.9 does not say what to do with an ambiguous exact rename or with copies.
I chose to fail on ambiguity rather than let git pick silently, and not to follow copies, which keeps the committed
record and the ADR's "touched its source file". See the risks.

## Known risks

- Copies are not followed. The old `--follow` did follow them, with exact or similar bytes, in linear history too
  (the copy test shows `c0` on both git versions before the fix). A future import whose source was created as a copy
  of another file will not list that file's history. If ADR-061 section 4.9 should cover copy origins, that is a rule
  change for Root and the owner: it would add `0631f3ab` to four K6 entries and need a regenerated, re-reviewed record.
- A rename whose bytes changed still uses git's `-M` pairing. Git has kept that pairing stable for years, but it is
  not this tool's own rule.
- An ambiguous exact rename now stops the import with an error, where git used to choose silently.
- The history check costs about 1 to 5 seconds per entry instead of about 0.2 seconds (lazy blob fetches in a
  blobless clone included). The K6 verify took 66 to 93 seconds here with three runs in parallel; one run of the old
  tool alone took 53 seconds.
