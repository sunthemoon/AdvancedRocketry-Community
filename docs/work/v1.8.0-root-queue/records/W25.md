## What changed

**L1, at the vent** (`ScrubberBank`, `OxygenVentBlock`).

- `recoverOrphan` and the new `releaseEmptyOrphan` share one loop, `releaseOrphan`. The W14F
  proof is unchanged:
  - the slot's cell must be in a loaded chunk, read without loading or creating anything;
  - a scrubber block whose entity is missing or pending is skipped;
  - an unavailable facade, or one whose identity matches the slot, is skipped.
- A release clears the slot and unbinds a loaded conflicting facade, inside the same
  `operating` guard. An empty release moves no item.
- The vent action recovers a cartridge first. Only when there is none does it release one
  empty association. Each sneak-use does at most one of the two.
- Messages:
  - new `message.advancedrocketrycommunity.vent.scrubber_association_released`;
  - the refusal key is unchanged, but its text no longer claims that the scrubbers are not
    loaded or readable. It now reads "Nothing to recover: no orphaned cartridge or stale
    association was found. Unloaded or unreadable scrubbers are left unchanged."

**L2, at the facade** (`ScrubberBank.disowns`, `ScrubberBlockEntity.releaseStaleBinding`,
`ScrubberBlock`).

- The empty-hand sneak-use at the facade first tries to withdraw, as before. When nothing is
  withdrawn, it calls `releaseStaleBinding`. That release needs the facade to be available
  and bound, and the owner cell's chunk to be loaded (`getChunkNow`). The cell is read only
  through `LevelChunk.getBlockEntities()` and `getBlockState`. Proof is one of:
  - the owner cell holds no vent block and no vent entity;
  - it holds a vent entity whose bank `disowns` the facade. The vent must be readable, which
    means `deviceAvailable()` and not mid-operation. The bank disowns the facade when its
    generation differs from the binding, or when its slot for that exact face does not hold
    this facade's identity.
- A release clears the binding exactly as `unbind` does (now the shared `clearBinding`),
  invalidates the old capability, moves no item and shows
  `message.advancedrocketrycommunity.scrubber.binding_released`.
- `protectedData()` is unchanged. A stale facade stays protected until the player acts.

Both changes go through the existing `DeviceAccess.player` gate: a connected, non-fake, live,
non-spectator player within 8 blocks who passes `mayInteract`. Automation cannot trigger them.

## Choices where the TASK was open

- **One release per action, cartridges first.** The vent sneak-use keeps the W14F direction
  order (DOWN, UP, NORTH, SOUTH, WEST, EAST) and recovers a cartridge if any slot can give one.
  Only otherwise does it release one empty association. A player may need several sneak-uses
  to clear several faces.
- **An empty association whose cell holds no scrubber at all** is released, under the same
  rule by which W14F recovers a cartridge from such a cell.
- **"Does not reference this facade"** means that the bank's slot for the exact face between
  vent and facade does not hold the facade's identity, under the bank's own generation. This is
  the face-and-identity check of `admits`. Another face's slot is not consulted, because only
  the owning face can ever admit the facade.
- **What proves nothing.** All of these keep the binding:
  - an unloaded owner chunk (`getChunkNow` is null);
  - a vent block whose entity is missing or pending;
  - a vent with retained, unsupported or corrupt data. Its in-memory bank is a fresh bank with
    a random generation, so a generation comparison would otherwise be a false proof;
  - a removed vent entity, or a bank that is in the middle of an operation.

  A cell that holds some other block or block entity counts as "no vent".
- **The action at the facade** is the empty-hand sneak-use, the same gesture as recovery at
  the vent. It first withdraws, as before, and releases only when nothing was withdrawn. A
  healthy or unbound facade still answers `FAIL` without a message, as before (review note I3
  is unchanged).
- **Disabled devices.** Both releases work while classic devices are disabled, as W14F's
  withdrawal does. They move no item and do no device work.
- **Protection is unchanged until the action.** `protectedData()` still protects a stale
  facade. W25 adds an explicit release; it does not make stale facades removable on its own.
- **Unloaded scenario for L1.** For the vent's association, the "owner position" whose loading
  matters is the facade cell at the other end. The L1 frontier test leaves that chunk absent.
  The L2 frontier test leaves the vent cell absent.
- **No loading waits, so no `GameTestTickPacer`.** Every W25 GameTest is synchronous within
  one tick, as the W14F tests are. The unloaded cases use the W14F frontier method and never
  wait for a chunk. The frontier tests call `releaseEmptyOrphan` and `releaseStaleBinding`
  directly rather than through a joined player, because a joined player adds chunk tickets
  around itself.
- **Removal in the tests** uses a creative player's `ServerPlayerGameMode.destroyBlock`, so that
  the removed block drops nothing that could hide a cartridge count.

## Known risks

- **`hasChunkAt` is not "loaded".** In 1.20.1 `ServerChunkCache.hasChunk` is true for a chunk
  that holds a FULL-level ticket but has not finished loading. A following `getBlockState` or
  `getBlockEntity` then waits for that chunk to load on the server thread. Two existing paths
  do this, and W25 does not change them:
  - the facade's `owner()` (used by `protectedData`, the item capability and `detach`). The
    facade action calls the capability's extraction before the new release check;
  - Forge's comparator update inside every `setChanged()`, as review note I1 describes.

  This is how the first GameTest run failed (see the table). It is not an arbitrary load: the
  chunk already had a ticket and was about to load. It does, however, mean that W14F's claim
  "no chunk is loaded" holds only for chunks without a FULL-level ticket. The existing W14F
  frontier test has the same exposure and could fail the same way if it ran after tests that
  join players. A possible follow-up is to make `owner()` read the owner cell through
  `getChunkNow` and `LevelChunk.getBlockEntities()`, as recovery and the new release do. I did
  not make that change, because the TASK excludes other scrubber behaviour.
- **Snapshot reverts after a release.** A release never moves an item, and a facade never
  stores a cartridge. A later revert of either chunk can therefore recreate a stale binding or
  association, but never a second cartridge. As in W14F, a real duplicate needs the vent chunk
  to revert while the player file keeps a withdrawn stack, which is the existing
  player-file/terrain atomicity boundary.
- **A release at the facade in the W14F mixed snapshot** leaves the other identity's cartridge
  in the bank. It stays recoverable at the vent once the released facade is removed or no
  longer matches, as the third L2 test shows.
- The replays are in-memory, not native interrupted-save or restart evidence. Real-client checks
  and a hosted CI run were not performed here.
