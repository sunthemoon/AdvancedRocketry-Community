# W194: satellite pending-file ownership

## Design note (2026-10-29, before implementation)

The assigned worktree starts clean at `6f18152deb0df93b9547963735d64da0d045ac69`
on `codex/v1.8.0-w194`. Write scope is `DiscoveryProgressFixture.java`, its
satellite persistence unit regressions, this record, and external evidence under
`D:/GitHub/ARCE-Task-Evidence/root-queue/W194/`. Other writers, ADRs, status,
ledger, build, workflow and checker files are not changed. No upstream material
is imported. Other live work uses W164, not this worktree.

The retained R156 log places `tau_ceti_path` immediately before
`endgame_menu_member`. The former uses `DiscoveryProgressFixture`, which swaps
the satellite SavedData without awaiting the original on installation or closing
the temporary writer on restoration. Restoration then requests an original-root
save. Both instances can therefore write the same stable target concurrently.
The other satellite batch fixtures already await/close across their swaps.

`CheckedSavedDataFile.replace` creates/truncates the shared `.arce-pending` file,
forces it, reads it back, and moves it to the target. Its exception cleanup can
delete that same pending file. These operations run on each instance's own
`ARCE-satellite-registry` thread. A second instance can move/delete the file
between the first instance's force and readback, explaining R156's missing-file
stack. A single instance serializes attempts; autosave requests its existing
writer, detached saves await that writer, and failure retry uses a fresh capture.
No production same-root second writer has been identified.

The fixture will await the original before installing a replacement, then await
and close/join the replacement before restoring and saving the original. The
original stays open because it resumes service. This follows ADR-074 items 4,
9 and 10 without changing production behavior, epochs, acknowledgement rules,
timeouts or bounds. Unit tests will exercise both real fixture hooks with real
checked-file IO and outstanding unpublished captures before the fix. A direct
two-instance collision test will establish the missing-file and retry behavior.

R156 failed before its committer, so it published FAILED, not COMMITTED: durable
epoch 99 and the prior acknowledgement remained, and dirty state remained.
The log later reports ACKNOWLEDGED at sequence 14341, epoch 99, at 09:32:15.691,
after the failure at 09:32:08.149. There is no automatic retry merely from FAILED;
pending/coalesced requests or autosave submit a fresh capture with the existing
200-tick backoff. Unacknowledged new changes cannot release dependent effects.
A crash before retry can lose only uncommitted RAM under the normal one-writer
contract. The fixture's competing whole-root writes violate that contract and
can overwrite even acknowledged test state, so the race is not harmless just
because this run later recovered. This fix changes test ownership, not player
save/recovery policy.
