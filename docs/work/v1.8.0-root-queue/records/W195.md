## Cause

The hosted failure is consistent with the periodic autosave invalidating the first, already returned proof while
the second capture is pending. Confidence is high, but the console log does not expose individual captures or
generation changes, so their exact ticks are inferred rather than directly observed.

Counting the GameTestServer progress lines, one per 20 ticks as established in W184, gives this interval in the
provided hosted log from run 40798480031 at `05f07d7d`:

| Log line | Last progress tick | Event |
|---|---|---|
| 20827 | 65,940 | The one-test `escrow_settlement_empty_slots` batch starts. |
| 20830 | 66,000 | The eleventh periodic autosave boundary lies inside the batch. |
| 20837 | 66,100 | The joint-retention assertion fails before the next progress line. |

The code explains both the failure and the extra approximately 100 ticks:

- `EscrowEntityStore.storeEntities` reports ordinary saves to `EscrowSaveMonitor`, including empty saves suppressed
  by vanilla's empty-slot cache. The monitor advances each watched slot's generation, invalidating its old proof.
- The fixture captures two different slots sequentially. Its final assertion checks both retained proofs, not only
  the result of the currently pending request. Two successful callbacks imply two stored proofs; validity is the
  part of the final assertion that can subsequently change.
- `EscrowGameTestProof` retries a pending `SUPERSEDING_SAVE` after the product's 100-tick first backoff, but never
  refreshes a proof already delivered to the fixture. Retrying the second capture therefore cannot repair the first.
- The batch contains no explicit save and only this test. Both distant slots retain their region tickets. The
  autosave boundary and retry-length delay fit this mechanism; no competing save is shown in the console log.

The fixture, request driver, autosave helper, entity-store decorator, monitor and barrier are unchanged between the
failed hosted revision and this task's base. W187's audit classified the empty-slot fixture as retry-tolerant, but
that classification did not account for retaining the first proof across the second request. This record corrects
that assessment without changing the historical record. No production defect was identified or repaired.

## Design choices

The fixture waits for both slots to be entity-loaded and ticking before starting the pair. The admission callback
checks `GameTestAutosave.within(server, 60)` while the index is zero, including subsequent admission attempts if
the barrier is temporarily busy. The 60 ticks comprise two sequential 20-tick force periods plus one period for
callback delivery and the final joint-validity assertion; that derivation is commented beside the constant.

Only the first capture is guarded. Pausing the second until after an autosave would itself invalidate the retained
first proof. The normal guard wait is at most 61 paced ticks per 6,000-tick cycle, within the unchanged timeout.
No ADR decision or new production retry policy was needed.
