Default behavior remains legacy-only. The option accepts a whole legacy success
message with the requested identities and existing block/rollback counts, or a
whole sealed message with the requested entity and logical IDs and `result=SEALED`.
The sealed form requires the preceding command answer `Release-test disassembly
pending` and subsequent exact `ARCE_DISASSEMBLY_DURABILITY_COMPLETE` diagnostic
with `phase=DONE reason=SEALED additional=[] overflow=0`. Missing receipts,
wrong identities, other results and successful-looking substrings fail. Pending,
receipt and durability use the original 45-second receipt budget, not separate
45-second waits. No block counts are invented for the sealed form.

C6's [completion callback](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/RocketDisassemblyRequest.java)
logs the sealed receipt. `SealedDisassemblyCoordinator.finish` unconditionally
calls `diagnostics.complete` in its `finally`; its tick then calls `diagnostics.flush`.
[SealedDiagnostics](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/SealedDiagnostics.java)
sets the completed phase to DONE. In these isolated, single-rocket fixtures there
is no competing diagnostic entry or capacity overflow, so this diagnostic is
required. It carries a transaction UUID, not entity/logical IDs; correlation
therefore relies on this existing single-request isolation, not a general
multi-rocket guarantee.

The opt-in flight method keeps the original five restored-block predicates,
entity absence and chest inventory assertions unchanged. For a fueled rocket it
supplies C6's existing `discard-fuel <exact reported fuel>` consent argument,
using the report already checked for identity and exact fuel preservation. It
does not zero fuel or modify world data to make disassembly succeed. Transaction
structure hashes, complete chest SNBT, authority/drop checks, durable staged
journals and both restart checks remain unchanged.

The source path explaining every unreachable legacy checkpoint is
`RocketDisassemblyService.disassembleForReleaseTest` ->
`RocketDisassemblyRequest.beginRetained` -> `SealedDisassemblyCoordinator.begin`.
It bypasses [RocketTransactionExecutor.disassemble](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/RocketTransactionExecutor.java)
and its `RocketTransactionReleaseProbe.bind(DISASSEMBLY)` instrumentation.
Each unreachable result below required an actual pending/SEALED/DONE sequence,
unchanged restored contents, block authority and an empty journal at clean stop.
It was not inferred from a timeout or a missing pause marker; no forced stop is
claimed for it. The transaction runner exits 1 with `status=INCOMPLETE` and
`complete_transaction_matrix=false` when these results exist.

The existing [sealed native runner](../../../../scripts/run_w152_native.py)
provides real process cuts from C0 through C5, recovery cuts and two stable
restarts, using a pinned diagnostic JAR built with `scripts/w152_native.init.gradle`.
It is not a replacement legacy checkpoint. C6 also contains
[SealedRecoveryGameTests](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/SealedRecoveryGameTests.java),
including `earlierRecordWithDProvesRollbackBeforeReleasingTheSurvivor` and
`electedRecordCompletesPartialCBeforeDiscardingD`. Those are recovery GameTests,
not external JVM kills. W437 did not rerun the diagnostic native cut matrix or
claim a new C6 sealed forced-stop acceptance result.
