# W37I: supersede a pending backup only by a changed tuple

## Design (written before the code, 2026-10-14)

This worker owns `SleepRespawnService`, `RespawnPointBackup`, their unit test, the GameTests in
`RespawnSupersessionGameTests` and `RespawnRecoveryGameTests`, one manifest entry in
`scripts/gametest_expected_log.json` with its pinned ERROR total, one sentence in the sleep section
of `docs/CELESTIAL-DATA-GUIDE.md`, and this record. Status files, the ledger, ADRs, the risk
register, build files and other tasks' files are not changed.

**The rule.** A decodable backup governs while the player's native tuple is either the backup's own
tuple (restored, waiting for completion) or exactly the cleared tuple: Overworld, null position,
raw angle bits of 0.0F, not forced. It does not matter who wrote the cleared tuple. Any other tuple
supersedes the backup. `RespawnPointBackup.governs` loses its foreign-setter parameter. The check
runs at the same points as in W37H: the server-tick END (decision and restore), the DISCARDED final
check, the respawn event, login and logout.

**The observation goes.** The `LOWEST` `PlayerSetSpawnEvent` observer, the `foreignSetters` set,
and its handling at clear, release, login, logout and server stop are removed. The only transient
state left is the once-per-session diagnostic sets, which decide nothing. A `PlayerEvent.Clone`
listener that copies the old player's cleared tuple, a setter that another listener cancels, and a
foreign null clear all leave the cleared tuple, so the backup governs and the restore puts the
point back.

**The trade-off.** If another mod clears the point of a player whose point W37 has already refused,
while the backup is pending, the restore puts the original point back. Root chose this.

**The interrupted-listener residual.** In W37F's window a respawn listener throws before ours. The
PlayerList then holds the replacement, the connection still owns the old player, and both share one
`PlayerPersisted` compound (Forge's `restoreFrom` puts the same object into the replacement). The
native disconnect save (`onDisconnect` calls `PlayerList.remove(this.player)`) writes the old
player, whose tuple is this service's clear. `/spawnpoint <name>` selects the PlayerList's player,
the replacement. A newer point set there superseded the backup at the next END, and the backup was
removed from the shared compound. The save then wrote the cleared tuple and no backup, so both
points were lost. The tuple-only rule does not change this, because the newer tuple is not the
cleared one. The loss therefore still happens. It can be fixed without a Mixin:

1. A superseded backup is removed only when the connection owns the player whose tuple superseded
   it. This is the alias guard that completion already uses. Until then the backup is kept and no
   field is written, so the replacement keeps its newer tuple.
2. At logout, before the native save, the service checks for the window: the player being saved is
   the connection's own, the PlayerList holds a different player with the same UUID and the same
   connection, a backup is pending, and the saved player's tuple is exactly the cleared tuple. Then
   the replacement's tuple is written into the saved player. This writes only into the cleared
   tuple. The normal check follows: a newer tuple supersedes and removes the backup; the backup's
   own tuple keeps it until login completes it; a cleared replacement leaves the backup governing,
   and login restores it.

So the newer point is saved and wins, and without one the backup survives the reconnect.

**Change during implementation (replaces items 1 and 2 above).** Item 1 would keep a superseded
backup until the respawn packet handler adopts the replacement, one tick later than now. That would
break the existing assertion in `spawnpointAfterCorpseRemovalIsTheNativeRespawnPoint` that the
backup is gone right after the packet. So the implemented fix keeps W37H's immediate removal and
moves the copy to the moment of supersession instead. When a newer tuple supersedes the backup on
a player that its connection does not own, and the connection's player (same UUID) holds exactly
the cleared tuple, that newer tuple is first copied into the connection's player. Then the backup
is removed. The logout save then writes the newer point. This also writes only into the cleared
tuple. During a normal respawn the copy lands on the old player just before the handler drops it,
so nothing reads it. The first native run also added a second manifest entry, a WARN from the
window tests' reconnect (see the commands below).

**Tests.**

- Unchanged and still required to pass: the `/spawnpoint` tests, the respawn-event setters before

## How each decision was carried out

**When a backup is superseded.** `RespawnPointBackup.governs(point, dimension, position, angle,
forced)` returns true for the backup's own tuple and for the exact cleared tuple, and false for
every other tuple. `SleepRespawnService.governing` applies it at every decision and restore point:
the server-tick END (decision for a dead or credits player, restore for every other player), the
DISCARDED final check, the respawn event, login and logout. Keeping the backup's own tuple as
governing is unchanged from W37H. It is the restored state that waits for the connection to adopt
the replacement, and it is not a newer point.

**The event observation goes.** The service no longer listens to `PlayerSetSpawnEvent`. Its only
transient state is the once-per-session diagnostic sets, which only limit WARNs. `clear` and
`release` become static, because they no longer touch service state.

**Tests and the change of expectation.**

- `aCloneListenerCopyingTheClearedTupleKeepsThePoint` (new): a `PlayerEvent.Clone` listener copies
  the old player's tuple, which is this mod's clear, onto the replacement with `setRespawnPosition`.
  The packet's replacement lands in the Overworld with the Moon point, angle and forced flag
  restored and the DISABLED message, and the next tick completes the backup. Under W37H the
  setter's event marked the backup as superseded and the point was lost.
- `aForeignClearWhileABackupIsPendingIsRestored` replaces W37H's
  `aForeignClearWhileABackupIsPendingIsNotUndone`. Same fixture: a dead player's backup is pending,
  and another mod writes `setRespawnPosition(OVERWORLD, null, 0.0F, false, false)`. W37H expected
  the backup to be removed and no point after respawn. **The new expectation is Root's W37I
  decision, not a weakened assertion:** the next decision keeps the backup, and the respawn
  restores the point with its message, then completes it. The method was renamed because the old
  name stated the old expectation.
- `aForeignClearKeepsTheBackupAcrossTheLogoutSave` replaces W37H's
  `aForeignClearIsAppliedBeforeTheLogoutSave`. W37H tested that the removed flag was applied
  before the logout save, so the reconnected player had no backup. With no flag, the same steps
  (clear, native `PlayerList.remove`, reconnect from the player file) now show the reconnected dead
  player still has the backup. Its next decision keeps it, and the respawn restores the point. This
  is the same decision, and the change is stated here for the same reason.
- `aNewerPointOnAnUnadoptedReplacementSurvivesTheLogoutSave` and
  `aRestoredPointOnAnUnadoptedReplacementSurvivesTheLogoutSave` (new) are described below.
- The W37H tests of a foreign setter with a new point are unchanged: the dead tick
  (`spawnpointBeforeCorpseRemovalIsJudgedAsTheNewerPoint`), the DISCARDED final check
  (`spawnpointBeforeCorpseRemovalWinsAtTheFinalCheck`), `/spawnpoint` after corpse removal
  (`spawnpointAfterCorpseRemovalIsTheNativeRespawnPoint`), and respawn-event setters before
  (`aRespawnListenerBeforeOursKeepsItsNewerPoint`) and after ours
  (`aRespawnListenerAfterOursKeepsItsNewerPoint`).

**The interrupted-listener residual.** It still happened under the tuple-only rule, and it is
fixed without a Mixin. The mechanism is in the design section. In short, W37F's window leaves the
listed replacement unadopted, and the native disconnect (`onDisconnect` calls
`PlayerList.remove(this.player)`) saves the old player, whose tuple is our clear. `/spawnpoint
<name>` selects the listed replacement. Before W37I, the next END removed the backup from the
shared `PlayerPersisted` compound, and the save then wrote neither point.

`carryToSavedPlayer` runs whenever `governing` finds a superseded backup. If the player is not its
connection's player, and the connection's player has the same UUID and exactly the cleared tuple,
the four fields are copied into the connection's player. Then the backup is removed as before. A
restore still writes only into the cleared tuple, and the copy also writes only into the cleared
tuple. In a normal respawn, the respawn event runs before the handler adopts the replacement, so a
setter at `HIGHEST` also triggers the copy. It lands on the old player just before the handler
drops it, so nothing reads it.

`aNewerPointOnAnUnadoptedReplacementSurvivesTheLogoutSave` enters the window with W37F's throwing
`HIGHEST` listener. After one tick, the replacement holds the restored Moon point and the backup is
still pending (W37F's guard). `/spawnpoint` then selects the replacement and sets an Overworld
point. After the next END, the backup is gone and the old connection player holds the newer point.
`PlayerList.remove(old player)` saves it, and the reconnected player has the newer point and no
backup. Under W37H, the old player kept the cleared tuple and the reconnect had no point.
`aRestoredPointOnAnUnadoptedReplacementSurvivesTheLogoutSave` runs the same window with no newer
point. The old player's save keeps the cleared tuple and the backup, and the reconnect restores and
completes the Moon point.

## Choices where the decisions left room

- The backup's own tuple still governs (the restored state waiting for adoption). Root's text names
  only the cleared tuple, but that state is not a newer point, and removing it would let a restored
  backup be "superseded" by its own restore.
- The residual is fixed by a copy at supersession time, not by holding the backup until adoption
  (see the change note in the design section).
- The copy needs no pending backup at logout and adds no transient state. After the copy, a later
  change on the unadopted replacement is not copied again (see the risks).
- The two window tests reuse W37F's exception message and add one expectation that matches them by
  their shared helper frame, `RespawnRecoveryGameTests.interruptedLogout`, with a count of 2. The
  W37F expectation still matches only its own test.
- The window tests reconnect while vanilla's unadopted replacement is still in the Overworld, as a
  real reconnect after that window would. Vanilla then logs `Force-added player with duplicate
  UUID` and discards the replacement from the Level. The tests keep this real path and expect the
  WARN, instead of removing the replacement first, because removing it through `PlayerList.remove`
  would save it over the file under test.
- The guide gains one sentence: clearing the point is not a newer point, and the kept point comes
  back.

## Proposed risk text (for Root; replaces W37H's)

**Planet-respawn backup (ADR-066 section 3.3; W37F, W37H, W37I).** When the policy refuses a saved
off-world point at a death or End-credits respawn, the exact tuple is written to
`ForgeData.PlayerPersisted.arce_planet_respawn_backup`. The tuple is the dimension, `x`, `y`, `z`,
the raw `angle_bits` and `forced`, in schema 1, at most 1 KiB and nine nodes. The four native fields
are then cleared, so vanilla uses the Overworld. The scope is one player's saved respawn tuple,
never a chunk or a Level. No save is refused, and no exception controls saving. A readable backup
lasts until a verified restore or until a changed tuple supersedes it, across logout, player
save/load, respawn and restart. An unreadable or future root lasts until offline repair or a
compatible reader.

1. **Newer points (F1, W37H; narrowed in W37I).** The backup governs only its own tuple or the exact
   cleared tuple (Overworld, no position, angle 0.0F, not forced), whoever wrote it. Any other
   tuple supersedes and removes it: a command, a bed, or another mod's setter, before or after the
   respawn event. No transient state takes part, so an abnormal stop changes nothing. The
   trade-off: if another mod clears the point of a player whose point W37 has already refused,
   while the backup is pending, the restore puts the refused point back. Vanilla has no command
   that clears a point, so only a mod's explicit clear reaches this case. In return, a
   `PlayerEvent.Clone` listener that copies the old player's cleared tuple, or a setter that
   another listener cancels, no longer loses the player's point.
2. **Logs.** One WARN per player, per case and per server session (`ARCE_PLANET_RESPAWN_DIAGNOSTIC`)
   for an unencodable tuple, a foreign non-compound parent, and an unreadable or future root.
   Nothing else is logged. Players with an ordinary pending backup can be found only offline, by
   the key above.
3. **Player experience.** With an unreadable or future root, or after ARCE is removed or downgraded
   while a backup is pending, the native point is empty. The player respawns at the world spawn
   with no chat message. While ARCE is installed, the `unreadable_backup` WARN is the operator's
   signal.
4. **Fail-open cases.** An unencodable native tuple skips the refusal: a non-finite angle, `x` or
   `z` beyond ±30,000,000, or a dimension ID over 256 characters. So does a foreign non-compound
   `PlayerPersisted` parent. Vanilla then reads the point, and may load its chunk, enter a denied
   station or place the player in vacuum. Only other mods or edited data reach these cases.
5. **Interrupted respawn.** If another respawn listener throws before this one, the backup stays
   pending and the server-tick retry restores the fields. Completion waits until the connection
   adopts the replacement, which can need a reconnect. A newer point set on the replacement in that
   window supersedes the backup, and it is copied into the old connection player's cleared tuple,
   which the logout save writes (fixed in W37I). One gap remains. Once the backup is removed, a
   further change to the replacement's point in the same window is not copied again. The logout
   save then keeps the first newer point, where vanilla would keep the old player's. Vanilla also
   leaves the unadopted replacement in the player list and its Level after that logout, until a
   reconnect force-adds the new player over it. This service does not repair that.
6. **Offline recovery.**
   1. The player must be offline. Back up `world/playerdata/<uuid>.dat`.
   2. In an NBT editor, open `ForgeData.PlayerPersisted.arce_planet_respawn_backup`.
   3. If it has `schema: 1`, copy `dimension` to `SpawnDimension`, and `x`, `y` and `z` to
      `SpawnX`, `SpawnY` and `SpawnZ`.
   4. Convert the int `angle_bits` to a float with Java `Float.intBitsToFloat` and store it as
      `SpawnAngle`. Copy `forced` (a byte, 0 or 1) to `SpawnForced`.
   5. Remove the key. If it has a `retained` child, put that child back under the key instead.
   6. A non-compound `PlayerPersisted` belongs to another mod. Repair it with that mod's owner,
      because replacing it loses that mod's data.
   7. Save the file and let the player join. Check `/data get entity <player> SpawnX` and that the
      key is gone.

## Known risks

- The trade-off in risk item 1: another mod's explicit clear of an already-refused point is undone
  by the restore.
- The remaining interrupted-window gap in risk item 5.
- The copy writes into the connection's old player object. Another mod that keeps a reference to
  the old player after a normal respawn would see the newer tuple there. Nothing in vanilla or
  Forge reads that object after the handler adopts the replacement.
- W37H's other risks are unchanged: the END listener at `LOWEST` still runs before any other mod's
  `LOWEST` END listener registered after it; the inter-tick task queue still runs before the read;
  with `allowPlanetRespawn` on, every dead or credits player is probed each tick, with no global
  cap; and a mod that replaces the native tick, `PlayerList.respawn` or the credits handler can
  bypass these Forge boundaries.

No upstream file or art was copied, and no configuration key, packet or Mixin was added. No version
or Gate is marked passed, and the current version's Required Gates are not all met. The next step is
Root's independent review of `c4d92cac..` this record, then W37b within v1.8.0.
