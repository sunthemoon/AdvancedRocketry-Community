# W37I: supersede a pending backup only by a changed tuple

## Design (written before the code, 2026-10-14)

This worker owns `SleepRespawnService`, `RespawnPointBackup`, their unit test, the GameTests in
`RespawnSupersessionGameTests` and `RespawnRecoveryGameTests`, one manifest entry in
`scripts/gametest_expected_log.json` with its pinned ERROR total, one sentence in the sleep section
of `docs/CELESTIAL-DATA-GUIDE.md`, and this record. Status files, the ledger, ADRs, the risk
register, build files and other tasks' files are not changed.

**The rule.** A decodable backup governs while the player's native tuple is either the backup's own
tuple (restored, waiting for completion) or exactly the cleared tuple: Overworld, null position,
raw angle bits of 0.0F, not forced. It does not matter who wrote the cleared tuple. Any other tuple
supersedes the backup. `RespawnPointBackup.governs` loses its foreign-setter parameter. The check
runs at the same points as in W37H: the server-tick END (decision and restore), the DISCARDED final
check, the respawn event, login and logout.

**The observation goes.** The `LOWEST` `PlayerSetSpawnEvent` observer, the `foreignSetters` set,
and its handling at clear, release, login, logout and server stop are removed. The only transient
state left is the once-per-session diagnostic sets, which decide nothing. A `PlayerEvent.Clone`
listener that copies the old player's cleared tuple, a setter that another listener cancels, and a
foreign null clear all leave the cleared tuple, so the backup governs and the restore puts the
point back.

**The trade-off.** If another mod clears the point of a player whose point W37 has already refused,
while the backup is pending, the restore puts the original point back. Root chose this.

**The interrupted-listener residual.** In W37F's window a respawn listener throws before ours. The
PlayerList then holds the replacement, the connection still owns the old player, and both share one
`PlayerPersisted` compound (Forge's `restoreFrom` puts the same object into the replacement). The
native disconnect save (`onDisconnect` calls `PlayerList.remove(this.player)`) writes the old
player, whose tuple is this service's clear. `/spawnpoint <name>` selects the PlayerList's player,
the replacement. A newer point set there superseded the backup at the next END, and the backup was
removed from the shared compound. The save then wrote the cleared tuple and no backup, so both
points were lost. The tuple-only rule does not change this, because the newer tuple is not the
cleared one. The loss therefore still happens. It can be fixed without a Mixin:

1. A superseded backup is removed only when the connection owns the player whose tuple superseded
   it. This is the alias guard that completion already uses. Until then the backup is kept and no
   field is written, so the replacement keeps its newer tuple.
2. At logout, before the native save, the service checks for the window: the player being saved is
   the connection's own, the PlayerList holds a different player with the same UUID and the same
   connection, a backup is pending, and the saved player's tuple is exactly the cleared tuple. Then
   the replacement's tuple is written into the saved player. This writes only into the cleared
   tuple. The normal check follows: a newer tuple supersedes and removes the backup; the backup's
   own tuple keeps it until login completes it; a cleared replacement leaves the backup governing,
   and login restores it.

So the newer point is saved and wins, and without one the backup survives the reconnect.

**Tests.**

- New: a `PlayerEvent.Clone` listener copies the old player's cleared tuple onto the replacement
  through `setRespawnPosition`; the point is restored.
- Changed expectation: the W37H foreign null clear test. The backup governs and the point is
  restored at respawn. The W37H logout variant of that clear tested the removed flag's logout
  lifecycle; it now shows the backup surviving the clear, the logout save and the reconnect, and
  the point restored at respawn.
- New: two interrupted-window logout tests, one with a newer `/spawnpoint` point on the replacement
  and one with only the restored point. Each uses W37F's throwing `HIGHEST` listener, so each logs
  the deliberate EventBus ERROR. One new manifest expectation counts both, and the pinned ERROR
  total becomes 85.
- Unchanged and still required to pass: the `/spawnpoint` tests, the respawn-event setters before
  and after ours, the dead-tick tests and W37F's interruption tests.
- Unit: the `governs` matrix without the flag.
