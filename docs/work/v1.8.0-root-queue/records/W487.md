## 2. F-W482-01 (P01): the precision assembler's hull beside its structure

### Where it comes from

- Fixture: `S/client/model/ObjModelFixture.java:99-101`. `PRECISION_ASSEMBLER` has `mirrorX` true, scale 1,
  offset (0, 0, 0), model rotation 90 degrees, and model bounds 0..3, 0..3, 0..4.
- Placement: `S/client/model/ClassicObjModelRenderer.java:61-68` turns by the controller's facing about the
  controller's centre, then applies the offset, the model rotation and the scale.
- Pattern: `src/main/resources/data/advancedrocketrycommunity/machine_patterns/precision_assembler.json`. Its
  size is x 3, y 3, z 4 and its controller anchor is (1, 0, 0), the middle of the 3-wide front row.
  `S/machine/multiblock/pattern/PatternTransform.java:11-20` maps it into the world.
- Render box: `S/machine/classic/runtime/K4ModelProjection.java:38` holds the union of hull and pattern,
  -1..4, 0..3, 0..4.

W482 calls the structure "3 by 4 by 3". In the pattern file it is 3 wide, 3 high and 4 deep.

### Cause

The legacy renderer drew the hull from the controller's corner with its 4-block side across the controller's
left-right axis (W241's placement table: translate (.5, 0, .5), turn, translate (-.5, 0, -.5)). The modern
pattern has the controller in the middle of a 3-wide face and is 4 deep. W241 kept the legacy placement under
its design note 1 ("Several v1.7/v1.2 patterns were redesigned and are smaller than legacy hulls") and left
overlap and placement to V1. For this machine the pattern is not smaller. It has the same 3 by 3 by 4 volume,
turned a quarter turn and shifted.

I computed the hull box from the 581 positions of the OBJ at C6 with the fixture's own formula
(`ObjModelFixture.toController`). The OBJ fills its bounds exactly.

| Facing | Pattern box | Hull box | Hull beyond the pattern |
|---|---|---|---|
| North | -1..2, 0..3, 0..4 | 0..4, 0..3, 0..3 | 2 blocks east |
| East | -3..1, 0..3, -1..2 | -2..1, 0..3, 0..4 | 2 blocks south |
| South | -1..2, 0..3, -3..1 | -3..1, 0..3, -2..1 | 2 blocks west |
| West | 0..4, 0..3, -1..2 | 0..3, 0..3, -3..1 | 2 blocks north |

In every facing the two boxes share a 2 by 3 footprint, so the hull covers 6 of the 12 pattern columns, leaves
6 uncovered and stands 2 blocks out over open ground on one side. The unions equal the `render_bounds` pinned in
`src/test/resources/obj-model-fixtures/precision_assembler.json`. This matches the frames: the hull "about two
blocks east", "six of the twelve top casings" covered, and a camera east of the structure inside the hull. The
hull has no collision by design (`ClassicObjModelRenderer.java:19-21`), so a player can stand in the overhang.

### Proposed placement

A placement that gives the hull exactly the pattern's box in all four facings exists. For north it needs
x = 2 - x(model) and z = z(model), which is model rotation 0 and offset (2, 0, 0):

```diff
 // S/client/model/ObjModelFixture.java:99-101
-            ModIdentity.id("models/precisionassembler.obj"), true, true, 1, 0, 0, 0,
+            ModIdentity.id("models/precisionassembler.obj"), true, true, 1, 2, 0, 0,
             new ObjModelCheck.Bounds(0, 0, 0, 3, 3, 4), ModIdentity.id("textures/block/precision_assembler_front.png"),
-            ENTITY_CUTOUT, 90, 3);
+            ENTITY_CUTOUT, 0, 3);
 // S/machine/classic/runtime/K4ModelProjection.java:38
-            case "precision_assembler" -> new AABB(-1, 0, 0, 4, 3, 4);
+            case "precision_assembler" -> new AABB(-1, 0, 0, 2, 3, 4);
```

What this placement cannot do: keep the hull's legacy front towards the controller's face. The hull's long side
is 4 blocks and the pattern's controller face is 3 blocks, so any placement that matches the box turns the
legacy front to a side face. In the OBJ the tray and the three process parts run along the 4-block axis close to
that side (tray at model x 0.59 to 1.31, parts up to x 1.58), so with this placement the working line is seen
through the east side of a north-facing machine, and the legacy controller cell lands one block east of the real
controller. The two other box-matching placements (rotation 180 with offset (-1, 0, 4), or no mirror with offset
(-1, 0, 0)) put that side on the west and the legacy controller cell further from the real one. I recommend the
placement in the diff, and a look on a real GPU before it is accepted.

Two alternatives, both larger:

- Change the pattern to the legacy 4-wide layout. That changes pattern data whose hash is pinned and invalidates
  formed machines in existing saves, so it needs a migration. I do not recommend it.
- Remove the hull and keep the block models, as the mirrored variant already does
  (`S/machine/precision/PrecisionAssemblerBlockEntity.java:56`). This is the fallback if the look of the turned
  hull is rejected.

One dependency: with a matching box, all five outer hull faces lie in the planes of the casings' faces. That is
the cause of F-W482-02, so this fix should go together with P02's.

### What the fix touches

- Models and screens: the precision assembler's formed hull only. The mirrored variant keeps its block models.
- Saved data, packets, registries, language keys: none. The fixture and the render box are client presentation.
- Tests:
  - `K4ObjModelTest.everyDrawnPositionInEveryFacingEqualsTheTranscribedLegacyRenderer` pins the legacy placement
    for this id (its `legacy` helper, line 116). The assembler's case has to be replaced by a new oracle: every
    drawn position lies in the pattern's box for each facing, and the hull's box equals the pattern's box. This
    replaces a pinned expectation on purpose. It is not a relaxed assertion, but AGENTS.md section 5 means Root
    should name it in the candidate decision.
  - `src/test/resources/obj-model-fixtures/precision_assembler.json` (`offset_north`,
    `model_y_rotation_degrees`, `render_bounds`), `ObjModelFixtureTest`, `K4ModelProjectionTest` and the
    assembler case of `K4ModelGameTests` follow the two changed lines.
- Real-GPU re-verification: C04 step 1 and I07 step 4, in all four facings, from four sides and from above, with
  the east-side camera position of C04 again.

## 3. F-W482-02 (P02): z-fighting on the precision laser etcher's hull

### Where it comes from

- Fixture: `S/client/model/ObjModelFixture.java:68-70`. Its hull box is -1..2, 0..2.25, 0..3.
- Pattern: `src/generated/v1.8/resources/data/advancedrocketrycommunity/machine_patterns/precision_laser_etcher.json`,
  3 by 3 by 3 with five air cells. Three of them are in the middle layer: above the controller, above the west
  energy port and above the rear centre casing.
- Draw call: `S/client/model/ClassicObjModelRenderer.java:47`, `RenderType.entityCutout`.

### Cause

The hull has a horizontal plate at exactly y = 1. Under the three middle-layer air cells, the tops of the
bottom-layer blocks are exposed at exactly y = 1. Both surfaces are drawn at the same depth, so they alternate
in bands. I checked this by testing every axis-aligned hull face on an integer plane against the exposed faces
of the pattern's full blocks: at y = 1 the hull covers 3.00 block faces beside air cells. Those are the
controller's top, which is the hazard-striped face W482 saw from the north, and a port's top, which W482 saw in
the east formation.

The same test shows that this is not special to the etcher:

- Nine K1 to K3 hulls have a pattern file. Eight of them have the pattern's footprint, so their side faces lie
  in the planes of the outer block faces. Examples: the centrifuge covers 4.33 block faces at x = 3, and the
  crystallizer 6.00 at y = 2. The ninth, the observatory, has no face on an integer plane, because its hull is
  offset by 0.005 block. The solar array has no pattern file to test against.
- The K4 hulls share some planes too, for example the precision assembler at y = 0, y = 3 and z = 0.
- The etcher also has small hull faces beside air cells at x = 0, z = 1 and z = 2 (0.50 block face each), and
  the lathe has 0.79 at y = 0.
- The frames show banding only on the etcher's plate. Where hull and block have similar grey faces, the same
  effect is hard to see. I did not inspect the other hulls' frames for it.

### Smallest fix

Draw all hulls with a render type that equals `entityCutout` plus polygon-offset layering, so the hull wins
wherever it shares a plane with a block face. That is one small client class holding the render type, and one
changed line, `ClassicObjModelRenderer.java:47`. C6 has no such render type (no `RenderStateShard` or
`POLYGON_OFFSET` use under `S/`). It changes no geometry, so the placement tests keep their exact values.

A data-only alternative is to scale the etcher's fixture slightly about the pattern's centre (for example 1.006,
which lifts the plate by about 0.006 block). It is weaker: the gap is smaller than the depth resolution beyond a
few dozen blocks, it fixes one hull, and it changes the exact positions pinned by `EtcherObjModelTest`.

### What the fix touches

- Models: all sixteen catalogued hulls are drawn through this line, including the three composed renderers.
- Saved data, packets, registries, language keys: none.
- Tests: no unit test can show depth behaviour. `ObjModelFixtureTest` and the renderer's constructor check
  (`ClassicObjModelRenderer.java:28`) keep the fixture's `entity_cutout` name. A construction test of the new
  render type is possible. The real check is on the GPU.
- Real-GPU re-verification: I07 step 6 in all four facings, with the north and east views of the failed frames,
  near and from about 30 blocks. Because every hull changes its render type, the passed hull steps of I07 and
  C04 step 1 need one frame each as a regression look.

## 4. F-W482-03 (P03): the data-pack test body shown as a raw identifier

### How body names are resolved

- `S/client/BodyDisplayNames.java:13-17`: `bodyName` builds the key `body.<namespace>.<path>` and uses
  `Component.translatableWithFallback(key, value)`, where the fallback is the identifier text itself.
- The console uses it for the route line and the third destination button:
  `S/client/RocketFlightScreen.java:398-400` calls `RocketStarMap.bodyLabel`
  (`S/client/starmap/RocketStarMap.java:230-232`).
- The test pack (`fixtures/K06/data_only_test_mars.zip`) defines `advancedrocketrycommunity:test_mars`. No
  language file has `body.advancedrocketrycommunity.test_mars`, so the label is the 36-character identifier.
- The route line is fitted to 204 pixels with an ellipsis (`RocketFlightScreen.java:332`), which gives
  "Earth → advancedrocketrycom...".
- The button is 98 pixels wide (`RocketFlightScreen.java:85-88`) and gets the full label. A vanilla button
  scrolls a label that does not fit, so a still frame shows a window of it with both ends cut and no ellipsis.
  The station button beside it is fitted and has a tooltip (`RocketFlightScreen.java:202-208`). The third button
  is not.
- Nothing in the body definition or in the client snapshot (`S/celestial/network/CelestialSnapshot.java:21-34`)
  says that a body is test content, so the client has nothing to mark it with.

Three more places resolve body names without this helper:

- `S/station/controller/WarpControllerMenu.java:174-176` has its own copy with the same raw fallback.
- `S/client/SatelliteTerminalScreen.java:193` and `:308` use `Component.translatable` without any fallback. A
  data-defined target would be shown there as the raw translation key. No frame shows this yet.

### Proposal

1. Add one pure helper, for example `celestial/BodyNameFallback.readable(ResourceLocation)`, that makes the
   fallback text:
   - the last path segment in words: `test_mars` becomes "Test Mars";
   - a marker in front: `[TEST]` when the last path segment starts with `test_`, otherwise `[PACK]`.

   The result is "[TEST] Test Mars". The marker is in front because every bounded label in these screens keeps
   the start of the text when it shortens (`BoundedTextLayout.fit`, `Font.plainSubstrByWidth` in
   `RocketStarMap.java:220-222`), so the marker stays visible at every scale.
2. Use it as the fallback in `BodyDisplayNames.bodyName` and in `WarpControllerMenu.bodyName`, and route the two
   satellite terminal lines through `BodyDisplayNames.bodyName`.
3. Fit the third destination button like the station button, with the full label and the identifier in its
   tooltip.

This reads the mark from a naming convention. That is my choice of the smallest fix, and Root should confirm it.
The alternative is an explicit `test` field in the body definition, carried in the client snapshot. That changes
the definition codec and the snapshot packet, so under AGENTS.md section 13 it needs a design note and a second
read-only review.

A marker written as a bracketed Latin code is the same in both languages, like the reason codes
(`[NO_POWER]`). A translated marker would need two new v1.8 language keys and a client-side check for a missing
key. I do not think it is needed.

### What the fix touches

- Screens: the rocket console (route line, third button, its tooltips), the star map's node and detail labels,
  the Warp Controller's orbit and target lines, the satellite terminal's target and orbit lines, and the endgame
  tooltips that name a body (`S/client/EndgameViewText.java:18`). Only bodies without a translation change.
- Saved data, packets, registries: none. Language keys: none.
- Tests: a new unit test for the helper (words, marker, other namespaces, nested paths) and for
  `BodyDisplayNames`; `RocketFlightScreenLayoutTest` gets the fit of the third button; `Round7ScreenTextTest`
  and `BoundedTextLayoutTest` cover the shortening already.
- Real-GPU re-verification: B06 steps 6 and 8 in all six cells. E05's 100-body and 128-body catalogues add
  bodies from test packs. I did not check whether those have translations. If they do not, their node labels
  change and E05 steps 1 and 5 need a look. F07 step 5 and A13 step 2 only change when their target is an
  untranslated body.

One more observation from the same frames, not traced: the test body's status reads "No available route",
although the pack ships `travel_routes/test_earth_mars.json`. The pack is data only and has no dimension for the
body's level, which may be the reason. The B06 oracle does not ask for a route.

## 5. F-W482-04 (P04): the refusal line cut mid-word

- Source: `S/client/RocketFlightScreen.java:369-371`. The status under the destination buttons is drawn with

- Cause: this call cuts at 204 pixels and adds neither an ellipsis nor a tooltip. The English text of

  Terminal" (`S/datagen/V140PlanetaryLanguageProvider.java:47`), is wider, so it ends at "Satel". The Chinese

- Smallest fix: draw the status in two rows with the screen's own helper, which keeps the full text on hover:
  `text.wrapped(graphics, font, status, 22, 136, 204, 2, MUTED)` (`S/client/ScreenText.java:26-38`). Two rows
  are 18 pixels and the Board and Leave buttons start 12 pixels below the status, at y 148, so these two buttons
  move down by about 8 pixels. The Launch button at y 176 leaves that room. A one-row alternative is
  `text.draw`, which gives an ellipsis and a tooltip but still hides the end of the instruction until the player
  hovers.
- Touches: the rocket console's status line in every state that uses it. Saved data, packets, registries and
  language keys: none.
- Tests: a width case in `RocketFlightScreenLayoutTest` for every `RocketNavigationStatus` text in English and
  Chinese against 204 pixels and two rows.
- Real-GPU re-verification: B06 steps 6 and 8, English cells at scales 2, 3 and 4.

The same uncut-by-ellipsis call is used for the console title (`RocketFlightScreen.java:329`) and for every
star-map line (`RocketStarMap.java:220-222`). No frame shows a cut there, so I propose no change, but the width
test above should include the star map's status line.

## 6. The other product defects

A rule for all text fixes: outputs under older `src/generated/v*` roots are immutable (WORKER-RULES). A text that
was generated before v1.8 can only change through a new v1.8 key and a code change to use it, as
