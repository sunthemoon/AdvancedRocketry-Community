## Result

Both cases are **oracle-contract**. In each case the faulted candidate and the next successful candidate were kept,
their SHA-256 values match the injector's lines, and the decoded roots differ in exactly three fields out of 48:
`clock/logical_game_time`, `clock/last_observed_game_time` and `save_epoch`. The satellite, its identity, owner,
blueprint, state, the research account, and the empty mission, instance and ground-survey lists are equal, field for
field and in key order. The runner's own classification stays `NOT_CAUGHT` for both, because the exact-byte retry
rule is unchanged and C6's retry is a fresh capture. Whether the oracle should accept this is Root's decision.

## Capture method and harness change

The crash-replay recorder cannot run beside the injector: `ReleaseTestStorageFault.install` refuses with
`reason=file-operations-already-replaced` when another file-operations implementation is installed
(`ReleaseTestStorageFault.java` lines 180 to 183). No change under `src/` was made.

Both READ faults rename the staged file first, so the faulted candidate is the store file itself until the retry
replaces it, about ten seconds later (`CheckedRootWriter.BACKOFF_TICKS = 200`, line 21). Commit `ca5ab9360` adds the
option `--keep-candidates` to `scripts/run_v180_storage_faults.py`, with the keeper in the new
`scripts/v180_fault_candidates.py`. With the option, a thread follows the first start's log, reads the store file
when an `ARCE_RELEASE_STORAGE_FAULT attempt ... moved=true` line of the faulted store arrives, and keeps the bytes
under `cases/<case>/candidates/` only when their size and SHA-256 equal that line. It writes `candidates.json` beside
the observation, and the manifest names the option. Without the option nothing is read or written, and every default,
classification rule, marker, oracle, count and timeout is unchanged.

Known limit: on Windows the read holds the store file open for one small read. A move of the store in that instant
would fail. `candidates.json` therefore lists every attempt that failed without an injected fault
(`unfaulted_failures`); both runs list none.

## Code that changes each field

Paths below are under `src/main/java/io/github/sunthemoon/advancedrocketrycommunity/`.

- **The retry is a fresh capture.** `satellite/persistence/SatelliteRegistryWriter.java` lines 117 to 122 build each
  capture from `epochs.toCarry()` and `registry.sections()` when the attempt starts; nothing keeps the earlier
  candidate. `SatelliteEpochRowGameTests` (`unknownCheckpointResolvesFresh`, `failedCheckpointRetriesFresh`) tests
  this, and its line 74 asserts `"Resolution reused a carried epoch"`.
- **Clock pair.** `SatelliteRegistryPayload.java` lines 107 and 108 write the two values from
  `RegistrySections`, which `SatelliteMissionRegistry.sections()` (lines 540 and 541) fills from the clock.
  `SatelliteManager.java` lines 126 to 137 call `completeDue(gameTime)` every 20 ticks, which calls
  `clock.advance` (`SatelliteMissionRegistry.java` lines 380 and 381, `MonotonicMissionClock.java` lines 24 to 33).
  The retry waits 200 ticks (`CheckedRootWriter.java` lines 274 and 296 to 298), so its capture reads a later clock.
- **`save_epoch` after UNKNOWN (READ_ERROR).** The unreadable readback gives UNKNOWN
  (`SatelliteRegistryCapture.java` lines 126 to 131). `SatelliteRegistryWriter.publish` line 308 then runs
  `registry.epochs().unknown(); acknowledged = null;`. `RegistryEpochs.java` line 75 reserves the carried epoch 2, and
  line 47 (`changed ? Math.addExact(Math.max(durable, reserved), 1L) : durable`) makes the next capture carry 3.
- **`save_epoch` after FAILED (READ_CORRUPT).** A readable but different root gives FAILED (same lines 126 to 131;
  the injector adds a marker key to the root that the readback returns, and the file itself is the candidate).
  `publish` line 300 computes `mutatedInFlight = mutationSequence != capture.sequence()` and line 307 runs
  `registry.epochs().failed(mutatedInFlight)`. `RegistryEpochs.java` lines 69 to 72 reserve the carried epoch only
  when the registry mutated during the flight. The durable epoch was 1 (hold line), so a retry that carries 3 means
  epoch 2 was reserved, that is, a mutation happened in flight. My reading of the logs is that this was the
  scheduler's clock observation at tick 20: a clock change calls `setDirty` (`SatelliteMissionSavedData.java` lines
  134 to 146), which advances the mutation sequence, and the status line at the pause shows `sequence=13`.

## Attempt 3's candidates, rebuilt

Attempt 3 kept no bytes, and its hashes (quoted in W446 U1) differ from this run's. `reconstruct_attempt3.py`
first shows that Python's raw deflate with the kept gzip header rebuilds both kept READ_CORRUPT candidates
byte-identically. It then changes only `launched_at`, `charge_time`, the clock pair and `save_epoch` in the kept
retried root and searches 7,808 combinations. All four SHA-256 values of attempt 3 are found, so those candidates
are known exactly:

  oracle contract.
