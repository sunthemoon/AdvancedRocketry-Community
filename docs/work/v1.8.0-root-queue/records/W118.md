decision, saved format, schema, hash, bound, dictionary, proof, lease, budget or timeout, and enables no admission.

**Classes.**
- New pure `rocket/cargo/RocketItemCargoMutation`: the storage rule, the container payload reader, the frozen
  item delta on one `vanilla_container_v1` payload and on the device's four-slot buffer, and the whole after
  snapshot. `RocketCargoMutation` gains one package-level replay helper shared by both kinds (replace exactly the
  cursor's payload, keep every other block, check the payload and aggregate bounds and the structure digest);
  its fluid path keeps its checks and order.
- New `rocket/cargo/RocketItemCargoSelection`: section 5.3's deterministic, server-side selection in both
  directions. It calls the caller's pure eligibility function only after its local checks pass.
- New `resourceescrow/EscrowItemCargoEligibility`: the item counterpart of `EscrowCargoEligibility`, with the
  synchronous check and the staged capture's final item step.
- Minimal dispatch only: `EscrowCargoEligibility.check` sends item kinds to the item class;
  `EscrowCargoPreparedCapture` takes the marker role from `cargoLoad()` and branches its final step;
  `EscrowCargoPublication` decodes an item delta; `RocketCargoPreparation` and `RocketCargoPreparations` accept an
  item delta (constructor, `begin` and `beginReplay` overloads) and keep a typed refusal's status;
  `RocketCargoSelection.Status` gains `UNRESOLVED_LOOT` at its end. `EscrowCoordinator` is not changed, because
  `prepareCargo` is already kind-independent. No refusal mapping changes; W117 owns that.

**Container rule.** A target is a `vanilla_container_v1` payload whose block is `minecraft:chest`,
`minecraft:trapped_chest` or `minecraft:barrel`, with 27 slots. A chest or trapped chest whose `type` property is
`left` or `right` is half of a vanilla large chest (a 54-slot container) and refuses with `NO_CARGO_STORAGE`, as
does any other captured `ChestBlockEntity` subclass. (Superseded by Root decision R44 in W118F below: each half is
a target, and only other block IDs refuse.) A `LootTable` refuses with `UNRESOLVED_LOOT`. Payload fields
are exactly `Items`, `CustomName` and `Lock`; slots are unsigned bytes 0 to 26 without duplicates. The after
`Items` list is sorted by slot; `CustomName` and `Lock` are copied unchanged. Trapped chests follow W106: the v1.8
`rocket_movable` extension omits them, so only a trapped chest already captured through a data pack is a target.

**Moves.** A load takes the first nonempty buffer slot; its target is the first container slot with the same item
and tags and room, otherwise the first empty slot, and it moves `min(buffer count, max stack - target count)`. An
unload takes the first nonempty container slot whose stack the buffer accepts, preferring a buffer slot with the
same item and tags and room, otherwise the first empty buffer slot, and moves `min(container count, room)`. Merging
uses D-K's `EscrowItemStackCodec.sameItemAndTags`; display names never decide. The remainder stays in its slot.
(Superseded by Root decision R45 in W118F below: a load looks across all containers for a matching slot before any
empty slot, and an unload offers the next slot of the same container after a refusal.)

**Bounds (all unchanged).** Stack 4,096 bytes, depth 16, 512 nodes, no `ForgeCaps`; item payload 8,192 bytes,
depth 12, 384 nodes; cursor 256 bytes, depth 2, 8 nodes; a block-entity payload 262,144 bytes; the payload
aggregate and the encoded snapshot 1 MiB (depth 32, 65,536 nodes); the native envelope bound; the device root
32 KiB, depth 20, 2,048 nodes; the escrow section 256 bytes, depth 8, 128 nodes; the operation, O1 and receipt
ceilings after R40 and R41. The device root key is `arce_rocket_item_cargo` with field `buffer` holding
`EscrowItemBuffer`'s encoded form; D-A must match it or change it before wiring.

**Refusals.** `NO_CARGO_STORAGE` (no qualifying container or no target), `UNRESOLVED_LOOT`, `CARGO_TOO_LARGE` (any
byte, depth or node bound, including O1 and the combined reservation), `INVALID_DATA` (malformed data, a failed
native stack check, any changed input) and `UNSUPPORTED_DATA` (an unreadable container that selection skips). Every
refusal happens before a sequence, queue entry, reservation or mutation, and keeps both endpoints.

**Tests.** A0: `RocketItemCargoMutationTest`, `RocketItemCargoSelectionTest`, `RocketItemCargoNestedBoundsTest`,
`EscrowItemCargoEligibilityTest` and `EscrowItemCargoPreparedCaptureTest`, covering the TASK's A0 list. A1:
`EscrowItemCargoGameTests`, which restores explicit load and unload after payloads for a chest and a barrel through
the unchanged adapter with recapture equality, and publishes one item mutation through W112's permit. Each new
class runs alone, then the whole unit suite, then one full GameTest with the unchanged log checker on committed
source under the heavy-JVM lock, with drive and memory checks first.

**Not in this leaf.** Devices, menus and spill drops (D-A), real transactions and reconciliation (D-E), data and
art (D-D), C-E, enabling admission, ADRs, the risk register, status files and the ledger.

### Choices where the design or the TASK was open

1. **Large chest.** The TASK's "a large chest" is read as the vanilla large (double) chest: a chest or trapped chest
   whose `type` is `left` or `right` refuses with `NO_CARGO_STORAGE`, because section 5.3 allows 27-slot targets
   and a large chest is a 54-slot container. Modded subclasses (any other block ID) refuse the same way. If Root
   meant only modded 54-slot subclasses, the `type` test in `RocketItemCargoMutation.storage` is the one line to drop.
   (Superseded: Root decided R44, and W118F dropped that test.)
2. **Trapped chests.** W106 left `minecraft:trapped_chest` out of the v1.8 `rocket_movable` extension, so normal
   assembly does not capture one. The mutation accepts a trapped chest that a data pack already let a rocket
   capture; the A1 restores cover a chest and a barrel only, and no trapped-chest round trip is claimed.
3. **Device root.** Item eligibility reads `arce_rocket_item_cargo` with `schema_version`, `owner`, `device`, `role`,
   optional `binding`, `buffer` (the `EscrowItemBuffer` form) and `resource_escrow`, at 32 KiB, depth 20 and 2,048
   nodes, mirroring the fluid root. D-A must save this form or change the eligibility with it.
4. **Selection.** One eligibility call per container, in canonical block order, so the check runs at most once
   per payload, as for Fluid. A load uses only the first nonempty buffer slot. An unload skips a container stack
   that fails the codec or the framed payload bound (it stays) and tries the next slot of the same container. No
   target and an empty buffer report `NO_CARGO_STORAGE`, as the fluid selection does; the device statuses
   (`DEVICE_EMPTY`, `CARGO_FULL` and the rest) are D-A and D-E display mappings. (Superseded in part by R45 in
   W118F: an unload now calls the check once per offered slot, and a load runs two passes.)
5. **Statuses through the coordinator.** `UNRESOLVED_LOOT` and `NO_CARGO_STORAGE` reach `EscrowCoordinator.prepareCargo`
   unchanged and, under its current mapping, become `Transfer.INVALID` (only `CARGO_TOO_LARGE` becomes
   `ESCROW_FULL`). The mapping is W117's, so this leaf neither changes it nor pins it in a test.
6. **Staged refusals.** The staged final item step converts an item codec size refusal to the shared `TooLarge`
   and leaves other refusals invalid, so `EscrowCargoPreparedCapture.advance` keeps its mapping. The preparation
   reports `NO_CARGO_STORAGE` and `UNRESOLVED_LOOT` through `cursor.failure()`. The capture's capacity argument
   does not apply to items and is ignored for them.
7. **Native checks.** Eligibility runs `EscrowItemStackCodec.validateNative` on the delta at admission (R39). The
   mutation also needs the native stack (merge identity and maximum stack), so a replay of an item whose mod is
   gone refuses; D-E must hold that operation for REPAIR, as R39 requires.
8. **Payload fields.** A cargo container payload has exactly `Items`, `CustomName` and `Lock`; any other field is
   invalid in a replay and unsupported (skipped) in selection. A merge never exceeds `min(64, max stack)`.

### What changed

- **R1.** Item stage 0 reserves `16 x (262,144 + 262,144 + 4,096 + 256)` = 8,458,240 bytes before it runs: the
  largest legal container payload (`RocketLimits.MAX_BLOCK_ENTITY_NBT_BYTES`), the largest replacement (the
  `RocketBlockEntityPayload` constructor enforces the same limit) and the largest moved stack
  (`EscrowItemStackCodec.MAX_BYTES`). The step reports `16 x (old + replacement + stack + 256)`, so its actual work can
  never exceed the reservation. The multiplier fell from 32 to 16, inside the review's 8 to 16. Unused capacity is
  returned after the step as before. The tank's 1 MiB reservation, the 16 MiB and 16,384-visit tick budget, the visit
  bounds and the 40-tick lifetime are unchanged.
- **R1, over-budget step.** `RocketCargoWorkBudget.perform` now throws `RocketCargoWorkBudget.Exceeded`, a subclass of
  `IllegalStateException` with the same message, so every existing caller and assertion sees the same type.
  `RocketCargoPreparation.advance` catches it, records `CARGO_TOO_LARGE` and closes the cursor, so `Ticket.advance`
  returns normally and the staged capture reports the status.
- **R3.** `storage()` is `STORAGE.contains(blockId)`. Each half of a vanilla double chest is a target; only other block
  IDs (other `ChestBlockEntity` subclasses) refuse with `NO_CARGO_STORAGE`. The refusal message no longer says
  "single". No other code read the `type` property.
- **R4.** On an unload, a slot that fails the stack checks or the supplied check stays where it is, and the next
  nonempty slot of the same container is offered before the next container.
- **R5.** A load first offers, in canonical block order, each container's first slot with the same item and tags and
  room, and only then each container's first empty slot.

### Choices where the TASK was open

1. **R1 reservation.** The reservation is the constant for the largest legal sizes, not one computed per payload, so
   it needs no block lookup before it is charged. Stage 0 is a ticket's first step in its first tick, and the session
   has one active ticket, so the 8.07 MiB always fits an empty tick.
2. **R1 status.** An over-reservation step reports `CARGO_TOO_LARGE`, the status for every other byte bound. Only the
   preparation converts it. `Ticket.performWork` callers (the staged capture, admission and publication) still
