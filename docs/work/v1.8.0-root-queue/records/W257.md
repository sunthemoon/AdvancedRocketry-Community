# W257: committed samples for the bay-exit descent

## Design note (2026-11-02, before implementation)

Authority: [TASK W257](../TASK-W257-S2-COMMITTED-SAMPLES.md), Root decision R283,
on branch `codex/v1.8.0-w257`, starting at `5ba122014d9430aa13ac458b6efc03dbecd53b8b`.
The worktree and index were clean. Other running sessions were inspected; none
uses this worktree. No agent is dispatched and no push or merge is authorized.

Write scope: `BayPassengerExitMotion`, `BayPassengerExitDescent`,
`BayPassengerExitService`, `BayPassengerExitEvents`, their bay-exit unit and
GameTest fixtures/tests, this record, and narrowly necessary native harness
changes. Runtime scripts and logs belong under
`D:/GitHub/ARCE-Task-Evidence/root-queue/W257/`.

Keep PlayerTick START, PlayerTick END and server-tick END, including their
existing authority, contact and hazard checks. Pass an explicit committed flag
from the event adapter: START and server END commit, PLAYER_END only checks.
Fall/attack revalidation also only checks. The initial exit sample is committed.
`Continuity.last` is the last committed sample; only successful committed
observations update it and its cumulative per-tick horizontal/downward usage.
A check-only observation projects its displacement from that baseline onto the
already committed tick usage without spending or replenishing that usage.
This avoids charging vanilla's temporary physics displacement twice, while
retaining cumulative limits across multiple committed observations in a tick.
Correction-counter acceptance remains one early step on the same connection;
it does not reset the origin, usage, first tick or deadline.

This reads W230-R2's "at most one tick between required samples" as a maximum
one-tick gap between committed samples, with additional check-only observations
at PLAYER_END and damage callbacks. A check-only observation cannot advance
the committed timestamp or hide a missing committed tick. An upward position
or positive vertical velocity relative to the committed baseline still refuses.
A return from a lower temporary PLAYER_END position to the same committed
position is not upward committed motion. This distinction is R283's explicit
change; it is not a promise to detect excursions between observation points.

Add a fixture mode that ticks the embedded rider connection once per server
tick, drains packets and answers keep-alives, following `ReleaseTestPlayers.pump`.
Retain every existing case and add descent, extended landing, expiry and late
correction cases in this mode. Capture their failures before production edits,
then rerun them, all bay-exit unit/GameTest batches and the whole unit suite.
Use detached, bounded scripts owning the heavy-JVM lock for every GameTest,
full build and native server; inspect disk capacity first and clean only this
task's disposable worlds. Rerun X2, X4, X5, X7 and the packaged smoke on the
reobfuscated JAR of a committed implementation, then run the repository validator.

Expected integration size is under 30 changed lines each in the event adapter,
service and descent; the motion helper stays under 150 lines. The existing
fixture is near 500 lines and retains lifecycle/orchestration only; new pumping
and test scenarios should use a separate helper if needed. No class may exceed
800 lines. No state schema, networking, admission, budget, deadline, radius,
contact classifier, asset, status file, ledger or risk-register edit is in scope.

R-042 draft for Root: The descent's movement continuity is checked against its
last committed server position (PlayerTick START or server-tick END), with at
most one tick between committed samples. PlayerTick END and synchronous damage
callbacks retain all hazard/contact and continuity checks but never replace
that baseline or renew movement allowance. Vanilla's temporary server-side
physics step and its restoration do not themselves revoke the offer; observed
upward movement relative to the committed baseline, excessive displacement,
missing committed ticks, invalid contact or authority, unsupported state,
deadline expiry and disallowed correction-counter changes still revoke it.
The existing one early counter step does not create a new descent. Movement
between observation points is not exhaustively traced. All other R264/R274
limits and the RAM-only residuals remain unchanged. This is draft wording,
not an edit to accepted risk text or a Gate approval.

## Correction (2026-11-02, W262 under Root decision R288)

This section corrects the record above; the text above is left as written. The independent review
(`D:/GitHub/ARCE-Task-Evidence/root-queue/W257-review/REVIEW.md`, SHA-256
`8c0f201cd853021e0e61ec029abe7db75b2b6701e26a0515add39e4d3ee43083`, finding W257-R1) found the following.

- "Failure evidence and landing correction" calls the gated drive's old timing a "spare tick" that the drive
  "manufactured", and `ddf008058`'s code comment said the drive "must not manufacture a spare landing". That is wrong.
  The old timing (the last airborne packet at pad + 0.25, one full server tick, then the landing packet) is what a real
  client does, because it sends one move packet per tick. The same-tick pair that `ddf008058` introduced is artificial;
  W262 (`c7505c87c`) restored the real timing and keeps the pair only as the GameTest `PACKET_PAIR`.
- X4's "exactly one cancelled FALL" in `final-native`, and the passing packet-landing GameTest, therefore did not show
  that a real client's extended landing is protected. With the real timing, X4 failed on this commit's rules for the
  named cause: vanilla's temporary step reached the pad at PlayerTick END and ordinary contact closed the offer
  (`committed-native`, and again in W262's red run).
- The R-042 draft above ("Vanilla's temporary server-side physics step and its restoration do not themselves revoke the
  offer") was not true of this commit: the temporary step revoked the offer on contact (W257-R1), and its displacement
  was charged on top of the tick's committed usage (W257-R2). Both drafts in this record are superseded by the single
  R-042 and R-043 draft in [W262](W262.md).
