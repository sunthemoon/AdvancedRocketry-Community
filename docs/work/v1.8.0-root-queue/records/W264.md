## Source evidence and design boundary

- [SuitWorkstationMenu](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/equipment/workstation/SuitWorkstationMenu.java),
  lines 25-33, creates a two-element container, armor input 0 and module
  input 1, plus the player's 36 main/hotbar slots. It does not expose the
  player's four equipped-armor slots. Lines 48-60 keep shift-click routing
  tied to those two workstation inputs. There is no `getNoItemIcon()`
  override or selected armor-part state.
- [SuitWorkstationBlockEntity](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/equipment/workstation/SuitWorkstationBlockEntity.java),
  lines 24 and 49-59, holds exactly two stacks and accepts any recognized
  suit part in input 0. No empty-input state identifies HEAD, CHEST, LEGS
  or FEET.
- [SuitWorkstationScreen](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/client/equipment/SuitWorkstationScreen.java),
  lines 33-38 and 46-60, derives the module display from the actual armor
  stack in input 0 and draws the existing menu slots. It has no four-part
  empty armor selector.

No behavior was invented to reconcile these facts. Adding equipped-armor
slots would change the menu and input contract; cycling four icons or
remembering the last armor part would introduce unspecified presentation
behavior. Replacing the player's separate inventory icons is not the
assigned workstation consumer. Importing all four without real consumers
would violate the task's own asset-use boundary.

A clarification request was issued during the session. Root needs to name
the intended real consumer for all four icons and its behavior on this
single empty armor input, or revise the requested scope. This is a task
clarification, not an ADR change, exclusion decision or Gate waiver.
