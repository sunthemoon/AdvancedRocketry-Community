This record is the proposal. It changes no code, ADR, status file or ledger.

## Recommendation in short

- **F4:** option F4-A (the mod's own serializers refuse through a bounded path and log one summary per reload) together
  with option F4-D (a docs/17 waiver ADR for the per-file entries that vanilla and Forge write). Neither changes a
  packet, the recipe-serializer format or saved data.
- **F5:** option F5-B (the shared ingredient codec treats a tag whose named set no item is a member of as absent). It
  changes no packet, serializer format or saved data. It deliberately differs from vanilla ingredients until the next
  restart, and matches what both do after a restart.

## 1. Trace

### 1.1 How a classic recipe file is read and refused (F4)

1. **Prepare, on a worker thread.** `SimpleJsonResourceReloadListener.scanDirectory` (lines 34 to 51) opens the
   top-most resource of each `recipes/*.json` id (line 40) and parses the whole file into a Gson tree with no size
   limit (`GsonHelper.fromJson`, line 41). A file that is not JSON is logged at line 47 ("Couldn't parse data file",
   ERROR with a stack trace) and never reaches a serializer. Gson 2.10 keeps the last of two equal keys without
   complaint (probe), so the classic codec's duplicate-field refusal (`ClassicRecipeCodec.java:108`) cannot fire for
   a data-pack file.
2. **Apply, on the server thread for `/reload`** (W179's log shows `Server thread`). `RecipeManager.apply` (lines 54
   to 86) skips ids that start with `_` (60), evaluates Forge conditions (63), requires a top-level object (67), and
   calls `RecipeManager.fromJson` (168 to 171). That method reads `type` (168), refuses an unknown or missing type
   with "Invalid or unsupported recipe type" (169), and calls the serializer (171) through Forge's three-argument
   `IForgeRecipeSerializer.fromJson(id, json, context)` (line 23), which the classic serializer does not override.
3. **The classic serializer.** `ClassicMachineRecipe.Serializer.fromJson` (`ClassicMachineRecipe.java:163-165`) first
   copies the whole tree with `json.toString()`, and only then does `ClassicRecipeCodec.parse`
   (`ClassicRecipeCodec.java:85-98`) apply the 64 KiB text bound (86 to 87) and the depth and node bounds (101 to
   102). Every refusal is an `IllegalArgumentException`. The rolling serializer, by contrast, runs the bounded
   `RecipeJsonSignature.canonical` walk first (`RollingMachineRecipe.java:320`).
4. **Vanilla's per-file log.** `RecipeManager.apply` catches `JsonParseException` and `IllegalArgumentException` and
   logs "Parsing error loading recipe {id}" at ERROR with the full stack trace (line 77). If a serializer returns
   `null`, Forge's patch logs "Skipping loading recipe {id} as it's serializer returned null" at INFO, without a stack
   trace (line 69). Line 85 then logs "Loaded N recipes".
5. **Later, at lookup.** `ClassicMachineManager.resolve` (`ClassicMachineManager.java:194-205`) logs one ERROR
   "Classic recipe {id} disabled" per recipe whose definition fails, per Level and reload (line 200, cut to 160
   characters). `catalog` (181 to 193) logs once per type and Level when a type has more than 1,024 recipes. The four
   other mod serializers' recipes log once per recipe and tag generation (`DeferredProcessDefinition.java:46`).
6. **Tags, on a worker thread.** `TagLoader.load` (40 to 69) parses every resource of every pack stack (49). A tag
   codec error is logged by `getOrThrow(false, LOGGER::error)` (53) and again at line 64 ("Couldn't read tag list",
   ERROR with a stack trace), so one file gives two entries (from reading, not measured); a JSON syntax error gives
   one. `TagLoader.build` drops a tag with a missing reference and logs it at line 105, joining every missing entry
   without a cap.
7. **The mod's pattern catalogs** (`MultiblockPatternReloadListener.java:31-82`) read each file with `readNBytes`
   up to 64 KiB plus one byte (84 to 92), refuse the whole candidate on the first problem and log one ERROR per
   catalog and reload (73). This is the aggregation that docs/17 asks for.

**Who controls which entries.** Measured in W179's isolated run `b4b2-1` (one over-limit pack, its first reload), with
`W192/tools/entry_sizes.py`:

| Source | Controlled by | ERROR entries | Log lines | Bytes |
|---|---|---|---|---|
| Classic serializers, logged at `RecipeManager:77` | the mod | 36 | 1,201 | 167,403 |
| Top-level array, `RecipeManager:67` | vanilla | 1 | 22 | 2,989 |
| Unparsable files, `SimpleJsonResourceReloadListener:47` | vanilla | 2 | 51 | 5,958 |
| Tags, `TagLoader:64` and `:105` | vanilla | 2 | 24 | 2,496 |
| Pattern catalogs, already one per catalog | the mod | 2 | 2 | 480 |

The restore reload adds one WARN from Forge (`NamespacedWrapper:386`, 223 bytes). The mod therefore controls 38 of the
43 ERROR entries and 93.6 percent of their bytes. The largest single entry is 6,607 bytes. Vanilla's five entries come
from files that never reach a mod serializer.

**Cost of the copy before the bound** (probe, on the calling thread, which is the server thread during `/reload`):
the classic serializer took 10 ms, 40 ms and 61 ms to refuse a tree holding a 1 MiB, 8 MiB and 32 MiB string. The
bounded `RecipeJsonSignature.canonical` walk refused the same trees in 0.12 to 0.18 ms.

### 1.2 How a tag reaches `resolveAlternatives` after a reload (F5)

1. `TagManager.reload` loads each registry's tags on a worker and stores the result in its apply step (lines 44 to
   45). Apply steps run strictly in listener order, because each waits for the previous listener
   (`SimpleReloadInstance$1.wait`, line 54). TagManager's result is therefore ready during `RecipeManager.apply`.
   Forge exposes it there as `ConditionContext.getAllTags` (34 to 46), and to mod listeners through
   `AddReloadListenerEvent.getConditionContext` (69).
2. Classic recipes keep their ingredient JSON and do not expand tags when parsed (ADR-064 section 2.1,
   `ClassicMachineRecipe.java:28`).
3. After all listeners, `MinecraftServer.reloadResources` (1318 to 1348) calls
   `ReloadableServerResources.updateRegistryTags` (1337), which binds each registry (`ReloadableServerResources:100`).
   The item registry is Forge's `NamespacedWrapper` (the probe saw `NamespacedDefaultedWrapper`). Its `bindTags`
   (379 to 407):
   - copies the old tag map and rebinds only the tags the new data defines (390);
   - binds Forge optional tags that the data lacks to their defaults (394 to 401);
   - rebinds every item's own tag set from the new data only;
   - warns once about the keys that vanished (386; the list is joined without a cap);
   - keeps the copy (404).

   A vanished tag therefore keeps its named set with the old items, while no item is a member any more. Vanilla's
   `MappedRegistry.bindTags` (363 to 395) does the same.
4. `TagsUpdatedEvent` (`ReloadableServerResources:90`) advances `RecipeTagGeneration`. `PlayerList.reloadResources`
   (859 to 872) then posts `OnDatapackSyncEvent` (863), and `ClassicRuntime.synced`
   (`ClassicRuntime.java:104-106`) clears every Level's resolution cache.
5. The next lookup calls `ClassicMachineRecipe.definition`, then `resolveInputs` (`ClassicMachineRecipe.java:33-36`),
   then `BoundedItemIngredientCodec.resolveAlternatives` (`BoundedItemIngredientCodec.java:59-87`). That method reads
   `BuiltInRegistries.ITEM.getTag` (67), which returns the old named set (`NamespacedWrapper.getTag`, 373). The
   electrolyzer, rolling and precision recipes call the same method.
6. Vanilla ingredients behave the same: `Ingredient$TagValue.getItems` (262 to 271) reads `getTagOrEmpty` (264). The
   mod's small plate press matches through vanilla `Ingredient.test` (`SmallPlatePressRecipe.java:62` and `:85`).
7. **Clients.** `PlayerList.reloadResources` sends the tags (864), built by `TagNetworkSerialization.serializeToNetwork`
   (31 to 43) from `registry.getTags()` (32), which includes the stale named sets. A remote client therefore binds the
   vanished tag as a defined tag, with its old items as members (`ClientPacketListener.updateTagsForRegistry`, 1466).
   Only a new login empties every named set first (`handleLogin`, 388, skipped on a memory connection). In single
   player the client shares the server's static item registry. JEI shows a classic recipe when `definition()`
   succeeds on the client (`ArceJeiPlugin.java:165-171`).
8. After a restart the registry has no named set for the tag, and the codec refuses with "machine ingredient has no
   bound alternatives" (probe, tag `never`). Today the result depends on the reload history, not on the data.

**Probe result** (`W192/probe/probe-report.txt`). After binding `arce_probe:vanishing` to iron and gold and then binding
data without it:

- `getTag` still returns a named set of size 2, while `iron.is(vanishing)` is false and no item is a member.
- The current codec resolves the tag to `[minecraft:gold_ingot, minecraft:iron_ingot]`, and so does vanilla
  `Ingredient.of(vanishing).getItems()`.
- The check proposed in F5-B reports `false` for the vanished tag and `true` for the tag that stayed defined.
- Forge logged one WARN, as in W179.

## 2. Options for F4

**What the mod controls.** It controls the refusals inside its eleven recipe serializers (the seven classic types,
electrolyzing, rolling, precision assembling and the small plate press), its lookup-time logs and its pattern
catalogs. It does not control:

- vanilla's parse of the file;
- RecipeManager's checks that run before any serializer: conditions, the top-level element and the type, including a
  mistyped type in the mod's namespace;
- tag loading and Forge's vanished-tag warning;
- refusals by vanilla's and other mods' serializers;
- Forge's INFO line after a `null` result.

### F4-A: a bounded refusal path in the mod's serializers (recommended, with F4-D)

1. **Bound before copying.** The classic serializer runs `RecipeJsonSignature.canonical(json)` before
   `json.toString()`, as the rolling serializer already does.
2. **A per-reload refusal ledger** (new class, for example `machine/recipe/RecipeRefusalLedger`).
   - The mod's `AddReloadListenerEvent` handler creates it and registers it under that reload's `ICondition.IContext`,
     compared by identity in a weak map.
   - A listener that the same handler adds flushes and removes it. Its apply step runs after RecipeManager's, because
     Forge appends event listeners after vanilla's (`ReloadableServerResources:77`) and apply steps run in order.
   - It holds the total count, the counts per serializer type and refusal kind (at most 16 kinds, the rest under
     "other"), and the first 8 ids (each cut to 96 characters).
   - A refusal kind is the first exception message, cut to 48 characters (the codec's messages are already short,
     for example "Recipe text bound").
3. **The serializers.** Each of the eleven (five classes; the seven classic types share one) overrides the
   three-argument `fromJson(id, json, context)`.
   - On an `IllegalArgumentException` or `JsonParseException`, it records the refusal and returns `null`, but only when
     a ledger is registered for `context`.
   - Without a ledger it throws as today. That covers data generation, direct calls, `IContext.EMPTY`, and other mods
     that call `RecipeManager.fromJson` after the flush.
   - Other exception types still propagate, so programming errors stay visible.
4. **One entry per reload.** When the count is above zero, the mod's logger writes one ERROR of at most 1,024
   characters, for example "Refused 36 data-pack machine recipes: lathe/Recipe text bound=1, ...; first 8: ...".
   Detail for each refusal goes to DEBUG, at most 64 entries per reload.
5. **Lookup-time logs.** `ClassicMachineManager.java:200` and `DeferredProcessDefinition.java:46` log the first 8
   disabled recipes individually (per Level for classic recipes, per tag generation for the others) and count the rest.
   At the next reload they write one "N further recipes disabled" entry when N is above zero.

**What a refused recipe becomes:** no registered recipe, as today.

- JEI never sees it, because the server sends only registered recipes (`PlayerList:865`).
- The recipe book never sees it. Classic recipes are special, and the book skips special recipes anyway
  (`ClientRecipeBook.categorizeAndGroupRecipes`, line 55; `ClassicMachineRecipe.java:144`).
- A machine with a running job for that id pauses with `RECIPE_MISSING` (`ClassicControllerBlockEntity.java:362`), as
  today.

**Effects.**

- Pack format, packets, recipe-serializer format and saved data: none.
- Logs, for W179's pack: 36 ERROR entries (167 KB with stack traces) become 1 ERROR of at most 1 KiB, plus 36 INFO lines
  from Forge (about 6 KB, no stack traces).

**Cost:** about 150 lines of main code (the ledger, the listener and the serializer overrides), the caps at two log
sites, and the tests below.

**Risks.**

- A refused recipe's stack trace moves to DEBUG. Its message stays in the summary as the refusal kind.
- The context-keyed weak map is static. Its lifecycle is the reload's: the flush removes it, or it is collected with
  the context when a reload fails. This must be stated under AGENTS.md section 3.3.
- A third-party mod that calls `RecipeManager.fromJson` with the server's context before the flush could now get
  `null` for a refused classic recipe. Forge allows `null`, but such a caller may not expect it.
- Nine log expectations and the pinned ERROR total change. This is a design change that the new assertions bound,
  not a weakening.

**Test plan.**

- **Unit tests** (with `MinecraftBootstrap`):
  - The ledger: counts, the kind and id caps, truncation, a summary of at most 1,024 characters for 10,000
    refusals, and no entry at count zero.
  - Each serializer with a ledger: returns `null` and records the refusal.
  - Each serializer without a ledger: throws as today.
  - A tree with a 32 MiB string is refused with the bounded walk's message ("recipe JSON text exceeds its bound"),
    which shows that no full copy was made.
  - A valid recipe still decodes.
- **GameTest:** `DataPackOverLimitReloadGameTests` asserts:
  - exactly one summary per reload, of at most 1,024 characters;
  - counts per kind equal to W179's: text 7, structural 14, rows 8, unknown field 1, number range 2, fraction 1,
    null 1, noncanonical id 1 and identifier length 1;
  - exactly 36 Forge INFO lines;
  - vanilla's five entries, unchanged;
  - every other existing assertion, unchanged.

  A scale case with 1,000 generated refused files must still log one summary.
- **Log manifest:** the nine codec expectations in `scripts/gametest_expected_log.json` (`w179-recipe-text-bound` to
  `w179-recipe-identifier-bound`, 36 entries) become one summary expectation. `w179-recipe-top-level-array`,
  `w179-recipe-file-unparsable`, the two tag, the pattern catalog and the WARN expectations stay. The pinned ERROR total in
  `tests/test_check_gametest_log.py` goes from 178 to 143 (178 − 36 + 1; recount when implementing).

### F4-B: a disabled placeholder recipe (not recommended)

The serializer returns a placeholder recipe that carries only the id, the type and the refusal kind.
RecipeManager registers it, so vanilla writes no per-file line at all.

**Effects:** a **recipe-serializer network format change and a protocol change**. `toNetwork` and `fromNetwork` must
carry a refused marker, and a client built without it fails to decode the recipe packet and disconnects. No saved-data
change.

**What players and tools see.**

- The recipe book ignores the placeholder, because it is special.
- `/recipe give` and advancement rewards accept its id.
- JEI must filter it.
- Every `getAllRecipesFor` consumer must skip it. Otherwise placeholders count towards a type's 1,024-recipe cap
  (`ClassicMachineManager.java:185`) and can disable the whole type, a new failure mode.

**Cost:** medium to high. **Test plan:** F4-A's tests, plus client decode tests and a mixed-build connection test.

### F4-C: a directory of the mod's own with a bounded reader (not recommended for v1.8)

Classic recipes move to a directory of the mod's own. A listener reads them like the pattern catalogs, with bounded
bytes before parsing, and inserts them with `RecipeManager.replaceRecipes`.

- **Benefit:** this is the only option that bounds the file read itself.
- **Effects:** a **pack data-format change** for every pack, for data generation and for imported data.
- **Cost:** high. The listener has to replace RecipeManager's contents after vanilla's apply step.

### F4-D: a docs/17 waiver for vanilla's and Forge's per-file entries (recommended, with F4-A)

[docs/17 section 10](../../../17-V1PLUS-QUALITY-BUDGETS.md) requires a new ADR for any change to a threshold. Proposed
content:

- **Scope, exactly.** Entries that vanilla or Forge writes for data that never reaches a mod serializer, or that is not
  the mod's:
  - `SimpleJsonResourceReloadListener:47`, for every JSON directory, not only recipes;
  - `RecipeManager:63`, `:67` and `:169` (conditions, the top-level element, an unknown or missing type);
  - `RecipeManager:77`, for vanilla's and other mods' serializers;
  - `RecipeManager:69` (Forge's INFO after a `null` result under F4-A);
  - `TagLoader:53`, `:64` and `:105`;
  - `NamespacedWrapper:386`.
- **The bound that still holds.**
  - There is one entry per refused file and reload. For tags this is one entry per pack resource, and from reading,
    two for a tag codec error.
  - Each entry is one message and at most one stack trace (vanilla's largest entry in W179 was 3,088 bytes).
  - The count is bounded by the files of the selected packs, which only the server operator installs.
  - Two messages join lists without a cap: missing tag references (`TagLoader:105`) and vanished tags
    (`NamespacedWrapper:386`).
- **Reason.** The mod cannot change these loggers without a mixin or coremod (AGENTS.md section 3.3 requires an ADR
  first). A log filter over vanilla's loggers would also hide other mods' and vanilla's errors, and would change the
  operator's logging configuration.
- **Data.** W179's isolated run: 5 vanilla ERROR entries, 97 lines and 11,443 bytes, plus 1 WARN, for 5 refused files
  and 1 vanished tag.
- **Owner, expiry and recovery.**
  - Root drafts the ADR and the project owner accepts it.
  - The waiver is temporary and expires at the v1.9.0 Gate.
  - At that Gate, re-measure with W179's pack. Lift the waiver when the platform offers bounded reload diagnostics or
    an accepted ADR allows a hook. Otherwise renew it with the new data.

### F4-E: a log filter on vanilla's loggers (rejected)

A Log4j filter could cap RecipeManager's, TagLoader's and the JSON listener's entries. It is rejected for the reasons
in F4-D: it hides errors that are not the mod's, and it changes logging that the operator owns.

## 3. Options for F5

**Should the classic codec treat a tag that the current reload did not define as absent?** Yes. Its result should
follow the data, not the reload history. After a restart, both the codec and vanilla already treat such a tag as
absent, and the server is authoritative.

**How it could know.** There are two ways:

- **Membership.** `bindTags` rebinds every item's own tag set from the current data only. So a non-empty named set
  whose items do not report membership was not defined by the current reload.
- **The reload's own tag result.** Forge exposes it through `ConditionContext.getAllTags`, but only on the server and
  only during the reload.

**Whether it should differ from vanilla's ingredients** is the choice between F5-B and F5-D.

### F5-A: keep vanilla's behaviour and document it

This costs nothing. The result keeps depending on the reload history until a restart, and the server and a remote
client disagree on membership (section 1.2, step 7).

### F5-B: a membership check in the shared codec (recommended)

**Design.** In `BoundedItemIngredientCodec.resolveAlternatives(JsonElement)`, a tag entry gathers its named set's items
into a temporary list (still stopping at 33 items). It adds them only if every item reports membership with
`holder.is(tag)`. Otherwise the tag contributes nothing, exactly as after a restart. If no alternative is left, the
existing "machine ingredient has no bound alternatives" refusal disables the recipe. The check is silent, rather than a
new refusal message, so that the outcome equals the outcome after a restart.

**Why it is exact.** Every item of a defined tag reports membership (the probe's tag `kept`). Forge's optional tags that
are bound to their defaults also report membership, so they stay usable.

**Effects.**

- Pack format, packets, serializer format and saved data: none.
- Behaviour: after a reload that drops a tag, classic, electrolyzer, rolling and precision recipes lose that tag's
  items at once instead of after a restart.
- A running job pauses with `RECIPE_TAGS_INVALID` (`ClassicControllerBlockEntity.java:365`). Nothing is consumed and
  the progress is kept, as ADR-064 section 2.3 requires and as after a restart.
- **This differs from vanilla until the next restart.** Vanilla crafting recipes and the small plate press still
  accept the old items.
- **Clients.** In single player the client shares the server's registry and agrees. A remote client receives the
  stale set as a defined tag, so its JEI may still show a recipe that the server disables. This affects display only:
  ADR-064 section 2.2 limits client resolution to JEI.

**Cost:** about 15 lines and the tests below. **Risk:** low; the check is local and bounded.

**Test plan.**

- **Unit tests** (with `MinecraftBootstrap`, like `DeferredRecipeTagTest`):
  - A defined tag that then vanishes makes a classic `definition()` refuse.
  - An ingredient array of a vanished tag and an item keeps the item.
  - A tag that is defined again resolves again.
  - The 33-item bound still applies.
  - A rolling or electrolyzer recipe becomes unavailable after the vanish and a tag reload.
- **GameTest** (a new batch or the restore phase of `DataPackOverLimitReloadGameTests`):
  - A pack defines tag T, and a classic recipe that stays loaded names T.
  - After T's pack is deselected, `definition()` refuses. Today it resolves to the old items, as W179's trial saw.
  - A machine that is running a job for that recipe pauses with `RECIPE_TAGS_INVALID`.

### F5-C: keep the reload's own tag result for the codec (not recommended)

A listener captures `ConditionContext.getAllTags(Registries.ITEM)` for the codec to consult. This is exact, but it
works on the server only, and it needs a server-scoped holder that the static codec can reach. Clients decode recipes
from the network without a context. On the server it has the same effect as F5-B, with more code.

### F5-D: empty vanished tags in the registry after each server data load (possible follow-up)

At `TagsUpdatedEvent` (cause `SERVER_DATA_LOAD`, highest priority), a handler binds every stale named set of the item
registry to an empty list. `HolderSet.Named.bind` is public in this jar. The handler runs before the tags are sent
(`MinecraftServer:1337`, then `:1339`), so clients receive the tag empty.

- **Benefit:** vanilla, other mods, the mod and JEI all see what they would see after a restart, so the server and its
  clients agree.
- **Effects:** no format change. The tag packet's contents change: an empty list for a stale key.
- **Risks:** it changes state that vanilla and every other mod can see, and its order relative to other
  `TagsUpdatedEvent` listeners matters. It would need its own review.

## 4. Recommendation and its effects

| Option | Pack data | Packet or serializer format | Saved data | Logs |
|---|---|---|---|---|
| F4-A | none | none | none | the mod's per-file ERROR entries become one bounded summary per reload, plus Forge's INFO line per file |
| F4-D | none | none | none | none (an ADR waiver with scope, data and expiry) |
| F5-B | none | none | none | none new |

F4-B would change the serializer's network format and the protocol, and F4-C the pack data format. F5-D would change
the contents of the tag packet.

## Other observations

- Vanilla's Gson parse merges duplicate keys before any serializer runs (`W192/probe/DuplicateKeyProbe.java`):
  `{"count":1,"count":64}` arrives as `{"count":64}`. The classic codec's documented duplicate-field refusal therefore
  applies only to text that does not come through Gson's tree. I did not change this, and Root may want to record it.
- The two vanilla messages that join lists without a cap (missing tag references and vanished tags) are the only
  vanilla reload entries whose length grows with the data, rather than only their number.

## Choices where the TASK was open

- "The mod's serializers" covers all eleven of them and the two lookup-time log sites, because docs/17 asks for a cap
  on a reload's errors as a whole.
- The summary stays at ERROR, the level of today's per-file entries. The caps (1,024 characters, 8 ids, 16 kinds and
  64 DEBUG entries) are conservative starting values for Root to adjust.
- The proposed waiver expires at the v1.9.0 Gate, the next version, rather than without a date.
- F5-B treats a vanished tag silently as absent rather than adding a new refusal message, so that a reload gives the
  same outcome as a restart.

## Not done

- No implementation of any option, no ADR, no waiver, no status file or ledger change, as the TASK says.
- No client run. The client side of F5 (a remote client keeping the stale set) is from reading
  `TagNetworkSerialization` and `ClientPacketListener`, not tested.

## Known risks

- The vanilla line numbers belong to Forge 47.4.10's userdev jar. A Forge update can move them, though not the
  behaviour described.
- The probe runs in plain JUnit. Its item registry is Forge's wrapper, but not after Forge's full bootstrap. W179's
  GameTest log shows the same warning from the same class on a real server.
- F4-A's timings come from one machine under other workers' load. They show the order of magnitude, not a budget.
- F5-B leaves a display-only difference on remote clients (section 3). F5-D is the way to remove it if Root wants
  that.
