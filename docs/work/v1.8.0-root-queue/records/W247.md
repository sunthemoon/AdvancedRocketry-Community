## Method

Each stage runs from a `git archive` export of its pinned commit, under the heavy-JVM lock, in a detached process
that also removes the export and the GameTest world. The focused stages (`before` at `c0648999e`, `after` at
`8973abf0a`) run four groups in fresh seed-zero worlds through the existing batch filter, in vanilla's unchanged
relative order:

- `k4`: the twelve `w241_*` batches;
- `k3`: the four `w236_*` model batches, which use the same helper;
- `neighbours`: `station_warp_deop` and `w133_escrow_fill_launch` alone, as a control;
- `mixed`: all eighteen batches together.

The development-only probe mod (`scripts/w247_probe/`, attached to the `gameTestServer` run configuration by an init
script, as the CI observer is) writes one JSON line for every server tick whose period is at least 100 ms. Each line
records the chunks generated, loaded, unloaded and saved in that period. A JFR `profile` recording runs in the same
process. The probe misses the run's final tick, which never sees a next tick start; this affects only the last batch
of each group, identically in both stages.

## Findings

**The stall is fresh terrain generation for the distant fixture regions, waited for on the server thread.** Each K4
facing created its own `K3ModelTestRegion`: 25 chunks, each ticketed at distance 2, so about 81 FULL chunks and the
lower-status generation ring around them, with four facings 160 blocks apart. The GameTest overworld uses normal noise
terrain, not superflat. In the baseline `k4` group each of the eleven four-facing K4 batches has exactly one long tick, its
setup tick, of 4.97 to 8.08 seconds (hosted: 10 to 14 seconds); the single-facing elevator test shares the server's
first tick (2.33 seconds). In that tick 229 to 251 chunks are newly generated to FULL and about 1,700
to 1,900 chunk holders are added. JFR puts the server thread in `K3ModelTestRegion.<init>` →
`ServerChunkCache.getChunk` → `BlockableEventLoop.managedBlock` with only 13 to 61 execution samples per stall:
it waits rather than works. The `Worker-Main` threads take 876 to 1,166 samples per stall, mostly in
`NoiseBasedChunkGenerator.fillFromNoise` and `buildSurface`. Saving is a minor secondary cost: unloads afterwards save
about 180 chunks per tick (5,393 saves in the `k4` run), in ticks of 100 to 190 ms. No entity work or ticket churn of
note appears.

**The neighbouring batches do not stall by themselves.** Alone, `station_warp_deop` and `w133_escrow_fill_launch`
never exceed 1.2 seconds (that tick is the server's startup tick) and otherwise stay at or under 0.5 seconds.
Vanilla prints "Can't keep up" only when the server is more than 2 seconds behind *and* 15 seconds have passed since
the previous warning. Until then the backlog carries over to later batches. In the hosted W244-fix shard-2 log
(run 41307843635), the 11.5-second warning "after" `station_warp_deop` (642.6 s) reports `w241_rolling_model`'s
setup stall at 616.2 s, which the gate held back after the warning at 616.1 s. The 14.4-second warning "after"
`w133_escrow_fill_launch` (727.7 s) is the backlog of `w236_observatory_model` (715.0 s) and the batches before it.

**K3's model tests have the same cost.** Their setup ticks take 4.35 to 7.39 seconds with 184 to 263 chunks generated,
because each K3 test also builds four 25-chunk regions. `w236_observatory_model` stands just before
`w133_escrow_fill_launch` in shard 2. K3 is outside this task (its tests stay unchanged), so this remains open: see
"Not done".

**Focused runs cannot show the overloaded count.** Once the server falls behind in a focused run, it never catches up
between the closely spaced stalls, so vanilla's 15-second gate suppresses every warning after the first (the baseline
`k4` group logs one warning against twelve stalls of 5 to 8 seconds). The probe's tick periods are therefore the stall
sizes below. The count that the checker limits comes from the full run below and from Root's hosted sharded run.

## The fix (`8973abf0a`)

The four facings of one K4 test now share one `K3ModelTestRegion` of radius 0: one ticketed chunk in the test's own
row, with the same ticket type and distance 2. The controllers stand 8 blocks apart, at local x and z of 4 or 12.
Each row stays 1,000 blocks from the next, so every test keeps its own chunks. Setup asserts that every cell that any
facing or mirror of each controller could validate lies in the ticketed chunk and apart from the cells of the test's
other facings, so the rotated revalidation cannot see a neighbour's blocks. The multiblocks reach at most 3 blocks
from their controllers. The region's forced-chunk fringe check (no forced chunk within two chunks, W233's lesson)
still runs. Every assertion, all four facings of every rotation test, the rows, the timeouts and the elevator's single
facing are unchanged. `K3ModelTestRegion` gains a radius parameter; its two-argument constructor keeps K3's radius of
2, and a `ticketed(BlockPos)` query serves the new assertion.

Each K4 test's region then has 25 FULL chunks around one ticketed chunk, instead of about 324 across four regions.

## Choices

- The shared region keeps the helper's ticket type and distance (2), so the controllers' chunk stays entity-ticking,
  as each facing's own chunk was before. A smaller ticket distance would cut generation further but would change the
  chunk's ticking level, so it was not used.
- Rows stay distinct, 1,000 blocks apart, rather than reusing one area across tests, which keeps each test's blocks
  and runtime state apart, as in the original design.
- The new reach assertion is stricter than needed: it claims all four facings and both mirrors of every controller.

## Not done

- K3's model tests (`w236_*`) still stall for 4.3 to 7.4 seconds locally, by the same mechanism, and stand next to
  `w133_escrow_fill_launch` in shard 2. Fixing them needs changes to K3's test files (one radius-0 region per test,
  with the facings in one chunk), which this task excludes. Root may want to queue this follow-up.

## Known risks

- The local stall sizes depend on this machine's load; both stages ran back to back with no other heavy JVM, and the
  hosted runner is about twice as slow (10 to 14 seconds there against 5 to 8 here before the fix).
- The fixtures now sit closer together. The reach assertion fails setup if a pattern change ever lets one facing's
  cells reach another facing or leave the chunk.
