### What changed, by item

- **R1.** `RocketItemCargoSelection.Cursor` reserves `16 × (payload bytes + 27 × buffer bytes + 256)` per container visit
  instead of `RocketCargoWorkBudget.MAX_BYTES`. That is a fixed multiple of the container payload, as the item
  preparation's stage 0 is, plus one comparison of each of the 27 slots with the buffer, because the walk compares every
  slot with the moving stack (load) or with each buffer slot (unload). At the largest legal payload (256 KiB) and four
  4 KiB stacks it is 11,276,288 bytes, under the 16 MiB tick budget; a `min` with `MAX_BYTES` keeps an impossible visit
  from stalling. Admission now steps the walk through the new `RocketCargoPreparations.select(cursor, tick)`, which
  returns null (the existing `retrying` path) while any ticket is active. The tick budget, `RocketCargoTicketLifetime.LIMIT`
  and every other bound are unchanged. New A0 test: `RocketItemSelectionReplayPriorityTest`, after the review's probe,
  walks 48 chests full of dirt with a heavy buffer (two visits per tick, so more ticks than a ticket's 40-tick lifetime)
  against a real item replay ticket. With the ticket active first, it progresses every tick and reaches READY while the
  walk reserves nothing; with the ticket begun mid-walk, it loses at most that tick. Both walks then finish with the
  undisturbed result and exactly one visit per block per pass.
- **R2.** `RocketItemCargoSelection.full(slots)` is the shared "four slots at `min(64, maxStackSize)`" predicate; the walk's
  `noMove()` uses it too. Admission's `inspect()` returns DEVICE_FULL for an unloader from it, right after the existing
  loader DEVICE_EMPTY check. A walk's no-move verdict (DEVICE_EMPTY, DEVICE_FULL, NO_CARGO, CARGO_FULL or
  INCOMPATIBLE_CARGO, which `noMove()` gives only when no candidate was offered or refused) is kept with the root and
  snapshot instances the walk used. While both are the same instances, `inspect()` returns the verdict and the device is
  not queued; any other root or snapshot drops it and walks again. It is also dropped when the binding no longer resolves
  and when the admission closes (load, unload, removal, rebind), and it survives the queue's per-walk `discard()`.
  New tests: `RocketItemSelectionBudgetTest.fullBufferIsFourSlotsEachAtItsStackLimitAndMatchesTheWalk`, and the GameTest
  `ItemCargoNoMoveGameTests.noMoveVerdictsNeitherWalkNorQueueAgainUntilTheDeviceChanges` (batch `item_cargo_no_move`,
  ledger detached, nothing admitted): a full unloader answers DEVICE_FULL without being queued; after its first walk an
  unchanged loader answers CARGO_FULL without being queued, also across two of its own 20-tick pacer periods; after
  their local ports change each buffer, both walk once more and then stay out of the queue again.
- **R3.** `run_v180_cargo_reconciliation.py` reads both Anvil records of an item case with a `TypedNbtReader` (a subclass of
  the bounded `NbtReader` whose numbers and arrays keep their tag type as `int`, `float` and `list` subclasses, so every
  other check compares as before). `item_amount` requires each stack to equal the fixture in values and types: `Count`
  and `Slot` as TAG_Byte, `b`, `s`, `i`, `l` as Byte, Short, Int, Long, and `ba`, `ia`, `la` as the three array types.
  The shared `record()` in `run_v180_escrow_forced_stop.py` gained an optional `reader` argument; its default, and the
  fluid oracle, are unchanged.
- **R4.** `ItemCargoReconciliationGameTests.mismatchedFrozenReplayDigestHoldsWithBothEndpointsUnchanged` (batch
  `item_cargo_replay_mismatch`) admits a real item operation in each direction with reconciliation paused, replaces its
  frozen binding, and unpauses. The load uses a wrong AFTER snapshot hash (the Preparation's phase 0); the unload a wrong
  rocket AFTER envelope digest, `sourceAfter` (phase 2). Each tick it requires both endpoints byte-identical to their
  pre-admission captures; at the end each operation is REPAIR with OTHER_STATE, both endpoints have epoch 0 and no
  markers, and the coordinator stays operational. The first direction's held endpoints stay loaded until cleanup, as in
  the R39 test.
- **R5.** `EscrowReconciliationAction.requireNativeResource` decodes the payload first (a structural failure is held as
  before, without a log line), then logs `ARCE_ESCROW_ITEM_UNAVAILABLE op={} item={}` with the decoded stack's ID, which
  `validateStructure` has already checked, before the OTHER_STATE refusal. As for fluids, the scheduler never revisits
  a manual record, so the line appears once per operation and session. The change stays inside `requireNativeResource`;
  a trial `git merge-tree` of `716fe2a0` with W131's current tip `c3ac6732` is clean.

### Choices where the review or task left room

- R1's estimate includes the buffer term because the walk's per-slot comparisons scale with the buffer stacks, not only
  with the container payload. The task's example (a multiple of `uncompressedBytes()`) alone would under-reserve for heavy
  buffers.
- R1 defers to any active ticket, not only replay tickets, because the session has one slot and an admission ticket
  that could not progress would also expire.
- R2 keeps only `noMove()` verdicts. Other refusals (unresolved loot, unsupported data, a rejected candidate) can depend
  on more than the buffer and snapshot, so they still walk again.
- R5 holds a structurally undecodable item payload silently, as before, because its ID would not be checked; durable
  decoding already rejects such payloads at load.
