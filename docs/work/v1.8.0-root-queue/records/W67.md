## How the test works

- **Registrations.** The test calls the real `ModRegistries.register` with a recording mod bus. Each
  `DeferredRegister.register(bus)` hands the bus Forge's `EventDispatcher`, which holds the deferred
  register; the test reads its registry name and entry IDs, and names the installing class from the
  call stack. A deferred register that the boundary installs therefore cannot be missed. Other
  listeners are allowed (two creative-tab listeners today), but a `RegisterEvent` listener fails the
  test, because it could register entries the test cannot see. `PumpContent` keeps the enabled
  supplier it is given, so the test restores the old one afterwards.
- **Resources.** The test reads the merged `build/resources/main`, the same tree the JAR packages
  after the build's superseded-file exclusions. It lists every file by exact path, so a name that
  differs only in case fails as it would in the JAR, not pass on the Windows file system.
- **The checks.** Each runs in `@BeforeAll`, which then writes
  `build/reports/registered-content-resources.md` (a summary table, every problem, the exemptions
  applied, reference counts by kind, and every registered ID per registry with its installers):
  1. IDs are unique in each registry, are in the mod namespace, and no two IDs (across all
     registries) differ only in case. 498 IDs in 18 registries.
  2. Every block has `assets/<ns>/blockstates/<id>.json` and `data/<ns>/loot_tables/blocks/<id>.json`.
     125 blocks.
  3. Every item has `assets/<ns>/models/item/<id>.json` and its name key in the merged en_us and
     zh_cn files of all packaged language namespaces. The key is `block.<ns>.<path>` when a block has
     the same ID and `item.<ns>.<path>` otherwise. 242 items.
  4. Every sound event is a key of `assets/<ns>/sounds.json`. 11 events.
  5. Every reference in the packaged recipes, loot tables, advancements and tags resolves. 835
     distinct references.
- **References.** The walker visits every string field and classifies it by field name: `item`,
  `items` and a string `result` are items; `fluid` is a fluid; `block` is a block; `enchantment`;
  `recipe` and `recipes` are recipes; `parent` is an advancement; `tag` is an item tag (a fluid tag
  under a `fluid` path). A loot entry's `name` follows its `type`. Types, triggers, texts and criteria
  are counted but not resolved, and any other string field fails, so a new data shape cannot be
  skipped. Tag files are checked by folder (items, blocks, fluids, entity types, biomes, damage
  types); an unknown folder fails. A mod ID must be registered by the mod and a `minecraft` ID by
  Minecraft; a tag, recipe or other data file must be packaged or, outside the mod namespace, be in
  a dependency JAR (Minecraft or Forge). An optional tag entry of another mod is skipped (none today).

## The exemption file

Each line is `<check> <registry ID> <reason>`, for the checks `blockstate`, `loot_table`,
`item_model` and `item_name`. A line that exempts nothing fails the test.

- `loot_table` for `rocket_fuel`, `enriched_lava` and `force_field`: all three are registered with
  `noLootTable()`. The first two are fluid blocks; the force field is the projector's barrier and has
  no item.
- `item_name_key endgame_casing block.advancedrocketrycommunity.advanced_machine_casing`:
  `AdvancedMachineCasingBlock` overrides `getDescriptionId`, so the item shows that key. Without the
  line the check passed on the unused legacy key `block.advancedrocketrycommunity.endgame_casing`
  from the v1.7 language file. To keep this from recurring, the test pins the main sources that
  override `getDescriptionId` (`AdvancedMachineCasingBlock`, and `UnlitWallTorchBlock`, which has no
  item); a new override fails the item name check until its items have `item_name_key` lines.

## Choices where the specification was open

- "Resolves" covers more than items, fluids and tags: blocks, enchantments, recipes, advancement
  parents and loot tables named in the same files, and the plain entries of every tag folder. Each
  is cheap and all resolve today.
- The case check runs across all registries. It cannot fail today, because `ResourceLocation`
  rejects upper-case paths; it is kept because S4 asks for it.
- Only recipes, loot tables, advancements and tags are walked, as S4 says. Other mod data
  (machine patterns, satellite definitions, laser drill tables, biome modifiers, world generation) is
  not.
- The item name check derives the key from the ID instead of creating items, because plain JUnit
  cannot run the deferred suppliers (block items need their block's registry object). The
  `getDescriptionId` pin covers the gap.
- The class has 595 lines, over AGENTS.md's 500-line review mark. It has one job, the S4 checks and
  their report, so I kept it in one class; it is under the 800-line ADR limit.

  guessed; a future block or entity predicate in an advancement needs a small extension.
