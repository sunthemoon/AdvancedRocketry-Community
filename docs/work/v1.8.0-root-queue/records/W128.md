**Order and the stop rule (Q6).** The first code commit is measurement only: `SatelliteRegistryBenchmark` and

server-thread work, so its P95 must be at most 50 ms and its P99 at most 100 ms (docs/17 section 4). If any misses, this
slice stops there: the record reports the measurement, and no coordinator code is written until Root decides. (They
missed; Root decision R121 answered Q6 at the resumption, so the benchmarks are not rerun. See "Resumption" below.)

**Placement.** Pure-Java domain in a new package `rocket/bay/deployment`: the reason enum (the `BayReceipt` reason
grammar, with menu codes), the round-robin step queue keyed by L (32 steps per tick, shared by restart work), the claim
book and member state machine, and the runtime rejection map (4,096 entries, oldest evicted, cleared at stop). The
Forge adapter `rocket/server/BayTransferRecovery` implements `RocketTransferBayRecoveryGate`; `RocketManager` owns it
for one server session (created at `ServerStartingEvent` at LOW priority, after `EscrowRuntime.starting`; dropped at
`ServerStoppingEvent` and on the crash path). `resourceescrow` gains no dependency on it: `BayReceipts` issues one
session handle (put, remove, find, acknowledged, issued sequence, the claims predicate, the rejection map and the
registry permit), and a second request for it throws. New classes stay below 500 lines; `RocketTransferService`
gains exactly one line, `recovery.bays().checkpoint(server, journal, record, source)` before the existing
`recovery.classify` at `ascent_complete`, which reaches a new default `ascentComplete` method of the gate interface.

**D0 (all on the server thread; admission only on the GameTest server and the gated release-test server).** At the
checkpoint the coordinator reads bays from T's source snapshot by adapter ID (at most 128 block-entity visits, cached
per snapshot ID and hash), keeps those holding a package, and enqueues L with a HELD claim at once (Q1); no package, no
claim. Group steps, in order: checked T (`journal.actionable(L)`, `logicalGuard(L)` naming T with a record digest, T
PREPARED; otherwise wait); the live source current at its altitude in TRANSIT, otherwise the claim ends
RELEASED_TO_ORDINARY; the neutral wrapper (epoch 0, no markers, no ledger binding, `escrowIdle`, no escrow logical lock,
floor or tombstone for L and T), otherwise every bay BAY_SOURCE_PROTECTED; writer availability and a blocked registry
(BAY_RECEIPTS_UNAVAILABLE, REGISTRY_BLOCKED); F5 on `plan.sourceBody()` for every kind (legacy `space`, missing or
non-orbitable body: TARGET_NOT_ALLOWED; no catalog: CATALOG_UNAVAILABLE); B14 `absenceStatus(L, snapshot, entity)`
under ADR-074 item 11 (revised at the resumption, R121; see "Resumption" below): PROVED continues;
ASSEMBLY_JOURNAL_PENDING rejects every bay; the first UNPROVED or WRITE_REQUIRED answer sends `requestCheckpoint`, and a
REFUSED request (the writer is unavailable) rejects every bay with ASSEMBLY_JOURNAL_UNPROVED; WRITE_PENDING waits with L's
claim HELD, its tickets renewed and no time limit; UNPROVED after the request rejects every bay with
ASSEMBLY_JOURNAL_UNPROVED; WRITE_REQUIRED after the request (mutated since) requests again; at server stopping a waiting
D0 is discarded without running any effect. Then one step per bay in position order (the first 8;
the rest ROCKET_DEPLOYMENT_LIMIT): package decoding (its availability reasons), bay, package and T owner agreement
(BAY_OWNER_MISMATCH), X already registered (DEPLOYMENT_UNAVAILABLE, Q4), the receipt for X (a blocking, released or
other-package receipt, or a stale REJECTED one at this key: BAY_CONFLICT; an unacknowledged REJECTED one:
RECEIPT_PENDING), and replay-first `SatelliteLaunchService.validate`, whose refusal keeps its code as the reason. Every
D0 refusal is a runtime reason in the rejection map; nothing durable changes.

**D1 and D2.** D1 puts INTENT (new `op`), or re-arms the acknowledged REJECTED receipt of X with the same `op`, new key
and new T context, through the store's `put`, so `tryReserve` and `tryRetain` of the real authority decide; each refusal
maps to its own reason (DEPLOYMENT_CAPACITY, ROCKET_PENDING_FULL, RECEIPTS_FULL, OWNER_RECEIPTS_FULL,
RECEIPT_IDENTITY_CONFLICT). FAILED_BEFORE_REPLACE gives runtime RECEIPT_WRITE_FAILED (the store restores the prior
state); UNKNOWN waits while the writer retries the exact candidate. Completions only mark state and enqueue; they never
write. D2, a queued step after the exact INTENT acknowledgement, revalidates through a new registry permit: the session
handle issues it for an `op` whose RAM receipt is INTENT for X, and `SatelliteMissionSavedData` honours it only inside
one scoped validation call and only for the validation previews; `launch`, `launchIdle` and `decommission` ignore it,
and no public caller can construct one. Every outcome becomes REJECTED: a refusal keeps its code (B9), SUCCESS or
IDEMPOTENT becomes DEPLOYMENT_UNAVAILABLE (Q4). A definitely failed REJECTED write is requeued; nothing times out.

**Exits (Q1).** When no member of L is INTENT or awaiting its REJECTED acknowledgement (D0 rejected every bay, an
INTENT write failed definitely, or the last REJECTED was acknowledged), the claim ends: READY_SOURCE(S) while S is
loaded and current, otherwise RELEASED_TO_ORDINARY; each is reported once by `claim`, which then forgets L. While held,
the coordinator renews T's recorded flight tickets on both ends each tick, without loads. **Restart rows**, classified at
`ServerStartingEvent` before the first tick: INTENT with T present, PREPARED and matching the receipt's owner and before
hashes, and X absent, becomes REJECTED (INTERRUPTED), then RELEASED_TO_ORDINARY once no blocking receipt names L; a
differing tuple becomes durable REPAIR (REGISTRY_SIGNATURE_CONFLICT); a blocked registry holds as runtime
REGISTRY_BLOCKED; an equal X, a REGISTERED or a released receipt waits unchanged at runtime; INTENT whose T is missing
or different holds as runtime REPAIR (TRANSFER_AUTHORITY_CONFLICT) with no write; REPAIR holds; REJECTED claims nothing.

**Gate lock (Q3, Q8).** `RocketEscrowGate.idle`, `logicalLocked` and `resourcesIdle` add a bay part; `escrowIdle` and
`escrowLogicalLocked` stay escrow-only. The bay part is `BayReceipts.holdsRocket(server, L)`: a coordinator claim on L
(including a pending handoff), or a blocking or released receipt naming L in any state; while the index is NOT_LOADED

`RocketFlightService.passengerMutationAllowed` (board, leave), `RocketTransferService` (`cancelCountdown`,
`resourceMutationAllowed`, so launch, loaders and disassembly), `LoaderEligibility`, `RocketCargoPreparations`,
`RocketCargoBindingChecks`, `RocketFluidCargoLinker`, `RocketItemCargoLinker`, `EscrowFluidCargoAdmission` and its item

`RocketTransactionRecoveryService` (two sites), the retained-release access and world callers `RocketReleaseAccess`

### Choices

- (choice) **Budget reading.** Each measured call is a whole server-thread operation inside one tick, so the P95 and
  P99 of the calls are held to the tick budgets. This is the conservative reading of "against docs/17 P95 and P99". A
  tick-frequency reading would still miss: one checkpoint tick of about 410 ms is eight times the P95 budget.
- (choice) **Registry fixture.** The root is filled with missions, and 32 registrations rotate per sample, so the root
  stays at the bound. Registrations are real `launchIdle` calls, decommissioned untimed afterwards.
- (choice) **Transaction fixtures.** The maximum is the largest equal padding at which 256 records fit the checked
  bound. The typical case is one 2,048-block record without block-entity padding.

### The design change (committed before code)

D0's B14 step in the one-page design above now follows ADR-074 item 11 and
[W129-DESIGN](W129-DESIGN.md) section 5.1. The coordinator asks `absenceStatus(L, snapshot, entity)` once per group
step, with T's logical rocket ID, T's source snapshot ID and T's source entity UUID:

| Answer | Before the group's request | After the group's request |
|---|---|---|
| PROVED | Continue to the per-bay steps. | Continue to the per-bay steps. |
| ASSEMBLY_JOURNAL_PENDING | Reject every bay with ASSEMBLY_JOURNAL_PENDING. | The same. |
| ASSEMBLY_JOURNAL_UNPROVED | Send `requestCheckpoint`. | Reject every bay with ASSEMBLY_JOURNAL_UNPROVED. |
| WRITE_REQUIRED | Send `requestCheckpoint`. | Send `requestCheckpoint` again (mutated since). |
| WRITE_PENDING | Wait. | Wait. |

- `requestCheckpoint` answering REFUSED means the writer is unavailable (a blocked or unreadable journal, or a
  stopping server). It rejects every bay with ASSEMBLY_JOURNAL_UNPROVED at once. This is the writer's availability
  joining D0's existing checks: it sits with the receipt writer's availability and the blocked registry in the group
  steps, before B14.
- A waiting group keeps L's claim HELD, and the coordinator renews T's recorded flight tickets each tick, as for every
  held claim. There is no time limit and no limit on repeated requests.
- At server stopping (`ServerStoppingEvent`, or the first observation of `server.isStopped() || !server.isRunning()`),
  the coordinator latches, discards every waiting D0 and every queued step, and runs no further effect
  (W129-DESIGN section 4.6). Its claims stay held in RAM until the session ends; nothing is written for them. Before D1
  no receipt exists, so at the next start T is UNCLAIMED and ordinary recovery applies; after D1 W27A's restart rows
  apply.

Differences from W27A-DESIGN section 9's B14 sentence ("require its exact checked write before D1; failure rejects
all bays"):
1. The checked write is a request answered on a later tick, not a synchronous write inside the step.
2. A stale NOT_COMMITTED or UNKNOWN outcome from an earlier write no longer rejects at the first query. It sends a
   request, and only an UNPROVED answer after that request rejects. WRITE_PENDING masks the stale outcome, so the
   first other answer reflects a capture taken at or after the request (ADR-074 item 8).
3. A writer that refuses the request rejects at once rather than after a failed write.
4. The ASSEMBLY_JOURNAL_PENDING half ("a record for L actually remains") is unchanged.

Every other B14 answer keeps its meaning, and the rest of the one-page design is unchanged.

**Q6 is answered (R121 item 2).** The registry benchmarks gate only W27d2's registry writes, which W129b and W129c
cover, so they are not rerun. W129a's B2 measured the transaction request on the server thread (P99 0.22 ms at the
bound); the IO write is not a server-thread cost, so it is not measured again.

  `EscrowRuntime.starting` indexed the receipts) and installs it into the transfer service's dispatch. At
  `ServerStoppingEvent` the coordinator closes its step queue and runs nothing more; its RAM claims stay held until
  `ServerStoppedEvent` clears the manager. The crash path has no stopping event: every step also checks
  `isStopped() || !isRunning()`.
- (choice) **Claim answers.** `claim` answers HELD for a coordinator claim (REPAIR for a record of L naming another T,
  as section 8.1 says), reports an ended claim's handoff once for its own T, and otherwise answers HELD exactly when the
  bay part of the gate lock holds L (`BAY_RECEIPT_HOLD`, or `BAY_RECEIPTS_UNAVAILABLE` while the index is NOT_LOADED).
  `beforeAction` answers HELD exactly when the bay part holds L; W27d1 issues no PERMIT. So an UNCLAIMED record never
  meets the bay part (N1). The claim's own reasons (`BAY_VALIDATION`, `ASSEMBLY_JOURNAL_CHECKPOINT`,
  `BAY_RECEIPT_WRITE`, `BAY_RESTART`) are diagnostics only and never persisted.
- (choice) **The live source** must be loaded, current for T and in TRANSIT for T at exactly the altitude position.
  When it is not (group step 1 or 2), every bay gets the runtime member reason `SOURCE_UNAVAILABLE`, which is not put in
  the rejection map, and the claim ends RELEASED_TO_ORDINARY, so ordinary recovery handles T.
- (choice) **Validation codes** stay the receipt reason verbatim (B9). Codes without their own status entry show
  `LAUNCH_REFUSED` in the menu; a missing launch service gives `SERVER_ERROR`. An INTENT receipt carries the reason
  `NONE`, shown as the new status reason NONE (code 0).
- (choice) **Re-arm** keeps the receipt's op, sequence, created tick, preexisting flag and registry epoch, and takes the
  new key, T, before hashes and orbit body; attempts grow by one up to `BayReceipt.MAX_ATTEMPTS`.
- (choice) **The exit** waits, one step per tick, while any pending receipt still names L in any state, so
  RELEASED_TO_ORDINARY and READY_SOURCE come only once no blocking receipt names L.
- (choice) **Restart rows** are claimed at `ServerStartingEvent` (one claim per rocket named by an INTENT, REGISTERED,
  REPAIR or released receipt); each INTENT row is decided and written by a queued step from the first tick. REGISTERED
  and released receipts hold with the claim reasons `DEPLOYMENT_PENDING` and `RELEASED_FLIGHT` (W27d1 creates
  neither). Receipts of one rocket naming different transfers hold as REPAIR (`TRANSFER_AUTHORITY_CONFLICT`). The row
  order is: blocked registry, then T's identity, then X.
- (choice) **Tickets.** Only a claim this session started at the checkpoint renews T's flight tickets: the origin
  column with `refreshOriginTicket` and the destination ticket set with the new `refreshDestinationTickets`, neither of
  which loads a chunk. A restart claim has no source authority and renews nothing (R1 is W27d2's).
- (choice) **Bounds.** At most 256 claims (four times the 64 pending operations); a checkpoint past it refuses every
  bay with `DEPLOYMENT_CAPACITY` and claims nothing. The snapshot bay cache keeps 64 snapshots.
- (choice) **The neutral wrapper** check is `RocketEscrowGate.bayNeutral`, inside `resourceescrow`, because the
  ledger's floors, tombstones and authority heads are package-private there.
- (choice) **Native cut seam.** `BayReceiptCommitCut` wraps the receipt committer only on GameTest and gated
  release-test servers. It can pause before or after the move, or throw before the move (UNKNOWN; the writer retries
  the exact candidate). A definite FAILED_BEFORE_REPLACE cannot come from a committer, because the writer counts any
  committer throw as attempted, so B12_FAILED puts a directory at the staging path instead. `BayReceipts.stop` and
  `abort` release a paused cut first, so a drain or the crash path's join can finish.
- (choice) **A1's solar bay.** The fixture owner has no lifetime research, so validation refuses the shipped solar
  satellite at D0 (`RESEARCH_LOCKED`) and only the data bay reaches INTENT. The test takes the expected code from the
  launch service itself.

### Choices where the TASK was open

- (choice) **B10's first start ends with a clean stop**, as B18_INTENT does. After a kill the source entity is not on
  disk (the earlier B1_MOVED restarts showed `rocket=NONE` until ordinary recovery rebuilt it), so only a saved source
  can show the rocket locked at altitude.
- (choice) **The blocked registry is the coordinator's view**, not a blocked registry file: an invalid registry file
  refuses startup, and the receipt fence refuses registering a conflicting X while INTENT exists. The REPAIR row is
  covered by the GameTest, where X can be registered before the receipt exists.
- (choice) **The TRANSIT resource row checks the gate**, not an entity update. In TRANSIT a native fuel change cannot
  be built (`RocketFlightData.withFuel` drops the plan, which an active state requires), so the row asserts
  `resourcesIdle` and `resourceMutationAllowed`, which every resource-changing path reads. The at-rest test keeps the
  entity-level refusal.
- (choice) **The N5 test counts the owner's retained slots**, because the other test of its batch changes the server's
  count concurrently.
- (choice) **New batches.** The section 8.1 test (`bay_deployment_hook81`), the refused request (`bay_deployment_b14`)
  and the loader saturation (`bay_loader_saturation`) each run alone in their batch, because they read server-wide
  state: the warp classification, the transaction journal's acknowledgement and the 64 shared slots.
