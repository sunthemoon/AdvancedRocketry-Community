# W210: synchronous C1 admission sizing

## Design note, before implementation (2026-10-30)

This task starts from `4e9a29487e12167de966b8632015e1f0660ea8b5`, clean on
`codex/v1.8.0-w210`. Its write scope is transaction-journal admission sizing,
the corresponding unit tests, W210 measurement scripts/diagnostic helpers,
and this record. Root owns independent review, integration and push. No
upstream code or asset is imported. No schema, file format, byte/count bound,
deadline, writer capture/publication, ADR, status file or ledger changes.

The first native C1 marker pair brackets `SealedJournalEntry.retain`, including
both `canAppend` and `journalFor(...).write(...)`. Before the change, admission
encodes every resident snapshot, performs the snapshot codec's native-write
size check, then walks the encoded entry with `BoundedNbt.measure`. The latter
also checks native tag classes, modified UTF, depth and node bounds. The write
only checks identity/capacity, replaces one immutable entry and marks dirty.
W208 measured 302-485 ms for this whole retain near 64 MiB versus 0.915 ms for
the small root. A separate pre-change diagnostic measures encoder, measurer,
admission and RAM insertion CPU, wall time and thread allocation; results
are recorded below before the implementation commit.

The remedy is a journal-owned, bounded table of exact sizes for resident
immutable entry versions. On insertion/replacement and successful decode,
measure only that entry using the unchanged canonical encoder and bounded
measurer. Store its identity and numeric count, not NBT or serialized bytes.
Admission keeps the same empty-root framing and the same resident iteration,
subtracts the three-byte named-root header per list child, and always encodes
the candidate normally. Count/duplicate/operational checks still precede any
sizing. The first admission after reload is therefore not a deferred whole-root
scan. Each mutation pays at most one entry's encoding, not all resident entries.

Every successful write replaces the old size; removal drops it; failed load
clears it. A reference-identity check prevents a size for a replaced entry
from being reused. `setDirty`, save encoding and writer publication do not
change entries and need no invalidation. Failed/UNKNOWN writes cannot grant
authority through this table: it describes RAM only and never participates in
acknowledgement, dirty-state or disk-proof decisions. It is rebuilt from decoded
canonical entries, never trusted from raw on-disk size or unknown fields.

An entry that cannot be measured is not cached. Eager measurement must not
introduce a new mutation/load refusal: a runtime encoding failure leaves the
entry uncached, and admission falls back to its old encoding/check behavior.
The existing `IllegalArgumentException` refusal remains; other runtime failures
still propagate when admission reaches that entry. Unsuccessful replacements
must leave the prior entry and size intact. Candidates are never retained in
the table, including rejected candidates and retries. Exactly-at-bound roots
remain admissible, one-byte-over roots refuse, the 256-entry limit and duplicate
ID refusal are unchanged, and a maximum-size candidate still undergoes every
snapshot and entry validation.

The additional retained memory is at most 256 map nodes and small size/identity
records (estimated below 32 KiB with compressed references), sharing IDs and
entry objects already owned by the journal. Removed/replaced entries are not
retained by the table. Transient encoding remains bounded to one entry. No
global cache, persisted size field, mutable NBT witness or new framework is added.

Verification uses failing-first allocation/work regressions and full-re-encode
equivalence for fresh/reloaded roots, every mutation path, failures/UNKNOWN,
byte/count edges, rejected retries and maximum snapshots. Native before/after
JARs come from committed source and use W208's unchanged operation/recovery
protocol under the machine lock, with supplemental CPU/allocation/JFR
observations only in diagnostic exports. Whole ticks and completion latency
remain authoritative, including both halves of retain. Three sealed/journal
GameTest runs and the whole unit suite follow. Docs/17's 25/50/100 ms mean/P95/P99
and 500 ms spike comparison is reported without claiming reference-node or
soak qualification. Required Gates remain unapproved.

### Pre-change attribution

The isolated diagnostic on the starting production source used Java 17.0.7,
`-Xmx4G` and the heavy-JVM lock. For the 67,100,518-byte W208 root, four admission
calls took 294.320/207.028/177.032/179.152 ms and allocated about 383.2 MB each.
Separate resident encoding took 143.296-146.447 ms and allocated 314,335,520
bytes; the bounded measurer took 35.243-35.790 ms and allocated 67,568,880 bytes.
CPU counters were 187.5-281.25 ms for admission and 140.625-156.25 ms for
encoding; the Windows thread CPU counter is coarsely quantized (15.625 ms).
RAM insertion itself took 0.052 ms and allocated 112 bytes. These are distinct
passes, not additive exact shares of a single native operation. The diagnostic
candidate has 2,048 blocks and is larger than the root's remaining margin;
admission therefore exercises the complete resident scan before refusal, and
insertion is timed separately, not asserted to be an admitted operation.
