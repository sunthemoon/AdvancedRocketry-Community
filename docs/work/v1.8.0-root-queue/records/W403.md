### Tick data source and its hard limit

The packaged server must be started with
`-Dadvancedrocketrycommunity.releaseTestHooks=true`. Both inspected release-test
command classes require permission level 2; use the server console. The sampler
issues only `arce satellite release-test perf ticks`, or, with `reference=True`,
`arce endgame release-test refload status`. It never issues the mutating build,
drive, advance, flush or worst-case commands.

The satellite reply starts `ARCE_RELEASE_TEST ticks` and prints `window=100`, the
server `tick`, mean/p50/p95/p99/max milliseconds, satellite-post p99/max and registry
counts. It adds vanilla tick timings to satellite post-tick work before sorting.
It **does not export the 100 individual durations or their ordering**. The
reference-load reply prints device/queue/player figures and an average `mspt`,
with no per-tick durations or tick number. Neither inspected command can supply
the requested raw per-tick stream without a product change, which is out of scope.

The implemented fallback polls every second, accepts intervals of 0.1 to 1 second,
deduplicates an identical tick number, preserves each returned window's figures,
and records overlap and gaps inferred from endpoint tick-number differences. A
delta above 100 exposes a missed window; wall-clock polling cannot guarantee
coverage when the server or channel stalls. The channel must impose its own bounded
reply timeout. Overlapping window averages cannot be de-overlapped. Thus the summary
labels its mean as an **unweighted mean of sampled window means**; raw tick count,
whole-run p95/p99/max and consecutive over-threshold tick runs are `null` (not
available). The largest returned window maximum is a separately labelled figure.
Startup windows may be incompletely populated. A server tick reset requires a new
CSV. Pure per-tick arithmetic tests do not qualify unavailable live measurements.

W399 can call `sample_ticks(channel, csv_path, duration=600, threshold_ms=500)`
after its discarded two-minute warm-up and persist the returned summary beside
the CSV and workload description. The threshold is a reporting argument, not a
new budget. Matched comparisons use the same world, machine, cell and sampling
plan, with two baseline runs. C4's four sampled hours, 30-minute flushed saves and
two-hour orderly restart remain harness scheduling parameters; restart halves get
separate CSVs and process handles. The force-load helper only queries vanilla
persistent tickets per named dimension; it cannot prove absence of every Forge
or transient mod ticket. Preserve replies and investigate against the baseline.

### JFR, host and evidence usage

For later locked C4 runs, the harness wraps its own server handle in
`CampaignJvm(server_popen, "server")`. `start_jfr` defaults to a 600-second,
128-MiB-retention profile; accepted bounds are 1 to 14,400 seconds and 16 to
256 MiB. `stop_jfr` uses the named recording and its evidence-root output. If the
bounded recording already finished, retain that file rather than overwrite it.
JFR chunk retention is not a strict final-file byte ceiling. The offline procedure
preserves filtered `jfr print --json --events
jdk.GCPhasePause,minecraft.ServerTickTime` output. It totals only top-level GC pause
events, avoiding nested phase double-counting. Minecraft tick events, if enabled,
contain event averages, not individual-tick percentiles. The tested JSON is
hand-made; no real recording or live attachment was used.

Example later evidence commands (not executed against the campaign root here):

The identity input contains `git_commit`, `jar_sha256`, `forge` and `java`.
The run input contains exactly the fields in docs/15 section 15. Windows swap is

VNC ports also require manual configuration review. Exit 0 does not resolve MANUAL
items. Existing host records and checksum seals are not replaced; corrections
need new files and Root's recorded resealing procedure.

### Client heap and cache observation steps

Use only W399's disposable, harness-started client `Popen` handle, never an owner's
already signed-in client. Record a matched empty-scene baseline, then the same
rocket scene, before and after a resource reload, and before and after an ordinary
dimension change. At each settled observation point, use allowlisted
`GC.heap_info` and, outside timed frame windows, `GC.class_histogram -all`; save UTC
labels and the relevant rocket snapshot/reassembly and OBJ-entry class counts and
bytes. Repeat the baseline twice and keep settings and waits identical. Histograms
are intrusive, include unreachable objects with `-all`, and cannot expose cache
keys, retained references or GPU allocations. They are cache-growth proxies, not
proof that a cache is empty or freed; unavailable cache-internal readback remains
NOT_COVERED. Do not force GC, dump heaps, use client JFR, read JVM arguments or scan
for clients. The owner's signed-in clients may contain access tokens in their
arguments and are outside the campaign's ownership and lifetime boundary.
