### 2.1 The warm-up

**Ticket and state.** One plain `TicketType<UUID>` named `arce_rocket_warmup` (natural order, vanilla lifespan 600, the
ceiling), never forced or saved. A warm-up W adds one region ticket at distance 2, keyed by the logical rocket L, on
each column of the selected destination's checked set (at most 16, from W90a's `RocketDiscoveryColumns`), in the
destination Level, exactly once at its start. The RAM record holds L, the initiating player (none for admin and
release-test launches), the source Level, entity and snapshot identity, the destination target, the selected
destination snapshot (its Level, exact region and columns), the starting request ID, the start tick, the lifetime
captured at allocation, the state and, while BOUND, T. The map is keyed by L, so there is one warm-up per rocket.

**When BOUND starts (R22 amendment 4).** The decision runs in `prepareLaunch`'s governed branch immediately before
`EscrowGovernedPreparation.begin`, after every existing check and the server's pad selection. W becomes BOUND when
`begin` returns true for a request whose decision named W (F1 accepted T = that request ID). If `begin` returns false,
W is released (`LAUNCH_ENDED`). A `discarded` callback that runs synchronously inside `begin`, before it returns, is
recorded, and the acceptance then releases W instead of binding it.

**The decision (design 7.2 with R22 answers 1 and 2).** "Ready" is the census's own readiness predicate
(`RocketTransferEntities.endAlreadyLoaded`) on the selected destination; "slot" is fewer than the global cap in every
state together and, for a player request, fewer than the per-player limit for that initiating player.

- If `begin`'s read-only preconditions fail, nothing is allocated or bound, an existing W runs to its deadline, and
  the request continues to `begin` exactly as before W90b.
- A BOUND W belongs to its launch and is never replaced; such a request also continues to `begin` without a warm-up.
- A W for another Level, region or source geometry is released first (`REPLACED`), then the "no W" rows apply.
- No W and a slot: W starts; a ready destination calls `begin` at once and binds on acceptance, a cold one answers
  `DESTINATION_LOADING`.
- No W and no slot: a ready destination calls `begin` without a warm-up; a cold one answers
  `DESTINATION_LOADING_LIMIT` and nothing is allocated.
- The same W, ready: `begin`, then bind or release. The same W, cold: `DESTINATION_LOADING`, with no ticket call, no
  new key and the start tick, starting request and deadline unchanged.
- A `DESTINATION_LOADING` or `DESTINATION_LOADING_LIMIT` refusal releases the request's tentative named-pad claim at once
  (`LandingPadService.release(server, plan)`), so no saved claim survives the wait.

**The kept pad (R22 amendment 1).** For a surface destination, when L has a WARMING or READY warm-up for the same
destination Level and target and the same source snapshot (ID and content hash), `RocketGovernedAdmission` passes W's
stored origin to `RocketLandingPadSelector.select`. The selector finds the fixed candidate with that origin and
evaluates it first with every ordinary check (surface, terrain, occupancy and every other journal, pending, landed and
warm-up reservation). Only when that candidate is invalid does ordinary selection run, over the remaining candidates in
their usual order. Station default pads and named pads have one candidate each, so their selection is already the
exact candidate: the named pad's identity, claim and loaded-only rules all run again. The decision then compares the
selected region with W's: the same region keeps W, its tickets and its deadline.

**The starting request (R22 amendment 2).** While W lives, in any state, `RocketGovernedAdmission` refuses its stored
starting request ID with `REQUEST_REPLAYED` before pad selection, for every launch and both entries. The actual replay
semantics are these. The player entry's `RocketOperationLedger` is process-local and bounded: it refuses a retained ID,
evicts completed entries once it holds 4,096, and is cleared with the runtime, so a FAILED `DESTINATION_LOADING`
request is refused only while the ledger still holds it. The trusted admin and release-test entry never consults that
ledger; it is reached only from server code. The warm-up check closes both gaps for exactly the warm-up's life. After
W ends or the process restarts, today's revalidation applies and no replay history is persisted.

**Reservations (design 7.4).** `prepareLaunch`'s reservation list, which already feeds every surface, station and named
selector, legacy launches included, gains the region of every live warm-up except the requester's own. From the bind,
F1's pending entry for L reserves the same region until F2, and from F2 the journal entry does; the journal's own
overlap guard stays the final guard.

**Release (design 7.6 and R22 amendment 4).** Each release removes the warm-up ticket on each started column in W's own
Level (found by key; an absent Level is skipped) and drops W and its reservation in the same call. Only the live entry
can be released, so a stale event never removes a later warm-up of the same rocket.

| Event | When | States |
|---|---|---|
| `HANDOVER` | Right after T's ACTIVE margin refresh that ticketed at least one column, in the same dispatcher visit | BOUND |
| `LAUNCH_ENDED` | `begin` refuses, or the launch's `discarded` callback runs (also after `journal.put`) | BOUND, or the W the decision named |
| `REPLACED` | A later request for L selects another Level, region or source geometry | WARMING, READY |
| `DISCONNECTED` | The service tick finds the initiating player offline | WARMING, READY |
| `ROCKET_REMOVED` | The service tick finds the source entity missing or removed in its source Level | WARMING, READY |
| `EXPIRED` | Age at least the captured lifetime (600 by default); the vanilla purge at age above 600 is the backstop | every state |
| `STOPPED` | The runtime is cleared; while the server runs on its thread the tickets are removed first, otherwise the map is dropped with the stopping Levels | every state |

A `discarded` callback is no proof that nothing was published: `EscrowGovernedPreparation.prepare` passes it to the
countdown effect after `journal.put`. It therefore releases only the warm-up bound to exactly that T, never journal,
pending or named-pad authority, which the warm-up does not own. A BOUND W whose T never reaches a successful ACTIVE
refresh (held, routed to HOLD, or both Levels not present) ends at its deadline.

**The service tick (TASK item 4).** `RocketTransferService.tick` calls `warmups.tick(server)` as its first statement,
before the journal's early returns at `:287-289` and `:294`, so deadline, disconnect, removal and readiness polling run
whether or not the journal is blocked. It is one inserted line, three lines away from W91's change of `:294`.

**Fresh revalidation (design 7.7).** The relaunch repeats every check from the rate limiter to selection and both
budgets, and F1 and F2 then evaluate the unchanged `RocketGovernedLaunchBoundary.allows`. W's tickets and its READY
state are never evidence for any check.

**Player text, logs and inspect (design 7.8).**

| Key | English | Chinese |
|---|---|---|
| `flight.advancedrocketrycommunity.request.destination_loading` | Preparing the destination; launch again when it is ready | 正在准备目的地，就绪后请再次发射 |
| `flight.advancedrocketrycommunity.request.destination_loading_limit` | Too many destinations are being prepared; try again shortly | 正在准备的目的地过多，请稍后再试 |
| `message.advancedrocketrycommunity.flight.destination_ready` | Destination ready; launch again to depart | 目的地已就绪，请再次发射 |

- The service tick polls each WARMING warm-up (at most 16 column reads); the first time its margin is loaded and
  entity-ticking it becomes READY and the initiating player, if online, gets the READY message once on the action bar.
- One INFO line per transition, at most four per warm-up: `ARCE_GOVERNED_WARMUP event=<STARTED|READY|BOUND|RELEASED>
  logical= request= transfer=<T|none> level= columns=<n> age=<ticks> reason=<none|HANDOVER|...>`. No WARN, so the log
  checker needs no warm-up expectation.
- `/arce rocket inspect <uuid>`: without a journal entry for that ID but with a warm-up for logical rocket `<uuid>`, one
  line `Warm-up logical= state= request= transfer= level= columns=k/n age= remaining= player=`. The transfer line gains
  ` warmup=BOUND remaining=<ticks>` while a warm-up is bound to it and ` warmup=none` otherwise. Both read RAM and the
  loaded index only.

### 2.2 Operator settings (R22 amendment 3)

Three COMMON values in a new `rocketFlight` section, each able only to lower its fixed ceiling in
`RocketWarmupSettings`:

| Key | Default | Range |
|---|---|---|
| `rocketFlight.destinationWarmupsGlobal` | 8 | 1 to 8 |
| `rocketFlight.destinationWarmupsPerPlayer` | 2 | 1 to 2 |
| `rocketFlight.destinationWarmupTicks` | 600 | 200 to 600 |

The decision reads them at each allocation (`CommonConfig.destinationWarmupSettings()`, the ceilings until the config
loads). A warm-up captures its lifetime at its start, so a change applies to the next allocation and never shortens,
extends or renews a live deadline; a lowered cap refuses new warm-ups until the live count is below it and ends none.
The flight-ticket bound stays `MAX_LANDING_CHUNKS`. A new configuration logs one "corrected from null" WARN for the
section and each key: four exact expectations, and the section is excluded from the generic rule, whose maximum stays
99.

## 4. Unit tests

`RocketWarmupRegistryTest` (18) drives the server-free registry with a recording ticket sink that models ticket
equality and a fake clock:

- a cold start adds exactly the checked set once, in its own Level, with one STARTED line;
- five repeated requests for the same destination make no ticket call and keep the start tick and the starting request;
- a ready destination starts, then binds on acceptance or is released on refusal;
- the global cap counts WARMING, READY and BOUND, a cold ninth gets LIMIT with no ticket call, a ready ninth proceeds
  without a warm-up, and one release lets a cold ninth start;
- the per-player limit counts every state, a cold third gets LIMIT, a ready third proceeds unbound, other players and
  admin warm-ups still start, and a one-per-player setting applies to the next allocation;
- a replacement removes the old set before the new set is added (the recorded call order) and logs REPLACED;
- each of the seven release events removes exactly its set in its own Level, drops the reservation and logs its reason;
- expiry at the captured lifetime (alive at age 599, released at 600), and an absent Level gets no ticket call;
- reservations exclude only the requester's own warm-up;
- disconnect and source removal end WARMING and READY, while a BOUND warm-up survives both and hands over;
- the kept pad is offered in WARMING and READY for the same Level, target and source only, and not once BOUND;
- R22 amendment 2 with the real `RocketOperationLedger`: the immediate replay is refused by both; after 4,096 later
  completions the ledger has evicted the FAILED entry while the live warm-up still refuses it; a runtime reset clears
  both, so today's revalidation applies; after expiry the registry refuses it no longer;
- a discard releases only the warm-up bound to exactly that transfer (another T or another L does nothing, and the
  post-publication discard makes only the four warm-up removals), and a discard during `begin` prevents the bind;
- a stale handover or discard of an expired warm-up never removes a later warm-up of the same rocket;
- a settings change applies to the next allocation only: a lowered cap refuses while the old warm-up keeps its 600-tick
  deadline, and the next warm-up gets the lowered 200-tick lifetime;
- the READY message is sent once, and one warm-up writes exactly STARTED, READY, BOUND and RELEASED;
- failed `begin` preconditions allocate and bind nothing and leave an existing warm-up to its deadline;
- settings outside the ceilings are rejected.

`CommonConfigTest` counts 100 values (was 97) and checks each new key's default and range.

## 7. Choices where the design was open

1. **Disconnect detection.** Design 7.6 names `RocketFlightService.onPlayerLoggedOut`. The service tick instead looks the
   initiating player up once per warm-up and tick (design 7.9 budgets one player lookup), so a logout releases WARMING
   and READY warm-ups within one tick, with the server at hand for the ticket removal, and no logout hook is needed.
2. **What "the same destination" means.** The same destination Level, the exact selected region and the same source
   snapshot (ID and content hash). A changed surface height at the kept pad therefore selects the same pad with another
   region and replaces the warm-up; a moved or rebuilt rocket never inherits one.
3. **The kept pad applies to surface selection only.** Station default and named pads have one candidate each, so their
   ordinary selection already is "that exact candidate" with every check.
4. **The stored starting request is refused for every launch**, governed or legacy, player or admin, while its warm-up
   lives: the most conservative reading of R22 amendment 2, at the cost of at most eight IDs.
5. **BOUND starts on `begin`'s acceptance**, as design 7.2 says; a `discarded` callback that arrives during `begin` is
   remembered and turns the acceptance into a release.
6. **The handover needs a refresh that ticketed at least one column.** W90a's refresh returns zero when a Level is
   missing or an end is not admissible; such a visit does not hand over, and the warm-up ends at its deadline.
7. **A warm-up starts on a ready destination only with a slot**, and its tickets are added before `begin`; a ready
   destination without a slot launches as before W90b (R22 answer 1).
8. **Settings.** The ceilings live in `RocketWarmupSettings` rather than `RocketFlightLimits`; the vanilla ticket
   lifespan is the 600-tick ceiling, so a lowered lifetime is enforced by the service and the vanilla purge stays the
   backstop at the ceiling. The settings are read at each decision, and a lowered global cap ends no live warm-up.
9. **Runtime clear.** `RocketTransferService.clear()` releases every warm-up with its tickets while the server is running
   on its own thread (in-process fixtures). On a real stop (`ServerStoppedEvent`) the server no longer runs, so the
   map is dropped and the tickets go with the Levels; one RELEASED line with reason `STOPPED` is still written.
10. **Post-publication discard in a GameTest.** A cut that throws once at `F2_PREPARED_ACK` is the only deterministic way
    to make the countdown effect fail after `journal.put`; a census change before that point would discard before
    publication instead. The cut removes itself before throwing, so it cannot reach another flight, and the journal's
    existing ERROR line gets one expectation.
11. **Product-entry scope of R22 amendment 2's tests.** The completed-ledger rollover cannot be driven through the
    player entry within one warm-up's 600 ticks (8 intents per 20 ticks per player against 4,096 entries), so it is a
    unit test against the real `RocketOperationLedger`, as is the ledger half of the runtime reset. The immediate replay
    runs through both entries in GameTests, and the warm-up half of the runtime reset runs in the capacity GameTest.

## 10. Known risks

- **Ticket load.** At most 8 warm-ups of at most 16 columns each, 128 tickets in all, each added once and removed once,
  plus at most 152 bounded lookups per tick (design 7.9). A cold destination may need its margin generated by the
  world-generation workers. Not yet measured (section 9).
- **A BOUND warm-up whose T never reaches a successful refresh** (held, routed to HOLD, a missing Level) keeps its
  tickets and reservation to its deadline, at most 600 ticks; the journal entry then reserves the region as before.
- **Readiness can be lost between READY and the relaunch** only if W's own tickets are removed; any other loss makes the
  relaunch answer `DESTINATION_LOADING` again with the same warm-up and deadline.
- **Merge with W91.** A trial `git merge-tree` of this branch with `codex/v1.8.0-w91-p1-f3` merges
  `RocketTransferService` cleanly (793 lines, every hook in place); its only conflict is the pinned ERROR total and its
  comment in `tests/test_check_gametest_log.py`, which needs both additions. W91's journal changes keep passing the
  same `completion.discarded()` to the governed discard callback, which is where the warm-up observes it. The discard
  GameTest relies on the journal catching an exception thrown by an acknowledged effect; if W91 changes that, the
  fixture needs another way to fail the effect.
- **Test cut.** The discard GameTest installs the exclusive escrow test cut; it removes itself when it fires, and the
  test removes it on a refused relaunch or after 400 ticks without the effect.
- **GameTest environment.** The five new batches each wait until their pads are cold and no earlier warm-up lives; a
  leftover ticket from a failed earlier test can only delay them to their timeouts.

**ADR-065**, under "The section 8.1 hook", replacing revision 2's warm-up bullet:

- **Destination warm-up (W90b, Root decisions R21 item 4 and R22 amendments 1 to 4).**
  - Immediately before F1's begin, after every existing check and the server's pad selection, and only when F1's
    read-only preconditions hold and a slot is free (a global cap and a per-initiating-player limit, each counting
