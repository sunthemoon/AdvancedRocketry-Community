# W115: structural decoding for durable fluid payloads

## Plan (committed before any code)

Base `91b9d665` (W110 and W110F merged), clean worktree `D:/GitHub/arce-v180-w115`. Authority:
[TASK-W115](../TASK-W115-FLUID-STRUCTURAL-DECODING.md) and Root decision R39 as recorded in R-035. This is a
persistence slice; an independent read-only review follows before merge.

**The defect.** Startup (`ManagedSavedDataPayloadValidator.java:33`, `ResourceEscrowSavedData.java:19`) decodes the
ledger through `EscrowCodec.operation` (`:54`) into `EscrowOperation`'s constructor. Its fill branch
(`EscrowOperation.java:43-50`) and its cargo branch, through `EscrowCargoPayload.decode` (`EscrowCargoPayload.java:51-55`,
constructor `:31-44`), look the Fluid up and require the native round trip, so a removed or renamed Fluid refuses the
world as `INVALID_SCHEMA`.

**Design.** No bound, field set, hash, saved format, schema version or dictionary changes.

1. New public `EscrowFluidCodec`, beside `EscrowItemStackCodec`. `validateStructure` checks the bound (8,192 bytes,
   depth 12, 384 nodes), the exact field set, the canonical ID syntax, an int `Amount` of 1 to 1,000 and a compound
   `Tag`; it never touches a registry or builds a `FluidStack`. `validateNative` adds the registry lookup, non-empty
   and the exact canonical round trip, and returns the `FluidStack`. Both throw `IllegalArgumentException` as today.
2. `EscrowOperation`: the fill branch uses `validateStructure`; the cargo branch reads its cursor through a new
   structural `EscrowCargoPayload.validateStructure`. New `Kind.fluid()` and `nativeFluid()`, the one native check
   for fill and fluid cargo operations.
3. `EscrowCargoPayload`'s constructor and `decode` stay native, so an `EscrowCargoPayload` object, which is what
   eligibility and `RocketCargoMutation` act on, exists only after the native check. W110F kept
   `EscrowItemStackCodec.decode` native the same way; existing assertions stay unchanged.

Cargo C2, O2 and readback do not exist (the driver answers `RECONCILIATION_UNIMPLEMENTED`,

**Scope of a hold (AGENTS 3.3).** Held: one operation, phase `REPAIR` with reason `OTHER_STATE`, the existing manual
state that the scheduler (`EscrowReconciliationScheduler.java:97-99`) already sets for C2 refusals. Its endpoints stay
locked, and under the existing rules operations chained behind it on the same endpoints wait; other components, the
ledger, its writer and the world continue. Duration: until audited settlement or offline repair; restoring the mod
before the first C2 attempt avoids the hold, after it the hold is sticky. Logs: one new WARN
`ARCE_ESCROW_FLUID_UNAVAILABLE` per refused C2 attempt, at most once per operation per session until the REPAIR is
persisted, plus the existing scheduler WARN. Before the check the driver only captures read-only and prunes markers
of already retired operations (C8, no resources change).

**Tests.** A new class, run first against the commit before structural decoding to reproduce the refusal: an
unregistered Fluid and a Fluid renamed through a Forge registry alias, in a fill and both cargo kinds, PREPARED and
SETTLING, through the real `WorldDataMigrationService` pre-start, decode and re-encode, SavedData load and coordinator;
the file bytes are unchanged and no backup appears; the native check refuses the same record. A consumer test drives
the real scheduler and `applyNext`: the held fill becomes REPAIR without publication, the other fill still publishes
and keeps `NONE`, and the persisted ledger differs only in that record. Admission gates refuse without a sequence,
reservation or queue entry; settlement freezing, receipts and the inspector work on the held record.

**Commits.** (1) This plan. (2) The native check exposed and called by every acting consumer, durable decoding
still native, so no behaviour changes. (3) Structural durable decoding with the new tests. (4) The record. Then each
changed class alone, the whole unit suite and one full GameTest with the unchanged checker under the heavy-JVM lock.

**Not in this task:** C-E, D-E, W114, W112F, machine and device roots, ADRs, the risk register, status files and the

### Choices where the task left room

- **The hold:** phase `REPAIR` with reason `OTHER_STATE`. That is the reason the C2 permit already gives every
  projection refusal, so no reason value is added to the saved dictionary.
- **Cargo payload objects stay native.** `EscrowCargoPayload`'s constructor and `decode` keep the native check, so
  every object that eligibility or `RocketCargoMutation` can act on has passed it; durable decoding uses
  `validateStructure` and never builds one. This keeps the existing assertions in `EscrowCargoCodecTest` (`:56`)
  and `RocketCargoMutationTest` (`:66`) unchanged, as W110F kept `EscrowItemStackCodec.decode` native.
- **Non-empty stays a native check.** `minecraft:empty` is valid ID syntax and is refused by `validateNative`, as the
  task lists it with the registry lookup and the round trip.
- **A changed canonical form** is simulated with Forge's public registry alias (`ForgeRegistry.addAlias`), which is
  how a mod renames a Fluid: the old saved name then loads a registered Fluid whose canonical name differs.
- **Messages:** the two duplicated checks now share one message per refusal ("Invalid escrow fluid amount",
  "Noncanonical or unavailable native Fluid"). No test or log expectation names the old messages.
- **One new log line,** `ARCE_ESCROW_FLUID_UNAVAILABLE op=<id> fluid=<name>` (WARN), so that an operator can tell a
  missing or renamed Fluid from other `OTHER_STATE` holds. The name is the structurally checked ID (canonical,
  printable, at most 128 characters).

### Scope of the hold (AGENTS section 3.3)

- **What is held:** one fill operation whose payload Fluid is unregistered, empty or no longer canonical. On its C2
  attempt the permit refuses before either projection, and the scheduler marks it manual; the next checked write
  persists phase `REPAIR`, reason `OTHER_STATE`. Its two endpoints stay locked, and under the existing component rule
  later operations chained on the same endpoints wait behind it. Other components, the ledger, its writer, startup and
  the world continue. No save is refused and no data is discarded or quarantined: the payload and the other fields keep their exact
  bytes, and only the phase, the reason and the writer generation change when the hold is saved (corrected by Root
  after W115-review).
  Before the check the driver only captures endpoints read-only and prunes markers of already retired operations
  (C8, which never changes resources).
- **Duration:** until audited operator settlement or a stopped-server offline repair. The hold is sticky: restoring
  the mod does not clear it. Restoring the mod before the operation's first C2 attempt avoids it. A fill whose C2
  already applied before the mod was removed is not held by W115, because C3 to C8 do not act on the Fluid; its
  endpoints follow their existing handling, which W115 neither changes nor re-tests.
- **Logs:** one `ARCE_ESCROW_FLUID_UNAVAILABLE` WARN and the scheduler's existing WARN ("needs audited settlement or
  offline repair: OTHER_STATE") per held operation, at most once per server session until the REPAIR is persisted;
  the scheduler never revisits a manual record. Admission refusals log nothing new; the loader shows its existing
  status.
- **Recovery:** settlement's intent, freeze and receipt code reads only structure, identity, `Amount` and
  `payload_hash`; the test freezes a held record and builds its receipt (the commands were not run). Settlement still
  observes the endpoints, whose own roots (the loader tank, the rocket's fuel bank) may be unsupported while the mod
  is absent; those roots are outside this task. The practical recovery is therefore to restore the mod set and settle
  the held operation, or to stop the server and repair a whole-world copy offline.
- **Older jars:** an older jar still decodes fluids natively, so it refuses such a ledger at startup as before
  (`INVALID_SCHEMA`, bytes kept). The saved format is unchanged.

### Where C-E must call the check

Cargo has no C2, O2 or readback yet; the driver answers `RECONCILIATION_UNIMPLEMENTED` for its bindings. C-E must call
`op.nativeFluid()`, or obtain the delta through the native `EscrowCargoPayload.decode`, before
`RocketCargoMutation.apply` and before changing the device tank: at admission (already true through
`RocketCargoSelection`, eligibility and the `prepareTransfer` gate), at O2, and at readback. It must map a refusal to
`REPAIR` for that operation only, as the fill's C2 permit does, and never let it fail the ledger or the world.

### Tests

`EscrowFluidDurableValidationTest` covers an unregistered Fluid and an alias-renamed Fluid:

- **Startup:** for the fill and both cargo directions, PREPARED and SETTLING_ACCEPT, through the real
  `WorldDataMigrationService` pre-start, decode and byte-identical re-encode, SavedData load and coordinator
  construction. The file bytes are unchanged and no backup appears. The native check, the admission gate and the
  native cargo `decode` refuse the same record; the structural checks accept it. The receipt, `status` and `inspect`
  work on it, and `status` and the PREPARED `inspect` are identical to a water control.
- **Structure:** exact fields, ID syntax, amounts, field types and the three bounds, with inputs unchanged; malformed
  records still refuse durable decoding.
- **C2 hold:** the real scheduler drives `applyNext` over a ledger with a valid fill and a held one on the same
  rocket, with stubbed endpoint captures, an always-true authority and a publication callback that only records the
  operation; it is not native publication or a full server-tick reconciliation. The valid fill receives its C2
  permit, reaches the publication callback and keeps `NONE`; the held fill never reaches the callback, gets
  `OTHER_STATE`, logs exactly one new WARN and one scheduler WARN, and is not revisited. The checked write persists
  only that record's change, and after a reload the scheduler visits only the valid fill. (Wording corrected by Root
  under W115-R1; the assertions are unchanged.)
- **Admission:** `prepareTransfer` returns `INVALID` and `prepareTest` refuses, with no sequence, reservation, queue
  entry, dirty flag or write; a valid fill then queues with sequence 1. Cargo eligibility returns `INVALID_DATA` with
  its inputs unchanged, and the cargo `prepareTransfer` gate returns `INVALID`.
