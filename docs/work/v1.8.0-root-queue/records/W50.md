### 1. `test_generate_v002_g0_evidence`: `test_generated_evidence_is_complete_deterministic_and_portable`

- **Cause.**
  - `_is_license_or_notice_path` in `scripts/generate_v002_g0_evidence.py` treats any file whose name contains
    "license" or "notice" as a license or notice document.
  - W22 (`760a7702`) added ten Java sources whose names contain "Notice": the eight `station/notice/StationNotice*`
    files, `V180StationNoticeLanguage.java` and `StationNoticeGameTests.java`.
  - The sources-JAR scan listed them, so it no longer equalled `PACKAGED_SOURCE_FILES`. The failure output names
    exactly these ten paths.
- **Why the list is not extended.**
  - `PACKAGED_SOURCE_FILES` in `scripts/validate_build_artifact.py` is not generated. It is a hand-written map of
    the five license and notice documents that both JARs must carry with the repository's bytes.
  - `validate_artifact`, which CI runs on the real binary JAR (`v180-development.yml` line 98), reads every listed
    path from the binary JAR. `_check_packaged_source_files` requires every path in both JARs.
  - The binary JAR has no `.java` entries, so adding the ten sources would break artifact validation. On a real
    binary JAR, the old rule would also have listed the `StationNotice*.class` files.
- **Fix.**
  - A `.java` or `.class` entry is never a license or notice document. Every other file name matches as before, so
    a stray license file in either JAR is still listed.
  - The sealed v0.0.2 scan (`docs/releases/v0.0.2/evidence/g0-mechanical/license-notice-scan.json`) lists only the
    five documents, so regenerating it from the v0.0.2 JARs gives the same result.
- **New test.** In `test_scan_lists_stray_notices_but_not_code_named_after_them`, the binary JAR holds
  `.../StationNotice.class` and a stray `META-INF/licenses/UNREVIEWED-LICENSE.txt`. The scan lists the license and
  not the class. With the old rule patched back in, both this test and the original test fail.

### 2. `test_validate_v090_resources`: `test_repository_resource_contract_passes`

- **Cause.** `audit_languages` compared the en_us and zh_cn placeholders as tuples in string order:
  - en_us `[%1$s] Warp to %2$s in %3$s s` gives `(%1$s, %2$s, %3$s)`;
  - zh_cn `[%1$s] %3$s 秒后跃迁至 %2$s` gives `(%1$s, %3$s, %2$s)`.
- **Which side is wrong: the validator.**
  - In Minecraft 1.20.1, `TranslatableContents.decomposeTemplate` gives `%n$s` argument n-1 wherever it stands.
    Each bare `%s` takes the next value of a counter. I checked this by disassembling the class with `javap` from
    the mapped Forge 47.4.10 JAR (bytecode offsets 157 to 184).
  - So both strings show the same three arguments. The Chinese puts the seconds before the destination, as Chinese
    word order needs.
  - W22's Java test `V180StationNoticeLanguageTest.everyTemplateUsesEachArgumentOfItsKindByPosition` states the
    same contract: every argument is used by position, compared as a set.
  - Rewriting the Chinese into English word order would make the translation worse only to satisfy a check that
    misreads the format.
- **Fix.**
  - A new `_placeholder_arguments` resolves each placeholder as Minecraft does. The audit compares the sorted
    (argument, conversion) pairs. `_placeholder_contract` and its existing test are unchanged.
  - A dropped, added, renumbered or repeated argument still fails, and so does a changed conversion.
  - Every string pair the old rule accepted is still accepted. Over all 1,321 bilingual keys, `warp_countdown` is
    the only key whose result changes.
- **New tests.**
  - `test_placeholder_arguments_resolve_as_minecraft_does`.
  - `test_language_audit_accepts_reordered_arguments_only`: a reordered key passes; a renumbered argument and a
    repeated argument each fail.

### 3. `test_validate_v180_content_ledger`: `test_owning_units_are_not_delivered_after_the_asset`

- **Cause.**
  - The rule in `scripts/validate_v180_content_ledger.py` (lines 548 to 552) applies only to an owning unit that is
    still PLANNED in a batch later than the asset rule's batch.
  - The test relied on the live ledger keeping `entity:ARSpaceElevatorCapsule` PLANNED in C18d. W46 (`5c3a0ad2`)
    delivered that row as REDESIGNED in v1.8.0, so the rule correctly stopped applying.
  - The validator is right. The test fixture was out of date.
- **Fix.**
  - The test now restores the capsule's pre-W46 PLANNED row (the row `5c3a0ad2` replaced) in its copied tree.
  - It first asserts that this tree has no errors. It then changes the asset rule and keeps the original
    assertion unchanged.
  - A later ledger delivery can no longer change this fixture.

  test, which compares a set.
