## 3. Fairness as built

The new [fairness tests](../../../../src/test/java/io/github/sunthemoon/advancedrocketrycommunity/resourceescrow/W231BayFairnessTest.java)
exercise the real store/authority and assert the existing loader status mapping. They do not claim to be two live clients.
The existing [BayLoaderSaturationGameTests](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/resourceescrow/BayLoaderSaturationGameTests.java),
lines 32–116, additionally drives a real unrelated-owner loader; it is inspected here, not rerun as new native evidence.

| Scenario | Observed result and duration |
|---|---|
| A queues 64 INTENTs on eight rockets, eight each; B and C try their own idle rockets. | Both loader previews return SERVER_FULL; loader status is ESCROW_FULL. Both real bay puts return DEPLOYMENT_CAPACITY, charge no retained slot and change no durable root. Queued/captured work already blocks, before its acknowledgement. This remains true after the root becomes durable and for 1,000 additional virtual ticks (50 seconds at 20 TPS). |
| A's first rejection is queued but unacknowledged. | The old durable INTENT still counts: 64 pending. After the exact rejection acknowledgement, pending is 63 while A still retains 64 receipts. There is no early slot release. |
| At 63, C previews a loader, then B queues a bay before C reserves. | C's preview says RESERVED but reserves nothing. B consumes slot 64, and C is refused again. There is no owner reservation or owner-fair admission at a freed slot. |
| B's bay is exactly rejected, then C actually reserves a loader. | The loader can reserve slot 64; the shared index counts it once. There are then 64 pending but 65 retained receipts, demonstrating that these quotas are independent. |
| Eight owners each hold eight INTENTs, and the real receipt file is reopened with a fresh authority. | There are still 64 pending and eight retained receipts per owner; a new owner is refused. Restart reconstructs the same global contention rather than clearing it. |

The 1,000-tick observation is finite; the **unbounded** duration is established by the reviewed no-eviction accounting,
not by extrapolating that sample. A loader retries at its paced opportunity, no faster than once per 20 ticks
([RefillPacer](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/fuel/loader/RefillPacer.java), lines 3–10, 19–30),
plus queue and IO delays; there is no fixed eventual-service guarantee. A refused bay is not admitted automatically
when capacity opens: its message asks for a later flight. It has not joined a pending-bay wait; when all of that
rocket's bays are refused, the coordinator can hand the transfer back to ordinary flight
([outcome handoff](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/BayTransferRecovery.java), lines 385–401).
Runtime refusal visibility lasts as described in section 1. A's receipt-backed menu retains the actual INTENT,
REGISTERED or REPAIR phase; a runtime REGISTRY_BLOCKED hold is not a new menu phase or an ETA. This display description
comes from the status code cited in section 1, not a V2 observation of connected players.
A's INTENT, REGISTERED, REPAIR or released holds can survive restarts and remain indefinitely until exact resolution;
releasing flight/landing does not by itself release a slot. Retryable storage may recover automatically; persistent
authority/physical conflicts may need stopped-server whole-world repair. Operators have no quota bypass in the
authority, whose request has no operator flag. Production loader/bay admission remains gated; the global contention
is demonstrated through permitted tests and can also arise from supported receipt-bearing restart worlds.

## 4. Candidate caps and recommendation

All candidates below deliberately cover the **same unique pending union across PROPULSION and BAY**, charged to the
server-validated stored owner, not the requesting player's identity. A bay-only counter would leave one owner able to
fill the remaining shared slots with loader work. Broadening the limit to both consumers is part of this proposal,
not something inferred as already authorized by D1c. **No operator exemption** is proposed for any candidate.

| Candidate | Maximum full eight-pending-bay rockets for one owner | Slots one owner cannot occupy | Tradeoff |
|---|---:|---:|---|
| 8 | 1 | 56 | Strongest isolation; one full rocket leaves no owner allowance for any outstanding loader/cargo operation. |
| **16, recommended** | **2** | **48** | Permits two full rocket groups, or one full group plus eight loader/cargo operations, without letting one owner occupy half the server pool. |
| 32 | 4 | 32 | Most generous to one owner, but two saturated owners can exhaust the whole server. |

The recommendation is a fairness/availability choice, not a new performance ceiling inferred from this A0 benchmark.
The 8-per-rocket bound remains in force, and owner allowance does not reserve a slot against another owner.
Four owners at 16 can still fill all 64; a fifth has no guaranteed service. Multiple identities can also defeat the
single-owner isolation policy. None of these candidates changes D6 proof fairness, IO progress or a held rocket's duration.

### Refusal, receipts and restart rules common to all three

- Add pending result **OWNER_PENDING_FULL**, distinct from retained OWNER_FULL/OWNER_RECEIPTS_FULL. The bay reason and
  new loader/cargo status are also OWNER_PENDING_FULL. Preserve existing identities and codes; append any wire/menu
  reason code without reusing or shifting existing codes. The limit is checked on the server thread before reservation,
  INTENT, capture or resource mutation. Preserve identity/unavailable/idempotent handling, then SERVER_FULL, ROCKET_FULL,
  OWNER_PENDING_FULL precedence for new operations. All refusals leave resources and counts unchanged.
- Proposed bay translation key: `screen.advancedrocketrycommunity.rocket_satellite_bay.reason.owner_pending_full`.
  English: "Your pending operations are full; wait for earlier work to finish, or ask an administrator to inspect held operations."
  Chinese: "你的待处理操作已达上限；请等待已有操作完成，或请管理员检查仍被持有的操作。"
  Loader English: "Your pending operations are full; no fuel moved. Wait for earlier work or ask an administrator."
  Chinese: "你的待处理操作已达上限；未移动燃料。请等待已有操作完成，或联系管理员。"
  Cargo uses "no cargo moved" / "未移动货物" instead. These messages apply to all candidates, without promising an ETA.
- The retained 128/owner, 4,096/server and byte allowance do not change. Acknowledged REJECTED releases pending only.
  Its re-arm reacquires pending with the same operation ID and can be refused by OWNER_PENDING_FULL. Existing pending
  operations, phase updates, recovery and exact retirement continue; they do not need an additional owner slot.
  A group with insufficient remaining allowance may admit only its fitting members under the existing per-bay protocol;
  this is not a new all-or-nothing group quota.
- Rebuild owner counts from both complete indexes before admission at startup. NOT_LOADED still fails closed.
  **Grandfather over-cap saves without dropping or rejecting data:** keep every valid existing operation, do not fail
  startup/save merely for the new owner quota, and allow bounded recovery/idempotent updates/removal. That owner admits
  no new operation until its count is below the selected limit. Other owners may use any global space that remains.
  A grandfathered owner can therefore still occupy all 64 until its old work resolves; this migration is not immediate
  redistribution of already-owned slots.
  No timeout, eviction, owner reassignment, per-file rollback or automatic receipt conversion is authorized.
- This is a derived admission policy, not a persisted field: no schema bump or data rewrite is needed. A downgrade
  removes only this admission restriction; existing schema/durability rules still apply. Do not silently make the number
  configurable before the owner selects its value and the policy's configuration authority is decided.
- A new TRANSFER_FLOOR_RETIRE operation also needs an owner slot; an existing one can continue recovery. At an owner
  bound, a new retirement intent can therefore wait until other work resolves. Its operator command must preview and
  report OWNER_PENDING_FULL rather than let the coordinator's existing reservation assertion turn that expected refusal
  into an exception. Proposed English: "The owner's pending operations are full; finish existing work before starting a new floor retirement."
  Chinese: "该所有者的待处理操作已达上限；请先完成已有操作，再创建新的下限退役操作。"
  This is an explicit consequence of applying the cap to the shared union, not an operator exemption or a recovery bypass.

### Exact proposed ADR-065 section 10 addition

For the selected candidate, use **one** of these literal opening sentences, followed verbatim by the common text.
The new normative paragraph supersedes only the absence of an owner pending limit; historical implementation notes
remain historical. Root must also update the current risk wording and the section 8 capacity summary when accepting it.

- Candidate 8: "The shared pending union permits at most 64 operations per server, 8 per logical rocket and 8 per owner across PROPULSION and BAY."
- Candidate 16: "The shared pending union permits at most 64 operations per server, 8 per logical rocket and 16 per owner across PROPULSION and BAY."
- Candidate 32: "The shared pending union permits at most 64 operations per server, 8 per logical rocket and 32 per owner across PROPULSION and BAY."

> Count each unique operation once across durable, queued, captured, successor and UNKNOWN states of both consumers,
> including every indexed escrow record and every INTENT, REGISTERED, REPAIR or released bay receipt. Derive the owner
> from server-validated operation authority, never the command actor. Operators are not exempt. Identity conflicts,
> unavailable indexes and an exactly already-held identity retain their existing handling. New admissions check
> SERVER_FULL, then ROCKET_FULL, then OWNER_PENDING_FULL before charging or mutating anything. The bay reports
> OWNER_PENDING_FULL with its readable menu message; loaders and cargo devices report their distinct same-named status
> and that no resources moved. Refusal neither writes INTENT nor changes a package, endpoint, sequence or reservation.
>
> The separate 128 retained receipts per owner, 4,096 per server and existing byte ceilings are unchanged. An exactly
> acknowledged REJECTED receipt retains its receipt allowance but not pending allowance. Re-arming it reacquires
> pending with the same operation ID. Idempotent existing pending work, recovery, phase changes and exact retirement
> are not new admissions. Per-bay admission remains per operation rather than all-or-nothing for a rocket group.
> Creating a new TRANSFER_FLOOR_RETIRE operation is a new admission; at the owner allowance its operator command
> returns OWNER_PENDING_FULL without writing or throwing an expected-capacity assertion. Existing floor-retirement
> operations continue recovery. This policy can delay a new floor retirement until other owned operations resolve.
>
> Startup rebuilds owner accounting from the complete indexes before admitting work; NOT_LOADED fails closed.
> Valid saves already over the owner allowance remain loadable and saveable with every operation preserved. Do not
> evict, truncate, convert, reassign or reject their existing data solely for this allowance. Continue bounded recovery
> and allow new work for that owner only when its count is below the allowance and all other checks permit it.
> Other owners can use remaining global space. No persisted counter, schema change, timeout, per-owner slot reservation
> or operator bypass is introduced. This prevents one owner monopolizing all pending slots but does not guarantee
> eventual service when several owners saturate the server or underlying work cannot progress.
>
> Before enabling bay admission, verify mixed-owner/mixed-consumer saturation, over-cap restart preservation, exact
> acknowledgement release, UNKNOWN/successor deduplication, rejected re-arm and refusal messaging under this policy.

### Tests needed after the owner selects the number

For each candidate, instantiate the following matrix at its literal bound (8, 16 or 32), without relaxing the existing
64/8, byte limits or docs/17 budgets. These are future acceptance tests, not claims that this branch enforces a cap.

1. Admit exactly the owner's allowance on distinct legal rockets; at allowance plus one, refuse both another bay and
   a loader/cargo operation. Repeat with owner A's mixed BAY/PROPULSION records, all cargo directions and operators.
   Assert package/envelope bytes, sequences, writer requests, retained and pending unions are unchanged on refusal.
2. With A at its allowance, B and C can still reserve/admit on their own rockets while global capacity remains. Fill
   the server with respectively 8, 4 or 2 owners at the chosen allowance; a further owner gets SERVER_FULL, not an
   owner-full diagnosis. At 63 plus one, both consumer orders respect the global bound. Verify simultaneous-limit precedence.
3. At 8 per rocket, another owner allowance does not admit a ninth operation. At an owner bound, ALREADY_HELD and
   updates of its exact existing identity still work. Conflicting identities cannot gain that exception.
   New floor-retirement intents at the owner bound return the readable typed refusal without an assertion/exception;
   existing retirement/settlement operations and exact removals still complete, including above-bound migrated owners.
4. Repeat deduplication across queued/captured/UNKNOWN/successor/durable states, including REPAIR and released flight.
   Queue rejection/removal and prove capacity is not freed before exact acknowledgement; after it, another owner can
   take the slot. A failed/guard-refused write restores its prior charge; UNKNOWN retains it.
5. Keep 128 REJECTED receipts for an owner with zero pending. They still block a new retained receipt but do not block
   its loader work under the pending allowance. Re-arm at the pending bound refuses without allocating a replacement
   operation; below it, re-arm succeeds with the original ID.
6. Restart real files with an owner at the allowance and already above it (including the current valid 64-owner-A
   fixture). Preserve all data and saves, continue recovery, refuse only A's new work, permit other owners if global
   space exists, and progressively resume A below the bound. Repeat cold start and interrupted writes; never reset counts.
7. Repeat coordinator/receipt/journal measurements three times at the selected limit, one above it and global 64,
   with a retained backlog and maximum legal payloads. Add active D0–D7/D6 and the docs/17 reference workload;
   include 64 one-bay rockets to exercise the 32-step queue budget, not only eight eight-bay rockets.
   Do not infer those costs from the waiting-state results here. Include at least two real clients for V2 refusal
   visibility, normal/operator parity and the fact that rejected flights need a later attempt. Verify stable menu and
   network codes, localization, no client-side authority and no repeated per-tick refusal logging.
