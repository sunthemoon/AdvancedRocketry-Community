## 1. `config:CATEGORY_GENERAL.makeMaterialsForOtherMods`: not fully delivered

### What the shared branch ships

- **The decision.** The legacy switch (`ARConfiguration.java:413`, default on) let the legacy
  machines make plates, rods and other products for other mods' materials. On 2026-10-08 the owner
  chose "通用标签互操作，额外配方由数据包提供（推荐）"
  (`docs/work/v1.8.0-c16d-components-graph/OWNER-DECISIONS-02.md:7`). The record of that choice
  says: built-in recipes accept common-tag members, data packs provide extra recipes for other mods'
  materials, "Disclose the legacy behavior gap. No makeMaterialsForOtherMods boolean is added."
  (lines 15 to 18). ADR-061 section 2.2 (lines 101 to 103) and ADR-064 section 2 (lines 165 to 191,
  item 4 at line 190) carry the mechanism.
- **No key.** No file under `src/` names `makeMaterialsForOtherMods`. `CommonConfigTest` line 77
  pins the exact number of COMMON values (97).
- **Tags in recipes.** I scanned the inputs of the 82 current machine recipes (scratch script
  `scan_recipes.py`). Every metal and ore input is a `forge:` tag, for example in the 18 rolling,
  17 press, 7 lathe and 2 crystallizer recipes. The remaining item inputs are listed at the end of
  this section. The codecs decode tags: `RollingMachineRecipe.java:332,367`,
  `PrecisionAssemblerRecipe.java:384,421`, `ElectrolyzerRecipe.java:287,324`,
  `SmallPlatePressRecipe.java:156,177` and `ClassicMachineRecipe.java:145`, all through
  `BoundedItemIngredientCodec.decode`. `66996a1f` (2026-10-03) made these recipes refuse tags until
  C16a, and `85a19757` (2026-10-04) ended that under ADR-064 section 2. The same commit added
  `V180KernelRecipeResourcesTest` (lines 19 to 53), which pins the v1.2 rolling and precision
  recipes on tags.
- **Common tags on products.** C15a's `V180MaterialResourcesTest` checks the product tags (line 141)
  and that rolling and press recipes take only tags (lines 64 to 67 and 97 to 98).

### What is missing

1. **The disclosure.** Nothing a player or pack author reads says that the setting is gone, that
   other mods' tagged materials now work as inputs, or that recipes for materials this mod does not
   define (for example plates of another mod's metal) are no longer generated and need a data pack.
   I searched `CHANGELOG.md`, `docs/versions/`, ADR-061 and ADR-062. ADR-061 section 2.2 says the
   tags replace the switch but does not name the gap. Only C16d's `CONTRACT-02.md` section 2.4
   (lines 140 to 148) names it, and that draft says it is "proposed, not frozen".
2. **The CHANGELOG contradicts the mechanism.** `CHANGELOG.md` lines 179 to 181, in the v1.8.0
   section, say that Rolling Machine, Precision Assembler and Electrolyzer recipes "must name items;
   tag ingredients are refused until the classic machine family resolves tags after they load". That
   was the rule of `66996a1f`. `85a19757` ended it, and the codecs above now accept tags. A pack author
   who reads this entry is told the opposite of the mechanism that replaces the switch.

### How to close it (for Root; I changed nothing)

- Correct `CHANGELOG.md` lines 179 to 185 to say that these recipe types accept tags. I did not
  check the remaining electrolyzer details of that entry, so I propose no wording for them.
- Add a v1.8.0 entry such as: "The legacy `makeMaterialsForOtherMods` setting is gone. Machine
  recipes take common `forge:` tags, so other mods' ingots, plates and dusts work wherever this mod
  uses the same material, and this mod's products work in theirs. Recipes for materials this mod
  does not define, such as plates of another mod's metal, are no longer generated; add them with a
  data pack."
- After that commit, the row can be checked again. The C16d contract already proposes REDESIGNED
  (`CONTRACT-02.md` line 147).

Not blocking, for Root's information:

- A few machine inputs name an item where a tag exists: `minecraft:sand` (`arc_furnace_silicon`),
