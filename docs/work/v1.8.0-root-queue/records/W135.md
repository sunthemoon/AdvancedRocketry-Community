## What the checker does now

Forge's `log4j2.xml` (fmlloader 47.4.10, read from the Gradle cache) rolls `logs/latest.log` into
`logs/<yyyy-MM-dd>-<n>.log.gz` at midnight in the JVM's time zone and when the next run starts. The debug log rolls
into `debug-<n>.log.gz`, which is a different log.

- **When it rebuilds.** Only for a file named `latest.log` whose first non-blank line is not the GameTest launch
  header. Every log that passes today begins that way, because the checker already rejects any event or
  unrecognized line before the launch. So every log that passes today, and every file with another name, is read
  and checked exactly as before, and its output is unchanged.
- **How it picks the parts.** It reads the event times (the timestamp carries the date), the launch header and the
  shutdown marker of `latest.log` and of every `<yyyy-MM-dd>-<n>.log.gz` in the same folder. The file name pattern
  only selects the main log, not the debug log. Walking back from `latest.log`, the earlier part is the one whose
  last event is the latest before its successor's first event. File names and modification times play no part.
  The chosen part must also meet these conditions:
  - a midnight lies between its last event and its successor's first event;
  - that interval is at most ten minutes;
  - it holds no GameTest shutdown;
  - it holds a launch only as its first line.

  The walk stops at the part that begins with the launch header. No other part may overlap the rebuilt run's time
  span. Each chosen part is decompressed again, compared with its first scan, and must end with a complete line.
- **What it checks.** The parts are joined in order, decoded as `Path.read_text` decodes `latest.log` (UTF-8,
  universal newlines). The joined text goes through the unchanged `parse_log` and `check`. Line numbers in problems
  refer to the rebuilt text. An `[INFO]` line names each file and its line range, for example
  `2026-10-19-1.log.gz (lines 1-5,599), latest.log (lines 5,600-11,477)`. The `[PASS]` line then says "the run
  rebuilt from 2 files ending in …".
- **When it refuses.** The rebuild is refused in these cases:
  - no earlier part exists (the first part is missing);
  - the interval is too long (a gap), or no midnight separates the parts;
  - two parts end at the same time, or another part overlaps the rebuilt run;
  - a part holds a shutdown, or a launch after its first line (a part of another run);
  - a part cannot be read (not gzip, truncated, or not UTF-8), or does not begin with a timestamped event;
  - the size bounds are exceeded.

  The refusal becomes the first `[FAIL]` line, and `latest.log` is then checked alone. It fails exactly as before
  (exit code 1). With `--inventory`, a refusal is printed as a `[WARN]` line on stderr.
- **Size bounds.**
  - A part is read through `gzip` with `read(MAX_PART_BYTES + 1)`, so at most 256 MiB is decompressed per part. A
    full v1.8 log is about 6.3 MB.
  - All parts together may expand to at most 2 GiB.
  - A folder may hold at most 1,000 rolled parts.

## Choices where the TASK was open

- **Ten minutes of silence across a roll.** Five full local runs (W131F, W134, W136, W137 R6 and W138) never went
  more than 22.1 seconds without an event (`max-gap.txt`). A longer silence therefore means a missing part, or a
  part of another run that did not shut down.
- **Refusal leaves the old failure in place.** A refused rebuild does not hide the plain check of `latest.log`: both
  are printed. A refusal does not use exit code 2, because that code still means that the log or the manifest
  cannot be read.
- **Unrelated parts can block the rebuild.** Any unreadable rolled part in the folder refuses the rebuild, even one
  from an older run, because it could be the missing piece.
- **Only `.log.gz` parts are read.** An uncompressed `<yyyy-MM-dd>-<n>.log` that log4j left behind is not a
  candidate.

- a run across two midnights rebuilt from three parts;

  reversed;
- a missing first part, refused in four variants: no part, only a completed previous run, only a crashed run, or
  only debug parts;
- a gap, refused: a missing day, a silent half hour, or no midnight between the parts;

- a `latest.log` that holds another launch, refused;
- unsplit logs checked as before, including a leading blank line and a name other than `latest.log`;
- the size and count bounds, including the exact boundary;
- unreadable parts and a part without a timestamped first event, refused.

## Known risks

- **A long silence is refused.** A real run that logs nothing for more than ten minutes across midnight is
  refused. It then fails as before, so the cost is a false failure, not a false pass.
- **A crashed run can stand in for a missing first part.** Suppose the split run's first part is missing, and a
  previous run crashed, without a shutdown, less than ten minutes before midnight. Then that crashed run would be
  taken as the first part. The joined text is still checked in full, and its batches and counts would almost
  certainly fail.
- **Month names are read in English only.** A JVM with another default locale writes other month names, and the
  rebuild is then refused. Logs on this machine and on the hosted runner use English.
- **Lost parts are possible on this machine.** In the local folder of `arce-v180-w74-natural-beds-flake`, the run
  that started at 23:52:47 on 2026-10-15 kept its first part, but no file holds its part after midnight. The next
  run's startup roll apparently lost it (`real/w74-parts.txt`), possibly through Windows file-name tunnelling of
  creation times. The
  checker refuses such a run as "first part missing" or "gap", which is correct, but the run then cannot be
  checked at all.
