## The items

### 1. `/arce atmosphere status` on Venus and Tau Ceti g (fixed)

**Design.** ADR-066 section 3.1 names the classes of a known, unsupplied cell: `VACUUM` is "pressure == 0 and cell is
not breathable"; `NON_BREATHABLE_ATMOSPHERE` is "pressure > 0 and cell is not breathable". In Space, including station
regions, the Space Level's own profile is used. ADR-003's original two states predate planets with atmospheres.

**Behaviour.** The command printed the internal `BreathabilityState`, whose `VACUUM` means "not breathable" whatever the
pressure. The analyzer (`AtmosphereAnalyzerService.compose`) and the detector (`DetectorMode`) already map it to the
ADR-066 classes, so only the command deviated.

**Change.** `AtmosphereCommands.label` keeps `BREATHABLE` and `PENDING` and names a non-breathable cell `VACUUM` only when
the Level's catalog profile has zero pressure, otherwise `NON_BREATHABLE_ATMOSPHERE`. The pressure comes from the new
catalog-only `AtmosphereManager.profileVacuum`, which reuses the manager's existing environment resolution (the Space
Level resolves to the Space body, pressure 0). The line stays an untranslated operator diagnostic in the same
`key=value` form; no other field changed.

**Tests.** `AtmosphereCommandsTest` (unit, two cases) covers the mapping. The GameTest
`AtmosphereAnalyzerRoomGameTests.statusCommandSeparatesVacuumFromANonBreathableAtmosphere` (batch `atmosphere_analyzer`)
runs the real command for a connected player in the open on Venus (`NON_BREATHABLE_ATMOSPHERE`) and on the Moon
(`VACUUM`). On the unfixed tree it failed with "advancedrocketrycommunity:venus status did not start with Atmosphere=NON_BREATHABLE_ATMOSPHERE : [Atmosphere=VACUUM vents=0 ...]" (see "Commands and results").

### 2. The warp target list offers `space` and `cygnus_x1` (as designed)

**Design.** ADR-044 section 4 (and ADR-065 section 5.1 for the warp controller, which "reuses the same ... discovery ...
rules as ADR-044") accepts a target that is "present, orbitable, known and not the current orbit". ADR-031 gives every
legacy definition `orbitable=true`, including the shared Space body. ADR-057 section 1 makes Cygnus X-1 "a public
object" with "no discovery requirement ... so it can never be locked", reachable only by interstellar warp.

**Behaviour.** `StationWarpService.warpTargets` lists exactly the bodies that pass this rule, sorted by ID, and the quote
and the commit check the same rule again. `cygnus_x1` needs no discovery, so it was never "undiscovered". `space` is
present, orbitable and known. Both entries therefore match the design, and nothing changed.

**For Root.** Whether the shared Space body should be a station orbit at all is a design question that ADR-044 does not
settle: the satellite bay already refuses it explicitly (`BayDeploymentChecks.orbitRefusal`: "legacy `space` never is"
an orbitable source), and the rocket star map leaves it out of surface targets. If Root wants `space` out of the warp
list, the narrow change is to exclude `CelestialIds.SPACE_ID` in both `warpTargets` and `quote`, with an ADR-044 note.
I did not test what a warp to `space` does.

### 3. The star map quotes abstract fuel in mB (fixed)

**Design.** ADR-065 section 3 (D1-A) keeps abstract fuel and Fluid apart: "Never invent Fluid from already abstract
units"; a Fluid rocket's actual debit is `ceil(Q * tierCoefficient / capturedFluidEfficiency)` mB, and "this limitation
must be visible in the menu/tooltips".

**Behaviour.** The star map's quote is `RocketFlightQuotes.Quote.requiredFuel`, the planner's route requirement `Q` from
`TravelFuelFormula` in the rocket's own units, the same number the flight console prints as "FUEL a/b · ROUTE NEEDS c".
The v1.4 key `starmap.advancedrocketrycommunity.quote` labelled it "mB" ("Fuel quote %s mB", "预计燃料 %s mB"), which is
wrong for an abstract rocket and also for a Fluid rocket, whose debit is scaled from `Q`.

**Change.** A new v1.8 key `starmap.advancedrocketrycommunity.route_quote` ("%s · Route needs %s fuel", "%s · 航程需要燃料
%s", from `V180StarMapLanguage`) replaces it in `RocketStarMap.quoteLabel`, which is now a static method so a unit test
can reach it. The v1.4 output is historical and keeps its key unused; no key is defined twice.

**Tests.** `RocketStarMapQuoteTest` (unit, two cases) reads the label's key from every packaged language root and requires
exactly one definition per language, no "mB" and both arguments. With the old key it failed: "en_us quotes abstract route
fuel in millibuckets: %s · Fuel quote %s mB" (result kept in `D:/GitHub/ARCE-Task-Evidence/root-queue/W294/before/`).

### 4. Venus without a helmet (as designed)

**Design.** ADR-034: cold, heat, pressure and sunlight are evaluated separately, but "every 20 exposed ticks, attempt at
most 2 health points of damage, selecting pressure, heat, cold, then sunlight if multiple hazards remain"; the
environmental damage is not added on a tick where life support applies suffocation damage. Hazards do not stack.

**Behaviour.** About one second without a helmet costs at most 2 HP of environmental damage plus the separate
suffocation damage, so 4 HP on Mars (cold) and on Venus (pressure) alike, and 2 HP on Tau Ceti g (no hazard in range,
only suffocation), exactly what the tester measured. The existing GameTests already pin this:
`PlanetaryExposureGameTests.registeredDamageUsesOneIntervalAndPlanetaryGravity` (one 2 HP attempt per 20 ticks, `pressure`
chosen on Venus) and `passiveTagsDoNotGrantOxygenOrAcceptWrongSlots` ("Coincident environmental exposure stacked another
damage attempt"). Nothing changed.

### 5. The laser gun's recipe (as designed)

**Design.** ADR-066 section 5.3 fixes the gun's behaviour (50-block server trace, 20 ticks per block, durability 512,
diamond harvest tier), not its ingredients. Section 9 item 6 makes "recipe ingredients" implementation inputs, and
section 6.3 requires a reachable survival route with no hard cycle for every registered item. The upstream mod had no
recipe for the gun (`docs/provenance/v1.8.0-c18b-laser-gun-preauthoring.md`), so there is no parity target.

**Behaviour.** The recipe is three steel plates, two iron rods, one diamond and one basic circuit plate. The basic
circuit plate comes from the precision assembler (gold, redstone, a silicon wafer, 100 FE/t) or the laser etcher, so the
gun sits in the same steel-plate and basic-circuit tier as the bionic leg upgrade (two steel plates, two iron ingots, a
basic circuit plate) and the jetpack (four steel plates, three titanium rods, a basic circuit plate), and the diamond
matches its diamond harvest tier. The jackhammer, a faster single-block tool, needs titanium, aluminium and a motor.
`RegisteredItemReachabilityTest` confirms the route: in its acquisition report the gun is first reachable in round 13, the same round as the bionic leg upgrade and the jetpack, after the basic circuit plate (round 9) and before the jackhammer (round 15), with no unavailable required node. This fits the design's progression, so nothing
changed. Balancing it later is the owner's choice, not a deviation.

### 6. Elevator audit lines write `owner=-` (fixed)

**Design.** ADR-054 section 13: "A line has the form `system action result device owner actor` plus bounded fields."
ADR-059 section 9 lists the elevator's audited actions (bind, unbind, refusals, rides).

**Behaviour.** `ElevatorPairs.audit`, which writes every elevator bind, unbind, ride request, cancel and commit line,
passed `null` as the owner, so each line had `owner=-`. The cargo lines (written by the endpoint itself) and the railgun
already carry the owner.

**Change.** `ElevatorPairs.audit` now looks up the device's owner in the endgame root (its index record or tombstone,
through the existing `owner` helper); a device the root does not know still writes `owner=-`. For rides the device is
the departing endpoint, so the owner is that endpoint's owner, the same owner the ride's protection check uses. No chunk
is read.

**Tests.** The existing elevator GameTests now assert the owner column: `cargoTravelsBothWaysAndAnUnbindLetsItArrive`
(bind and unbind), `membersRideUpAndDownStrangersDoNotAndNoTicketRemains` (a member's ride commit from the owner's
anchor) and `aZoneJudgesARideByTheDepartingEndpointsOwner` (ride request and cancel, where the anchor belongs to another
member, so the terminal's owner, the anchor's owner and the rider all differ). No assertion was removed. On the unfixed tree all three tests failed at their first new assertion with the line's `owner=-` (bind, ride_request and ride_commit).

### 7. The laser drill's `settled=false` after a restart (as designed: recomputed, not saved)

**Design.** ADR-055 section 3: the controller's `ops_paid` and the marker's `ops_done` "are saved independently", and
"at every contact (both chunks `FULL`, before each operation)" the controller settles a debt or the marker uses a
credit. "A controller may change or clear its link after a contact with no debt and no credit", or at any time when
the marker can no longer be contacted.

**Decision: recompute, do not save.** Settlement is a fact about two counters in two chunks, often in two Levels, that
only a contact can compare. A saved flag would be wrong after the crash case the ADR describes: the controller's chunk
saved `settled=true` before a layer ran, the marker's chunk saved after it, so after the restart there is a debt while
the saved flag says there is none, and the owner could change the link without paying it. Recomputing at load would need
the marker's chunk, which the drill must never load. So the runtime field `linkSettled` starts false at every load
(`resetState`, called by `EndgameDeviceBlockEntity.load` before `readState`) and is set by the next contact, which only
the physical evaluation makes. A drill switched to physical mode makes a contact even while stopped, and an unreachable
marker never blocks a link change. In logical mode the link is unused, so the field stays false, as the tester saw; no
data is lost (`ops_paid` is saved). Nothing changed, so no schema version or migration test is needed.

**For Root.** `device inspect` shows that runtime field as `settled=false`, which reads like "unsettled" when it means
"no contact since the drill loaded". Renaming it in the operator output (for example `settled=unknown` until the first
contact) would be a diagnostic wording change, not a design fix, so I left it for Root to decide.

### 8. Standing on a 0 % station platform (one fault fixed)

**Why `OnGround` is false.** At exactly zero gravity Forge's gravity attribute is 0, so a resting player's vertical
motion is 0, `Entity.move` never collides downwards, and `onGround` stays false on the client and, through the movement
packet, on the server. I checked each mechanism the TASK lists against the 1.20.1 code (`javap` of the mapped jar
`forge-1.20.1-47.4.10_mapped_official_1.20.1.jar`) and this repository:

- **Fall damage.** Correct. With no gravity no fall distance builds up, and `CelestialGravityController.onLivingFall`
  scales any landing by the applied multiplier, 0 here.
- **Block interaction: breaking was five times slower (fault).** `Player.getDigSpeed` divides the speed by 5 when
  `!onGround()` (bytecode offsets 181 to 193) and then posts `PlayerEvent.BreakSpeed`. A player standing on a 0 % platform
  therefore broke every block five times slower than anywhere else, including the Moon, although they stand on a block.
  Placing and using blocks do not depend on the flag.
- **Sneaking at edges.** Correct. `Player.isAboveGround` also accepts a collision within the step height below when the
  fall distance is under it, so edge protection works for a player standing at 0 g.
- **The safety return's support check.** Correct. `SpaceSafetyReturnService.adriftThreshold` does not rely on
  `onGround`: without it, it probes 1/16 block below the feet for a block collision, so a standing player is supported.
  W285's `aSupportedZeroGravityPlayerIsNotReturned` covers it. `LowGravityFlightAllowance` only acts while vanilla's
  floating counter runs, which stays 0 next to the platform.
- **Suit motion.** Correct. `SuitMotionService` reads no ground state; it resets only vanilla's floating counter and the
  fall distance on paid thrust.
- **Seats.** Correct. The sneak "ground LEAVE" (`RocketSeatInput`) and seat release use the rocket's flight state
  (`ASSEMBLED`, `FUELED` or `LANDED`), not the player's `onGround`. The bay exit's one limited fall safeguard
  (`BayPassengerExitMotion.sample`) treats `!onGround()` as airborne, so at 0 g it waits for a landing that never comes
  and ends within its existing 200-tick bound; there is no fall damage to guard there, because falls scale to 0.

**Change.** `ZeroGravityFooting` (registered next to `LowGravityFlightAllowance`) handles `PlayerEvent.BreakSpeed`: for a
player who is not on the ground, not flying, gliding, riding or spectating, whose applied gravity multiplier is exactly
0, and who has a block's collision shape within 1/16 block below the feet (the safety return's probe, loaded chunks
only), it multiplies the speed by 5, undoing only vanilla's airborne factor. It is common code with no state, so the
client predicts the same speed from the synchronized gravity attribute (`forge:entity_gravity` is syncable) and its own
blocks, and the client's progress and the server's check agree. Jumping, movement, falls and the safety return are
unchanged.

**Tests.** `LowGravityFlightGameTests.aPlayerStandingOnAZeroGravityPlatformDigsAtGroundSpeed` (batch
`low_gravity_flight`) drives W285's real connection fixture: a survival player on a 0 % platform whose movement packets
report `onGround` false digs at the ground speed; off the platform edge (unsupported) the penalty stays; and a 1 g
player reporting airborne over a block keeps it too. On the unfixed tree it failed with "A player standing on a 0 % platform digs at 0.2 instead of the ground speed 1.0".

## Choices where the design was open

- Item 1: the command stays an untranslated operator line; only the state's name changed, and only ADR-066's two
  existing names are used. The pressure comes from the atmosphere manager's own catalog profile for the Level, not
  from the analyzer item's runtime, so the operator command does not depend on an item's lifecycle.
- Item 3: a new v1.8 key rather than an edit of the historical v1.4 output, as WORKER-RULES requires; the wording
  matches the console's "ROUTE NEEDS".
- Item 6: the owner is the audited device's owner. For a ride that is the departing endpoint, which is also the owner
  ADR-054 section 5.1 uses for the ride's protection check (review C12R-M2).
- Item 8: the narrowest fix that keeps vanilla's movement rules: compensate the one dig-speed factor in the existing
  Forge event, instead of reporting the player as on the ground, which would also enable jumping and step-up at 0 %
  (W285 kept 0 % jumping unchanged).

## Known risks

- Item 8 changes gameplay: blocks break at normal speed on a 0 % platform. Other mods that also compensate the airborne
  penalty in `BreakSpeed` would compound with it; none is known in the supported set.
- Item 8's client prediction relies on the synchronized `forge:entity_gravity` modifier. If the client briefly lacks it
  (for example right after a Level change), the client predicts the slower speed and the break only takes longer; the
  server still decides.
- The local GameTest run had one `server-overloaded` warning, within the checker's limits; the hosted sharded run
  decides.
