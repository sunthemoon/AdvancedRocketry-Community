## The candidate as an argument

The forced-stop, released-flight and exit runners now require `--jar-sha256` and `--candidate-commit` next to `--jar`.
Before any session or Java start they refuse unless the JAR's SHA-256 equals the argument and
`git diff --quiet <candidate> HEAD -- src/main src/generated build.gradle settings.gradle gradle.properties` exits 0.
That is W325's production-equality check, now against the named commit. The runners recheck the JAR bytes at the end
and record a `candidate` object (JAR, SHA-256, candidate commit, harness commit, the diff command and its exit code) in
`results.json`.

`python -B scripts/bay_integrated_evidence.py pin --jar ... --jar-sha256 ... --candidate-commit ... --output <new json>`
records the same check for a driver. It never overwrites a record and writes nothing when it refuses.
`--source-commit` keeps its meaning, the clean harness HEAD. The whole bay matrix can therefore run on C2 without code
changes. Every W331 smoke invocation recorded both the runner's `candidate` object and a `candidate-pin.json`.

### Findings from the smokes

None of these is a production defect.

1. **D0 records its reason on each bay.** `BayTransferRecovery.reject` sets the reason on every member and remembers it
   for the bay menu; the claim line only shows wait reasons and the READY_SOURCE handoff. Family T reads the reason
   through `deployment-status` on every bay.
2. **An epoch-only wrapper is invalid, not non-neutral.** The `protected` fixture command threw before its launch line.
   The escrow model requires an unbound wrapper to have epoch 0 (`EscrowSettlementIntent.Observation`, "Invalid neutral
   observation"). That is the likely cause; the command's exception is logged only at DEBUG, so no stack trace was
   captured. The variant was withdrawn and must not reach C2.
3. **B15.5 uses one write.** The write that D0 itself requested was replaced, then unknown, and D0 then rejected every
   bay with ASSEMBLY_JOURNAL_UNPROVED. The oracle requires an injection between D0's request and the handoff.
4. **B6.5: production keeps the consumed source.** D6's barrier proof writes the consumed S' to its entity chunk, and
   the transfer removes the source only in RAM. A restart with the destination absent after D7 therefore finds S' and
   chooses KEEP_SOURCE: the source keeps T's source UUID, sits stationary at its origin with the consumed op, T is
   removed, and nothing is re-created on the Moon. W27A's B8 row allows this ("ordinary restart may choose stationary
   consumed-source recovery"). A destination rebuild from T' would need S' absent too, which W27A's B7 row forbids
   manufacturing. **Root decides whether this reaches B6.5 as worded.**
5. **B7.3: the normal transfer carries the rider.** During the queued retirement the login was neither routed nor
   settled, T stayed PREPARED with seat 0, the guard refused, and a fresh D6 proof preceded READY_SOURCE. After the
   handoff, the normal acknowledged transfer carried the assigned online rider to the destination, as W27A section 4.1
   says. The GameTest checks the rider only at the handoff.

## Choices where the contract was open

- New fixtures are commands, fixture variants or a value of the existing gated cut enum. `B15_D1` reuses the receipt
  committer's MOVED and UNKNOWN modes, which `B15_D4` already combines for D4.
- B4's rows with X absent use the `B6_D5` stall, because no existing pause lies between D4's acknowledgement (which
  decommission needs) and D5. So T' is durable at the cut and S' is not; the copy fixture puts S on disk or removes it.
  This is the B5.2 mixed state with X absent, not a pure `(S, T)` state.
- B4.6 and B4.7 use the same pre-kill decommission as B4.3 and B4.10, so X is absent on the initial disk.
- B8.7 and B8.8 use three bays: two that register and one research-locked bay. "Partial" follows W325's reason, which
  named the existing one-accepted, one-rejected group and only the second REGISTERED member as missing.
- B14.3 reaches "failure rejects all bays" through a definite failure of the checkpoint that D0 requested. The
  `requestCheckpoint` REFUSED answer (writer unavailable) stays covered only by the B14 GameTests.
- B14.4's stale record names L in a dimension that never loads, as `transaction-writer add` does, so restart recovery
  never removes it. The case shows the refusal, not a later legitimate removal.
- B11.7 counts captured and successor copies once; the UNKNOWN copy is not held by any gated control.
