### Player impact and proposed follow-up

None of these five observations establishes a PRODUCT liveness or data-loss
defect. A stop during descent or immediately after landing can expose the normal
settlement/preparation boundaries, but the evidence must not be described as a
permanently locked player rocket. No product-fault known-issue paragraph is
asserted from these harness failures.

Proposed player guidance: “After arrival or a server restart, disassembly can
briefly report busy while the landing finishes settling. If the old departure
area must be prepared, the first interaction only prepares it; make a new
interaction and, when offered, a fresh exact-fuel confirmation once preparation
is ready. Waiting for the first preparation interaction does not authorize a
later destructive action. Do not delete transfer records or edit fuel NBT as a
workaround.” This is proposed guidance, not a newly published acceptance claim.

For a Root-queued runner fix, separate landed settlement, bounded cold-site
preparation and destructive submission. Correlate the retained/settled event,
prepare the fixture's exact recorded discovery columns, and issue a fresh
authorized disassembly only after readiness; still require the identified
SEALED/DONE receipt, entity absence, every restored block and inventory within
the unchanged counted budget. The admin command's generic pending answer is not
a sufficient destructive-admission receipt. Keep the existing defaults and
isolate any future compatibility option. No rerun closes a case unless Root
queues it. A v1.9 hardening follow-up can add distinct preparation/ready telemetry
and durable per-phase checkpoint hooks, with fresh-candidate forced-stop and
real-player cold-restart tests rather than relabelling these five failures.
