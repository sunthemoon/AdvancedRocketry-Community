### Tick mapping and command phase

Inspected the local Forge 47.4.10 sources JAR's MinecraftServer patch and the
official-mapped 1.20.1/47.4.10 MinecraftServer and DedicatedServer classes, both
with `javap -c -private` and with the cached ForgeFlower decompiler. The official
Forge 1.20.1 patch was also checked at
`https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.1/patches/minecraft/net/minecraft/server/MinecraftServer.java.patch`.
The mapped artifacts are under the local Gradle `caches/forge_gradle` tree.
The temporary two-class decompilation is inspection only, not a delivered asset.

`MinecraftServer.tickServer` fires START, increments `tickCount`, runs
`tickChildren`, writes `tickTimes[tickCount % 100]`, and then fires END.
`DedicatedServer.tickChildren` runs console commands before that write.
`SatelliteManager.onServerTick`, registered at NORMAL priority, measures its END
work in a `finally` block and stores it at `floorMod(tickCount, 100)`.
`SatelliteRuntime.postTickNanos()` returns a clone of that ring, or 100 zeros if
the service is absent, matching the aggregate command's combination.

Consequently, at END of completed tick C, tick t maps to slot `t % 100`, for
`max(1, C - 99) <= t <= C`. Slot zero first represents tick 100, not tick zero.
For C below 100 there are exactly C populated entries, including a real measured
zero if present; unfilled slots are omitted based on tick identity, not value.
The formatter adds the vanilla and satellite values at the same slot, without
sorting them. Tick 101, for example, produces ticks 2 through 101 in that order.

Reading the live rings directly during a command would be ambiguous: console
tick N is still in progress, whereas a between-ticks task can already observe
completed tick N. Instead, the LOWEST END listener clones both rings after the
NORMAL satellite listener. Commands format this completed snapshot on the server
thread. The header is the command's actual `getTickCount()`: it is C between
ticks, or C + 1 during the next tick. Data always ends at C. Before the first
snapshot, the line has zero entries. The exact line format is:

```text
ARCE_RELEASE_TEST ticks_raw tick=<command tick> entries=<0..100> data=<tick>:<integer nanos>,...
```

The formatter stays below 4096 characters even with 100 maximum signed-long
durations and maximum positive int tick IDs. Hook-disabled registration adds
neither the command nor timing listeners. Repeated command registration does not
register another listener. Stop clears both arrays and the server reference;
another server cannot read the previous server's snapshot.

### Observer use and boundaries

The owning harness saves replies to `arce satellite release-test perf ticks raw`,
polled every 100 ticks or sooner, and passes parsed polls to
`summarize_raw_ticks(polls, threshold_ms)`. Alternatively, analyze one saved run:

```text
python -B scripts/campaign_observe/raw_ticks.py <saved-reply-log> --threshold-ms 500
```

The parser accepts a normal log prefix and preserves integer nanoseconds.
Malformed, oversized, nonconsecutive or out-of-range replies are refused. Exact
overlap is counted and dropped; conflicting durations and backwards command tick
counts are errors. Gaps are compact ranges, not invented zero-duration samples,
and break slow-tick runs. Percentiles cover only distinct observed ticks; missing
ticks and time outside the first-to-last observed span cannot be reconstructed.
Empty summaries use null figures, while the CLI refuses an empty/no-data log.

Use a separate collection per server lifetime. A reset that exceeds the prior
counter before the next poll cannot be detected from these lines alone: candidate
and process identity remain the harness's responsibility. Positive int counter
rollover also requires a new run. Startup and save spikes are included; this
module cannot classify them. This module neither polls a live server nor changes
W403's aggregate observer; selecting the raw command is the integrating harness's
responsibility.
