### Concrete blocking object and call paths

`minecraft:chest` and `minecraft:barrel` are in the shipped movable tag, and
[VanillaContainerRocketAdapter](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/forge/VanillaContainerRocketAdapter.java)
lines 29-30 and 44-54 accept them and load their real inventory. They are not
ARCE-owned inventory implementations. Inspection of the exact Forge 47.4.10
classes and six executable A0 diagnostics establishes:

1. `BaseContainerBlockEntity.getCapability(ITEM_HANDLER)` returns its own
   `itemHandler` before calling `super`. A provider added with
   `AttachCapabilitiesEvent` does not wrap that return. The native handler is an
   `InvWrapper` over the actual `Container`; extraction calls `removeItem`
   without an ARCE callback. Chest has its own equivalent handler override.
2. `invalidateCaps()` invalidates the `LazyOptional`, not an already resolved
   `InvWrapper`. The cached barrel handler still extracts one diamond from a
   restored four-diamond payload while the region lock rejects overlapping
   transaction acquisition. Adding a vanilla `Lock` string also leaves that
   extraction available; the lock gates menu opening, not item-handler calls.
3. Returning no capability is insufficient even for ordinary vanilla automation.
   `HopperBlockEntity.suckInItems` calls Forge's `extractHook`, and on its null
   result falls back to `getSourceContainer` / `tryTakeInItemFromSlot`. The latter
   calls `Container.removeItem`. Invoking that unchanged native fallback transfers
   one diamond from either invalidated chest/barrel into a hopper. Direct
   `Container.removeItem` likewise remains available. This is not an assumption
   about a malicious third-party caller ignoring capability invalidation.
4. These methods have no cancellable per-extraction Forge event. Cancelling
   break, interaction, piston or explosion events does not intercept them.
   A region index or a final native readback therefore cannot establish the
   required access exclusion. Suppressing the target's ticker also does not
   suppress an adjacent hopper's access, and suppressing unrelated same-chunk
   activity would violate the design's scope.

This is an in-scope guard gap, not a claim that no alternative architecture can
ever solve container isolation. Replacing native instances/registrations,
changing the adapter contract, staging different terrain or adding bytecode
interception would need a separate design and proof of saved identity, cached
references, reentrancy and reload behavior. None is silently introduced here.
In particular, W148 expressly forbids adding ASM/Mixin to complete this leaf.
