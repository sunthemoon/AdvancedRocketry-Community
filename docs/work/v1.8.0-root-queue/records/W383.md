# W383: the legacy pad occupancy recovery path

## Outcome

The outcome is **a test cause**. The fix is one test-only commit, `94ca9c2f1`. No production code changed, and no log
expectation, bound, timeout or retry changed.

## Which component started the recovery

The server's own `RocketManager` did, through its ordinary journal recovery pass:
`RocketManager.onServerTick` → `RocketFlightService.tick` → `RocketTransferService.tick` →
`RocketTransferRecoveryService.recoverNext` → `recover`. It was not an entity join, the GameTest batch cleanup or a
neighbouring test.

The chain of events in `wideParkedStructureAppearingAfterPreparationRefusesUnnamedPreSpawn` was as follows.

1. The test prepares the launch with a detached `new RocketTransferService()`. The transfer is live in that service
   only. To the runtime's service it is an unclassified PREPARED record.
2. The station fixture waited for entity sections on the pad's own chunk row only. The station pad's z is a multiple
   of 16, so the arrival's ticket set (`RocketDiscoveryColumns`, from `(min - 1) >> 4` to `(max + 2) >> 4`) is four
   columns that also span the row before the pad's. The fixture's region ticket loads those columns, but the fixture
   never waited for them.
3. When one of them was still loading, the test's `spawnDestination` call stopped at the arrival's PREPARED wait
   (`ARCE_ARRIVAL_ENTITIES_LOADING ... columns=3/4`) and never reached the pad recheck. No return to the source began.
4. The runtime's `recoverNext` skips only records that are live or settled in its own service. It took the waiting
   record, kept the source and logged `ARCE_TRANSFER_RECOVERY ... action=KEEP_SOURCE`.
5. The test's wait saw the record leave. Its assertions (source kept, fuel unchanged, nothing created) hold after a
   recovery as well, so the test passed and only the log check failed.

Both known failures carry the `columns=3/4` line for the failing transfer: shared run 44254384368 (shard 0,
log line 6745) and W301F's local full run of 2026-11-05 (`W301F/final/full-latest.log`, transfer `20dbf05f`).

A forced variant confirms the component. With a temporary, uncommitted patch that skips the `spawnDestination` call
and logs a stack trace at `recover`, the log shows exactly the failure's lines (`RETIREMENT_PROVED site=RECOVERED_SOURCE`,
then the KEEP_SOURCE WARN), the stack above with `live=false`, and all six tests passing (stage `forced-log`).

## Can production race the two paths

No. I found no path where the ordinary return and an automatic recovery both act on one PREPARED transfer.

- In production one `RocketTransferService` prepares and ticks the transfer, so the transfer is in that service's live
  set. A waiting arrival stays live. `recoverNext` never selects a live or settled record; the existing unit test
  `RocketTransferRecoverySelectionTest.liveAndSettledRecordsAreNeverSelectedAndAnEmptyJournalChecksNothing` covers this.
- Once a fail-back has begun, `recoverNext` also skips the record because its retirement is pending. Once a recovery
  has begun, the transfer is no longer live, so the ordinary tick no longer visits it.
- An operator's `recoverById` and a reconnect can reach a live record on purpose. They run on the same server thread
  and the same retirement coordinator: `begin` for a record that already has an entry only nudges it and discards the
  second caller's effects, and both paths need the journal reservation first.
- Both paths set the source from the same function, `RocketTransferEntities.stationarySource(record, ...)`, so fuel
  is the same either way. Neither touches cargo. A fail-back refuses when a destination was admitted, and KEEP_SOURCE
  discards destination copies, so neither leaves a duplicate or a lost rocket.

The two-service arrangement exists only in tests. I therefore wrote no production race test.

## The fix (`94ca9c2f1`)

File: `src/main/java/.../rocket/server/LegacyLandingPadOccupancyGameTests.java` (27 lines added).

- `StationFixture.awaitReady` now also waits for every column of the arrival's ticket set (`arrivalColumns()`). The
  80-tick readiness bound is unchanged.
- The test asserts, before the pre-spawn recheck, that the fixture's set covers the prepared record's own
  `destinationTicketSet` and that all of it has entities loaded.
- The test asserts, right after `spawnDestination`, that its own service's coordinator holds the return. A run in
  which the refusal does not happen now fails the test by name instead of passing on a recovery. The forced variant
  shows this: stage `forced-pin` fails with "Pre-spawn refusal did not begin the ordinary return to the source".
