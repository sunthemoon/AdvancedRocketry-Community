# W270: separate chained-flight preparation and landing budgets

The task is a test-fixture reliability change on `codex/v1.8.0-w270`, based on
`9054512715eeebbdd4b75364e57f743f451b279b`. Work is in progress. Production behavior,
retirement constants, status files, the queue, ledger, protocols and persistence formats
are outside this task's write scope. No upstream code or assets are imported.

## Cause and reproduction

`RocketOrdinaryRetirement.start` sets a destination demand's `notBefore` to its admission
tick plus `RETRY_TICKS` (200). `proved` and `prove` request delay 1 for `SUPERSEDING_SAVE`,
but `fail` keeps the maximum of that deadline and `now + delay` at destination sites.
`RocketFillRetirementPacing.admit` independently retains the same admission interval.
Consequently, replacement cannot start its fresh capture on the next tick. The new
capture still needs its own entity store, the barrier's 20-tick force batch, readback,
the other census slot's proof and the journal replacement acknowledgement. Only then
can the new flight start its 60/80/20/80-tick countdown/ascent/transit/descent.

The supplied hosted log's SHA-256 is
`f8605c07ff7017f3a501edc43881dbe970c5396650e69c3fc319b18c04bc50ea`.
Its leg 1 landing deadline includes this predecessor retirement, and expires in ASCENT.

The new sibling uses the same three-leg route and conservation assertions. A test-start
tick callback observes the first BEFORE_REPLACE capture and makes exactly one vanilla
`storeChunkSections` call for its survivor slot. It checks that SUPERSEDING_SAVE and a
fresh attempt are observed. It does not mutate clocks, proofs, retirement queues or
production constants. Its separate serial batch uses the existing discovery and Earth
return-pad setup and restoration.

## Design and affected-test inventory

The unchanged 270-tick landing clock starts only on the requested UUID's PREPARED journal
record for the logical rocket. The independent preparation budget is
`DEMAND_TICKETS * (RETRY_TICKS + ATTEMPT_TICKS) + 100 = 3 * (200 + 100) + 100 = 1000`.
The 100-tick margin covers admission and journal acknowledgements. `MAX_ATTEMPTS` limits
concurrent proofs; it is not a per-demand attempt count and is not used as one.
The outer timeouts use the same arithmetic, with original setup and flight allowances:
3870 for each planetary route, 1620 for the station round trip, 1760 for the Moon round
trip, and 3400 for the Tau Ceti route. No landing allowance or production budget changes.

The same pattern exists in `RocketFlightGameTests` (station and Moon return legs) and
`TauCetiPathGameTests` (descent after docking/warp and immediate ascent after landing).
They now use the same exact-transfer, two-stage wait. Every original assertion remains;
each affected callback additionally checks that preparation happened before its bound.
The planetary failure-only scalar and service observations remain unchanged.

`MoonArrivalGameTests` is not affected: both cases assemble a new rocket and fly one
outbound leg. `MoonLandingRuleGameTests`, `ClassicMilestoneAdvancementGameTests`,
`RocketPassengerPersistenceGameTests`, `RocketPassengerContinuedUseGameTests`,
`RocketLegacyFuelGameTests`, `RocketPropulsionGameTests`, `RocketTransferRecoveryGameTests`,
the bay deployment, arrival-footprint and named-pad cases also have one flight per
fixture, or exercise return/recovery/disassembly instead of launching from LANDED.
The concurrent-flight case launches two distinct logical rockets, not chained legs.
The admission/discovery/interlock classes' multiple calls are refusal/replay or separate
fixtures. `EscrowFillLaunchGameTests`, `EscrowGovernedMarginGameTests` and the governed
warmup/refusal classes retry a pre-launch terrain/admission request or use distinct
rockets, rather than chaining landed callbacks. `RocketPredecessorLaunchGameTests`
starts with a constructed committed predecessor and has its own retirement-aware state
machine; it does not wait a fixed 270 ticks for a chained landing. These tests are unchanged.

## Files and boundaries

The three affected GameTest classes and `RocketFlightGameTestFixtures` are modified.
`RocketFlightLegBudget` and its unit test isolate the deadline policy. The new
`RocketFlightRetirementGameTestSupport` exposes test-only arithmetic and the forced-save
observer in the retirement package without changing production visibility or code.
This record is the only documentation change. There are no new ADR decisions, save or
network changes, asset imports, release tags, merges or pushes.
