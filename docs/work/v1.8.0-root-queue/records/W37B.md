### Latest safe point and the remaining window

In an otherwise uninterrupted native call, the tuple can be restored after
the setter returns and before the sleeping-time event dispatch begins.
The latest pre-listener point is before offset 14 in
`ForgeEventFactory.fireSleepingTimeCheck`; a sleep-specific interception
before offset 127 in `ServerPlayer.startSleepInBed` would also precede it.
Neither is an existing Forge listener boundary owned by this adapter.

A HIGHEST time-check listener is not sufficient for the requested guarantee.
Another previously registered HIGHEST listener can call the public
`player.server.getPlayerList().saveAll()` before restoration, persisting the
bed tuple; if it then throws, restoration never runs. Without that explicit
save, an interrupted dispatch still leaves the tuple exposed to subsequent
autosave, logout or shutdown. The remaining window starts at the native
field writes at 77-93 and ends only when the restoring listener actually
runs; under interrupted dispatch it has no guaranteed endpoint. Ordinary
server-thread serialization does not interleave a queued stop or logout
between individual instructions, but it does not prevent these synchronous
callbacks or guarantee completion after a callback exception.

Cancelling only an exactly attributed native bed setter would avoid the
temporary writes if its cancellation remained final. However, a later
LOWEST listener receiving cancelled events can reverse that cancellation,
and the setter then performs its writes. Forge supplies no reserved terminal
listener or immutable veto. Exact arguments, call-stack attribution and
tuple equality therefore do not by themselves close this final-writer gap.
I did not implement a token, stack-based veto or delayed rollback and call
it a proven boundary.

This is a failure to establish the full assigned guarantee, not a claim
that a HIGHEST restore could never work with a particular cooperative mod
set. Root can evaluate a narrowly scoped interception under a **new ADR and
owner confirmation**, or another mechanism with evidence for the same
frozen scope. ADR-073 authorizes only its IOWorker injection.

### R-036 interaction

W37's `governing` method releases a pending backup when the native tuple is
neither its saved point nor its exact cleared tuple. An exposed temporary
bed tuple can therefore be mistaken for legitimate supersession during a
reentrant logout/reconciliation, or after interrupted sleep dispatch.
Removing a lost backup later by tick cleanup would not repair that loss.
No backup root, direct restore field, supersession rule or schema was changed.
