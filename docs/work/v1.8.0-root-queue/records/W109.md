## Design decisions and changed files

Implementation follows [W11CD](W11CD-DESIGN.md) and [W11B3](W11B3-DESIGN.md),
including the existing ADR-065 cargo note and R-035. Neither policy was changed.

- `rocket/cargo/device/` adds the fixed LOAD/UNLOAD roles, all 27 status members,
  strict schema-1 `arce_rocket_fluid_cargo`, block/entity, lifecycle index, local
  port/exchange, binding/linker, scalar menu and protection handler. Block and
  block-entity IDs are exactly `rocket_fluid_loader` and `rocket_fluid_unloader`.
- Root limits are 32 KiB, depth 20 and 2,048 nodes; the 0–16,000 mB tank reuses
  the native 8 KiB envelope. Escrow allows one role-matched marker within
  256 bytes, depth 8 and 128 nodes. Unknown/future/invalid roots remain raw.
- Capabilities fill only LOAD and drain only UNLOAD, on every side including
  null. Simulation is pure; stale, off-thread, reentrant, unclaimed or locked
  access returns zero. Matching-drain arguments are inspected only after
  acquiring the local guard. Owner container exchange reuses
  `TankContainerExchange.plan` in both directions and does not start escrow.
- Binding checks preserve logical/physical UUID, dimension, owner, locator,
  station, loaded sections, range and passenger/interlock checks. Actual
  coordinates must equal the recorded origin, including sub-block movement.
  The existing ten-tick linker cooldown and selection codec are reused.
- The existing `FluidFuelLoaderItem` and `LoaderCarrier` are unchanged:
  owner/tank only, 12 KiB/depth 18/1,024 nodes, fresh device UUID on placement,
  no binding inheritance, and rejection of item `BlockEntityTag`.
- `resourceescrow/RocketCargoDeviceHold.java` only reads existing protection
  state. No admission, ledger creation, capture, preparation or mutation is added.
  The eleven-scalar menu includes role and relative cursor fields; no operation
  is prepared, so the cursor is absent and eligible bindings show
  `ADMISSION_DISABLED`. There is no new packet.
- `client/RocketFluidCargoScreen.java` is client-only. Registries, creative tab,
  linker dispatch and generator/language entry points append only this leaf.
- Protection reuses `SatelliteBayRoot.nativelyKeepable` and
  `GuardedChunkSaves`. Work-budget excess preserves raw data without denying
  saves; only observed native incompatibility invokes the existing terrain
  guard. Player removal, explosion loot, extraction and live replacement are
  protected. Command/raw replacement remains the recorded residual.
- `V180RocketCargoArt` and `V180RocketCargoData` replace the scaffold's
  loot-only provider. Two original 16x16 textures use distinct teal load/down
  and amber unload/up port marks. Fourteen new generated resources cover
  textures, models, blockstates, loot, shaped recipes and advancements.
  Each language file gains 36 keys: two names, 27 statuses and seven screen
  labels. Recipes use the prescribed hopper/board/casing layout and existing
  `EmptyTankIngredient`; filled or unreadable tanks do not match.
- [Pre-authoring declaration](../../../provenance/v1.8.0-c17a-rocket-fluid-cargo-preauthoring.md)
  precedes resource authoring. [Generated provenance](../../../provenance/v1.8.0-c17a-rocket-fluid-cargo.json)
  records target/generator hashes and shared-language keys. No upstream,
  LibVulpes, Minecraft or Forge asset was copied. Root/human review is pending.

All touched Java classes are below 500 lines (largest: existing `ModBlocks`,
476 lines; largest new class: the 244-line block entity). Domain codec, local
operations, bindings, menu, index and protection are separate responsibilities.

`V180RocketCargoDataTest` tests. Coverage includes both roles, malformed/future

empty-tank recipes, passenger/mount/teleport cut-G2 boundaries, unchanged held
