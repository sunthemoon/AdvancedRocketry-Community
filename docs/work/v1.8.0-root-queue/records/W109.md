### Design choices and incomplete behavior

The registered block and block-entity IDs exactly match W11CD. Both devices use
the single menu type `rocket_fluid_cargo`. The existing `FluidFuelLoaderItem` and
`LoaderCarrier` are reused unchanged, including the historical carrier key,
nonstackability, owner rule and `BlockEntityTag` rejection. A cargo root uses the
existing `RocketEscrowSection` encoding with the additional one-marker,
256-byte/depth-8/128-node bounds and role validation; this preserves C-P's frame
layout without making a propulsion unloader. The new IDs/root are schema 1;
there is no existing-world migration or network packet change.

The native preflight calls `SatelliteBayRoot.nativelyKeepable`, whose work-limit
outcome permits raw preservation. The terrain guard and its saturation lifecycle
are unchanged. This is reuse of the recorded R-035/ADR-065 scope, not a new save
refusal policy. Its behavior on the cargo device is **not yet verified**.

The menu has eleven scalar fields: amount, capacity, two halves of the session
Fluid ID, status, binding presence, role, cursor presence and relative x/y/z.
No C-A operation is prepared, so the cursor currently remains absent. Binding
checks stop at `ADMISSION_DISABLED`; payload selection/publication and escrow
integration are not wired. Existing generic fuel-loader container/screen text
is reused temporarily; cargo names/status translations are not generated. These
are a scaffold, not a completed player-facing feature.
