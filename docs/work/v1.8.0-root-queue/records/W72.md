## 1. The persistence-to-progression seam

`AtomicSavedData.flush(Path)` now calls a static `CommitterSelector` that the persistence package owns. Its default,
`NORMAL_COMMITTER`, returns the normal atomic move. `installCommitterSelector(selector)` replaces it, and `null`
restores the default. The field and the default are package-visible; the install method is public, because the
installer is in another package.

`FirstEventCutSeams.validateAtStartup` restores the default first. When a cut is configured and the empty-server gate
passes, it installs `FirstEventCutSeams::ordinaryCommitter`, which keeps its exact logic (FM12a and FM12b refuse the
progression root's ordinary moves; everything else gets the normal committer). `ordinaryCommitter` is now
package-private.

Why the behaviour is identical:

- Production: no cut is configured, so the selector is the default and returns the same committer as before.
- W44L's cuts: `ordinaryCommitter` only ever differs for `CLASSIC_PROGRESSION`. That root is first obtained by
  `ClassicProgressionSavedData.get(server)` in `ClassicFirstEventDelivery.onServerStarted`, on the line after
  `validateAtStartup`. No other code flushes a progression root through `flush(Path)`; the barrier passes its own
  committer. So the selector is in place before the first ordinary save of that root in every cut run.
- An unknown cut ID, or a refused gate, still throws at startup before the root is obtained, as before.

The journal's root 1 and 2 to root 3 migration in `SavedDataSchemaMigrator` also named two progression classes to
build the empty outbox. `RocketTransferSavedData.emptyFirstMoonLanding()` now supplies the same bytes.

`git grep -n "progression\." -- "src/main/java/io/github/sunthemoon/advancedrocketrycommunity/persistence/*"` now finds
one line, not four:

```text
src/main/java/io/github/sunthemoon/advancedrocketrycommunity/persistence/migration/ManagedSavedDataPayloadValidator.java:26:                case CLASSIC_PROGRESSION -> io.github.sunthemoon.advancedrocketrycommunity.progression.classic.firstevent
```

**Not done, on purpose:** this line is the pre-start validator's table of semantic decoders. It names the root class
of every managed type in the same way (celestial, rocket, station, satellite, endgame, escrow and progression).
Removing only the progression entry would need a registration step that progression performs before the first world
start. If that step were ever missed, every world start would refuse, which is not the identical behaviour the TASK
requires. So this proof criterion is met for the seam and the migrator but not for the validator. Root can queue the
validator table as its own task. The test sources under `persistence` still name progression classes in their
fixtures (`ManagedSavedDataLoaderMigrationTest`, `PopulatedManagedDataFixture`); those are cross-package fixtures.

Tests: `AtomicSavedDataTest` adds a case for the hook (the default, an installed selector consulted by both an
explicit flush and an ordinary save with the type and the normal committer, and `null` restoring the default).
`FirstEventCutSeamsTest` adds a case: production startup replaces a stale selector with the default, and a configured
FM12a cut whose gate refuses leaves ordinary saves on the normal committer.

## 2. The fuel loader's status for a recovery-locked rocket

`FuelLoaderStatus` gains `RECOVERY_PENDING("recovery_pending")` as its last member. The existing eight members keep
their ordinals; `FuelLoaderStatusTest` pins the order.

`FuelLoaderBlockEntity` splits eligibility into `candidate` (every rule except the recovery admission) and
`eligible` (a candidate that `RocketRuntime.resourceMutationAllowed` admits). When no eligible target is found, the two
no-target branches call `waitingStatus`, which shows `RECOVERY_PENDING` if an otherwise eligible rocket of the owner is
in range, and `WAITING_FOR_ROCKET` otherwise. The extra entity query runs only in those no-target ticks, over the same
bounded box. The name follows the hand path, which shows `propulsion.recovery_pending` for the same admission refusal.
No recovery or admission rule changed.

**Wire form:** the status is not sent through `ContainerData`. The loader has no menu, no update tag and no saved
status field (`load` recomputes the status). It reaches the client only in `FuelLoaderBlock.use`, as the translatable
key `status.advancedrocketrycommunity.fuel_loader.<diagnosticKey>` inside the action-bar message. The only wire change
is the new key `status.advancedrocketrycommunity.fuel_loader.recovery_pending`. No ordinal is sent anywhere.

**Text:** the English and Chinese strings are in `V180PropulsionLanguage` and were generated into
`src/generated/v1.8/.../lang/{en_us,zh_cn}.json` by `runData`. `FlightLanguageProvider` writes the historical v0.6
root and loops over every status, so it now skips `RECOVERY_PENDING` the way it already skipped `UNSUPPORTED_FUEL`;
`runData` changed no v0.6 file. `FuelLoaderStatusTest` checks that every displayed status has text in both locales
in exactly one generated root, and that the new key is only in v1.8.

**GameTest:** `RocketResourceRecoveryGameTests.fuelLoaderNamesTheRecoveryLockOfAnOfflinePassengerSource`, in its
own batch `resource_source_loader` (the fixture clears the shared journal). It uses W63's fixture: a PREPARED
bipropellant source with an offline recorded passenger, recovered through both owners to WAITING_FOR_PASSENGERS. The
owner's loader with a queued fuel cell shows `RECOVERY_PENDING` after three ticks, and keeps its saved data, its
queued cell, no target and no buffer. The rocket's fuel is unchanged (2,000 mB hydrogen, 1,000 mB oxygen). Another
owner's loader beside it still shows `WAITING_FOR_ROCKET`. The recovery logs the existing
`ARCE_TRANSFER_RECOVERY ... status=WAITING_FOR_PASSENGERS` WARN twice, so that expectation in
`scripts/gametest_expected_log.json` gains `"resource_source_loader": 2`. No ERROR expectation changed.

**W63's native probe:** `ResourceRestartReleaseProbe` asserted `waiting_for_rocket`, which Root accepted for W63
because the status had no member for the lock. The loader now shows `recovery_pending` in that case, so the probe
requires it. The native W63 matrix was not rerun.

## 3. Links to untracked files in the Markdown check

`scripts/validate_repository.py` keeps the full `git ls-files --cached` inventory that the check already queries
(`tracked_files`), and builds `TrackedTargets`: the tracked files and every directory that holds one.
`TrackedTargets.holds` joins a link target to its file's directory lexically and accepts only a tracked file, a
tracked directory or the repository root. Leaving the repository fails, as before. The comparison is case-sensitive,
as on Linux. The W61 correction-file rule and its inputs are unchanged. `markdown_link_report` and
`markdown_link_errors` take the inventory as an optional argument, which defaults to the repository's index.

New tests in `MarkdownLinkInventoryTests`: links to an untracked file and to an ignored ZIP fail, while a code span
naming the ZIP is not a link; links to a tracked file, a tracked directory, the root and the file itself pass, even
when the tracked target was deleted locally; a wrong-case link and a link out of the repository fail. The two bounded
tests use non-Git directories, so they now pass an empty inventory explicitly; their assertions are unchanged. The
patched report in the real-tree test accepts the new argument.

The new check found one real broken link: `records/W69.md:83` linked `W21b.md`, but the tracked file is `W21B.md`.
