## 1. Plan (committed before any code)

The task changes how an ordinary return and its recovery wait or proceed, so it follows the persistence-slice rule.
No saved format, journal schema, hash, bound, proof rule, lease, budget or timeout changes, and no assertion is relaxed.

1. **W98-R3, the discarded copy's column.** Where an attempt now refreshes only the source origin's flight ticket
   (`keepLoaded` in `start`), it refreshes the same ordinary flight ticket (the transfer-keyed `arce_rocket_flight`
   ticket every ordinary flight holds on its origin columns) on each census column that is an end's origin column. The
   I1 and I2 census holds only origin columns (R4); an I3 discarded slot off the origin column gets no ticket (W90 allows
   one column per end) and keeps its existing `SLOT_UNLOADED` hold. No new ticket type, governed or margin ticket. The
   source keeps today's origin load; the destination column, already checked loaded, gets only the refresh.
   GameTest: REMOVE_DESTINATION_KEEP_SOURCE with the destination copy in a cold Moon column held only by flight tickets,

## 5. The design as implemented, and choices

- **R3 tickets.** The refresh is the ticket the ordinary flight already holds (`arce_rocket_flight`, keyed by T's
  transfer ID), on the destination's origin column only when that column is in the census. For I1 and I2 that covers
  every census column (R4 keeps all candidates on origin columns). An I3 slot off the origin column gets no ticket and
  keeps today's `SLOT_UNLOADED` hold: W90 allows one column per end. The destination column is refreshed, not loaded;
  the attempt has just checked it loaded.
- **The escrow rule.** `RocketTransferEscrowRules` has one private rule body. The existing overload keeps its order and
  its `resourceMutationUnproved` check; the token-aware overload checks L's actionability, with the caller's own
  reservation recognized, before any bay boundary, exactly as the coordinator's copy did. Both orders are unchanged,
  so a bay gate sees the same calls as before.
- **The port.** Every check of `start`, `prove` and `finish` runs in the same order with the same reasons and logs;
  only the place of the server calls moved. The save-off WARN now names the slot's dimension, which is the same
  `ResourceLocation` as before. `tick()` no longer takes the server; each entry ticks with its own port's clock.
- **Mixed batches (W98-R10, second bullet).** A batch with only governed or only ordinary attempts runs the unchanged
  `forceBatch` code, so governed-only behavior and its native cuts are untouched. In a mixed batch a governed attempt
  fails only on a governed own-store failure, or on the failed force of a worker that a governed attempt uses; then
  the whole batch fails as before. Otherwise only the ordinary attempts fail, uncounted. Every ordinary capture uses
  its Level's entity worker, so a governed ENTITY endpoint in the same Level shares that worker: a failed force there
  is the governed attempt's own failure and still fails and counts it. The force count per worker and batch, the
  readback order and the labels each sink sees for an all-governed batch are unchanged.
- **Test seams.** `stageForTests` in `EscrowBarrier` and the read-only `attempts(L)` and `reason(L)` in the coordinator
  exist for tests; neither changes production state.

## 6. W98-R6: why it is withdrawn, and the options for Root

The task's rule: pass `offlineAllowed = true` exactly when the PREPARED record's recovered source never left its pad,
judged by its loaded image (COUNTDOWN, or stationary at its origin). It was implemented in `1c9c88a4` with a unit test
and three GameTests, and on the commit without it the two GameTests of that side failed as intended
(`gt-unfixed-923f76ab`). The full GameTest on `4ffa8c56` then failed two existing tests:

- `RocketResourceRecoveryGameTests.offlinePassengerRecoveryLocksBothBanksAcrossRepeatedReloads`;
- `RocketResourceRecoveryGameTests.fuelLoaderNamesTheRecoveryLockOfAnOfflinePassengerSource`.

Both get RETRY_LATER where they assert WAITING_FOR_PASSENGERS (`gt-full-4ffa8c56/latest.log`, SHA-256
`83afa671c69802994fb51b473002c74c2bc9ca12104bca294c0bd13967ebdfc4`, lines 5256 and 5772). Each test first recovers
an in-flight source with an offline passenger through the installed service, which returns it to its origin and holds
it. A second, fresh recovery owner then recovers it again, as after a restart; the first test goes on to reload the
entity from its saved NBT and repeat this three times. The second owner sees an image stationary at its origin, so the
rule retires T without the passenger, although the rocket flew.

The image cannot tell the cases apart:

- **A source that recovery already returned.** Recovery writes the same stationary flight data as a countdown
  cancellation (`stationarySource`). Once that image is saved while recovery waits, a restart sees "stationary at its
  origin". This is the case the two tests pin.
- **A stale COUNTDOWN image (inferred).** An autosave during the countdown keeps COUNTDOWN on disk while the rocket
  then launches. T stays PREPARED through ascent and transit, and the rocket entity is not saved again before a crash.
  A passenger who logged out in flight was saved in the air.

In both cases the rule would retire T, and the offline passenger would later log in where their save put them, with
no record to remount them: the fall residual that R-035 already names, widened to offline crews across restarts.
Before W116 (and after `82905b4b`), recovery waits for them and the reconnect remounts them at the pad.

Options, for Root to decide:

1. **Keep recovery waiting (today's code)** and record W98-R6 as a named R-035 residual: a countdown cancellation
   killed before its proof holds its offline crew's return until they reconnect. Safe, one rocket per hold.
2. **Accept the rule as stated**, and change the two tests' expectations as a deliberate Root decision, with the
   widened fall residual above added to R-035.
3. **A durable cancellation intent** (for example, a phase or marker written before the in-memory return), which would
   let recovery know the countdown was cancelled. That is a saved-format change, outside this task.

My recommendation is option 1 now, with option 3 considered with N3-B if crew holds turn out to matter in play.
