### F4: the bounded refusal path (W192 option F4-A)

- **Bound before the copy.** The classic serializer (all seven types) and the small plate press serializer now run
  the bounded `RecipeJsonSignature.canonical` walk before `json.toString()`. The electrolyzer, rolling and precision
  serializers already did. The set of accepted recipes does not change: the classic codec already ran the same walk
  on everything it accepted, and every field of a small plate press recipe was already checked as strictly. Only the
  message of some refusals changes (below).
- **`null` instead of a throw.** Each of the five serializer classes overrides Forge's
  `fromJson(id, json, context)` and calls `RecipeRefusalLedger.decode`. While the reload that owns `context` has an
  open ledger, an `IllegalArgumentException` or `JsonParseException` is recorded and the result is `null`. Forge's
  RecipeManager then logs its INFO line "Skipping loading recipe ... as it's serializer returned null" and registers
  nothing, as before. Without a ledger (data generation, direct calls, `IContext.EMPTY`, a call after the reload) the
  serializer throws as before. Other exceptions always propagate.
- **One summary per reload.** `RecipeRefusalReload` opens a ledger at `AddReloadListenerEvent` under the reload's
  `ICondition.IContext` and adds a listener whose apply step logs the summary and closes the ledger. Forge appends
  event listeners after vanilla's, and apply steps run in order, so it runs after RecipeManager. The summary is one
  ERROR entry of at most 1,024 characters: the count, the reasons with their counts (at most 16 by name, the rest as
  `other`), and the 8 smallest recipe ids with their reasons. Parts that do not fit end with ` ...`. The detail and
  stack trace of the first 64 refusals per reload go to DEBUG under the logger `...machine.recipe.RecipeRefusalLedger`.
- **Lifecycle (AGENTS.md section 3.3).** Open ledgers are kept in a static weak map keyed by the reload's context,
  which Forge's `ConditionContext` compares by identity. The flush removes the ledger. A reload that fails before the
  flush leaves its ledger to be collected with its context. A ledger holds only diagnostics, never world state. This is
  stated in the class's Javadoc. It is not a protection that refuses a save, so no risk-register entry is needed.

### F5: a vanished tag (W192 option F5-B)

`BoundedItemIngredientCodec.resolveAlternatives(JsonElement)` collects a tag's items into a copy of the alternatives
(at most 32 entries, so the copy is bounded). It keeps the copy only if every item of the named set reports
membership (`holder.is(tag)`), and it stops at the first item that does not. After a reload whose data drops a tag,
the registry keeps the named set with its old items but rebinds every item without it, so the tag now contributes
nothing, which is what both the codec and vanilla see after a restart. If nothing is left, the existing "machine
ingredient has no bound alternatives" refusal disables the recipe. The membership check runs before the item checks,
so a vanished tag is absent even if it held an item that would now be invalid. The 32-variant bound still applies to
a defined tag. This covers the classic, electrolyzer, rolling and precision recipes, which share the method.

### W192's side note: duplicate keys

Vanilla parses a data-pack file with Gson, which keeps the last of two equal keys, so the classic codec's
"Duplicate recipe field" refusal (`ClassicRecipeCodec.java:108`) cannot fire for a data-pack file: the serializer
decodes `json.toString()` of a tree that has no duplicate keys. The check stays in place. It still guards
`ClassicMachineRecipe.Serializer.fromNetwork`, which decodes the raw string that a server sends.

## Choices where the TASK or W192 was open

- **Reason length.** W192 suggested cutting a reason to 48 characters. Several of the mod's codec messages are 49 to
  68 characters (for example "recipe has missing or unexpected top-level fields"), so the cut is 72 characters. The
  1,024-character bound on the whole summary is unchanged.
- **Which ids.** The summary names the 8 smallest ids in string order, not the first 8 decoded, because RecipeManager
  iterates a hash map. The summary is then the same on every run, which lets the log manifest match it exactly.
- **Reason of a refusal.** It is the message of the innermost `IllegalArgumentException` or `JsonParseException` in
  the cause chain, which is the codec's own short message rather than a serializer's wrapper ("Invalid Electrolyzer
  recipe <id>: ..."). The recipe id is replaced by `<id>` so that equal reasons count together.
- **Per serializer type.** W192 suggested counts per serializer type and reason. The TASK asks for the count, ids and
  reasons, so the summary counts by reason only; each named id shows its own reason.
- **The F5 GameTest.** The TASK asks for a test that reloads without the tag and fails first. That is the unit test
  `VanishedTagIngredientTest`, which binds the registry's tags without the tag, as a reload does. The GameTest adds
  the same check after a real data-pack reload, without a separate failing-first run.
- **The ADR number.** ADR-076 was the next free number on every branch at the time of writing. Root may renumber it.

## Known risks

- A third-party mod that calls `RecipeManager.fromJson` with the server's context during a reload, before the flush,
  now gets `null` for a refused recipe of this mod instead of an exception. Forge allows `null`; such a caller may not
  expect it.
- A refused recipe's stack trace moves to DEBUG; its reason stays in the summary.
- F5 deliberately differs from vanilla ingredients until the next restart: vanilla crafting recipes and the small
  plate press (which matches through vanilla `Ingredient.test`) still accept a vanished tag's old items. A remote
  client receives the stale named set as a defined tag, so its JEI may still show a recipe that the server disables
  (display only; W192 section 3).
- The membership check reads `Holder.tags()`, which throws if a holder's tags were never bound. A named set can only
  be iterated after a binding that also binds every registered holder, so this is not reachable in practice.
- The ADR's line numbers belong to Forge 47.4.10; a Forge update can move them.
