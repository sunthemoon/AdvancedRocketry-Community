### The gate

- The mode is selected only when the release-test hooks are on, `escrowScenario` is `verify`, and `escrowCase` is one of
  `FF_X03_OBSERVE`, `FF_X03_UNLOAD` and `FF_X03_LAUNCH`. Without the hooks every combination is inert.
- `EscrowCargoCutProbe.accepts` includes the three cases, so the existing cargo-cut branch of `EscrowRuntime` routes
  them. `selected` returns false for them under `start` and `recover`, and false for every existing case under `verify`.
- `attach` throws, before any probe is created, when the hooks are on and exactly one of "the scenario is `verify`" and
  "the case is an X03 case" holds. The probe's constructor checks the same gate and
  `EscrowTestEndpoints.requireEnabled` before the base class takes its chunk tickets.

### The probe

Every case waits for the fixture chunks, the existing ledger (load-only lookup; it never creates one), the checked
journal, an operational coordinator and an idle writer, and for the 400 ticks that the seed's protected restart also
waits. It then requests one full save, waits for the journal's acknowledgement, and reads the server's state.

| Case | Behaviour | Result line |
|---|---|---|
| `FF_X03_OBSERVE` | Nothing further. | `ARCE_RELEASE_CARGO_CUT_RESULT cut=FF_X03_OBSERVE state=OBSERVED ...` |
| `FF_X03_UNLOAD` | Logs the first observation as `ARCE_RELEASE_CARGO_VERIFY_OBSERVED`. Names the device with `EscrowCargoSwitches.forTests(..., FLUID_CARGO_UNLOAD, device, true)`, withdraws the switch when the ledger shows the operation, waits for the retirement (no ledger record, no markers, idle writer), and saves. | `... state=UNLOADED named_device=<id> switch=withdrawn ...` |
| `FF_X03_LAUNCH` | Logs the first observation. Calls `RocketRuntime.requestAdminFlight` once (logged as `ARCE_RELEASE_CARGO_VERIFY_REQUEST`), waits until the same logical rocket is LANDED somewhere other than where it stood, waits for the journal and the ledger to be at rest, and saves. | `... state=LANDED route=... code=... debit=primary:..,oxidizer:..,revision:..,resource:..,catalog:.. fuel_before=.. fuel_after=.. landing=<dimension>,x,y,z ...` |

Each observation reports: the rockets in the fixture area and in all loaded Levels; the rocket's cargo, epoch, markers,
IDs, flight state, fuel and `resourceMutationAllowed`; the device's tank, epoch, markers and ID; the number of journal
entries and the journal's action authority; and the ledger's schema, generation, and counts of records, floors,
receipts, READY heads, ARMED flights, fluid accounts and the launch serial. The probe asserts nothing about amounts.
Each step is bounded by 6,000 ticks.

## Choices where the design was open

1. **Any other case under `verify` also stops the start.** The design says the existing cases "are not accepted" under
   `verify`. Not selecting them would let the dispatch reach the generic release fixture, which creates objects. `attach`
   therefore throws for `verify` with any case that is not one of the three, including no case. No existing runner uses
   the value `verify`.
2. **An X03 case with no scenario at all also stops the start**, as "any other scenario".
3. **The launch route is a runner property.** The design fixes the route in the runner, so the probe reads
   `advancedrocketrycommunity.escrowVerifyRoute`, a `RocketDestination` name (`EARTH`, `MOON`, `SPACE_STATION`);
   absent means `MOON`. An unknown value refuses in the constructor. The skeleton's command builder passes it only for
   the launch case.
4. **A repeated request only for `DESTINATION_LOADING`.** That code means no flight was started and asks for a fresh
   request. The probe repeats the request then, every 100 ticks and at most 20 times. `SUCCESS` and `JOURNAL_PENDING`
   count as accepted; every other code fails the case.
5. **The journal's baseline write.** A journal that was only loaded has no acknowledgement, and a full save does not
   write a clean journal. Like every existing cargo cut, the probe therefore calls `journal.retryChecked`, which lets
   the journal write its own unchanged content once. X03-B should expect the transfers file to be rewritten in every
   verification start when it derives the file lists of section 3.6.
6. **The save covers every Level.** The probe's save flushes the entity storage and the chunk writer of all Levels, not
   only the overworld, so that a landing in another dimension is on disk.
7. **A separate tag for the intermediate observation** (`ARCE_RELEASE_CARGO_VERIFY_OBSERVED`), so that a runner that
   waits for the result line does not stop the functional cases early.

## Known risks

- **The probe's waits are untested natively.** In particular: whether an Earth-to-Moon admin flight of the fixture
  rocket is accepted and lands within 6,000 ticks; whether the typed debit is visible in the journal record (otherwise
  the line says `debit=unobserved`, and `fuel_before` and `fuel_after` remain); and whether the unload's operation is
  seen in the ledger before it retires (the probe also accepts a changed epoch or tank as the sign).
- **`FF_X03_OBSERVE` after the launch** reports only loaded rockets. After a restart nothing loads the landing chunk in
  another Level, so that observation is expected to say `rockets=0 rocket=absent`; the oracle has to read the landed
  rocket from the files. If X03-B needs the probe to load the landing site, that is a further Java change.
- The misrouting refusal is a server crash by design; a runner with a wrong scenario fails at its first tick.
- The open GameTest failure above.
