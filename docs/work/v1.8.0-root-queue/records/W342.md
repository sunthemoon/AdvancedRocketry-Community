## The failure in full run 1

`coalescedAndAutosaveRequestsArePublishedOnLaterTicks` (batch `satellite_registry_tick`) checks that the registry
commit covering its change was requested by the 100-tick coalesced flush, that is, that
`SatelliteManager.coalescedFlushes` rose. Any other registry write request in that window covers the change first and
fails exactly this check: for example the periodic autosave (every 6,000 server ticks, `saveEverything`, whose
DataStorage save requests the registry write), or a write still queued from an earlier batch. The class comment
relies on each batch running alone. It failed 0.4 s into its batch, 47 minutes after the new batch had finished.

Why I read it as unrelated to W342:

- The new tests touch the registry only inside their own batch (two registrations and their cleanup), and the new
  batch does not change the other batches' relative order (800 batches with it, no HashMap resize).
- The filtered run with the new batch, the failed test's predecessor and the test, in run order, passed.
- The new batch does add ticks before every later batch, which moves where the 6,000-tick autosave falls. That
  could expose a timing assumption in the test but is not a defect of the new tests.

I did not find the request that produced the commit: no writer line names it, and the autosave logs only at DEBUG,
which these logs do not hold. No earlier record names this failure. Full run 2, at the same commit, passed all
1,855 tests, this one included, so the failure did not repeat. Root may want to watch it in hosted runs.

## Choices where the task was open

- **The guard.** No production check named "consumed state" exists in the ordinary rebuild, so the negative check
  disables the two points that carry the property (section 3 of the cut list), not one invented check.
- **One Level.** Both ends are in the GameTest's own Level, as in every bay GameTest. The decision and the rebuild do
  not depend on the Level; the cross-Level save gap is what the native assessment covers.
- **R3's state.** An unconsumed record with registered satellites and retired receipts is unreachable under W27A
  section 5 condition 3, so R3 uses the reachable case, a group that never registered (W27A section 7: unresolved
  packages fly on unconsumed). It adds no REJECTED receipts, which W27A says never block and which have their own
  tests.
- **Registry comparison in R2.** The proof spans many ticks, during which a solar satellite's state may advance, so
  R2 compares the owner's satellite IDs and each entry's owner, definition and launch time instead of whole records.
  R1 compares whole records, in one tick.
- **Reload.** "Stable across a reload of the SavedData" is checked on the acknowledged journal file on disk, read with
  `RocketTransferSavedData.load`, plus an NBT round trip of the surviving entity.

## Known risks

- The GameTests prove recovery's behaviour on a state built in RAM. They do not prove that a native crash reaches
  that state; that remains the native assessment's open question, and B6.5's native row stays NOT_COVERED until such
  a case runs.
- The rebuilt destination enters live descent on the tick after recovery; each case asserts and cleans up in the
  recovery tick, so a later change that makes recovery finish across ticks would need the cleanup to follow it.
- With the new batch the run has 800 batches, far from the next HashMap resize (1,536), so the other batches keep
  their relative order. It does run between two existing batches, so an unrelated failure right after it should be
  read as a placement effect first.
