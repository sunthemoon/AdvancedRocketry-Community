# W226: finite gas canister exchange (PAD-D4)

## Design note (before implementation)

The assigned branch is `codex/v1.8.0-w226`, starting at `f2261aefedb63d9a7551c0d007bcdd00c7df9ec3`.
Write scope is the new gas-pad domain, codec, block adapters, data provider, tests and this record; the existing
canister item-use bridges, armor editor and registry/data-generator entries may change for this slice only.
No status, ledger, build, workflow, accepted ADR, other task or other worktree file will change. No push or delegation.

The pad owns a schema-1 single-gas bank (0 to 16,000 mB) and two one-canister slots. A filled input adds exactly
1,000 mB and becomes empty. An empty output consumes exactly 1,000 mB and becomes filled. Each operation prepares
one complete next pad value before publishing it: bank and slot never publish separately. The pad uses no FE.
Configuration and redstone pause new work; safe output withdrawal remains possible. Item use inserts into the
appropriate empty slot; empty-hand use withdraws output (sneaking selects input). The fill-only fluid adapter accepts
only oxygen/hydrogen. No standing-player charging is implemented, including for the integrated owner.

The player-local editor selects gas from the actual oxygen/hydrogen canister. It edits exactly one installed matching
tank, otherwise the first EMPTY tank in position order. Invalid/duplicate-gas layouts, unsupported roots, external
provider chests, disabled configuration and less than 1,000 free units refuse unchanged. An enchanted native chest
accepts only oxygen into its active buffer. Normal oxygen use retains the existing active-buffer interaction;
sneaking oxygen use requests the new tank editor, and hydrogen use requests it directly. Even creative use of this
finite route consumes one filled canister and returns one empty canister.

Preparation validates bounded roots before copies, snapshots exact inventory references/counts/tags and chest, and
reserves a return slot or merge for an empty canister. A single held canister may be replaced in its own slot. Stacked
canisters require another inventory destination. No room means no debit, and no item entity is ever spawned. Commit
revalidates the connected, live, nonspectating real player on the server thread, selected slot/hand, all affected
stack identities/counts/tags, chest identity and configuration. Publication uses prepared values without intervening
callbacks. Plans are one-shot and are not persistent receipts.

An undecodable pad root is retained, inert and protected from ordinary removal. Native-unwriteable roots use the
existing whole-chunk guard, not a BlockEntity save exception. The exact R-027 scope addition and ADR-066 note are
drafted outside Git for Root with an audit script; Root must apply and review those notes before integration.
There is no new lifecycle hook, Access Transformer, Mixin, receipt, readback, prompt save or automatic protocol.

The pad-to-player inventory move remains ordinary vanilla container tearing (ADR-054): independent saves can lose
or duplicate the moved item. The refill itself is local to one player's saved inventory, not cross-store atomicity.
W174-R13 also remains: switching a dedicated-hosted world to an integrated host can restore stale `level.dat` Player
inventory in either direction. Before that switch, validated whole-world repair must remove the stale Player tag or
replace it with the intended host's current playerdata. This slice does not perform that repair or accept its risk.

### Key design decisions

- The stable block/item ID is `advancedrocketrycommunity:gas_charge_pad`; the pad root is `arce_gas_charge_pad`,
  schema 1. Future/invalid roots are retained inert instead of reset. A future schema requires an explicit decoder
  or migration, not reinterpretation of this schema. Existing suit/module IDs and schemas are reused unchanged.
- The pad supports plain oxygen/hydrogen/empty canisters only. Metadata or serialized Forge capability payloads
  refuse rather than being erased by its compact slot representation. It has a fill-only fluid capability, bounded
  16,000 mB bank, two one-item slots and one immutable bank/slot publication. It never scans or credits players.
- The player editor uses the existing strict armor codec. It prefers the matching gas tank, otherwise the first
  EMPTY position, and refuses duplicate gas, unsupported roots, partial room or an unavailable empty-canister
  destination. Enchanted native chests receive oxygen active-buffer units only; external providers are not edited.
  Normal oxygen use retains the old active-buffer route; sneak-use selects the new tank route. Hydrogen uses it
  directly. Offhand and single-source-slot replacement are supported; stacked use needs a separate return slot/merge.
- Revalidation checks connected real player membership, server thread, life/spectator state, selected hand/slot,
  count, reference/tag witnesses, chest and configuration. Prepared slot/chest values publish directly into vanilla
  inventory storage, without item callbacks, capability calls, add/drop or prompt saving between publications.
- Even creative finite use debits one filled canister. The item adapter returns the untouched pre-use stack after
  publishing native inventory: this takes vanilla `ServerPlayerGameMode.useItem`'s unchanged-stack fast path instead
  of reinstalling a result and restoring its creative count. Normal inventory broadcasting synchronizes the slots.
- Redstone/configuration pause new pad work, not safe withdrawal. No new lifecycle hook, AT, Mixin, receipt,
  readback, network channel, configuration key or persistence framework was added. Art is original procedural art;
  no upstream or official artwork was copied.

### Known risks

Pad-to-player and external capability/container transfers remain ordinary independently saved stores: every
unmatched transfer may lose or duplicate the moved item (ADR-054). Neither single-root pad publication nor local
inventory publication establishes cross-store exactly-once or S2 crash durability.

W174-R13 remains in either direction: dedicated-to-integrated hosting may restore the stale `level.dat.Data.Player`
inventory, including refilled tanks, possibly for a different UUID. The mod neither logs nor enforces repair.
Before that switch, validated whole-world repair must remove the stale tag or install the intended host's current
playerdata; after a saved rollback, restore a consistent whole-world backup.

Malformed/future pad roots are retained inert and ordinary removal is blocked until compatible decoding/offline
repair. Native-unwriteable roots use the existing GuardedChunkSaves whole-terrain-chunk denial; saturation after
256 coordinates extends denial to that Level until it closes. Retry ERROR pairs/stacks have no total log cap,
and dirty state does not prevent unload. Recovery requires offline backup, scoped repair, restart/native save
and conservation checks. Forced commands and third-party movers bypassing ordinary Forge policy remain outside
that protection. The audited external drafts describe this exact scope/duration/logging/recovery for Root to apply
before integration; they are not risk acceptance or an applied ADR.
