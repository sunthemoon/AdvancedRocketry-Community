## J19: the observer

### 1. Does the wire allowlist allow only reads?

Yes. `T/w509_jdwp.py:12` allows ten commands, and `Client.command` refuses any other before sending
(`w509_jdwp.py:52`). I checked each number against the Java 17 JDWP command table from memory, not from the
network: VirtualMachine ClassesBySignature (1,2) and IDSizes (1,7); ReferenceType Signature (2,1), Fields (2,4)
and Instances (2,16); ClassType Superclass (3,1); ObjectReference ReferenceType (9,1) and GetValues (9,2);
ArrayReference Length (13,1) and GetValues (13,2). None of them writes a field, invokes a method, suspends or
resumes a thread, loads or redefines a class, sets an event request or ends the VM. The reply parsing matches
the specification's layouts for all ten.

Three limits apply to that answer.

- **F1 (medium). `ReferenceType.Instances` stops the server while it runs.** `w509_jdwp.py:112` sends (2,16)
  for `ServerPlayer` in every snapshot (`w509_jdwp.py:126`), so twice per frame and 192 times per row. HotSpot
  answers it with a heap traversal inside a VM operation at a safepoint, and tags the objects it visits. No
  thread is suspended in the JDWP sense, so the receipt's `suspended: false` is true, but all server threads stop
  for the length of the walk. With `-Xmx3G` this is unmeasured. Case: two walks of 1.8 seconds each plus a
  0.4-second capture exceed the four-second budget at `w509_jdwp.py:157`, the second snapshot raises
  `TimeoutError` after the PNG is written, and the request fails. Fix if the observer is kept: find the player
  once per connection and reuse its object ID for the second snapshot, or reach it through static fields with
  ReferenceType.GetValues (2,6), which is also a read.
- **F2 (low). The allowlist binds only this client.** Between frames the agent listens without authentication
  for the whole session. Any local process that connects has the full debugger: method invocation, field
  writes and class redefinition. The port is on loopback only, so this needs a process already on this PC.
- **F3 (low). The tests do not pin the allowlist.** See "Tests" below: adding (1,18), (11,2) or (9,7) to
  `ALLOWED` passes all 18 tests.

### 2. The agent

`T/w509_runtime.py:6` is `-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=127.0.0.1:0`: loopback,
ephemeral port, no start-up suspension. It is inserted only into the harness's `server_command`
(`w509_runtime.py:25-27`), and the client connects only to a port printed by the `CapturedProcess` that was
launched with that flag (`w509_runtime.py:33-38`, `:50`). The agent lives inside the server JVM, so it is gone
when the harness's process job stops the server. I confirmed that `session.py:139-140` calls both patched
names through its module globals, that `CapturedProcess` exposes `process`, `lock` and `lines` as the hook
expects (`scripts/campaign_client/processes.py:119-156`), and that round 07's J19 server console has 358 lines,
far below the 10,000-line buffer that holds the first port line.

- **F4 (medium). A re-run under another label loses every frame.** The hook adds the agent for any label that
  starts with `j19-` (`w509_runtime.py:22`), but accepts a frame only when the frame map's session equals the
  label (`w509_runtime.py:47`). Round 07's completed J19 cells are the folders `j19-r6-s0-r1-w492op1` to
  `j19-r6-s5-r1-w492op1`. A run with such a label starts the agent and then refuses all 16 screenshots of
  the cell with "J19 frame is not bound to its owned running server".
- **F5 (low). The agent is added to sessions with no mapped frame.** The older `j19-s*` labels and the
  `j19-r6-sN` labels without `-r1` get the listener and never use it.
- **F6 (low, not measured). The flag changes more than attachment.** The JVM runs with the debugger's JVMTI
  capabilities for its whole life, which costs some JIT optimisation and makes exception paths slower. This
  changes timing, not results. The console gains one "Listening for transport" line at start and one after each

### Recommended readback for J19 step 1

operations, and do not schedule the JDWP observer.** Beside each of the 96 frames, record the controller's
identity root, its `arce_classic_machine.structure`, and `arce_classic_hatch.energy` of its power-input hatch,
whose position is in that structure.

Reasons:

1. W505 left one question on this step: whether an unformed controller that shows 0 FE really stores 0, after
   the formed one showed 10000 FE. The menu array cannot answer that. Slot 6/7 is what the screen draws, so the
   observer would record 0 beside a screen that shows 0. The hatch's own `energy` answers it: if it still reads
   10000, the screen's 0 FE means "no formed structure to sum over", and Root can record that as a wording
   observation instead of a pass by echo.

   `readOpening`, which sets only slot 15 (menu lines 19-21 and 32-38), and `refresh()` returns at once when the
   controller is null (line 45). Every other number on the screen can only arrive through vanilla's data-slot
   packets from the server array.
3. In step 1's frames there is no job (W505 reads "Survey: None / analysis: None"), so the slots that only the
   menu computes are constants or follow from the formation state.
4. It adds no instrument. `data get block` requires already run in every J19 request, so the 92-minute row is
   not put behind a debugger that has never met a JVM.

Its risk: it does not read the status code, the diagnostic cell or the selection from the server. Those stay
judged from the frame and from C6's source. If Root decides that the oracle needs the literal array, the JDWP
observer is the only way without a change to C6. Then fix F1 and F4, restrict the agent to the six mapped labels
(F5), pin the allowlist by equality (F3), and run one cell (16 frames) as a trial before the other five.
