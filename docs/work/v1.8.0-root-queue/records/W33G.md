## F1-R: Forge fluid placement

### Why `forceSolidOn()`, and why nothing narrower exists

Forge 47.4.10 `FluidUtil.tryPlaceFluid(player, level, hand, pos, IFluidHandler, FluidStack)` (the `ItemStack`
overload delegates to it) admits a cell when it is air, **or** `!state.isSolid()`, **or**
`state.canBeReplaced(BlockPlaceContext)`, **or** a `LiquidBlockContainer` accepts. If the container refuses, it falls
through to `BlockWrapper`, whose `fill` calls `destroyBlockOnFluidPlacement` (`Level.destroyBlock(pos, true)` for a
non-solid, non-liquid block) and then `setBlock(..., 11)`. Neither call has a veto. For the torch, only the
non-solid clause is open: `replaceable` is false and the container already refuses quarantine.

`isSolid()` returns the per-state field `legacySolid`, set by `calculateSolid()` in `initCache` from
`Properties.forceSolidOn/forceSolidOff` or the cached collision shape. It cannot see a position or a block entity.
I rejected these alternatives:

- A solid collision shape changes movement and the mounting shape.
- A separate quarantined block, or a state property, would have to change in the world on every pair-catalog reload,
  and needs new IDs, data generation and a migration.
- Accepting quarantined torches in `canPlaceLiquid` and refusing in `placeLiquid`: `LiquidContainerBlockWrapper.fill`
  returns 1,000 mB regardless, so the tank would be drained and the fluid lost. The bucket would be emptied the same
  way.
- Restoring the torch from `onRemove` after `destroyBlock`: a re-entrant `setBlock` inside the removal, and the tank is
  drained anyway.
- A Mixin is not allowed (ADR-073).

### Side effects of a solid unlit torch

`forceSolidOn` makes `isSolid()` true. `blocksMotion()` is `isSolid()` unless the block is cobweb or bamboo sapling,
so it is true as well. Collision, the outline, light, occlusion, suffocation and view blocking do not change: the
default `isSuffocating`/`isViewBlocking` also need a full collision shape, which stays empty. The atmosphere seal
scans in this mod use collision shapes, and no source in this mod calls `isSolid()` or `blocksMotion()`.

(`forge-1.20.1-47.4.10_mapped_official_1.20.1.jar`, SHA-256 `95eecc59…d71e`). The scan covered method references to
`isSolid()Z` or `blocksMotion()Z` on any owner, including method handles. It found 34 references in 33 classes, which
`javap -p -c` resolved to the methods below. I then followed the heightmaps built on `blocksMotion` to their users.

**Decision.** The neighbour and attachment effects are real but small, and none touches a torch's own identity. A
narrower mechanism does not exist without a Mixin. F1-R is a High-severity permanent identity loss through a
standard Forge API, so I kept Root's recommended mechanism. The portal case is the only new removal route the change
creates, and it is a direct `setBlock`, outside the protected routes. Root may decide differently on any row.

## F2-R: the nine-chunk neighbourhood

`TorchWorldChanges.neighbourhoodLoaded` replaces the axial and second-ring cell check. It requires
`CombustionAir.loaded` for the torch cell (build height, world border, FULL chunk). For the torch's chunk and its eight
neighbours, it requires `hasChunk` **and** `getChunkNow != null`. `hasChunk` alone would admit a FULL-level holder
whose chunk is still loading, and reading that holder would block. Neither call acquires a chunk or adds a ticket.

Every cell within two blocks along an axis is inside these nine chunks, so the new check contains the old one. The
only exception is the old world-border clause for neighbour cells. Reading a FULL chunk beyond the border acquires
nothing, so that clause has no counterpart. `extinguish` (both modes) and `relight` run the check before any native
read, and `admit` reruns it after the cancellable preflight. A deferred conversion keeps its bounded queue entry. A
deferred relight returns before `CHANGED`, so nothing is spent.

**What it covers.** This is the neighbourhood vanilla guarantees its own block ticks: the eight neighbours of a
ticking chunk are FULL. It covers the `UPDATE_ALL` shape updates, a neighbour's own reads such as the re-review's
stair reading its diagonal front cell, and `BlockEntity.setChanged`'s comparator output.

**What it does not cover.** A callback chain that reaches beyond those nine chunks, such as long redstone or observer
propagation, is vanilla's own behaviour for any block change. This is not a claim that no callback ever reads
further.

## N1: lava source conversion

Root keeps the current outcome. `lavaSourceConversionDropsTheTorchOnce` enables `lavaSourceConversion` and restores
it in `finally`, inside one synchronous callback, so no other test observes it. It places a resolvable standing torch
on iron between two caged lava sources and ticks the west source. The torch cell becomes a lava source with no block
entity. The test then ticks the east source, the west source and the new source, and asserts exactly one item entity:
one torch.

**Known difference from vanilla.** Vanilla lava would fizz (level event 1501) and drop nothing. This adapter's source
branch drops the source item once. There is no duplication. The adapter does not try to tell a bucket from flow inside
`placeLiquid`.

## Proposed R-034 text for Root

Quarantine affects one unlit torch with an undecodable retained root or an unresolved source identity. It lasts until
the matching pack, mod or backup returns, or an explicit scoped repair restores the root, and it adds no log line.

**Protected.** These refuse to discard that block or its root:

- ordinary player breaking, support loss, explosions and piston movement;
- native water and lava flow;
- native water and lava buckets, and dispensers emptying them;
- Forge `FluidUtil.tryPlaceFluid`, whether a tank, its bucket-item overload or another caller uses it.

Removed-pair restoration recovers the original IDs and facing.

**Not protected.** Forced command replacement, and mods or vanilla code that call `setBlock`, `destroyBlock` or
similar directly. This includes a third-party fluid block that destroys and replaces a cell itself, and nether-portal
frame generation.

**Loaded-only changes.** Extinguishing, the drop mode and relighting change a torch only when its chunk and all eight
chunks around it are FULL, checked without acquiring any chunk; otherwise a conversion defers in its bounded queue
entry and a relight is refused without spending an item. This is the neighbourhood vanilla gives its own block
ticks. A callback chain that reaches beyond those nine chunks, such as long redstone or observer propagation, is
vanilla's own behaviour for any block change; this is not a claim that no callback ever reads further.

**Other notes.**

- Unlit torches are solid for `BlockState.isSolid()` (`forceSolidOn`), with a torch's empty collision. The side
  effects are listed in W33G.
- A lava source formed by `lavaSourceConversion` drops the torch item once, where vanilla would fizz.
- The existing oversized-root chunk-save refusal and inherited R-027 remain unchanged.
- The former fluid limitation is fixed, not accepted. This record grants no owner acceptance or Gate approval, and
  Root must still reconcile ADR-066's fluid wording.
