## Method: reading ticks from a console log

The hosted job logs carry the console output only. `GameTestServer.tickServer` logs one progress line whenever the
overworld game time is a multiple of 20 (bytecode in `scripts/javap/GameTestServer.txt`, mapped 1.20.1 jar). The number
of progress lines before a line, times 20, is therefore its tick. W166's debug logs contain the world saves, and there
every periodic save falls just before progress line 300, 600, 900 and so on (`scripts/save_ticks.py`). That confirms both
the calibration and vanilla's `tickCount % 6000 == 0` autosave. The same bytecode shows that the GameTest origin is
fixed at (0, -60, 0), so test positions do not vary from run to run, and that `waitUntilNextTick` only runs tasks: ticks
are unthrottled.

## Failure 1: `SealedLazyGameTests.loadedDiscoveryFindsCarriersBeyondTheHintBoundWithoutReplayingNativeCells`

**What it does.** It installs 70 carriers in one tick. The coordinator's hint queue keeps 64 of them, and the other six
(indices 64 to 69, one row at relative x 1 to 6) must be found by loaded discovery. The test succeeds when every carrier
except the first has published back to iron. The first is replaced with gold and must not be overwritten.

**What the logs show.** In the failed hosted batch, 20 progress lines passed (400 ticks) before the timeout
(`job-122773813392.log` lines 18874 to 18898). In the other hosted runs at the same or nearby code, the batch took 220 to
320 ticks. Local full runs by W129aM, W129bc, W152G, W152H and W152I took 240 to 360 ticks, and a filtered run took 40
(`scripts/batch_speed.py`). So the test has had a thin margin in the full suite since W152.

**Instrumented full run.** I ran one local full GameTest with a temporary diagnostic in the test. It was never
committed; the patch is `diag/lazy-diagnostic.patch`, SHA-256
`69647b25d9aa4e2955163034b06628a46170f28dc2e6ac1346add5f0d3d2fe44`. It logged the loaded world and every carrier
publication (`diag-full/run-1/w184-diag-lines.txt`, SHA-256
`f2c3bc63e86e9e6cfb2a553351a68d04cc336818ec446a2582bf3be241b25d68`, from `latest.log`, SHA-256
`1bffbff5dba92a74bc73fed32263beaa90d443a06d6e6cefa00165015ac16f22`):

- **The world at installation** (tick 64,093, batch 544 of 597). Only the overworld had chunk holders: 10,454 holders, 3,492 full chunks and
  5,348 block entities. A full discovery sweep therefore costs 15,811 budget units. Its tickets were `forced` 2,254,
  `unknown` (level 33) 1,059, `unknown` (level 36) 124, `player` 30, `arce_rocket_flight` 2 and `start` 1.
- **Publications.** At age 1, all 64 hinted carriers had published. The six overflow carriers are all in chunk (6, 94).
  Two of them published at age 3, two at age 79 and two at age 154, when the test succeeded.
- **The journal** stayed acknowledged current throughout (mutation sequence 709 unchanged), so no attempt was held or
  deferred.

One sweep took 75 to 76 ticks, about 210 units per tick of the 256-unit `SealedWorkBudget` (other sealed work uses the
rest).

**Cause, in four parts:**

1. **Vanilla leaves chunks forced.** `StructureUtils.spawnStructure` calls `forceLoadChunks`, which forces the 5 by 5
   chunks from (x - 1, z - 1) to (x + 3, z + 3) around every test structure (`scripts/javap/StructureUtils.txt`).
   `GameTestServer` never releases them. Batches are laid out along z (this test's first carrier is at z 1,507), so
   forced chunks accumulate through the suite: 2,254 by this batch.
2. **The sweep visits everything loaded.** `SealedLoadedDiscovery.advance` visits every chunk holder of every Level,
   one budget unit per holder, block entity and Level. So a sweep's length grows with the suite's position.
3. **One or two publications per chunk per sweep.** A publication changes its chunk's block-entity map. The cursor's
   next step meets `ConcurrentModificationException` and moves on to the next chunk (`SealedLoadedDiscovery` lines 44
   to 48; W152: "a later sweep revisits it"). `SealedLazyWork.tick` alternates discovery and attempts. When a find lands
   on a discovery turn, the next step attempts it and the chunk is left after one publication. In the other phase, a
   second find comes first and two publish.
4. **The fixture's layout and budget.** The six overflow carriers share one chunk, so the test needs 3 to 6 sweeps:
   about 150 to 450 ticks at this point of the suite, plus up to one sweep before the cursor first reaches the chunk.
   Three sweeps pass easily (this run: 154 ticks). Five or six exceed 400, which matches the hosted values.

The process is bounded by the per-tick budget, not by wall-clock work, so pacing (W166's remedy for failure 1) would not
shorten it. The test that leaves the state behind is not one test: the vanilla harness forces every earlier structure's
chunks. The margin shrinks a little with every batch that runs before this one.

**Why no fix is committed.** Every remedy I found needs Root's decision:

- **A. The harness.** Release each finished batch's forced structure chunks, for example from an after-batch hook
  installed where `GameTestBatchFilter` narrows the batch list. This would shrink the world that nearly every batch
  sees, which by batch 544 is about 10,000 holders, to the spawn area and the running batch. It would make their unpaced ticks faster and would write the
  leftover entities of finished tests to disk. W166 traced revived rockets to exactly such unloads. It is test-side,
  but it changes the environment of most of the suite, so it should be its own task with a full hosted run.
- **B. The fixture.** Spread the overflow carriers over several chunks, so one or two sweeps suffice. The template is
  8 blocks wide, and its chunk boundary depends on the batch's position, so this needs positions outside the template.
  More importantly, the test would stop exercising a chunk that several overflow members share, which is W152's
  "a later sweep revisits it" path. That narrows the test, which WORKER-RULES forbids without a decision.
- **C. Production.** When a published member changes the chunk's map, revisit the same chunk, bounded by its block
  entity count, instead of moving to the next one. Then one visit publishes all of a chunk's overflow members. The
  diagnostic run above is the reproduction. For scale: on a server with this many loaded holders, a sealed rocket with
  100 overflow members in two chunks needs 25 to 50 sweeps of about 75 ticks, roughly 1.5 to 3 minutes at 20 TPS. This
  is designed behaviour today, so whether it is a defect is Root's call.

I recommend C if Root considers that tail too slow, and otherwise B with an explicit note that the multi-sweep path is
covered elsewhere or deliberately dropped. A should not be folded into a flake fix.

**W170, W176 and W179.** `ad8e360c` contains W176 but neither W170 nor W179. W176 changes the fluid fuel loader and adds
three save batches with 20- to 40-tick timeouts. Its forced chunks are in native S1 probes that run only on disposable
dedicated servers. It touches neither sealed discovery, the sealed journal nor chunk tickets. Its few new structures add
well under one tick per sweep. The thin margin predates it. W176 does not cause this failure.

## Failure 2: the stray CAPTURE_FAILED WARN in `rocket_rejoin_command_h1`

Log: `W170-hosted/1af1d76ed/job-122757783964.log` (run 40671103652, attempt 1). All 1,464 GameTests passed; the log
check failed on this one WARN.

| Line | About tick | Event |
|---|---|---|
| 15910 | 53,960 | B0 |
| 15912 | 53,980 | S1 |
| 15913 | 53,980 | E1; B1's captures begin |
| 15915 | 54,000 | `ARCE_REJOIN_RELEASE_HELD ... state=CAPTURE_FAILED` |
| 15926 | 54,200 | B1, after the 200-tick retry; then J1 and S2 |

Tick 54,000 is the ninth periodic autosave. `saveEverything` stores every changed entity section, including the authority
slot's. The escrow save monitor advances that slot's generation, and B1's pending capture completes as a superseding
save. `RocketReleaseCoordinator` (line 258) fails B1 with `CAPTURE_FAILED`, logs the WARN once, and retries after
`RETRY_TICKS`. The retry passed and so did the test. However, the WARN is expected only in `rocket_release_boarding`,
where W161 supersedes B1 on purpose. In B0, the same save would have dropped the admission (`B0_FAILED`), and this
fixture would have waited in phase 2 until its 580-tick bound. Production behaves as W80 designs it. W166 guarded the
boarding fixture for this (W166 failure 5). `RocketRejoinAdmissionGameTests`, the other fixture that admits a release,
had no guard. The capture window is about 20 ticks of the 6,000-tick period and contains the autosave tick exactly,
hence the high confidence.

**Fix, `92715351e`.** `admit()` waits while `GameTestAutosave.within(server, 100)` holds. The window covers B0, S1 and
B1's captures of at most three slots (authority, source and destination). Each capture completes with its Level's next
20-tick force, and S1's sidecar write between them takes about one more such period at paced ticks. The wait is at most
100 paced ticks, once per 6,000-tick period. The budget is 580 ticks, and a green run uses about 140. The refusal-only
scenarios never admit, so they skip the guard.

## Failure 3: nine `moon_landing_rule` timeouts

Log: `W170-hosted/1af1d76ed/job-122788553270.log`, the rerun of run 40671103652.

**The governed return the task mentions is expected.** The TASK's `DESTINATION_PAD_BLOCKED` governed arrival is case 12a,
`aGovernedFlightBelowY80WhoseSupportIsRemovedReturnsToItsSource`. That case removes the destination's support on
purpose, and its `ARCE_GOVERNED_RETURN_CHECKPOINT ... reason=DESTINATION_PAD_BLOCKED` also appears in green runs
(`job-122757783964.log` line 9545, `job-122696211947.log` line 9526). It passed in the red run. Case 6's
`FAIL_BACK ... DESTINATION_PAD_BLOCKED` is deliberate too, and it passed as well.

**The case that hung** is case 12b, `aGovernedFlightAtY80KeepsTheLegacyRecheckAndLandsAtItsRecordedOrigin`:

| Line | About tick | Event |
|---|---|---|
| 9633-9634 | 17,980 | warm-up STARTED and BOUND; F1 began, and the request returned `JOURNAL_PENDING` |
| 9635 | 17,980 to 17,999 | `ARCE_LAUNCH_DISCARD site=F1_CALLBACK ... reason=NO_ACKNOWLEDGED_RECORD`, two paced ticks later |
| 10053-10063 | batch start + 9,000 | nine "Didn't succeed or fail within 9000 ticks" |

In green runs this case goes STARTED, BOUND, `ARCE_TRANSFER_PREPARE ... code=SUCCESS`, and then lands. Tick 18,000 is
the third periodic autosave. `EscrowFlightCheckpoint.begin` completes F1 with no record when the barrier result is not
confirmed (line 157), which a superseding save causes, or when the ledger write fails. Neither the `F1_QUEUE_REFUSED`
nor the `F1_AFTER_ARM` note appears, and no write failure is logged. The autosave stored the source rocket's newly added
entity section while F1's own-store capture was pending, and F1 discarded the launch. That is designed behaviour.

**Why nine cases failed.** The cases take turns on the fixed pads (`MoonPadArea.turn`). Case 12b held the turn and waited
in `prepared()` for a PREPARED record that nothing would write, until its own timeout. Eight ordinary cases still
waiting for the turn reached the same 9,000-tick timeout at the same tick, because it counts from the batch start. The
four cases that passed had already had their turns.

**Fixes.**

- `1884025ad`: `Flight.request()` waits while `GameTestAutosave.within(server, 60)` holds. F1's source capture
  completes with its Level's next 20-tick force, and the ARMED ledger write must capture while that proof is valid.
  Three force periods bound both, as in W166's boarding fixture. This covers both governed cases.
- `42a16fad9`: when the journal has no record for the launch, `prepared()` asserts that F1 still holds the logical lock
  (`EscrowFlightCheckpoint.locked`). F1 takes that lock in the same call that returns `JOURNAL_PENDING`. Its ARMED
  callback releases the lock and writes PREPARED in one call, so "no lock and no record" means the launch was discarded.
  The case then fails with "The governed launch was discarded before its PREPARED record was acknowledged", and its
  cleanup passes the pads on. A discarded governed launch now fails one case instead of nine. The commit adds an
  assertion and changes nothing else.

**W170, W176 and W179, for failures 2 and 3.** `1af1d76ed` contains neither W176 nor W179. W170's diff
(`git diff 02d705aa3..c4ab71611`) changes these:

- bay deployment;
- a refactor of `RocketTransferSavedData`'s insert validation, plus a bay-consumption write;
- a startup journal hold behind a system property;
- `RocketEntity.setPos` and `remove`, which now report to the bay coordinator;
- a pacer in `SealedRecoveryGameTests`.

None of these touches the periodic autosave, the escrow barrier, `EscrowFlightCheckpoint` or `RocketReleaseCoordinator`.
Its new GameTests move later batches relative to the autosave ticks. That decides which window an autosave happens to
hit, but it does not create the hazard. W170 does not cause these failures.

  covered by the existing `GameTestAutosaveTest`.

## Choices where the task left room

- **Window sizes.** I used 100 ticks for the release and 60 for F1. Both are derived from the 20-tick force cadence, are
  conservative, and cost at most one short wait per 6,000-tick period.
- **The fail-fast check.** It is an added assertion, not a changed one, so I made it a separate commit. Root can drop it
  without losing the guard.
- **Failure 1.** I fixed nothing, because each remedy changes the suite's world, narrows the test, or changes
  production.
