## Cause

### What the proof-retry lines belong to

`ARCE_GAMETEST_PROOF_RETRY` is logged only by `EscrowProofRetryGameTests`. `entities=true` is
`supersededEntityProofRetriesTheSameFrontierAfterBackoff` (fixture chunk (34250, 34125)) and `entities=false` is
`supersededTerrainProofRetriesTheSameFrontierAfterBackoff` (chunk (34125, 34125)). Every `inject_save` and `superseded`
line in the TASK's table is that retry test's own, deliberate supersession of its own slot, followed by its retry. None
of them belongs to `ownTerrainAndEntityStoresConfirmTheExactFrozenFrontier`, which logged nothing before this task.

### Root's lead: refuted for supersession, confirmed in part for delay

- **Supersession: refuted.** `EscrowSaveMonitor` keys a watch by Level, slot kind and chunk. The injected saves touch only
  the retry fixtures' chunks; the core tests watch (32500, 32500) (own-store) and (33125, 33125) (joint), and the
  reconciliation tests (42563..42573, 42563). A save of another chunk cannot change a core proof's generation.
  `EscrowFixtureAreasTest.noTwoFixturesShareASlot` pins that no two fixtures share a chunk.
- **Delay through the shared IO worker: confirmed, in both directions.** Each test has its own `EscrowBarrier`, but all
  terrain barriers force the Level's one region `IOWorker` (and the entity barriers its one entity worker). A force is
  `IOWorker.synchronize(true)`: it waits for every pending write, then fsyncs every open region file, and concurrent
  forces run one after another. A proof whose force is queued behind other tests' forces, or behind bulk chunk writes,
  waits for all of them. This affects whichever proof is last in the queue, not only the core tests.
- **What the core proofs waited on: first, their own fixture's generation.** Each terrain proof starts with W36's
  precondition, `EscrowGameTestProof.freshTerrainSave`, which returns false until vanilla's `ChunkMap.saveChunkIfNeeded`
  can save the fixture chunk. That needs `ChunkHolder.getChunkToSave()` complete, which waits for every generation step
  in range and for the entity-ticking promotion of the test's START ticket of radius 2, that is, for the whole 5x5 FULL
  area. In tick 0 each test's `level.getChunk` blocks only until its own centre is FULL; the rest of the area finishes
  during the paced, timed ticks.

## The fix

`gametest/EscrowFixtureAreas` (commits `1389e925` to `59011494`) holds batch hooks for two batches: `escrow_core`
(joint, own-store and the six reconciliation fixtures) and the new `escrow_proof_retry` (the terrain and entity retry
fixtures).

- **`@BeforeBatch`**, before the batch's first test tick: adds its own ticket (`arce_escrow_fixture`, the same radius
  2) on each fixture chunk of the batch, loads each centre, then runs the chunk source's main-thread tasks until each
  centre is entity-ticking and every chunk of its 5x5 area has a complete chunk-to-save future. It then saves those FULL
  chunks with vanilla's own `saveChunkIfNeeded` (125 for escrow_core's 8 areas, 50 for the retry batch's 2), runs vanilla's `processUnloads` for the previous
  batch's dropped chunks, and waits for the region worker's `synchronize(true)`. A GameTest timeout counts the ticks
  after its test starts; the hook runs before them. One INFO line reports the result.
- **The tests** keep their own START tickets, `getChunk` calls and every existing assertion and timeout. Each of the ten
  remote-fixture tests now asserts `EscrowFixtureAreas.prepared(level, chunk)` right after its setup: the hook prepared
  this area and still holds it. A single `/test run`, which has no batch hook, prepares the area in the test's own setup
  instead.
- **`@AfterBatch`**: removes the batch tickets, any START ticket a failed test left, and vanilla's one-tick UNKNOWN
  tickets on the batch's own area chunks (a chunk access in the batch's last tick leaves one, and the hook runs inside
  that tick; the first native run showed the retry-terrain centre held at level 33 by one). It then runs
  `processUnloads` until the areas are unloaded and waits for the region worker's flush, so the unload saves do not land
  in the next batch's first ticks. One INFO line reports the result.
- **Bounds.** Both hooks are wall-clock bounded (600 seconds to prepare, 60 to release, 60 more to flush) and never
  throw for slowness. A prepare that runs out leaves the areas unprepared, and each remote-fixture test then fails its new
  assertion at its start, explicitly rather than by a race.
- **The retry tests' own batch.** With preparation done first, every proof captures at tick 0 to 2, so every barrier
  forces at ticks 20 to 22. Verification run 12 of `95d6cba0` failed the terrain retry's 40-tick window ("exceeded its
  explicit force/IO completion budget"): its force was queued behind the joint test's on the region worker, each fsync
  round taking about 3 seconds on the starved CPU (joint force 3.2 seconds, own-store force 6.8 seconds, the retry's not
  finished after 5.4 seconds). Run 10 showed the same on the entity worker (entity retry window 1 to 41, beside the
  own-store entity proof). The core tests' 200-tick budgets absorb such a queue; the retry tests' explicit 40-tick
  windows cannot. In `escrow_proof_retry` the terrain retry is the only user of the region worker's force and the
  entity retry the only user of the entity worker's.

Fixture positions moved into named members (`EscrowCoreGameTests.JOINT_FIXTURE` and `OWN_FIXTURE`,
`EscrowProofRetryGameTests.fixture(boolean)`, `EscrowReconciliationGameTests.fixture(int)` and `FIXTURES`), with the
same values, so that the hooks and the tests share one definition. No production class changed.

### Why the races can no longer occur

1. **Late preparation.** Every fixture area is generated, and the fixture chunk saveable, before tick 0. The terrain
   precondition succeeds at the first attempt, independent of host speed. If the hook cannot finish, the tests fail at
   their start with an explicit message; they no longer spend their budget waiting.
2. **Bulk writes inside proof windows.** The newly FULL chunks are saved and flushed before tick 0. The batch ticket
   keeps every area loaded while tests finish and remove their START tickets, so no area unloads during the batch. The
   only writes left inside a batch are the tests' own stores, the retry tests' one-chunk injected saves, the
   reconciliation tests' own writes, and vanilla's re-save of a chunk dirtied after its 10-second cooldown.
3. **Force queues.** The retry tests, the only proofs with a 40-tick window, no longer share an IO worker with another
   test's force. The core tests share theirs, within budgets of 200 and 400 ticks.
4. **Cooldown stretch.** Tick 0 no longer contains other tests' multi-second generation blocks, so the 10-second cooldown
   that `freshTerrainSave` installs right before each terrain attempt covers that test's own proof window.
5. **Supersession by another test.** Ruled out by the slot keys above.

With preparation at tick 0 to 2, one natural supersession still fits the unchanged 200 ticks: 2 + 2 x 27 + 100 = 156.
The remaining natural writer of the core slots is vanilla's 6,000-tick entity autosave, at most once per test.

No timeout, window budget, retry limit or existing assertion changed.

**Batch name.** One batch name is added, `escrow_proof_retry`. The batch run order is HashMap order; one more name keeps
the count far below the next resize at 768 names, so the other batches keep their order and only the new batch takes a
new place in it.

## Incidents

Two faults in this session's own run harness, both recorded with times in `incident-burners-20261020.txt`:

1. **Leaking CPU burners, 06:20 to about 06:27.** The first burner command built a list in a loop, and `python` was the
   pyenv `.bat` shim, so stopping the kept PID left the interpreter running. Three burners reached 6.5 GB of commit each
   before W111 stopped them by PID. W111's own run in that window failed in Gradle ("The paging file is too small");
   W27C1F's GameTest JVM started at 06:23:17, inside the window, and was still running at 06:31. Root should check W27C1F's
   result for a memory failure. The burner now runs the real interpreter with a constant-memory generator and still ends
   by itself after 900 seconds.
2. **A GameTest without the lock, 07:32 to 07:33:31.** The runner threw on a date conversion after starting Gradle, and
   its `finally` released the lock while that Gradle tree ran on; the unpinned run ended at 07:33:31. Its output was not
   used. The runner now kills its own Gradle tree before releasing the lock.

## Not done and risks

- **The hosted timeout was not reproduced locally.** Nine baseline runs at three loads reproduced the late preparation
  (up to 162 of 200 ticks) but did not cross the limit. The hosted-IO attribution for the two retry-window failures is
  from the source and the timeline; the local force queue on `95d6cba0` is a captured trace of the same failure message.
  The new trace lines will name the stage if a hosted run fails again.
- **IO latency is not bounded by the tests.** A single force still waits for the region worker's pending writes and
  fsyncs every open region file. In the full run the proof windows were 22 to 28 ticks, so force and readback took 2
  to 8 ticks after the 20-tick cadence; under the starved local load the retry windows reached 25 ticks. A host whose single fsync round takes more than 20 ticks (one second) still fails the retry tests' 40-tick
  windows, and an extreme stall can still exhaust the core tests' budgets. Their forces now share a worker only with
  each other (core) or with nothing (retry).
- **Natural supersessions that remain.** Vanilla's 6,000-tick entity autosave can supersede an entity proof once; one
  retry fits the 200 ticks. A host stall over ten seconds can let the terrain cooldown expire inside a window. Both were
  W94B's residuals and are unchanged.
- **The hooks block the server thread** for the preparation (8.3 seconds in the full run, up to about 4 minutes under
  the starved load) and the release (under 2 seconds in the full run). The GameTest timeouts do not count that time. A
  long block in a filtered run can log one "Can't keep up" warning; the full run logged none near the escrow batches
  (two, both before them, against a limit of 8).
- **One batch name added** (`escrow_proof_retry`), as described above.
- **Not in this task and not done:** other flaky tests, production code, ADRs, the risk register, status files and the
  ledger. No push or merge.
