and `LF_M_N2_UNKNOWN` with three starts apiece. `LF_M_N3_FULL` failed at its first start before the pause marker,

The C2 code implies **`ESCROW_PENDING` before the queue**. The probe replaces the BAY delegate with a synthetic
index; `retarget` makes the delegate `LOADED`, but `BayReceipts.store` is still null in this fresh world. In order:

1. `FluidFuelLoaderBlockEntity.attempt` calls `LoaderEligibility.evaluate` before `EscrowLoaderAdmission.offer`.
2. `RocketEscrowGate.idle` requires `escrowIdle` and no `bayHeld`. In `BayReceipts.holds`, the `LOADED` branch
   returns `store == null || store.holdsRocket(logical)`. The synthetic index thus holds even an unrelated rocket.
3. `EscrowLoaderAdmission.chainable` cannot proceed without an operational escrow ledger. With no ledger, eligibility
   returns `ESCROW_PENDING`. Neither the fair queue nor its `EscrowTransferPreparation.preflight` is reached.

`git log`, `git show` and `git blame` identify `91de93e86c9c489fca96d7d0e29e943bcd18c0a9`: it added both
the bay term in `idle` and the null-store hold. [W128](W128.md)'s gate-lock section cites R49 Q3/Q8 and names
`LoaderEligibility` among the affected call sites. [W27A-DESIGN](W27A-DESIGN.md) section 8 and
[ADR-065](../../../decisions/ADR-065-CLASSIC-PROPULSION-STATION-CONTROLS-AND-SOLAR.md) section 8 describe the bay
interlock. The old fixture is inconsistent with that deliberate guard. The original C2 log shows PROPULSION
`NO_FILE` at the first tick, and the synthetic substitution is to `LOADED`, so neither W329's missing-ledger
hold nor W332's load-failure seam explains this path. The old fixture's hold was reproduced in a unit test;
the returned status has **not** been independently observed on a W354 native start.
