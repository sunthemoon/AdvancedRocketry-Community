**Model** (no Minecraft type; checked `long` arithmetic; refusals are `Status` and `Result` values):

- A `Key` is a fluid ID and a digest of `arce-escrow-fluid-key-1:`, the ID and the tag digest. An absent tag and an
  empty tag give different keys. Keys are ordered by ID, then by digest.
- A `Vector` holds the amounts of one endpoint, summed per key, so the same key in both banks is one amount. An
  empty unit is a known zero.
- A `Baseline` has a scope (fuel: 2 baseline keys and 5 union keys; cargo: 1 and 3) and entries of four longs. It
  refuses a plan that does not move exactly one key by 1 to 1,000 mB, and planned deltas that do not sum to zero.
  `verifyPlan` is the preparation check against the planned AFTER vectors.
- `classify` and `outstanding` give the four partial-application combinations and `q * (aS - aD)`.
- `project` and `withoutLater` are the projected baseline and the later-prefix subtraction. They work on any
  endpoint chain, and a result below zero is `BROKEN_CHAIN`.
- `settle` freezes a connected component. It counts each unit once, by the full typed `EscrowEndpoint.Key` and a
  resource scope, from its earliest baseline to its final observation. It checks numeric continuity of every
  chain, and stores each key's signed discrepancy once, in the row of the lowest-sequence member whose own keys
  include it. A half-applied transfer comes out as `loss = outstanding`.
- Knowledge is PLANNED (no frozen part), KNOWN, UNKNOWN_BASELINE (a legacy member), UNKNOWN_ENDPOINT (a missing
  observation) or NOT_APPLICABLE (no row). An unknown amount is an empty `OptionalLong`, never a zero.
- `verifyGroup` checks a set of frozen rows without the operations: one group owner, one member set, the same
  knowledge, and one present owner per key.

**Codec.** The row is `v`, `op`, `b` and the optional `f`. The class comment of `EscrowFluidAccountCodec` gives the
full layout. Decoding applies the byte, depth and node bounds before it reads any field. It then refuses unknown
fields, wrong types, a digest that is not 32 bytes, a mask that disagrees with its fields, excess keys, duplicate or
unsorted keys, negative amounts, an incorrect balance and a non-canonical form. `encodeRows` and `decodeRows` bound
the list at 128 rows and refuse a repeated operation. The bounds are a `Limits` parameter, because Root has not fixed
the ceiling. `MAXIMUM` is the design's upper limit: 4,096 bytes, depth 8, 65 nodes, 64 members.

**Tests.** Every case of the TASK's item 3 is covered. The less obvious ones are:

- the same total in a different fluid, and a different tag, each reported as a loss and a gain;
- a move of one key between the two banks, which leaves the account unchanged;
- chains on the same bank, on alternating banks and through a cargo device, in both directions;
- a cross-kind UUID alias, kept as two units;
- shared ownership whose adjustments sum to the component discrepancy;
- a 64-member owner row (1,639 bytes with ordinary IDs), which round-trips inside `MAXIMUM`.

### 3.2 Frozen component fit

**Dated correction, 2026-11-13 (Root decision R447, implemented in W362).** The original search below used

incorrect and is superseded by this correction. Unsettled and legacy components can decode above that count;
the operation envelope constrains freezing, not the component decoder.

Method: build a component of n fuel fills, run the real `EscrowSettlementIntent.preview`, `confirm` and
`freeze`, and take the largest n that is not refused. Past eight fills on one rocket (the saved per-rocket bound),
rockets can only be joined by a cross-kind UUID alias, so the components beyond 8 use it.

|---|---|---|---|---|
| Smallest valid IDs (`a:b`), every endpoint missing (ABANDON) | **14** | 10,310 | 12,287 bytes, 450 nodes | operation bytes |
| Smallest valid IDs, every endpoint present | 9 | 10,252 | 12,228 bytes, 475 nodes | operation bytes |
| Registered loader and rocket types, `minecraft:overworld`, every endpoint missing | 12 | 9,716 | 11,835 bytes, 403 nodes | operation bytes |

The corrected search builds actual root-3 operations and rows, attaches the commitment before confirmation,

### 3.3 Row ceiling

**Dated correction, 2026-11-13 (R447).** The earlier 1,977-byte proposal measured the worst row layout at the
14-member historical root-2 frozen fit, not the minimum needed by new-format frozen components and not the
largest component that can decode. Its exact layout assertions remain unchanged, including refusal at one
byte, level or node below that layout.

The largest measured new-format frozen fit is **13 members**. The worst row layout with that member count is
**1,961 bytes, depth 5, 65 nodes** (1,753 + 16 × 13), leaving 87 bytes under 2,048. The ordinary frozen owner row
of that minimal, all-missing fixture is 492 bytes; the 1,961-byte figure deliberately uses the maximum
key/ID/optional-field layout from section 3.1.

**Root's retained decision: 2,048 bytes, depth 5, 65 nodes, at most 14 members.** This is a conservative saved-row
bound, not a claim of a measured minimum or a cap on decodable unfrozen components. A 14-member worst layout
still fits at 1,977 bytes. The byte ceiling alone fits an 18-member layout (2,041 bytes), but the separate
14-member list bound remains in force. A 64-member layout needs 2,777 bytes and its historical capacity cost
is shown in section 3.5. No existing ceiling, member limit or pinned assertion changed for this correction.

## 5. Choices where the design was open

- **Scope byte.** The baseline stores its scope (fuel or cargo), so a row can check its own key counts without its
  operation. It costs 5 bytes.
- **Group owner.** Every frozen part stores the group owner's UUID (`g`, 24 bytes), so a row that does not own the
  member list can still be matched to it.
- **Member list.** It holds the row-bearing members in sequence order, owner first. This is the same set that the
  intent's commitment covers. Item and legacy members are not in it.
- **Unknown components.** When the knowledge is not KNOWN, no row stores any adjustment, even for a key whose
  endpoints were all observed. UNKNOWN_BASELINE takes precedence over UNKNOWN_ENDPOINT.
- **Endpoint masks.** One endpoint is observed for every key of a row or for none.
- **Balance check of one row.** A single-member row is checked in full (`dS + dD + loss = 0`). A row of a larger
  group cannot be, because shared units belong to several rows. `settle` recomputes the component, and Slice B has
  to call it with the operations' endpoints.
- **Key digest.** The tag part is `CanonicalNbtDigest` of the native Tag, and the fluid ID and absence are hashed
  as text. Slice B should confirm this before a row is ever saved, because the digest becomes a saved identity.
