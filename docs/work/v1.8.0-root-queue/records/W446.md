### H1: damaged gzip observation must fail without aborting restart two

Each of the four `observation.json` files reports
`EOFError: Compressed file ended before the end-of-stream marker was reached`.
Each first damaged log, `damaged-FC_LOAD_L2_REPLACED-1.log.gz` for the ledger or
`damaged-FS_O3J_AFTER-1.log.gz` for the journal, line 169, already says
`[ARCE-BETA-2000] Beta world data check blocked startup; type=RESOURCE_ESCROW;` or `type=ROCKET_TRANSFERS;`.
The native refusal preceded the Python EOF; this was not a native failure to reject the store.

`run_v180_escrow_forced_stop.ledger` and `run_v180_escrow_pre_f2.journal` decompress directly. Their callers' raw
observation boundaries now retain `EOFError` and `zlib.error` as failures and still perform restart two.
The shared bounded `loader_cut_nbt.read_gzip` also normalizes damaged-stream errors to its existing `NbtError`.
Neither a failed process nor a failed raw decode becomes a successful oracle. The new six-subcase test checks
both starts stay FAILED, the oracle is not called on undecodable data, the file is unchanged, and cleanup occurs.
All four v3 native cases complete both refused restarts, preserve the damaged SHA and return CAUGHT_LATER.

### H2: ledger faults were injected before the cargo fixture existed

In `cases/X02-RESOURCE_ESCROW-MOVE_ERROR-1/logs/live-FC_LOAD_L1_REPLACED-0.log.gz`, line 196 injects at
`operation=move attempt=1`; lines 197 and 200 show the same 263-byte SHA failed, then moved on attempt 2.
Line 264 says `Cargo restart fixture exceeded its bounded wait`. The corresponding first-start exception is
at line 265 for MOVE_DENIED, 266 for READ_ERROR, and 266 for READ_CORRUPT. These are probe failures, not evidence
of cargo loss. The MOVE_ERROR run closes with 182 attempts despite never reaching the selected cargo cut.

`EscrowCargoReconciliationProbe.tick` creates and autosaves its empty baseline before it waits for `writerIdle`
and creates the rocket. The ledger UNKNOWN retry and successor autosaves prevent that setup wait from finishing.
Four separately named `-S1` native controls all reached the intended L1 cut and passed the unchanged checks.
Model v3 therefore declares skip 1 for exactly those four cases; the canonical IDs were rerun and all returned
SEEN_HELD. This is a changed injection position, not evidence that the original bootstrap experiment passed.
Explicit `-S0` IDs preserve that experiment. Counts, cut, oracle and timeout remain unchanged.

### U1: satellite retry policy conflicts with the fixed exact-byte rule; payload cause remains undecided

For READ_ERROR, `live-R3-0.log.gz:224` reports faulted attempt 2, 550 bytes, SHA
`333e23dcd442cdfcee91d98d1b5616526fd9c91ac62c88438b72b2e965856928`; line 226 reports
`ARCE_SATELLITE_REGISTRY_UNACKNOWLEDGED outcome=UNKNOWN sequence=2 epoch=2 durable=1; retained dirty state`.
Line 258 reports successful attempt 3, 550 bytes, SHA
`3d8a49c497e74cfdab0015383a1646c68ba09b998d778fda97ba280aadd37b29`.
For READ_CORRUPT, line 225 reports faulted attempt 2, 551 bytes, SHA
`7acbe16d281cca6598df3a3f63801de366f113896f2d5b1a433a0470b00b356a`; line 227 reports the same hold with
`outcome=FAILED`; line 246 reports successful attempt 3, 552 bytes, SHA
`58d5d2d15ccafec412f6ec7054a690fa23e74f695ef9349a00f72e400abf5739`.
Both original and v3 healthy-restart native oracles pass, but exact-byte retry fails: both remain NOT_CAUGHT.

`RegistryEpochs.unknown()` reserves the carried epoch; `SatelliteRegistryWriter.published` clears the
acknowledgement on UNKNOWN and obtains a fresh capture later. FAILED reserves it if mutation occurred in flight.
`SatelliteEpochRowGameTests` explicitly tests `unknownCheckpointResolvesFresh` and `failedCheckpointRetriesFresh`;
its line 74 rejects reuse of the carried epoch. Thus an identical compressed candidate cannot be assumed to be
the correct UNKNOWN retry under C6. This is not an unobservable W368 residual: the fault is explicitly reported.
Hashes alone cannot establish that only an allowed epoch or clock field changed, especially for READ_CORRUPT.

The deciding run must retain the faulted candidate and next successful candidate, validate their hashes against
the injector lines, decode and compare the entire bounded roots, and retain the same first-start and two-restart
oracles. Unexpected mission, identity, resource or proof changes would be product evidence; only documented
epoch/clock differences would isolate an oracle-contract problem. That comparison and Root's contract decision
are not done. Replacing exact-byte equality with epoch-normalized equality here would loosen a fixed rule, so
neither it nor a production workaround was implemented.

### R1: a valid old ledger is the declared single-store rollback residual

The trace has generation 1 with `issued_through=0` and no records, generation 2 with one PREPARED record, then
an in-flight generation 3 at the cut. STALE selects the bytes before the last completed write: valid generation 1.
It rewinds the issued history while retaining newer world effects. The cut context totals 1,000 rocket plus
4,000 device units. Both restarts retain SHA `5590104d36b0d5ca5c1c2bed209616e56fc0e9c973e2ba4fd980c9db7cb6a3ff`.
`damaged-FC_LOAD_L2_REPLACED-1.log.gz:186` says
`Restart violated cargo conservation, epoch, identity or pruning`; that compound assertion alone does not prove
a quantity loss. There is no declared production refusal. Valid-old-root rollback is excluded by W368/R-035,
so the cause is residual and the original NOT_CAUGHT stays visible. Any separately proven simulated loss would
still be a defect; consistent whole-world backup, not single-store replacement, is the supported recovery.
