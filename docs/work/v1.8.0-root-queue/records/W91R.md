### Item 1: M2 opts in during a failed write

- `RocketLandedDisassemblies.Port` gains `queueRemoval`, which only M1's removal continuation uses.
  `RocketLandedDisassemblyPort` implements it with the six-argument `afterAcknowledged(server, reservation, false, true,
  ...)`. The plain removal (`removePlain`) and M3's write-back keep `queue`, which does not opt in.
- M2 still never runs on the immediate path: right after M1's `remove`, L's slot is not acknowledged, so the continuation
  is queued. During a definite failure the visit runs M2 once the retained acknowledgement covers the removal. It still
  moves past every acknowledged entry that does not opt in.
- New A0 case `RocketLandedDisassembliesTest.anAcknowledgedRemovalRestoresWhileADisjointGenerationFailsDefinitely`:
  - The removal's own generation commits. It also holds an ordinary continuation for another rocket.
  - A disjoint generation then ends NOT_COMMITTED before the visit, as when both complete in one writer tick.
  - At the visit, during the failure, M2 restores within the confirmation lifetime. The ordinary continuation waits for
    the retry. In mode 1 (a clean failure) M3's write-back also waits; its `reserve(L)` succeeds during the failure, as
    W86 section 6 says.
  - With the fake port's opt-in turned off, the case fails at its restore assertion (line 341). The opt-in was then
    restored. Evidence: `r1-negative-control-opt-in-off.log`.
- The A1 GameTest bridge (`RocketLandedDisassemblyGameTestSupport.releaseDetached`) and the A0 `FakePort` implement
  `queueRemoval` the same way, through new `duringFailure` overloads of `RocketJournalGameTestSupport.queueDetached` and
  `RocketJournalTestAccess.queue`. No existing landed GameTest reaches "removal acknowledged, then another write fails",
  so their outcomes do not change. The full GameTest confirms this.

### Item 2: the precheck is dropped

- The `journal.actionable(L)` refusal before `reserve(L)` in `RocketTransferService.prepareLaunch` is removed. The
  interlock (`resourceMutationAllowed`, line 79) admits exactly `actionable(L)` plus the pre-baseline untouched-absent
  case, and `reserve(L)` refuses a busy L. So the only state whose answer changes is the one W91-R2 names.
- New GameTest `RocketJournalInterlockGameTests.legacyLaunchBeforeTheSessionsBaselineCommitIsAdmittedAndCountsDownAfterIt`,
  in the new batch `journal_pre_baseline_launch`:
  - It installs a reloaded copy of the settled world root with 128 slots (`boundedFixture(helper, 128)`). The copy has
    no acknowledgement yet in this session, and the test asserts that.
  - A launch while the rocket's L holds a reservation is refused with `TRANSFER_JOURNAL_BLOCKED`. The mutation sequence,
    the outstanding count, the journal records, the rocket's state and its fuel stay unchanged.
  - The launch is then admitted as `JOURNAL_PENDING`. Every tick, the rocket stays FUELED until the root's first
    acknowledgement. It then counts down, and the flight lands.
  - In the full GameTest the batch ran from 14:18:31 to 14:18:44 and passed. It logged no WARN or ERROR.
- No negative-control GameTest was run against the old precheck, because the build has no GameTest filter and a second
  full run did not seem worth the lock time. With the precheck, the admitted launch returns `TRANSFER_JOURNAL_BLOCKED`,
  so the test's `assertPendingLaunch` would fail.

### Item 6: the slow matrix cases

Where the time went, measured on this host with a throwaway probe that was not committed:
- A committed `saveChecked` costs about 11.7 ms. About 6 ms of that is the writer drain's one-millisecond sleeps: the
  same write, polled without sleeping, costs 5.75 ms, and a bare 200-byte write with `force` costs 2.9 ms.
- A failed save costs about 0.74 s, because the drain retries it three times, 200 ticks apart, with one sleep per tick.
  This was measured for UNKNOWN; NOT_COMMITTED takes the same path in `RocketJournalWriter.tick`.

`acknowledgedAbsenceLease...` makes 1,027 commits, and `generatedCommits...` makes 28 failed saves. The changes:
- **`acknowledgedAbsenceLease...`**: each commit goes through the same writer, checkpoint, file and atomic policy, but
  the owner polls `pollWriter` for the one completion instead of sleeping per drain tick. Nothing is queued in this case,
  so the visit runs nothing, and the result is the same as the drain's. The helper asserts that nothing is queued and
  that each write COMMITTED, with a ten-second bound.
- **`generatedCommits...`**: the eight sessions share only the random stream, and each session draws a fixed sequence
  (one rocket per step and one outcome every 16 steps). The draws are taken in the original order. Each session then
  runs on its own owner thread and its own file, so the failed saves' backoffs overlap.
  - A separate file changes nothing. Before, each session's first write overwrote the previous session's file, and the
    root's presence is LOADED, so the first write never checks the target.
  - A throwaway check (`r6-trace-equivalence-check.java.txt`) ran the old shared-file sequential form and the new form.
    The per-step traces were identical in all eight sessions: 696 trace lines and 28 failed saves
    (`r6-trace-equivalence-output.txt`).

## Choices where the task left room

- **Item 1:** a separate `Port` method rather than a flag on `queue`, so that the one opt-in site is visible by name.
  The A1 bridge opts in too, so that the detached GameTests keep the production port's behaviour.
- **Item 2:** the pre-baseline state is made with `boundedFixture(helper, 128)`, the existing reload fixture, rather
  than with a detached journal, because `prepareLaunch` reads the world root. The test gets its own batch.
- **Item 3:** the hook also clears the terminal-cut hook (see item 3).
- **Item 6:** polling and parallel sessions instead of a test committer. A committer cannot avoid the main cost: the
  staged file's `force` runs before the committer is called, and skipping the move would save under 1 ms of the 5.75 ms.

## Not done and known risks

- **Item 2's GameTest has no recorded negative control** (see item 2). Its pre-baseline state depends on
  `boundedFixture`'s reload leaving the copy without an acknowledgement. The test asserts that state first, so a change
  there fails loudly rather than passing vacuously.
- **Item 3's hook is the batch's only `@AfterBatch`.** Vanilla keeps one after-batch function per batch name, so a later
  hook registered for `escrow_benchmark_supply` would replace this one.
- **Item 6's `generatedCommits...` now runs eight owner threads and eight writer threads at once.** Its wall time is the
  slowest session, about 3.5 s. Its total work, mostly the drains' sleeps, is unchanged, so the sleeps also overlap on a
  two-core hosted runner. A session's assertion failure is rethrown unchanged on the test thread.
- **The benchmark's quiet-machine rule is fragile with several workers.** Run 1 was lost to another worker's unit tests,
  and any later rerun can be rejected the same way.
- **The DEFER-visit and F2-callback differences in item 5 are reported, not explained.**
- **Not in this task:** W91N and W91N2, the F3 and N2 kill and restart cuts, ADRs, the risk register, the status files
  and the ledger. W91-R6 and W91-R7 are informational and unchanged.
