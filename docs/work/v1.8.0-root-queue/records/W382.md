## 2. The three probes

The file and line numbers are those at `d45bc94f5`. A write is in flight only between `EscrowLedgerWriter.request` and the
`tick` that takes its completion. `writer.idle()` is `active == null`, and a successor exists only beside an active
request (`EscrowLedgerWriter` lines 126 to 128, 231 and 274).

### `EscrowCargoRecoveryProbe.place`, line 55 (cuts `FC_LOAD_R1_255` and `FC_LOAD_R1_256`)

Not possible.

- Its only caller is `EscrowCargoReconciliationProbe.tick`, line 150, in step 0.
- Line 136 of that method returns unless the ledger's generation is at least 1 and `coordinator.writerIdle()`. The same
  server-thread call then reaches line 150.
- Lines 137 to 149 create the rocket and the device. None of them asks the coordinator for a write.
  `contention.place()` on line 149 is absent here: the contention probe selects only `FC_LOAD_E3_CACHE_CLOSE` and
  `FC_LOAD_E5_STALLED` (`EscrowCargoContentionProbe` line 35), never an `R1` cut.
- So the writer is idle at the replacement, with no successor. The next write is the `autosave()` on line 57, after the
  replacement, and it captures the replaced ledger.
- When that `autosave()` is throttled, the seed stays dirty and unwritten. `FloorBaseline` (lines 211 to 240) already
  covers this for `R1_256`. For `R1_255` the admission's own write captures the seeded ledger.

### `EscrowLoaderFloorProbe.place`, line 184 (cuts `LF_M_R1_FLOORS_*`)

Not possible.

- `place` runs once, in step 0 of a first run (`tick`, line 157).
- `startTick` (line 105) requires that no ledger exists at the first tick's start.
- Nothing creates one before `place`:
  - production creation needs a loader fill, and the loaders are created in `place` itself with their gates closed
    (opened on line 162); the constructor (line 69) refuses the global admission switch;
  - for an `LF_` case the runtime runs no other probe (`EscrowRuntime.tick`, lines 386 to 399).
- So `forTests` on line 182 creates the ledger and `bind` creates its writer in the same call. That writer has never
  received a request when line 184 replaces the ledger.
- The `autosave()` on line 185 follows the replacement and captures it. Step 1 (line 159) waits for generation 1 and an
  idle writer.

### `EscrowSettlementCompletionProbe.createFloor`, line 269 (cases `SR_FLOOR__*` and `SR_NAMED_*`)

Not possible on the fresh world these cases use.

- `createFloor` runs only in step 0 of a first run (lines 99 and 105); a recovery run returns on line 94.
- The probe creates the ledger and its writer on line 88 with `forTests`. A new `SavedData` is not dirty.
- Between line 88 and line 269 the probe makes no coordinator call:
  - the floor case only waits for the journal and the target chunk;
  - the named case creates its source fixture and an unpublished rocket (lines 101 to 103), which take the ledger's
    ID only.
- The runtime cannot start a write on that ledger either. Every writer entry point needs something the empty, clean
  ledger lacks:

  | Entry point | Needs |
  |---|---|
  | `commitPreparations` (line 256) | a queued admission |
  | `autosave` (line 315) | a dirty root; a vanilla save reaches it only through `ResourceEscrowSavedData.save`, line 29, which also needs a dirty root |
  | the settlement and retirement writes | a record or a floor |
  | `collectFloors` (`EscrowRuntime` line 360) | a named floor |
  | a flight write | a launch |

- The `CONSUMER` boundary, which runs journal traffic first, exists only as `SR_ACCEPT__CONSUMER`
  (`escrow-probe-cases.tsv`), which never calls `createFloor`.
- So no generation has been requested when line 269 replaces the ledger. The `autosave()` on line 270 follows it, and
  lines 106 and 152 wait for an idle writer before the next step.

The limit of this reasoning: the probe does not assert a fresh world, as the floor probe does. A first run on a world
that already holds a ledger with work in flight would not be covered. The native harness always gives these cases a new
world.
