## Cause and evidence

`MinecraftServer.tickServer` saves every 6,000 ticks. The ordinary entity-section
store increments `EscrowSaveMonitor`'s generation, invalidating retained native
proofs. `EscrowBarrier.Proof.valid()` checks that generation again, including
after successful readback. An F1 preparation can therefore have a confirmed
readback but lose its proof while the ARMED ledger write waits for capture or
replacement. `EscrowFlightWrites` refuses that request; `EscrowFlightCheckpoint`
reports `F1_WRITE / LEDGER_WRITE_FAILED` and supplies no acknowledged record.
`EscrowGovernedPreparation` then calls the discard callback with
`F1_CALLBACK / NO_ACKNOWLEDGED_RECORD`.

`EscrowGameTestLaunch` deliberately retries only an identity-matched
`F1_PROOF / SUPERSEDING_SAVE`, not this later write refusal. The live-return
fixture incorrectly assumed that checked journal and loaded chunks alone made
its launch preparation uninterrupted. Keeping a revoked disk proof would be
incorrect production behaviour; broadening the retry whitelist would hide a
different refusal. The corrected fixture waits before publishing its source or
starting F1, rather than extending its timeout or weakening its final checks.

The three available historical logs show the same periodic boundary. Vanilla's
GameTest progress line occurs every 20 game ticks after the server tick returns;
the retained `javap` output confirms both this ordering and the 6,000-tick save.

These console logs alone bracket the tick; they do not expose the exact failed
proof check. The deliberate reproduction supplies that missing observation.
An uncommitted diagnostic patch invokes the real
`server.saveEverything(true, false, false)` at `F1_READBACK_AFTER`. At server tick
34 it saves; at tick 35 the ARMED write refuses with `proof=false`,
`source=true`, `journal=true`. The same original dismount-after-return assertion
then fails. One selected test runs and fails, with no timeout. Its raw log,
instrumentation patch and result are retained, and every diagnostic source
change is removed before the implementation commit.

Thus server overload warnings are not the refusing check. Asynchronous IO and
the preceding batches affect which F1 phase meets the periodic save, explaining
why a rerun or a neighbouring case can pass. They need not corrupt any neighbour's
source or journal state. The W116 hosted occurrence is listed in the TASK; its
raw log is not independently reanalysed here.
