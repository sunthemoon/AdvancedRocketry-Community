## 4. The design as implemented, and choices where the design left room

- **Ownership and lifetime.** One coordinator per transfer service, owned by its recovery service; entries are RAM only,
  one per logical rocket, at most 64. A restart recovers from T, or from the already proved standalone survivor.
- **Reservation (R1).** The call site reserves before its mutation (N2 unchanged) and the coordinator takes that
  reservation for the first attempt, which starts at once. Any wait or failure releases it; later attempts reserve
  again. An attempt holds its reservation for at most 100 ticks. Between attempts T is settled, so launch, refuelling
  and disassembly refuse L, and recovery skips it. A fail-back keeps its own reservation until the next tick even on an
  immediate wait, so a countdown cancellation still reports JOURNAL_PENDING and completes its request only once.
- **Census (R4).** The survivor's origin-column slot plus each discarded candidate's slot. A candidate off its end's
  origin column is refused before any change, with one WARN per rocket and reason (`ARCE_TRANSFER_RETIREMENT_HELD`).
- **Validator.** The survivor slot must hold exactly one entity naming L or the survivor's UUID, at any passenger depth,
  and it must equal the frozen projection: type, UUID, position and the whole `RocketEntityData` payload, with no
  nested entity. A discarded slot must name neither. Before freezing, the survivor must be T's loaded identity, owner and
  snapshot, stationary at its snapshot origin, with T's source fuel and debits.
- **Final check.** On the owner thread: identical T, the survivor's projection unchanged, the crew rule, the bay
  boundaries, and the escrow rule with this attempt's own reservation recognized (the token-aware recheck W96 asks
  for, written in the coordinator so `RocketTransferEscrowRules` is unchanged), and every proof still valid.
- **Crew (R3).** R17's placement rule against T's source manifest: online, alive, connected, not a spectator, in the
  survivor's Level, aboard it or unmounted. A placement is remembered, so a later dismount or logout never undoes it.
  Offline seats do not block a countdown cancellation; any other return waits, settled and unreserved, and the
  passenger's reconnect (I3) retries it at once. No player-data adapter.
- **Backoff (R11).** A superseding save or a busy budget retries at the next barrier tick; IO, force, bounds, veto and
  deadline failures back off 200 ticks; a waiting crew, an unloaded slot and a save-off Level are polled every 20 ticks
  without a reservation. A one-tick retry runs at most once per real tick (`EscrowBarrier.retryOrdinaryNextTick`).
- **Save-off (R5(d)).** A save-off Level holds every return there, with one WARN per Level until saving resumes.
- **Another mod's entity storage (R5(c), Root's choice).** Today's ordering: T is removed after the in-memory return,
  with one WARN per Level (`ARCE_TRANSFER_RETIREMENT_UNSUPPORTED_STORAGE`) and an INFO per return. This is the
  residual Root named.
- **Feedback (W96-R12).** `returnedToSource` still runs at the mutation, so it is provisional: a kill before the proof
  can recover the flight from T, and a refused publication with no saved source rebuilds the destination.
- **Abandonment.** If another owner changes T (removal, replacement, a fence, a bay claim, a live re-add or a stopped
  journal), the entry is dropped with T unchanged and its request is discarded; this logs at INFO. A survivor missing
  from its loaded slot logs a WARN and unclassifies T, so recovery rebuilds it.
- **Tickets.** The attempt refreshes the ordinary origin flight ticket the flight already held; no governed or margin
  ticket is borrowed.

### 7.1 The Space sleep test depends on its position

`SleepRespawnGameTests.sealedBreathableRoomsAdmitSleepButAPendingRoomDoesNot` builds a sealed room in Space at its own
structure's x and z and expects sleep there to be admitted "outside stations". Vanilla places each test's structure
after all earlier tests', so its position depends on how many tests run before it. The ten new tests run before it
(498 tests before it, against 488 in W100's run), and in both full runs with them (`e04fbe81` and `397e7898`) sleep is refused
with `station_denied`: a station committed by an earlier test covers the new position. It passes in W99's and W100's
full runs without them, and check B above shows that on `397e7898` itself, with only the new batch removed from the
same prefix, it passes. This task's production code is therefore not the cause. Which station covers the position was
not identified; the full run commits 96 stations and logs only 3 deletions. The fix belongs to the sleep test (for
example, a position known to be outside every station cell) or to the earlier tests' station cleanup. Both are
outside this task's write scope, so Root decides. Renaming the new batch to move it would only hide the dependency, so
that was not done.

## 8. Problems found on the way

- The first coordinator abandoned a pending return whenever a bay's RELEASED_TO_ORDINARY handoff unclassified T, so
  recovery re-ran it forever (`6e4d8481`).
- The one-tick retry first used the server task queue. Tasks run between ticks while the tick count stands still, so a
  return whose budget stayed busy queued itself again and the loop spun: the run on `e04fbe81` stalled for 7.5 minutes
  at the start of the new batch. The retry now runs once per real barrier tick (`abe1a18e`).
- Fixture bugs: a negative backdated game time, a save-off target outside the entity-ticking chunk, and the matrix
  predicate taking its completed report twice.
- Background runs started through the tool are stopped after two hours, lock wait included. Two of this task's runs
  were stopped that way; later heavy runs were started as detached processes.

## 10. Known risks

- **Players see the rocket stationary while it is still briefly unavailable.** Launch, refuelling and disassembly are
  refused until the proof completes, normally a few ticks and at most about one 20-tick barrier batch longer.
- **Indefinite holds per rocket:** an offline passenger after an end-of-transit return or a recovery, a save-off Level,
  an unloaded slot, a candidate off its origin column, or a survivor whose image keeps failing validation. Each holds
  only that rocket, without a reservation, and logs once per reason.
- **The end-of-transit fall residual (W96-R3)** remains: a player saved mid-flight and killed before the next player save
  logs in where that save put them. No synchronous player save was added.
- **R5(c):** in a world where another mod replaced the entity storage, ordinary returns keep today's ordering.
- **The coordinator's tick and the barrier's shared one-capture-per-tick budget:** an ordinary capture can delay a
  governed capture by one tick; the sub-quota bounds how often.
- Existing tests that construct their own services or managers now depend on the barrier's callbacks and retries to
  finish a return, or tick the coordinator themselves.

### F.3 W98-R2 (R35 item 1): why it is not implemented

R35 item 1 assumes that a ledger that exists but is not operational leaves the coordinator holding returns it can
never prove. The code shows otherwise:

- **A non-operational ledger locks every logical rocket.** `EscrowCoordinator.logicalLocked` returns true whenever
  `!operational()` (`resourceescrow/EscrowCoordinator.java:562-564`). Once bound, `ResourceEscrowSavedData.operational()`
  is that coordinator's `operational()` (`ResourceEscrowSavedData.java:20`), and `EscrowRuntime.tick` binds it before it
  checks (`EscrowRuntime.java:284-287`). `EscrowLedgerBaselineTest` (lines 55 to 59) already pins this: with an
  unavailable baseline, `data.operational()` is false and `logicalLocked` is true for any rocket.
- **So no ordinary return starts, and a pending one is taken away.** In that state, I1's `failBack` is refused by
  `RocketTransferEscrowRules.flightAllowed`. `RocketTransferFences.classify` fences every ordinary record
  (`ESCROW_PENDING_OR_TOMBSTONE`, one existing `ARCE_TRANSFER_FENCED` WARN per record), so I2 and I3 skip it. A pending
  entry is abandoned as `FENCED` (INFO) on the next service tick, because `classify` runs before `tickRetirements`;
  T stays with its fence. When the ledger is operational again, fence re-evaluation hands T to recovery, which proves
  it as an I2 return. This is what happened to every ordinary record in that state before W98.
- **A fallback cannot run without bypassing that lock.** The coordinator's own `escrowAllowed` refuses for the same
  reason. A fallback placed after it would never run; one placed before it would remove T while the escrow coordinator
  reports L locked.
- **What is left of W98-R2:** an attempt that had already staged a capture when the ledger stopped leaves that capture
  in the stalled barrier, with its slot watch and one of the eight ordinary pending slots, until the barrier ticks
  again or the server stops (`quiesce` releases them). This is bounded by the sub-quota, holds no reservation and is
  not visible to players.

Root may want to correct R35 item 1 and the review's proposed R-035 hold (7): that hold is the existing escrow fence,
not a W98 hold. No code, ADR or risk text was changed for it.

### F.4 Choices where the task left room

  `BUSY` reason (INFO, once per reason change).
- **R7:** the hold re-checks every 200 ticks, logs one WARN when the slot is refused and one INFO `WAIT CENSUS_LIMIT`.
