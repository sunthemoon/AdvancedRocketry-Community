### Design before implementation

Use `PlayerLoggedOutEvent` at LOWEST priority, before `PlayerList.remove`
serializes the player. Require the native `hasDisconnected()` flag, the
loaded physical rocket, an operational stationary flight (ASSEMBLED, FUELED
or LANDED), no active transfer and no rejoin/internal-move guard. Held bay
transactions remain transfer-owned rather than becoming voluntary exits.

Resolve the existing `getDismountLocationForPassenger` destination and prove
that exact standing box safe with the existing `BayExitSafety` loaded-world
adapter and the installed exit service's shared per-tick budget. This uses at
most one candidate, 96 block reads and 16 entity visits; unavailable chunks,
unsafe support, hazards, collisions and exhausted budgets leave saving
unchanged. No search, chunk activation, private save format or file rewrite is
introduced.

that vanilla calls after saving. Its `stopRiding`/`LivingEntity.dismountVehicle`
chain uses the existing rocket exit hook. Do not call LEAVE or mutate the
manifest. Inspection shows the ordinary unheld detach has no roster mutation:

### Pre-implementation design and save contract

**Hook.** The installed Forge 47.4.10 mapped bytecode confirms that
`PlayerList.remove` fires `PlayerLoggedOutEvent` at bytecode offset 1, calls
`save(player)` at offset 18, and only then calls `player.unRide()` at offset 70.
The event is early enough to change the player's live position while retaining
the physical mount and durable manifest, but the serializer below does not
write that whole position. Normal server shutdown first calls
`PlayerList.saveAll`, then `removeAll`; the latter disconnects connections,
whose `onDisconnect` calls `PlayerList.remove` and its logout save. The initial
shutdown `saveAll`, like an autosave, does not itself fire the logout event.
This shutdown call graph was inspected, not exercised with a native server.
(W312F correction, R375: for players still online at a normal dedicated-server
stop, `removeAll`'s disconnect does not reach `PlayerList.remove`; see the
revision 2 correction above.)

**Exit computation.** LEAVE SEAT and ground sneak eventually use
`RocketEntity.getDismountLocationForPassenger`, delegated to
`RocketRuntime.bayPassengerExitLocation`. For an ordinary, unheld stationary
rocket the existing exit is `rocket.position().add(1.5, 0, 0)`. W312 must not
substitute the rocket's center or the high seat. A future adapter must prove
this exact destination safe using bounded, loaded-only collision, support and
hazard checks; an unproved destination must retain the existing save position.
It must not trigger the held-bay exit service's detach-only side effects.

**Eligibility.** Use the existing stationary states ASSEMBLED, FUELED and
LANDED, with no active transfer. In-flight, transfer-owned, guarded or
unavailable cases remain owned by existing recovery. Neither logout nor
autosave may mutate the durable seat assignment. An ordinary autosave while
seated remains unchanged. Old saves retain the old behavior once; no offline
player file is migrated.

**Additional constraint found before implementation.**
`Entity.saveWithoutId` does not serialize the mounted player's whole position.
When its `vehicle` field is non-null it writes `Pos` as
`[vehicle.getX(), player.getY(), vehicle.getZ()]`. Consequently moving the
still-mounted player to the computed exit changes only the saved Y: the saved
X/Z remain the rocket's center. This would move the reported high-seat fall
into an inside-the-rocket login, not satisfy R364's exit-placement requirement.
`PlayerDataStorage.save` exposes no pre-write NBT event: it calls
`saveWithoutId`, writes and replaces the file, and only then fires
`PlayerEvent.SaveToFile`, which supplies file paths rather than the NBT tree.

No production adapter has been written. Temporarily detaching the physical
rider while retaining its manifest would permit vanilla to save the complete
exit position, but violates R364's explicit no-dismount instruction. Replacing
the serializer, moving the rocket during saving, or rewriting native player
files is not an authorized substitute. A clarification was requested in this
session; no decision changing R364's no-dismount condition was received before
delivery. No connected-player reproduction is claimed.

## Evidence for the stop condition

1. [RocketEntity](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/entity/RocketEntity.java),
   method `hasExactlyOnePlayerPassenger`, deliberately returns `false`. Its
   comment explains that rockets remain world/journal owned rather than being

2. Inspection of the cached Forge 47.4.10 mapped `ServerPlayer` bytecode confirms
   that vanilla writes `RootVehicle` only when that predicate is true. This is
   not just an assumption about vanilla behavior.
3. The existing
   [RocketPassengerPersistenceGameTests](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/gametest/RocketPassengerPersistenceGameTests.java)
   explicitly asserts `!savedPlayer.contains("RootVehicle")` for mounted rockets
   with one and two riders. This test was inspected, not run in this session.
   Enabling embedded vehicle saves would contradict this existing invariant.
4. [RocketRejoinGuards.join](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/rejoin/RocketRejoinGuards.java)
   returns without installing a guard unless the player's UUID is in the
   pending release index. That index unions release roots and admissions, not
   ordinary passenger logout history. The operator seat release only updates
   the existing manifest through
   [RocketSeatRelease](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/RocketSeatRelease.java);
   it creates no such obligation or player-save identity.
5. [RocketTransferRecoveryService.tryReconnect](../../../../src/main/java/io/github/sunthemoon/advancedrocketrycommunity/rocket/server/RocketTransferRecoveryService.java)
   returns immediately for an empty journal. With a journal, it uses the loaded
   settled rocket's current manifest when available and skips a player whose
   assignment is absent. It has no ordinary former-rider fallback.

The field report labels its explanation involving `RocketRejoinProtection` and
vanilla remount as an unverified code inference. The observed fall and health
loss remain valid reported symptoms, but a normal rocket rider does not have a
vanilla `RootVehicle` to remount in the first place. A login fix limited to that
NBT key would miss the reported ordinary logout case.

After a released seat and its rocket/transfer record are removed, an ordinary
airborne player's save and a former rider's save can contain the same relevant

logout map cannot survive a server restart. Broadly relocating airborne logins
would change unrelated player behavior. None of those substitutes was added.

Root needs to revise W312's authorization before implementation: either permit
a bounded durable former-rider/rocket reference with compatibility behavior for
older unmarked saves, or approve a different save-position policy and its
limits. Saving an exit position proactively is not equivalent to selecting the
loaded rocket's exit at login, and cannot identify already-offline old saves.
No design or ADR choice was accepted on Root's behalf.
