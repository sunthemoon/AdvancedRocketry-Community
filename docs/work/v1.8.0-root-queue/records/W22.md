### Notices

- **Kinds.** Each kind is `Component.translatable` with a key under
  `station.advancedrocketrycommunity.notice.`:
  - `warp_started`: the countdown start, in chat, live only;
  - `warp_countdown`: one countdown second, on the action bar only, live only;
  - `warp_committed`: the commit, in chat, and stored;
  - `warp_aborted`: a cancel (`WARP_CANCELLED`) or a refused commit, in chat, and stored;
  - `warp_outcome`: the brief form of a stored outcome (station and code), used only when
    the full envelope exceeds 512 bytes;
  - `while_away`: the login wrapper around one stored outcome.
- **Arguments.** The first argument is always the station name. An outcome's second
  argument is the existing code key `station.advancedrocketrycommunity.code.<code>`. The
  cost class is its own key, `station.advancedrocketrycommunity.warp_class.<class>`.
  Bodies and numbers are literal text. Every argument is checked against its role (the
  station-name rule, a canonical body ID, a canonical non-negative int, a code that the
  kind allows, a known cost class). No notice carries a player name, a UUID or a
  coordinate. The actor and every detail stay in the existing `ARCE_STATION_WARP` audit.
  (Correction, W55 on 2026-10-15, after W22 review F9: this holds for the argument roles,
  not for every value. The station name is free text, and a default name is the creator's
  player name followed by " Station" (`StationManager.java:94`), so a notice that names
  such a station also shows that player name to everyone told, visitors included. ADR-065
  section 5.3 requires the station name in visitor notices.)
- **Recipients.** They are computed from the live registry each time a notice is sent:
  - the live owner and members who are online, wherever they are;
  - the acting player, when online;
  - players in the Space Level whose block position is inside the live station's region.

  Each player is told once per notice. Without a live station (deleted, or a blocked
  registry), only the actor is told. Players in another station's region or in the gap
  are not told.

### The offline member-notice store

- **Root.** `advancedrocketrycommunity_station_notices`, stored with the Overworld data, root
  schema 1:
  `{schema_version, stations: [{id, rev, acks: [{id, rev}], outcome?: {key, args}, owner?: {id, rev}}]}`.
- **Bounds.** At most 4,096 entries and 32 member acknowledgements per entry. The owner's
  acknowledgement has its own field, because members exclude the owner. A stored envelope
  is at most 512 bytes of exact NBT payload. The root is preflighted at 8 MiB, depth 16 and
  a fixed node count before it is read. The largest valid store (4,096 stations, each with
  a 512-byte envelope, an owner and 32 member acknowledgements) encodes inside 8 MiB.
- **Updates.** Station creation adds an empty entry (revision 0). A commit or abort
  replaces the entry's outcome in place at revision + 1, and acknowledges the owner and
  members who were told live. Nothing grows per event.
- **Membership.** Every change that names a live station first drops the acknowledgements
  of players who are no longer its owner or a member, and an ownership transfer moves an
  acknowledgement between the two fields. Member removal and ownership transfer reconcile
  the entry at once; deletion removes it. Server start reconciles every entry, drops the
  entries of missing stations and adds an empty entry for each station without one.
- **Login.** For each live station whose owner or member the player is now, an
  unacknowledged outcome is shown once as `while_away`, and the acknowledgement is recorded
  at once. At most 16 are shown per login; the rest wait for a later login.

## Choices where the ADR was open

- **Language namespace.** ADR-065 section 5.3 names `advancedrocketrycommunity_v150`. The TASK
  and W07 use the v1.8 namespace (`advancedrocketrycommunity_v180`), because `runData` writes
  only `src/generated/v1.8`. The keys keep the established
  `station.advancedrocketrycommunity.*` form.
- **Authorized actors.** These are the live owner, the live members and the acting player
  (an operator acting on a station they do not belong to is told as the actor). Operators
  who did not act are not told.
- **Visitors.** A visitor is any player in the Space Level whose block position is inside the
  station's current region (base or expanded) when the notice is sent.
- **A cancel is an outcome.** A cancel is stored as an abort with the code `WARP_CANCELLED`
  and replaces the summary, because it ends the countdown that members were told about.
- **The owner's acknowledgement** has its own field, so one station can hold 33
  acknowledgements: the owner's and at most 32 members'. The ADR bound of 32 applies to the
  members, which matches the station's own member limit.
- **Envelope admission.** The 512-byte budget is the exact NBT payload of `{key, args}`. An
  outcome over it is stored as the brief `warp_outcome` (station and code), which is at most
  250 bytes for any valid name and code, so a valid outcome is never lost.
- **Told live means acknowledged.** An owner or member who saw the outcome live is not shown
  it again at login. Rapid outcomes are summarized: only the latest one is shown.
- **Login limit.** At most 16 outcomes are shown per login, so a player in many stations is
  not flooded. The rest wait for a later login.
- **Revision exhaustion.** At revision `Long.MAX_VALUE` the summary keeps its last outcome and
  refuses new ones, with one WARN `ARCE_STATION_NOTICE_NOT_KEPT`. This is unreachable in
  practice.
- **No configuration key** was added; the ADR asks for none.

### ADR note text (for ADR-065, after section 5.3)

```markdown
### W22 implementation note: station notice data preservation

This note documents protection mechanics, not a changed decision or accepted
risk (risk R-029). Neither mechanism refuses a save or throws from serialization.

- **Notice root.** An `advancedrocketrycommunity_station_notices` SavedData root
  that reads as NBT but does not decode (unknown, future, malformed or over a
  section 5.3 bound) is kept by reference and written back unchanged. The
  affected unit is the whole server's offline member-notice store: no outcome
  is recorded, no login notice is shown and no acknowledgement is recorded.
  Live warp notices still reach the online owner and members, the actor and
  visitors inside the region. None of the stored summaries is deleted. It lasts
  until the file is repaired, because a restart with the same file refuses it
  again; one WARN (`ARCE_STATION_NOTICES_REFUSED`) is logged per load. Recovery
  is an offline repair of `data/advancedrocketrycommunity_station_notices.dat`
  from a backup, or its removal, and a restart. Removal loses only the outcomes
  that some owner or member has not seen yet; the next server start gives every
  station an empty summary. The warp audit stays in the server log either way.
- **Unreadable notice file.** As for the beacon index, a `.dat` file that cannot
  be read as NBT at all (for example a truncated gzip) makes vanilla
  `DimensionDataStorage` log an ERROR and start an empty store, which the next
  outcome overwrites. The loss is soft: only unseen outcomes.
- **Revision exhaustion.** A summary at revision `Long.MAX_VALUE` keeps its last
  outcome and refuses later ones, with one WARN `ARCE_STATION_NOTICE_NOT_KEPT`
  per refused outcome; live notices continue. It is unreachable in practice.
```

## Known risks

- **Orphaned summaries in GameTests.** Production creates and deletes stations only through
  `StationManager`, which keeps the store in step. Several GameTests create or delete
  stations directly through the registry; a summary they leave behind stays until the next
  server start or until the store is full, when missing stations are dropped first. This
  affects only the test server.
- **Visitor delivery is positional.** A player standing just outside the region at the
  moment of a notice is not told, and one standing inside is told even when only passing
  through.
- **Two service instances.** `StationWarpService` and the mod constructor each create a
  `StationNoticeService`. The service holds no state, so both act on the same SavedData.
- **Size guidance.** `StationWarpService` (656 lines) and `StationWarpGameTests` (705 lines)
  were already over the 500-line guidance and stay under 800. `StationManager` is now 508
  lines; the addition is the lifecycle callbacks of the same authority.
