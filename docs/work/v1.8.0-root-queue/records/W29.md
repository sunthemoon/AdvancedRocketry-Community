## The rule on the final source

`read` and `probe` make these reads, in this order:

1. h1: the slot's 4-byte location and 4-byte timestamp entries, and the 5-byte length and
   compression prefix at the sector that the location names;
2. p1: the payload bytes; then the bounded decode;
3. h2: the same entries and prefix again, which must equal h1;
4. p2: the payload bytes again at the same offset, which must equal p1;
5. the file must not end before the record (`start + 4 + length`), and the path's file
   identity (`fileKey`) must be unchanged.

The whole-file size and modification-time comparison is gone. External records, bounds, the
bounded NBT envelope and trailing bytes are checked as before. The external branch applies
steps 1, 3 and 5 to the region header around its size-only `.mcc` probe.

## Why no false confirmation becomes possible

**Source.** `javap -c -p` of `RegionFile`, `RegionFile$ChunkBuffer`, `RegionBitmap` and
`ChunkMap` from the mapped jar
`forge-1.20.1-47.4.10_mapped_official_1.20.1.jar` (SHA-256
`95eecc5985233d83a6571299f89f02de034267646da171f7b36a5be2d394d71e`). The output is in
`javap-RegionFile.txt`, `javap-RegionFile-ChunkBuffer.txt`, `javap-RegionBitmap.txt` and
`javap-ChunkMap.txt` in the evidence directory. Offsets below are bytecode offsets in those
listings.

**Vanilla facts.**

- V1, write order. `RegionFile.write(ChunkPos, ByteBuffer)` is `synchronized`. It allocates a
  run first-fit (`RegionBitmap.allocate`, offset 144), writes the whole record there (offset
  170; an external record writes its 5-byte stub at offset 131 after writing the `.mcc`
  temporary file), updates this slot's in-memory location and timestamp (174-199), writes the
  whole 8-KiB header from memory (`writeHeader`, offset 204), runs the commit (deletes or moves
  the `.mcc` file, 209), and only then frees the old run (`RegionBitmap.free`, 227).
  `clear(ChunkPos)` writes the header with location 0 and then frees the run.
- V2, the only writes. A region file is written only by the record write (170 or 131), the
  header write and `padToFullSector`, which writes one byte at or after the end of the file
  and is called only from `close`. `RegionFile` never truncates.
- V3, used runs. `allocate` returns only clear bits and marks them used. The constructor marks
  the two header sectors (offset 189) and every valid slot's run (450) as used. A run
  therefore stays used from its allocation until after a header write that no longer names
  it.
- V4, other slots. A header write copies every entry from memory. An entry changes in memory
  only inside its own chunk's `write` or `clear`. Another chunk's header write rewrites this
  slot's eight bytes with the bytes already on disk.

**Invariant.** While the on-disk entry of a slot names a run, no write touches that run (V1
to V3). When a read sees an entry, the record that the entry names is already complete,
because the record write returns before the header write starts on the same thread, and the
reader shares the same host file cache. (Durability after a crash is the barrier's force,
which is unchanged.)

**Interleavings.** Write this chunk's run as S and its record as R.

1. *Another chunk is saved during the read.* By V1 and V3 its record goes to a free run, not
   S. By V4 its header write leaves this slot's eight bytes as they were, so no torn value is
   possible. So h2 = h1 and p2 = p1, and the reader returns R. The file grew and its time
   changed, which is exactly what the old rule refused. Test:
   `aNeighbourSaveInTheSameRegionDuringTheReadIsStable` (the neighbour's record grows the
   file, then moves, then reuses its own freed sectors).
2. *This chunk is rewritten to new sectors.* At allocation S is still used (V3), so the new
   run S' is disjoint from S.
   - The header write comes after h2. The entry named S during the whole of h1 to h2, so S
     did not change (invariant), and p1 is R. The reader returns R, the consistent old
     record. When R lacks the frozen frontier or marker, the barrier's validator rejects it.
     Test: `aRewriteOfThisChunkIsRefusedOrReadsTheConsistentOldRecordWhichTheValidatorRejects`
     replays vanilla's own bytes for the new sectors between the reads, then checks that the
     real `EscrowTestEndpoints.validator` rejects the returned record and accepts the new one.
   - The header write comes between h1 and h2. Then h2 names S' or a new timestamp, and the
     read is refused. The same test covers the sectors written before the first read with the
     header between, both writes between, and a whole vanilla `RegionFile` write between.
   - The header write comes before h1. That is an ordinary read of the new record.
3. *The old sectors are freed and reused by another chunk between the reads.* The free
   (offset 227) follows this chunk's header write (204), so h2 already names the new run and
   the read is refused. The test makes the neighbour's reused record byte-identical to R, so
   only the header can refuse it, and it does: `oldSectorsFreedAndReusedBetweenTheReadsAreRefused`.
4. *The file is truncated.* Below the record's end, h2 fails its own bounds check or p2 is
   short, and the read is refused; the final size check covers truncation after p2. Ending
   exactly at the record's end is accepted, because vanilla pads to whole sectors only on
   `close`: an open region legitimately ends at its last record. Test:
   `aTruncatedRegionFileIsRefused` (record end accepted; record end minus 1, 8,192 and 0
   refused).

**Same sectors, same second.** The entries can return to h1 only if this chunk is written at
least twice during the read: once away from S, which frees S, and once back into S, which
first-fit allocation can choose, within the same wall-clock second. Because the header is
reread before the payload, p2 then reads the record that h2 names (unless this chunk moves a
third time before p2), and acceptance needs p1 to equal it byte for byte. The returned bytes
are then that record. The test writes a
different record back into S and restores the timestamp, and the read is refused by the
record comparison (second case of `oldSectorsFreedAndReusedBetweenTheReadsAreRefused`). Every
write of this chunk is a save that the barrier's generation monitor counts, and the barrier
refuses any readback whose generation changed (`EscrowBarrier` lines 143 and 168), so the
barrier cannot confirm through this case even when the bytes match.

**External records.** The region-header checks around the `.mcc` probe follow the same rule.
The `.mcc` file belongs to this chunk alone and vanilla replaces it with `Files.move`, so its
whole-file attributes are this record's, and its attribute and byte checks are unchanged. The
probe never issues proof. Test: `externalProbeKeepsTheSlotRule`.

**What the narrowing gives up.** Compared with the whole-file rule, the reader now accepts a
read during which other slots changed. It does not accept a read during which this slot's
entries or record bytes changed, except the same-second return described above, which the
generation check refuses.

## Choices where the TASK left room

- "The slot's end" is the record's end, `start + 4 + length`, not the end of its last sector.
  Vanilla pads only on `close`, so the last record of an open region file ends the file.
- File identity (`fileKey`) is still compared, because the W11a design (section 3) asks for
  file identity. It is not a size or time check, and on Windows it is `null`, so it is
  neutral there.
- A package-private `probe(directory, pos, afterRead)` test seam mirrors the existing `read`
  seam. In the external branch the seam runs between the `.mcc` probe and the second header
  check.
- "The K, C, E and G cases" is the harness's complete default selection: K0-K10, C1-C3, E2,
  E2_CAPTURE, E4L1_FAIL, E4L1_UNKNOWN, E4L2_FAIL, E4L2_UNKNOWN, E4L2_RESAVE, E5, G3 and G3L2
  (24 cases).
- No ADR changed. The change removes a cause of refusal and adds none, so it needs no
  risk-register entry under AGENTS.md section 3.3.

## Known risks

- **Intermittent GameTest failure (open).** `jointterrainslotproofretainstheotherendpointlease`
  failed once and passed in the rerun on the same source and JAR. It was added in `16f439dd`.
  About ten earlier runs that included it (W11b1 and W11b2 evidence, and hosted CI run
  38357901251) show no failure of it.
  The assertion message does not include the barrier's reason, so the cause is unknown. The
  reader change cannot produce it. On any interleaving, the new reader accepts every read that
  the old one accepted, with the same root: the only removed condition is the size and time
  comparison, and the header reread already enforced the new size condition. The test asserts
  its first barrier attempt. One cause of a first-attempt failure under the old reader was a
  vanilla eager save of a neighbouring chunk in the same region file. `ChunkMap.processUnloads`
  saves up to 20 dirty chunks per tick when the tick has time (offsets 178-244), with a
  10-second cooldown per chunk (`saveChunkIfNeeded`, offset 101). That cause is now gone.
  Other causes, such as a save of the fixture's own chunk (`SUPERSEDING_SAVE`, which is correct
  barrier behaviour), still make this single-attempt test timing-dependent. Root should track
  it as an open intermittent failure. Adding `result.reason()` to the assertion message would
  make the next failure diagnosable. That is W11b1's file, outside this task.
- **Same sectors, same second.** As above, the reader alone can at most return a record that
  the slot named during the read. The barrier's generation check refuses this case. A vanilla
  writer the mod cannot observe remains the residual that the W11a design already registers.
- **Shared file cache.** The argument assumes that the reader and the vanilla writer see one
  host's file cache, as they do in one server process. A region directory on a network file
  system with weaker coherence is outside it, as it was before.
- **Torn header reads.** A torn 4-byte read can only happen while this chunk's own header
  entry is being changed, which is a rewrite of this chunk (cases 2 and 3 above).
- **Commit order.** `1a125e8e` alone has the weaker read order; review it together with
  `d2820e6f`.
