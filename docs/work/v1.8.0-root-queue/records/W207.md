## Execution

### Profile-informed remedy (before production edits)

The calibrated baseline source is `ef6ee93b8`. Its new-contained request is
457.587 ms (433.950 ms API); its new-square request is 690.695 ms. JFR shows the
server blocked under `RocketLandingPadSelector.loadChunks`, with vanilla worker
generation active. Recorded long parks overlap 28.940/62.673 ms respectively;
shorter parks are below JFR's threshold, so these are not total waiting times.
The relaunch ticks are 105.416/116.031 ms, with 16.386/18.991 ms of transition
observation. Relaunch samples include first-use ModLauncher class loading and
`EscrowGovernedLaunch.record` projection/validation. Recorder tails are tens of
microseconds in these ticks. These are measured components, not subtracted from
the whole-tick budget. The full baseline campaign continues on its clean export.

1. Capacity refusal will use a loaded-only selector when no warm-up slot is
   available. It reads at most the existing eight server-owned candidates and
   never loads terrain. An already-loaded valid selection still reaches the
   unchanged readiness decision and can launch without a warm-up when ready.
   Unknown terrain yields `DESTINATION_LOADING_LIMIT`, before any ticket or
   claim. Named pads keep their existing loaded-only selection and claim rules.
2. A governed cold selection will return its checked footprint demand instead
   of loading it synchronously. A RAM-only preparation occupies the same global
   and per-owner capacity as a warm-up. It acquires only that candidate's old
   footprint columns, using plain level-33 tickets, and polls loaded terrain;
   the public `getChunkFuture` is unsuitable because bytecode confirms that it
   calls `managedBlock` on the server thread. Preparation is not a landing
   reservation or named-pad claim. Exact terrain/height/support/occupancy and
   reservation checks still precede a normal warm-up. The original start and
   captured 600-tick-or-lower deadline cover both stages. At most one pending
   selection is advanced per tick; at most eight candidates and sixteen columns
   per demand remain. No F1 or automatic launch runs on completion: the player
   sees destination-loading, then the existing ready hint, and must send a new
   request which revalidates everything. Replacement, disconnect, removal,
   expiry and stop release only owned tickets; restart saves no preparation.
3. F1 may reuse a single immutable projected record for an exactly equal ARMED
   tuple within one preparation object. A changed serial, generation or tuple
   reconstructs it. Root/authority/boundary/capacity and checkpoint checks still
   run at every existing boundary. The cache is neither persistence nor an
   acknowledgement. This targets repeated projection/hash work, not vanilla
   class loading; any residual class-loading/observer overrun remains reported.

The preparation ticket influence is no greater than the synchronous FULL
footprint acquisition it replaces. Before normal level-31 warm-up tickets are
installed the preparation tickets are removed. No forced flag, new column,
longer deadline, early authoritative reservation or durable format is added.

Preparation found the assigned worktree clean at the specified commit. Other
workers were observed and left untouched. C: and D: exceeded 10 GiB free.
OpenPet was unreachable. No upstream source or asset is imported.
