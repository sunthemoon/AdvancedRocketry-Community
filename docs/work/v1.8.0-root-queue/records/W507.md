## C6 Observatory findings for Root

All server files cited here were compared against `c8fa16e16` with
`git diff --exit-code`; they are unchanged. Line numbers therefore apply to
C6 and this branch. Files in this section use the Java path prefix above.

1. **Menu data:** `machine/classic/runtime/ResearchService.java:81` reports
   UNFORMED (or UNLOADED) when formation is absent.
   `ResearchControllerMenu.java:47-58` sends that status in slot 0, the current
   `controller.storedEnergy()` in wide slots 6/7, required FE/t in slot 8, and
   the missing-cell coordinates/role in slots 9-12. Owner relation remains
   encoded in slot 1. There is no additional formation bit in this menu wire.
   `ResearchControllerMenu.java:67` decodes those same energy slots, and
   `client/ResearchControllerScreen.java:62` draws `menu.energy()` without
   substituting or caching a different value. No energy-display fix is needed.
2. **Start is refused; Cancel is not formation-gated.**
   `ResearchControllerMenu.java:92-97` validates the viewer/menu and delegates
   to the service. `ClassicControllerMenu.java:61-67` validates physical
   presence, player, interaction and distance, but does not require formation.
   `ResearchService.java:135-142,218-220` applies `basic()` before Start, so an
   unformed Start is refused. However, `ResearchService.java:212-216` handles
   Cancel before `basic()`: an operational registry, valid admitted identity
   and selected job can reach cancellation even while unformed. With no
   selected job it reports JOB_NOT_FOUND. `satellite/mission/GroundSurveys.java:175-189`
   checks authorization and ACTIVE phase, not structure formation. This
   distinction is reported, not changed: the requested inactive Cancel button
   is a presentation restriction, not a new server authority rule.
3. **The server aggregate becomes zero; the intact power hatch keeps its FE.**
   `machine/multiblock/lifecycle/MultiblockLifecycleCoordinator.java:45-59`
   unbinds loaded parts and replaces the active part set with an empty set on
   a mismatch. `machine/classic/runtime/ClassicControllerBlockEntity.java:257-260`
   stores that state, and `:317-323` totals energy only from its active part
   positions. The empty set therefore produces the transmitted 0 FE.
   `ClassicHatchBlockEntity.java:54-59` clears/replaces the binding and refreshes
   facades without clearing its `energy`; `:133-134` distinguishes the stored
   field from a debit, and `:171-181,201-202` saves/restores that field.
   Breaking an ordinary shell cell is not an energy debit. This explains the
   frame's 10000-to-0 aggregate without establishing physical energy loss.
   No server aggregation, binding or storage logic was changed. This conclusion
   is from C6 source inspection, not a new live energy readback.
