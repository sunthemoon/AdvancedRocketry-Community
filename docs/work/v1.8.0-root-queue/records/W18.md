### The beacon

- **Block.** `planetary_beacon` faces its placer, and the pattern extends behind it. Pistons cannot move it.
  Breaking it with a pickaxe drops the block; explosions follow the usual `survives_explosion` rule.
- **Pattern.** `machine_patterns/planetary_beacon.json` is 3 wide, 5 high and 3 deep, in all four rotations:
  - a 3 by 3 base of `machine_casing` with the controller at the front centre;
  - a column of three casings above the base centre;
  - a `minecraft:redstone_block` on top;
  - the 32 cells around the column must match `machine_clearance` (air or a thin decoration).
- **Validation.** The v1.2 kernel validates the pattern as the endgame structures do (`EndgameStructure`'s
  rotation and box helpers, its change tracker and its round-robin budget are reused):
  - when a block in the pattern box changes, and every 200 ticks;
  - at most 8 validations per server tick for all beacons together;
  - through the loaded-chunk view, so an unloaded cell is "part not loaded" and no chunk is loaded.
- **Ownership.** Placement by a connected, non-fake player makes that player the owner, and a valid custom item
  name becomes the beacon's name. Only the owner or an operator (permission level 2) changes it:
  - an empty hand switches it on or off;
  - a named name tag renames it, and the tag is kept;
  - sneaking with an empty hand only reports the status.

  Everyone else learns only that it belongs to another player. A beacon placed without a player (for example
  by `/setblock`) has no owner and never activates.
- **Identity and generation.** Each beacon has a stable UUID. Its structure generation goes up by one each time
  it becomes formed, and saturates at `Long.MAX_VALUE`.

### The index

- **Storage.** One `advancedrocketrycommunity_planetary_beacons` SavedData in the Overworld storage, schema 1.
  Each record holds the beacon UUID, owner, body, Level, position, generation, active flag and name (at most 32
  characters).
- **Bounds.** 32 records per owner, 256 per body, 4,096 in all, and a root of at most 1 MiB. The 1 MiB bound
  counts the exact NBT payload bytes; a unit test checks the count against the real NBT writer.
- **Lookup.** Records are also indexed by owner, so a finder lookup reads only the viewer's own 32 records at
  most.
- **Reconciliation.** It is event-driven: the first tick after loading, each structure validation, and each
  switch or rename. A record is written only when it changes.
  - The record is active only while the full loaded structure is formed, the beacon is enabled and it has an
    owner. Unforming or switching off marks it inactive at once.
  - Unloading leaves the last record unchanged, and the finder then shows it as last known.
  - Removing the block deletes only the beacon's own record.
- **Missing body.** A missing catalog or body pauses resolution: an existing record keeps its last body, and
  nothing is deleted.
- **Copies.** A beacon whose UUID is already registered at another position (a copied block entity) stays
  inactive as a duplicate. It takes the record over only when the old position is loaded and provably holds no
  such beacon.

### The finder

- **Item.** `beacon_finder` is registered once, in `ModItems`. Because its ID is the shared `ModuleKind` entry,
  the merged workstation installs it into either of the built-in helmet's two HEAD positions with no change to
  the equipment code.
- **Eligibility.** A connected, living, non-spectator player is eligible while the finder is held in either
  hand, or while `ArmorEquipment.summarize(player).beaconFinderEnabled()` is true. That summary is the only
  source for the worn case. Holding and wearing together still give one stream.
- **Stream.** `BeaconFinderService` evaluates each player at most once per 20 ticks and sends a
  `classic_controls` index 2 snapshot only when it differs from the last one sent.
  - The snapshot holds only the player's own records that are last known active on the player's
    server-resolved body and Level: the nearest 8, sorted by distance and then by canonical UUID.
  - A marker is live only when its block entity is loaded, formed, enabled, registered and of the record's
    generation. Otherwise it is last known.
  - A player who stops being eligible is sent one empty snapshot, which clears the markers.
  - The state is forgotten at logout and cleared at server stop. A Level change or respawn resets what the
    client is known to show. A data reload forces the next snapshot to be sent again.
- **Client.** The client package draws a heading strip at the top of the screen, with one mark per marker
  (bright when live, grey when last known), and the name and distance of the marker nearest the view direction.
  The W07F cache in `classiccontrol/network` keeps the snapshot and still clears on logout, a Level change and
  respawn.
- **Channel.** `ClassicControlsNetwork.sendBeaconSnapshot` is the one new method. The channel table, the
  protocol and the frozen codec are unchanged.

### Data preservation (AGENTS 3.3)

An index root that does not decode is kept by reference and written back unchanged. While it is kept, the index
is unavailable for the whole server: no beacon registers, and every finder receives an empty snapshot. A
block-entity root that does not decode is kept and written back unchanged, and that one beacon stays inactive.
Neither refuses a save or throws from serialization. Because this isolates player data, AGENTS 3.3 asks for a
risk entry and an ADR note, so the commit `adeadf5e` adds risk R-028 and a labelled W18 implementation note
after ADR-065 section 7. They state the scope, duration, logging and offline recovery, and change no decision.
R-027 is the highest ID in any local branch; Root may renumber R-028 when merging.

## Choices where the ADR was open

- **Clearance around the column.** The legacy pattern accepts anything there; the kernel has no "any" matcher.
  The 32 cells use the existing `machine_clearance` tag (air, snow, torches, rails, carpets and similar). This
  is stricter than the legacy layout.
- **Front.** The controller is the front centre of the base, and the column stands behind it. This follows the
  pinned fact of a casing base, a column and a redstone cap.
- **No power cost.** Section 7 forbids inferring one.
- **Same body and same Level.** A marker must be on the viewer's body and also in the viewer's Level. A station
  resolves to its orbit body, so without the Level check an Overworld beacon would show in the Space Level with
  meaningless direction. This shows fewer markers, never more.
- **Visibility.** Section 7 shows only owned beacons, so every beacon is private to its owner. Operators can
  switch or rename any beacon but see only their own markers.
- **Switching and renaming.** This uses the vanilla block interaction instead of a menu, because the
  `classic_controls` kind table is frozen and no menu kind exists for the beacon. Placement takes the item's
  custom name; an invalid name is ignored there, and refused with a message when it comes from a name tag.
  Names refuse control and formatting characters and unpaired surrogates.
- **Clearing message.** One empty snapshot goes to a player who stops being eligible, so the client drops its
  markers. It carries no beacon data. This is the conservative reading of "only to an equipped or holding
  player" together with "unequipping clears markers".
- **"Resource reload".** This is read as the server data reload: the next snapshot is sent again. The client
  cache still clears on logout, a Level change and respawn. A client resource-pack reload does not clear it,
  because the server would not resend an unchanged snapshot.
- **Stale records.** A record is removed only when its own position is loaded and holds no beacon or another
  readable beacon, and only during a duplicate check. The finder never deletes records.
- **Cache location.** The W07F cache stays in `classiccontrol/network`, which has no client import, so the
  common packet handler can reach it. Only the drawing code is in the client package.
- **Recipes.** These are community recipes from C16 parts:
  - the beacon: steel plates, an advanced circuit, two user interfaces and a control board;
  - the finder: aluminium plates, two user interfaces and a basic circuit.

  They make no claim of legacy parity.
- **No configuration key.** No disable switch was added, so there are no new log expectations.

## Known risks

- **Strict clearance.** A decoration such as a lantern or a sign next to the column unforms the beacon.
- **Finder load.** It evaluates every online player once per 20 ticks. An eligible player costs one body
  resolution and at most 8 block-entity reads of loaded chunks.
- **Phantom markers.** A beacon removed while the index was unavailable leaves its record. Its owner sees a
  last-known marker until a duplicate check or an offline repair removes the record (R-028).
- **Disk space.** C: dropped from 3.0 GB to 0 bytes during this session through other processes. None of the
  large temporary directories on C: are mine, and I deleted none of them. My only C: writes were Gradle's
  shared caches and daemon logs.
- **Merge conflicts.** `docs/11-RISK-REGISTER.md` and ADR-065 may conflict with other open branches.
