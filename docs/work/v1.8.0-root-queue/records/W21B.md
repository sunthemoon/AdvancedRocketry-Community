## Implementation design before persistence changes

Registry root 4 has instance schema 2 and ground-job schema 1. Historical root 3
continues to require instances/save_epoch and `v1.6.0-satellite-missions`;
roots 1/2 forbid those sections. The existing 1/2-to-3 transformation is validated
as root 3 before the separate 3-to-4 transformation. Migration returns the actual
transformed payload, not any load-time quarantine/repair output.

The frozen single-record matrix is:

| Effective phase | Survey progress | Analysis | completed_at | resolved_at |
|---|---|---|---|---|
| ACTIVE | 0 through ticks - 1 | WAITING, zero, no claim | absent | absent |
| READY | ticks | WAITING, zero, no claim; or RUNNING, below analysis ticks, full claim | required | absent |
| PROCESSED | ticks | CREDITED, analysis ticks, retained full claim | required | required |
| CANCELLED | 0 through ticks - 1, preserved | WAITING, zero, no claim | absent | required |

QUARANTINED retains fields and validates this matrix against its first,
non-QUARANTINED previous phase. Only QUARANTINED carries a reason/previous-phase
block. Claim epoch/device/Level/position are all present or all absent. Timestamps
are nonnegative, completion is not before creation, and resolution is not before
completion (or creation for cancellation). Survey and analysis final advances
publish their terminal progress and paired availability/account credit atomically;
an intermediate ACTIVE-at-full-progress or RUNNING-at-full-progress is never made.

Cross-record failures hold affected records without payment or deletion. Strict
decode failures preserve and block the entire root. An ACTIVE quarantined pair
cannot be released online: offline repair must restore the PENDING instance and
ACTIVE job together with matching snapshot/backlinks. Duplicate retained RUNNING
claims require offline repair of the conflicting processor identities/claims;
neither release operation may change them. The first previous phase and credited
state survive re-quarantine and repeated loads. Count, lifecycle reservation,
record, root and bounded-read checks precede publication of any new state.

## Proposed ADR-051 implementation note for Root

Root should add the W21a section 1 origin, registry, backlink and retention note
with these implementation clarifications before merge:

1. The phase/analysis/field matrix in this record is normative. CANCELLED retains
   partial progress. QUARANTINED validates its first non-QUARANTINED previous
   phase and preserves the first reason, claim and CREDITED marker. Survey and
   analysis final ticks publish their paired state changes in one mutation.
2. An ACTIVE quarantined job/PENDING-instance pair and duplicate RUNNING processor
   claims are offline-repair-only. Both job release and instance release refuse
   without changing records, reservations, time or epoch, with an explicit reason.
   Repair all implicated identities, snapshots and backlinks together while the
   server is stopped. Other release operations validate the resulting state and
   serialized root before publishing it.
3. Instances/save_epoch are required from historical root 3; ground_surveys is
   required only from root 4. Roots 1/2 forbid both historical sections. Epoch 3
   remains `v1.6.0-satellite-missions`. The 1/2-to-3 intermediate uses a historical
   instance-schema-1 validator before the separate 3-to-4 transformation. Upgrade
   output is the detached transformed payload, not load-time repair output.
4. Admission checks fixed counts, record bytes, unchanged instance/account section
   budgets, the new 1 MiB job reservation, the 16 MiB root and the actual bounded
   reader before mutation. A valid restored over-reserved section keeps its data
   and refuses new admission rather than deleting records. Instance reservation
   includes QUARANTINED with an allocation, not just ALLOCATED; the longer state
   name costs two additional bytes. A tombstone whose `resolved_at + 1,200` cannot
   be represented is retained, never pruned early. Retained instance references
   prevent job pruning even when an offline diagnostic found a bad cancellation.
   The migration snapshot compares both instance envelopes under that complete
   lifecycle policy; its schema-1 `reservationBefore` is recomputed, not the old
   allocator-only implementation's counter (which was two bytes smaller per record).
5. Cross-record isolation affects only named jobs/instances and, for an invalid
   allocation, the existing affected mining mission. It lasts until a valid repair;
   no credit or refund is issued. One bounded aggregate restore warning is emitted
   per changed load, rather than per record/tick. Strict decode, schema, count or
   read failures preserve the whole satellite registry and block its use; the
   existing pre-start service refuses world startup and keeps the original file.
   Migration uses the existing atomic backup/staging flow. No new exception-based
   routine save-control mechanism or destructive recovery is introduced.
6. Ground reason strings retain their 48-character bound. Lifecycle reservation
   accounts for NBT modified UTF-8's three-byte maximum per Java character, while
   mission reason codes retain their existing ASCII-only constraint. The complete
   maximum ground encoding is 1,406 bytes; 1,310 is only the ASCII-reason variant.
   This corrects the byte estimate without raising any budget or discarding data.

## Proposed risk-register text for Root

Root assigns the risk ID and adds this entry before merge: schema 4 extends
satellite authority to ground jobs and changes persisted instance origins. A
malformed/future job or origin, a fixed-count/byte/read violation, or an impossible
missing-account repair blocks the whole satellite registry, and pre-start
validation may refuse world startup. The original root/file remains intact; no
player record is silently discarded. Cross-record inconsistencies instead hold
only implicated jobs/instances and dependent invalid mining missions. The hold
has no automatic expiry and does not award research/resources. A changed restore
logs one aggregate warning; a migration attempt logs one bounded budget summary;
blocked pre-start attempts use the existing migration diagnostic.

Recovery is offline: stop the server, retain a copy of the original data and
backup manifest, repair all implicated UUIDs/snapshots/claims consistently or
restore the matching pre-upgrade world authority files, and restart through the
validator. ACTIVE quarantined pairs and duplicate RUNNING claims cannot be
recovered by online release. Downgrading requires the pre-upgrade backup; an old
host must not read or overwrite root 4. The native harness checks that refusal and
backup recovery on disposable copies. Residual risk is operator repair error and
the cost of full-root bounded-read preflight; the device-runtime slice must measure
that cost against its scheduler budget rather than relaxing persistence limits.
