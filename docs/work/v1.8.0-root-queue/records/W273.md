## Cause and product-defect exclusion

The item belongs to the framework's start control, not a rocket. For the focused selection,
`GameTestInfo.spawnStructure` places a north-facing stone button at `(141, -60, -2)`,
backed by the command block at `(141, -60, -1)`. The button is at structure-relative `(1, 0, -2)`.
**Its support was not removed.** At server/game tick 761, water destroys the still-supported button:
the entity-creation stack runs through `WaterFluid.beforeDestroyingBlock`, `FlowingFluid.spreadTo`,
`Block.dropResources`, and `Block.popResource`. The support is still a command block during creation
and at the surrounding tick-700/tick-800 samples. Terrain water is the source inference: the empty
template and the selected fixtures place no water.

The unchanged base passes both unloaded and four-worker loaded selections, 11 tests each, while the
button still exists outside the assertion region. Its settled Z coordinate is `-1.0588548947829646`
in both runs; the original region starts at Z = 0. Holding that actual framework item at
`(142.5, -60, 0.5)` deterministically fails the original capture-throw test at server tick 2024 with
`age=1264`, matching the reported age. This is tick 761's creation counted through tick 2024 inclusively.

No rocket path occurs in the creation stack. The fault/registration rockets consist of a motor,
seat, guidance computer, and external fixture inventory; their cargo is diamonds and iron ingots.
The component rocket uses diamond, emerald, oak-plank, gold, and quartz blocks. None contains a button.
The template contains only an air entry, and the public inventory adapter captures/restores only
the fixture inventory. The framework button is outside the template and disconnected from every
rocket. No production assembly, capture, restore, or disassembly change was necessary.

## Change, tests, and design decision

Fixture setup now removes only its own framework stone button, after verifying the command-block
backing, before rocket operations. It uses block removal without generating drops. This fixes the
source instead of filtering the item or reducing the monitored region. The original `region` and
`noDrops` implementations are unchanged, as are the original batches, assertions, and timeouts.
No ADR choice, adapter API, persistent schema, network protocol, asset, or provenance entry changed.

Two GameTests were added in the same class. `flowingWaterCannotDropFixtureStartButton` drives water
across the real framework control while retaining its support; it fails before the fix and passes
afterward. `fixtureStillRejectsMemberAndCargoDrops` verifies that the unchanged assertion rejects
motor, seat, guidance-computer, diamond, iron-ingot, and stone-button item entities after setup.
The latter deliberately creates and then removes its negative-control items.
