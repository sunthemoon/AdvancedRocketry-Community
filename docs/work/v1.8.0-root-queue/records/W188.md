## Design note (written before the fix)

### Cause

The cause is a fixed packet order that JEI 15.56 does not wait for. Three sources show it:

- **The server sends recipes before tags.** Forge 47.4.10's `PlayerList` patch sends a joining player
  `ClientboundUpdateRecipesPacket` and then `ClientboundUpdateTagsPacket`. A `/reload` sends them the other
  way round: tags, then recipes.
- **The client binds item tags only when the tags packet arrives.** `ClientPacketListener.handleUpdateTags`
  binds the server's tags to the shared static registries, including `BuiltInRegistries.ITEM`. It then posts
  `TagsUpdatedEvent` with cause `CLIENT_PACKET_RECEIVED`. Before that packet, a fresh client has no item tags.
- **JEI 15.56.0.205 never waits for tags.** Its `mezz.jei.forge.startup.StartEventObserver` listens to
  `LoggingIn`, `RecipesUpdatedEvent`, `LoggingOut`, `ScreenEvent.Init.Pre` and resource reloads. It does not
  listen to `TagsUpdatedEvent`. The disassembly is `jei-inspect/StartEventObserver.javap.txt` in the evidence
  folder. When the server has no JEI, JEI starts at `LoggingIn` with the client's default recipes. On
  `RecipesUpdatedEvent` it restarts with the server's recipes. That restart runs inside the recipe packet's
  handler, before the tags packet is handled.

W181's client log (`W181/attempt-4/matrix/forge-47.4.10-jei-present-debug.log`) shows this order:

1. 01:08:30.610: start on `LoggingIn`. All 11 categories log `recipes=0`.
2. 01:08:31.756: `RecipesUpdatedEvent`, then the restart.
3. 01:08:31.984 onwards: every lookup that names a tag finds no bound alternatives.

### Where tag expansion happens

All ARCE machine recipes sync their authored ingredient JSON, including tag entries. The client therefore
expands tags itself; vanilla recipes instead sync resolved items.

- **Server (machine lookup).** The block entities and resolvers expand tags through
  `BoundedItemIngredientCodec.resolveAlternatives`, either directly or through `DeferredProcessDefinition`.
  The integrated or dedicated server has bound its tags before any lookup. This task changes none of it.
- **Client.** Only the JEI plugin looks recipes up on the client. A search of `client/` and of every
  `getRecipeManager()` caller found no mod screen that resolves a recipe; the machine screens show menu data
  that the server sends. The JEI categories expand tags in two ways:
  - the classic categories through `ClassicMachineRecipe.resolveInputs()`, and the rolling machine and
    precision assembler through `processDefinition()`. Both throw before the tags arrive. The classic filter
    then drops the recipe without a message, and JEI reports the rolling and precision recipes as broken.
  - the small plate press and the electrolyzer through vanilla `Ingredient.getItems()`. Before the tags
    arrive, Forge's `TagValue` returns a barrier named "Empty Tag: …". `Ingredient` caches that array, and
    Forge does not reset `getItems()` when tags arrive. The press's 17 recipes therefore reached JEI with
    barrier inputs. W181 counted recipes, so it did not see this.

### How the client path sees the server's tags

The fix holds recipes back until this connection's tags arrive, then hands them to JEI's runtime.

- A new client-only class, `client/compat/jei/ServerTagGate`, has no JEI types, so unit tests can run it.
- Each category's registration hands JEI only the recipes that name no tag. A recipe that names a tag waits
  until the client receives this connection's tags. The test is a JSON check (`hasTagIngredients()`) that
  resolves nothing and logs nothing.
- On `TagsUpdatedEvent` with cause `CLIENT_PACKET_RECEIVED`, the plugin adds the held recipes through
  `IJeiRuntime.getRecipeManager().addRecipes`. Each category keeps its current filter: the classic categories
  still drop a recipe whose `definition()` fails. JEI indexes recipes added at run time like registered ones,
  so focus lookups find them.
- `ClientPlayerNetworkEvent.LoggingIn` and `LoggingOut` reset the gate, so tags bound before the connection
  are never taken as this server's. Examples are a single-player world or an earlier server.
- JEI's `onRuntimeUnavailable` drops the held recipes, because JEI's next start registers everything again.
  A JEI restart after the tags arrived (a `/reload` or a resource reload) holds nothing back.
- The listeners use the explicit-class `addListener` form. They run on the render thread, as JEI's callbacks
  do. The gate ignores the integrated server's own `SERVER_DATA_LOAD` event, which runs on the server thread.
  The tags listener has low priority, so it runs after `RecipeTagGeneration` has advanced the tag generation
  that `DeferredProcessDefinition` checks.
- Single-player follows the same path. The held recipes are added when the client receives the tags packet
  through the memory connection.

The receipts change so that the matrix can see the hold:

- Each registration still logs one `status=registered category=<id> recipes=<n>` receipt, where `n` counts
  the recipes handed to JEI then.
- A category with held recipes also logs `status=held category=<id> recipes=<n>`.
- When the tags arrive, each such category logs one more `status=registered` receipt with its new total.

That last receipt is the one the R148 runner rule (F2) checks.

### What does not change

- No packet, recipe serializer, synced field or bound changes.
- No server lookup changes.
- No ADR changes, and no recipe content changes.

In common code the fix only adds two read-only accessors. One is `ClassicMachineRecipe.hasTagIngredients()`.
The other is `SmallPlatePressRecipe.hasTagIngredients()`, which matches the existing accessors on the rolling,
precision and electrolyzer recipes.

### Known limits of the design

- A tag recipe is shown only after the client receives the server's tags. A server that never sends a tags
  packet would never show it, but vanilla always sends one at login.
- A JEI restart after the tags arrived registers with the tags then bound. That is the same moment JEI uses
  for its own recipes.
