## Cause

The failing assertion is the COUNTDOWN check right after `acknowledgeFixture` in `launchAndCancel`. The launch request
itself answers `JOURNAL_PENDING`, because `RocketTransferService.prepare` does not check that the entity is loaded. The
acknowledged continuation (`RocketTransferService.java:194-206`) does: it calls `RocketTransferEntities.currentEntity`,
which requires `loadedEntity`, that is `isAlive`, `isAddedToWorld`, `level.areEntitiesLoaded(chunk)` and
`level.getEntity(uuid) == entity`. If any of them is false, the continuation returns false, the effect is discarded, no
`ARCE_TRANSFER_PREPARE` is logged and the rocket stays FUELED.

The station fixture waited only for `level.getEntity(rocket.getId()) == rocket`. In vanilla 1.20.1 (checked with
`javap` in the mapped Forge jar):

- `PersistentEntitySectionManager.updateChunkStatus` first stores a newly accessible chunk's visibility, which makes the
  chunk's existing sections, and so the fixture's new rocket, visible and even ticking at once. It only queues the
  chunk's entity storage load (`ensureChunkQueuedForLoad`).
- The load is read on the IO worker and then deserialized on the server's own task queue: `ServerLevel` passes the
  server as the executor of `EntityStorage`'s `entity-deserializer` mailbox.
- `areEntitiesLoaded` turns true only in the Level's next entity-management step (`PersistentEntitySectionManager.tick`,
  the last step of `ServerLevel.tick`).
- A server that is behind runs its own tasks only once they are three ticks old (`MinecraftServer.shouldRun`).

So on a busy host the rocket can be visible, and even tick, for one or more ticks before its entities count as loaded,
and a departure in that window is refused by the continuation. That is the failure.

The journal acknowledgement, the flight permission and the test's journal wait were not the cause: in every failing
trace the journal was acknowledged, the rocket was actionable, no effect was outstanding and the record was still
present (the effect had run and been refused). Production behaviour is correct: a departure must not start from an
entity whose chunk's entities are not loaded.

### A second, latent race in the same batch

`launchAndCancel`'s deferred check (`cancelRetired`) compares the whole shared transfer journal with the snapshot it
took before its launch. The station departure (test 3) and `closedMappedSourceCanLaunchAndCancelThroughPlayerAuthority`
(test 2) ran in the same batch, so if their launch-and-cancel windows overlap, each test sees the other's record and
fails with "Cancelled departure changed saved authority". In every earlier failing log the windows did overlap (test 2
was still retiring when test 3 launched), but the COUNTDOWN assertion failed first. Once the first fix made test 3 ready
earlier, verification run 2 of `c589b0a7` hit exactly this in both tests.

## The fix

Test code only, in `gametest/PlanetaryAdmissionGameTests`, `gametest/EntitySections` and
`gametest/EarthReturnPadFixture`:

- **Wait on the actual condition.** `awaitVisible` waits until `loaded(level, rocket)`: the rocket is visible and
  `level.areEntitiesLoaded(rocket.chunkPosition())`, the part of the continuation's `loadedEntity` check that the old
  wait did not cover. The bound (`helper.getTick() < 80`), its failure message, the pacing (`GameTestTickPacer`) and the
  enclosing 100-tick timeout are unchanged. A trace line is logged if the bound expires.
- **Isolate the fixture.** `closedOrbitStationCanDepartButStillRequiresLiveMembership` moves to its own batch,
  `planetary_admission_station_departure` (`PlanetaryAdmissionGameTests.STATION_DEPARTURE_BATCH`), so no other test's
  launch or cancellation shares its journal window. Its destination is Earth, so `EarthReturnPadFixture` installs and
  restores the Earth return pad for the new batch, as it does for `planetary_admission`. Tests 1 and 2 stay in
  `planetary_admission`.
- **Load the pad chunk's entities in setup.** `holdPadChunk` adds the existing fixture ticket (same type, radius 2 and
  key) on the station's pad chunk at setup, right after the station commit, loads the chunk, and calls
  `EntitySections.loadNow`. The rocket is installed at the pad origin plus half a block
  (`RocketEntity.initializeTransferred`), so its chunk is known then; a new assertion checks that the rocket is in the
  held chunk, and another that the load finished.
- **`EntitySections.loadNow`** waits in the server's managed block (`BlockableEventLoop.managedBlock`), which runs the
  server's own tasks at once (among them the entity deserializer), and inside it polls the Level's chunk-source tasks
  (the chunk's promotion) and runs the Level's entity-management step (`PersistentEntitySectionManager.tick`, reached by
  reflection on `ServerLevel.entityManager`, SRG `f_143244_`, checked in the 1.20.1 mapping), until the chunk's entities
  are loaded or a 600-second wall-clock bound passes. GameTest timeouts count ticks; this setup step uses none. The
  bound is the one W111's fixture areas use.
- The warp dock test (`dockedRocketDepartsFromTheStationsNewOrbitAfterRelocation`, batch `planetary_admission_warp`)
  shares `awaitVisible` and the same setup, so it gets the same setup load and wait.

No timeout, tick bound, budget or existing assertion changed. Against the base, the only removed lines that mention an
assertion or a timeout are the station test's `@GameTest` line (new batch, `timeoutTicks = 100` kept) and a comment;
three assertions were added.

**Batch name.** One batch name is added. Vanilla orders batches by `HashMap` iteration; the new name's bucket at the
current capacity of 1,024 is 337 (`planetary_admission_warp` is 351 and `planetary_admission` 695, which matches the
order seen in the logs). W120's full run had 465 names, so the table stays below its resize at 768 and every other
batch keeps its order. The batch filter keeps the same order, so in the filtered runs below the new batch ran first,
right after server start, which is the slowest point under this load.

## Incidents

1. **Three heavy JVMs overlapped, 22:09:46 to 22:13:51 (for Root).** When W125's case `LF_M_NAMED_E5` released the
   heavy-JVM lock, this runner (run 11 of `verify-pinned-83ca80f0`, acquisition logged 22:09:45.986) and W128's
   benchmark driver (`W128/bench-20261021-195130/driver.log`, "lock acquired" 22:09:45.987) both took it. Both use the
   [WORKER-RULES](../WORKER-RULES.md) loop, `New-Item -ItemType Directory`, which is not atomic: PowerShell checks for the
   directory and then calls .NET's idempotent `Directory.CreateDirectory`, so two callers in the same instant both get
   the directory back. W128's `finally` then removed the lock without checking its owner (`Remove-Item $lock`, as in the
   WORKER-RULES example) at 22:12:48.73, while run 11 still ran, and W125's waiting case `LF_M_NAMED_CROSS_K2` took it at
   once (its server started 22:12:50). Run 11's `finally` found W125's owner and correctly left the lock alone; W125
   released it normally. Run 11 passed under the extra load. This runner then switched to `cmd /c mkdir`, which fails
   if the directory exists (set `verify-pinned-83ca80f0-b`), and set A was ended after run 12 with its `stop.txt`.
   Every runner that copies the WORKER-RULES loop has both faults: the acquisition race and the unchecked release.
2. **A mis-quoted waiter.** The first waiter for the `c589b0a7` set passed the batch list through `Invoke-Expression`,
   which would have split it at the comma; it was stopped before it started anything and relaunched with explicit
   parameters.
3. **Expired waiters.** The full-run waiters after `c589b0a7` (stopped by hand) and after set A (three-hour wait ended
   while other workers held the lock) started nothing; the full run was then chained after set B and ran there.

- **The setup load runs the server's own tasks inside a test tick.** `loadNow` uses the server's managed block, so any
  server task queued at that moment (for example a deferred effect of an earlier batch) runs during the station test's
  setup rather than between ticks. The station test and the warp test are each alone in their batch. Under the pinned
  load the block took at most 1,999 ms (20 runs); in the full run without load it took 23 and 24 ms.
- **Reflection on a vanilla field.** `ServerLevel.entityManager` is read with `ObfuscationReflectionHelper` (SRG
  `f_143244_`), as W102 and W111 read `ChunkMap` fields. A mapping change fails the two station tests loudly at setup.
- **The wall-clock bound.** A host that cannot load one empty chunk's entities in 600 seconds fails the station tests
  at setup with "Station pad chunk entities did not load in setup", explicitly rather than by a race.
- **Hosted runs.** The test has not failed on a hosted run; the change is verified only locally.
