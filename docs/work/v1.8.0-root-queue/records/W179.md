## B4b: the over-limit data-pack reload (VDOC 12.4)

`DataPackOverLimitReloadGameTests` (batch `datapack_overlimit`) writes a world data pack, `OverLimitDataPack`, into
`world/datapacks`, selects it through `MinecraftServer.reloadResources`, checks the result, deselects it and checks the
restored server. The pack holds:

- 37 classic recipes that the classic codec or vanilla refuses while loading: for each of the seven classic types,
  one over the text bound (65,536 characters), one over the depth bound (16), one over the node bound (4,096) and one
  with five item rows; one invalid shape per type (unknown field, schema 2, a fraction, a null, a noncanonical id, a
  count of 65, three fluid rows); an id longer than 128 characters; and a top-level array;
- two recipe files that are not JSON;
- nine recipes that load and are refused when a machine resolves them: one per type that names a 33-item tag (the
  bound is 32), one that names a tag vanilla refused, and one with an unknown output item;
- three item tags: the 33-item tag, one with a missing reference and one that is not JSON;
- 300 pattern files, more than the 256 definitions a catalog may hold.

The test asserts that both reloads complete, that every refused recipe is absent, that every resolution-time recipe
throws the expected bound from `ClassicMachineRecipe.definition()` (the call `ClassicMachineManager.resolve` makes
before it disables a recipe), that the classic recipe counts change by exactly the loadable recipes, that the refused
tags are unbound, and that the valid content (for example `lathe_iron_rod`) stays. Logging: every refusal logs
exactly one entry, its first cause is the expected refusal, no entry or cause is longer than 512 characters, and
nothing else warns. Both pattern catalogs refuse the whole candidate once and keep their last valid generation. After
the restore no recipe, tag membership or pattern of the pack remains, both catalogs accept the 16 original patterns
again, and the only warning is vanilla's one "Not all defined tags" for the vanished 33-item tag.

`scripts/gametest_expected_log.json` gains 15 exact expectations for the batch, one per refusal kind (43 ERROR
entries and the one WARN). The pinned ERROR total in `tests/test_check_gametest_log.py` goes from 135 to 178.

## B4a: the menu-authority matrix (VDOC 12.1)

`MenuAuthorityMatrixGameTests` (batch `menu_authority`) has two parts.

- `everyRegisteredMenuTypeIsProbedOrExemptForEveryCheck` enumerates the mod's `MenuType`s from
  `ForgeRegistries.MENU_TYPES` (28, including `suit_workstation`, which `SuitEquipmentContent` registers) and fails
  when a menu has a check with neither a probe nor an exemption, when a probe or exemption names an unregistered
  menu, when a cell is both probed and exempt, or when an exemption line is malformed.
- A `@GameTestGenerator` makes one required GameTest per probe in `MenuAuthorityProbes.all()`, so the matrix cannot
  claim a cell that no test runs. Each builds the menu's real holder, joins an owner and a stranger as connected
  survival players, and runs the probe's cells.

The cells, all on the server's own paths:

- **DISTANCE**: the owner opens the menu, moves 16 blocks away, and the menu must no longer be valid.
- **SPECTATOR**: the owner, switched to spectator, must neither keep the open menu valid nor get a valid menu from a
  new use.
- **FOREIGN_OWNER**: a stranger must not get a valid menu; where the holder lets anyone view (the endgame devices
  outside stations, the observatory, the rocket flight menu), the stranger's action must be refused.
- **RATE**: a burst of at most 16 identical actions by the owner in one tick must meet a refusal (the rocket flight
  limiter admits 8 per 20 ticks; every other limiter refuses the second).
- **UNLOADED**: the holder's block entity gets `onChunkUnloaded` and `setRemoved`, as Forge's chunk unload does (the
  rocket gets `setRemoved(UNLOADED_TO_CHUNK)`), and the open menu must no longer be valid.

Every cell starts with a positive control: the owner's menu opens and is valid, and an action's first use is
accepted. "Valid" is `stillValid`: the server closes an invalid menu at the player's next tick, and vanilla drops
slot and button clicks for it; the `classic_controls` targets check the same. Opening is `useItemOn` with an empty
hand on the holder block (for a spectator vanilla then opens the block's menu provider directly) or
`Player.interactOn` for the rocket.

`src/test/resources/menu-authority-exemptions.txt` holds 41 entries, one reason each: 23 `not-applicable` cells
(holders without an owner, menus whose only actions are vanilla slot clicks or that have none), four `elsewhere`
cells (the station controllers' UNLOADED: the holder is a plain block, `StationControllerHolderTest` covers the
unloaded-chunk refusal, and a connected player within reach always keeps the chunk loaded) and 14 `gap:` cells,
the findings below. No menu type lacks a holder, so there is no `no-holder` entry. A gap cell still runs and must
still show the gap, so its line has to go when the gap is fixed.

## Findings for Root (not fixed here)

- **W179-F1, spectators keep 12 menus.** The electrolyzer, microwave receiver, satellite builder and terminal,
  rolling machine, the six endgame device menus and the rocket flight menu do not refuse spectators: a spectator
  (the owner, in the test) opens them through vanilla's spectator path and they stay valid. Vanilla still drops
  spectators' slot and button clicks, so the exposure is viewing. The other 16 menus refuse spectators. Related, from
  reading only: the spectator path calls vanilla `openMenu`, which sends no Forge extra data for these
  `IForgeMenuType` menus; what a client does with that was not tested.
- **W179-F2, two menus outlive their holder.** The electrolyzer and rolling machine menus check only the block at the
  position and the distance (`stillValid(ContainerLevelAccess, ...)`), so a menu stays valid on a removed block
  entity while a block of the same kind stands there.
- **W179-F3, rocket flight intents, from reading only.** `RocketFlightService.request` checks the open flight menu
  and spectators only for intents with a landing pad; the other launch, cancel, board and leave intents need neither.
  The matrix tests the menu, not this channel.
- **W179-F4, no aggregation cap for vanilla's data-pack errors.** docs/17 section 5 asks for an error aggregation
  bound on data-pack reloads. The mod's pattern catalogs aggregate (one entry per catalog), but vanilla logs one
  ERROR with a stack trace per refused recipe or tag file, so the count grows with the number of bad files. Each entry
  is bounded (the longest was 164 characters). Vanilla also parses a whole recipe file before the classic codec's
  64 KiB text bound applies.
- **W179-F5, a vanished tag keeps its old contents.** After a pack is deselected, vanilla's `MappedRegistry.bindTags`
  keeps the named set of a tag the data no longer defines, with its old items, while item membership is cleared.
  `BoundedItemIngredientCodec.resolveAlternatives` reads `Registry.getTag`, so a classic recipe of another pack that
  names a vanished tag would resolve to the old items. Observed in a trial; not tested further.

## Choices where the TASK was open

- The cell semantics above, including FOREIGN_OWNER by action for holders that let anyone view, and RATE as a bounded
  burst, are documented in `MenuAuthorityMatrix`.
- UNLOADED cannot be a real unload within reach: a connected player keeps the chunk loaded and the test area is
  force-loaded. Removing the holder object as an unload does is the closest faithful state.
- The exemption file lives under `src/test/resources`, as the TASK asks, and the GameTest reads it from the working
  directory upwards (`build/gametest` in Gradle), or from `-Dadvancedrocketrycommunity.menuAuthorityExemptions`.
- Single-block holders use the one-block `empty` template; multiblocks and the rocket use `rocket_test`, the solar
  array `solar_array_test`. With all 27 in `rocket_test`, the batch start alone lagged 8.9 s (grid chunk generation);
  fixture builds are also staggered three ticks apart and their cost logged (`build_ms`, 429 to 539 ms in total).
- B4b starts each reload from a worker thread. `/reload` blocks one server tick for the whole reload (about 1 s
  here); started off-thread, the same reload chain runs while the server keeps ticking.
- "Tags" are the item tags classic recipes name; "patterns" are `machine_patterns` files.

**The failure in the first complete run, caused by B4b and fixed.**
`RocketTransactionProofGameTests.autosaveAndSaveAllRequestAndPublishOnLaterTicks` (batch `rocket_transaction_proof`)
failed with "/save-all failed". Its direct `saveEverything` call passed; only the `/save-all` command returned 0, and
nothing logged. A filtered run of `datapack_overlimit`, `menu_authority` and `rocket_transaction_proof` reproduced it
(`repro-1`). The cause: `GameTestServer` is not a `DedicatedServer`, so `MinecraftServer.reloadResources` rebuilds the
INTEGRATED command set (checked in the 1.20.1 bytecode), which has no `save-all`, `stop`, `op` or other
dedicated-only command. Any data-pack reload on the GameTest server therefore removes those commands for every later
batch; a real dedicated server keeps them. Commit `2c06558c7` puts the server's own command set back into the
reloaded resources after the restoring reload (and in the after-batch cleanup) and checks that `save-all` is there.

## Known risks

- The UNLOADED cell removes the holder object as an unload does, but cannot unload the force-loaded test chunk. The
  station controllers, whose holder is only a block, are exempt and rely on `StationControllerHolderTest`.
- Several probes read internal signals to tell a rate refusal from another refusal: the research status, the station
  menu's status object, the monitor's view status, the satellite and endgame status messages and, by reflection, the
  rocket flight service's result. A refactor of those signals can break a probe; the failure names the probe.
- The GameTest reads the exemption file from the source tree; a run outside the repository needs
  `-Dadvancedrocketrycommunity.menuAuthorityExemptions`.
- B4b puts the command set back by reflection on `ReloadableServerResources`' one `Commands` field, found by type.
  If a Minecraft or Forge update changes that field, the test fails with that message rather than leaving later
  batches without `save-all`.
- The two new batch names change the global batch order, which is how B4b's command-set effect surfaced; other
  latent order dependencies could surface the same way in the hosted run.
- The spectator gaps (F1) were tested on the server only; what a client does with the vanilla open packet is unknown.
