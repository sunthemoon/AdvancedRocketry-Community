# W01: hatch family and lathe

## Implementation design (2026-10-11)

The write scope is the classic hatch/lathe runtime, its registry entries, generated
data and original art, its display-only client adapters, tests, and this record.
Other machines, existing v1.2 ports, ADR-068, probes, status files and the ledger are
not changed. The worktree started clean on `codex/v1.8.0-hatch-kernel` at `1568699e`.

The runtime uses the v1.2 pattern validator and formation coordinator. Level-owned
scheduling bounds formation and recipe searches. Recipe lookup checks the entire
candidate set in full resource-ID order before selecting its first match. Reloads
retire cursors but preserve active recipe identity and JSON signature.

Item/Fluid resources use the existing immutable `ClassicResources` model and codec.
A bank key contains the hatch's absolute position and kind, within its controller
UUID and Level. Retained Fluid banks count toward both existing limits. A rebuilt
same-position, same-kind hatch can reach that bank only through a fresh binding.
Hatches retain their owner claim while unformed, separately from live formation
access. The controller independently persists at most 64 claimed positions,
including plugs, so losing the kernel's live part list cannot orphan a power claim.
Live facades also pin the exact hatch instance and binding epoch.

Recipe completion prepares detached before/after banks and uses kernel process
simulation/transaction ordering before publishing one controller checkpoint. No
Item/Fluid resource is persisted at a hatch. Energy remains plug-owned and is not
covered by the controller snapshot's crash-atomicity claim. Kernel transaction
journal phases are detached preflight state; there is no persisted pending journal.
The published checkpoint contains the complete resources, progress, batch ordinal
and last transaction ID. This publication choice needs Root's storage review; it
does not supply native crash/restart evidence for ADR-019 or ADR-064.
Unsupported roots are
preserved and gameplay/removal is refused. Ordinary removal never loads chunks.
Controller removal is conservatively refused while a claimed part is unavailable,
so loaded-part cleanup cannot leave an inaccessible owner claim behind.

Oversized/missing resource roots reuse `GuardedChunkSaves`, not a new save policy.
The existing R-021 behavior rejects the entire chunk using an exception; denial
persists for the Level lifetime, and more than 256 different denied coordinates
saturate the Level. Dirty retention does not guarantee cross-storage durability.
There is no production online reset or total log/retry bound. Back up and repair
offline before restarting; restarting alone does not repair data. Root must review
this classic-root use and synchronize the risk register's scope before integration.
Commands/mods that bypass Forge-aware removal are outside the promised removal
boundary; ADR-068 and native/JDI probes are not wired in.

The original lathe's layout is used as a behavioral fact, not as copied source or
art: [pinned TileLathe](https://raw.githubusercontent.com/Advanced-Rocketry/AdvancedRocketry/c5cd5af62fc07cd4e0d24f06a16033f181c47c04/src/main/java/zmaster587/advancedRocketry/tile/multiblock/machine/TileLathe.java).
Its upper row is controller, motor, air, Item input; its lower row is power,
casing, casing, Item output. Textures are newly drawn from code without bitmap inputs.
