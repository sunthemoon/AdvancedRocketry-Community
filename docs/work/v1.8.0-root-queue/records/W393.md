## What was done

Commit `b0a3d92d0` changes the SAFE branch of `check_saved_rider` in `scripts/run_v180_bay_exit_cuts.py`.
The flushed safe exit `X8_SAFE_MENU` now accepts exactly two saved vertical motions, 0.0 and
-0.0784000015258789, instead of only 0.0. Every other condition from W373's check (`f058c8bcf`) is unchanged:
the rider is not riding, `saved["y"]` equals the cut's y, the saved position is exactly the pad
(8.5, 2.0, 8.5), and the cut reports `mounted=false`, `slot=SAFE`, `offer=none` and `history=closed`.
The falling cases still require `motion_y < 0`.

The grounded value is the module constant `GROUNDED_MOTION_Y`, placed directly above the function. Its comment
says where it comes from: vanilla's gravity 0.08 multiplied by the float drag 0.98F, which a grounded living
entity keeps after one physics tick. `-0.08 * float32(0.98)` evaluates to exactly -0.0784000015258789 in Python.
I did not read the vanilla source for this task; the derivation rests on that arithmetic and on the three
native runs that saved this exact value.

The refusal message now says "not grounded on its checked pad" instead of "not stationary on its checked pad".
The function's docstring describes the two accepted values.

## Choices where the TASK was open

- The write scope names "the function `check_saved_rider` only", and the TASK also asks for a named constant.
  I put the constant at module level directly above the function, so the tests can pin it. Nothing else in the

  refused.

## Known risks

- The check accepts only saves taken at most one grounded physics tick after the exit, or any later tick while
  the rider stays grounded with the same stored value. If vanilla stored a different grounded value under some
  condition not seen in these four runs, the check would refuse it, which is the conservative direction.
