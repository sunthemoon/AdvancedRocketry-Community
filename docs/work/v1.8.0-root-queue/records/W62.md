# W62: the v1.8 checklist mapped to existing tests and evidence (audit)

Auditor: a headless Claude session (audit only, no subagents). Branch
`codex/v1.8.0-w62-test-inventory`, based on the shared branch at `66113ab9`. Date: 2026-10-15.
Root reviews and merges. No code, test, status, ledger, ADR or workflow file changed. This record
is the only new file.

## Summary

- **Section 9 (automated tests).** Two items are covered by every hosted v1.8 regression: DataGen
  determinism and recipe-graph reachability.
  - Unique registry IDs are enforced only implicitly: Forge refuses a duplicate name at
    registration, so any hosted launch would fail. No test states the rule or leaves evidence.
  - References are partly checked. `validate_v090_resources.py` checks model, texture, blockstate
    and sound references, case collisions and en/zh parity. It does not check two rules of ADR-061
    §5.2: "language key → registered object" and "recipe → registered item".
- **Per machine (9.5).** The ledger delivers 26 machines and devices in v1.8.
  - Every one has a happy and a failure GameTest.
  - Four have no restart test: the crystallizer, the chemical reactor, the precision laser etcher
    and the atmosphere detector.
  - Three save no state of their own, so a restart test does not apply to them.
  - Seven machines have only an in-place block-entity NBT round trip as their restart test.
  - Five have a native run with at least two same-world restarts: the pump, the tank, the
    combustion generator and the two research machines. Those runs are local only.
- **Sidedness (9.6).** A source-text scan runs in hosted CI and passes, and all 1,068 GameTests run
  in a `DEDICATED_SERVER` dist. Nothing scans the shipped bytecode. The packaged dedicated-server
  smoke runs only on PRs and `main`, never on the v1.8 branch. Proposed: a JAR bytecode scan (S3).
- **Provenance (9.7, 12.5).** I found no v1.8 implementation of ADR-061 §4.7's enforcement:
  - no check over the tree or the JAR that a file with a legacy-manifest hash has a record;
  - no JAR check for QUARANTINED or REJECTED targets.

  Two further gaps:
  - `import_v180_assets.py verify` is in no workflow.
  - All 12 v1.8 JSON records are `PENDING_HUMAN_REVIEW`.

  A naive "record target hash differs" rule would fail today on 19 entries in 9 sealed records,
  because the shared v1.8 language files grew and one texture was redrawn. The check must follow
  the latest record per target and check language files per key.
- **Sections 10 and 13** are mostly class B (final campaign). Two items (10.5, 13.5) need a
  "reference modpack". The roadmap defines it only in v1.9, so the owner must decide (class C).
- **Section 15.** The unit tests write the recipe-graph and reachability reports under
  `build/reports/`, but no workflow uploads them. Five evidence items have no generator: the
  PORTING_MATRIX update, a provenance index, a progression report, a migration report and a
  modpack report.
- **Eight class A slices** are proposed in section 7. The first is restart tests for the four
  machines (size S).

## 1. Conventions

- `M/` means `src/main/java/io/github/sunthemoon/advancedrocketrycommunity/`. `T/` means
  `src/test/java/io/github/sunthemoon/advancedrocketrycommunity/`.
- A GameTest reference is `Class:line`, where the line is the line of its `@GameTest` annotation.
  Section 4 gives each GameTest class's folder.
- Hosted workflows:
  - **REG** is "v1.8 development regression" (`.github/workflows/v180-development.yml`). It runs on
    every push to the shared branch and to `codex/v1.8.0-w*` that changes `src/`, `scripts/`,
    `tests/` or the build files. It runs a clean build with all unit
    tests, the artifact audit, `check_client_imports.py`, `runData` twice with a clean tree, all
    GameTests, the GameTest log check, and the ledger validator with `--require-accepted`.
  - **GOV** is "Repository governance" (`.github/workflows/repository-docs.yml`). It runs on
    pushes to the shared branch and on PRs. It runs the full Python suite,
    `validate_v090_resources.py`, the upstream and vanilla-derivation checks, the art screen and
    the strict repository validator.
  - **FB** is "Forge bootstrap" (`.github/workflows/forge-bootstrap.yml`). It runs on PRs and
    `main` only. It runs the packaged dedicated-server smoke and the v0.2 to v0.9 native smokes.
  - **local** means the check runs only on this machine.
- Restart strength:
  - **N:** a packaged dedicated server with at least two same-world restarts. The pump and
    combustion runners do two, the tank runner three, and the research runner eight starts.
  - **D:** a GameTest that reloads from SavedData files on disk, or across a real chunk unload.
  - **R:** a GameTest that saves a block entity's NBT and loads it back into the live object.
  - **—:** none.
  - **n/a:** the block saves no state of its own.
- Classes:
  - **A:** automatable now.
  - **B:** needs the final campaign.
  - **C:** needs an owner decision.
  - **covered:** nothing is missing except archiving the candidate commit's hosted run.
- Slice names S1 to S8 refer to section 7.

## 3. Checklist inventory

### Section 9: automated tests

**9.1 每个 registry ID 唯一 (every registry ID is unique).**
- Existing coverage:
  - Forge's `DeferredRegister` and `ForgeRegistry` refuse a second registration of the same name
    at mod construction. Every launch (REG's two `runData` runs and `runGameTestServer`) would
    therefore fail on a duplicate.
  - `T/recipegraph/RegisteredItemReachabilityTest.java:123` discovers the real deferred
    registrations.
  - The ledger validator refuses duplicate ledger rows (`scripts/validate_v180_content_ledger.py:255`).
    It also requires every IMPLEMENTED target to be registered; it reads the registered IDs from
    the language files (`:155`).
  - `scripts/validate_v090_resources.py:186` refuses case-colliding resource paths.
- Hosted: REG (implicitly, through every launch) and GOV (the path collisions).
- Missing: no test asserts the rule, reports the IDs per registry, or checks names that differ only
  in case across registries.
- Class: **A** (S4).

**9.2 所有模型/纹理/sound/lang/recipe 引用存在 (every reference exists).**
- Existing coverage:
  - `scripts/validate_v090_resources.py:165` covers every resource root, including
    `src/generated/v1.8` and `src/imported/v1.8`. It checks model parents and textures, blockstate
    → model, `sounds.json` → OGG, case collisions, en_us/zh_cn key parity and placeholders, and
    Java translation literals with fixed prefixes.
  - 33 unit-test classes that read `blockstates/` or `models/item/` paths (most are
    `T/**/V180*DataTest` and `*ResourcesTest`) check each slice's own files.
  - The OBJ/MTL reference check is `tools/audit/obj_mtl_check.py`, used by the importer and by
    `ObjModelCheckTest`.
  - The server parses recipes, tags, loot tables and advancements at GameTest startup. Vanilla logs
    a parse failure at ERROR, and `scripts/check_gametest_log.py` fails on any unexpected ERROR.
- Hosted: GOV (resource audit) and REG (unit tests and the log check).
- Missing:
  - ADR-061 §5.2's "language key → registered object";
  - "every registered block has a blockstate and a loot table, every item a model";
  - a static "recipe → registered item or tag" report;
  - client-side model baking, which only a real client exercises.
- Class: **A** (S4) for the static checks. **B** for the client: V1 with no missing-model or
  missing-texture log lines and no purple-black blocks (also §11 item 4).

## 5. Dedicated-server sidedness (9.6)

What exists:

1. **Source-text scan.** `scripts/check_client_imports.py` fails on the text `net.minecraft.client`
   in any `src/main/java` file outside a path with a `client` folder. REG runs it in "Audit the
   built artifact" (`v180-development.yml:100`); FB runs it too. It passes on `66113ab9`.
2. **GameTest dist.** All 1,068 GameTests run in a `DEDICATED_SERVER` dist. The fixture items in
   `M/gametest/AtmosphereAnalyzerGameTests.java:85` register only when `FMLEnvironment.dist` is
   `DEDICATED_SERVER` on a GameTest server, and the tests that use them pass in REG. Loading a
   client class there would crash or log an ERROR, and `check_gametest_log.py` fails on any
   unexpected ERROR or FATAL. This only covers code paths that some GameTest executes.
3. **Packaged dedicated-server smoke.** `scripts/run_dedicated_server_smoke.py:82` fails on
   "Attempted to load class net/minecraft/client" and on `NoClassDefFoundError` for client
   classes. It runs only in FB (PRs and `main`) and inside the local native runners, never on a
   push to the v1.8 branch.

What the scan misses:

- Common code references client classes of the mod. Four common classes do this:
  - `M/endgame/railgun/RailgunBlockEntity.java:233` uses `ClassicSoundClient`;
  - `M/equipment/motion/EquipmentEnabledPacket.java:26` uses `SuitVisorClient`;
  - `M/equipment/motion/JetpackImpulsePacket.java:44` uses `JetpackClient`;
  - `M/rocket/network/RocketFlightPlanPacket.java:128` uses `RocketFlightPlanHandler`.

  They are safe today only because each reference sits inside a
  `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, ...)` lambda. `M/config/ClientConfig.java:3` imports
  `client.LifeSupportHudLayout`, which has no client references itself. The text scan sees none of
  these, because it looks only for `net.minecraft.client`.
- It does not read what ships: compiler-generated code, and files under any `client` folder, which
  it exempts wholesale (for example `M/equipment/laser/client/`).
- It does not see calls to vanilla members marked `@OnlyIn(Dist.CLIENT)`, which the dedicated
  server strips.

**Smallest proposed check (S3).** `scripts/check_client_bytecode.py` reads the built JAR with only
the standard library: `zipfile` and a constant-pool reader of about 60 lines.
- It marks a class "client-bound" when it is in `net/minecraft/client/` or `com/mojang/blaze3d/`,
  or when it is a mod class that references a client-bound class, transitively.
- It fails when a class outside the mod's `client` packages references a client-bound class, unless
  the pair (class, referenced class) is in a committed allowlist. The allowlist holds exactly the
  four `DistExecutor` sites above.
- `ClientConfig` passes because `LifeSupportHudLayout` is not client-bound.
- Root adds one line after `check_client_imports.py` in REG.
- Optionally, Root also runs `run_dedicated_server_smoke.py` on the v1.8 JAR in REG. It needs no
  new code.
- The `@OnlyIn` member check needs the mapped Minecraft JAR, so it is left for later.

## 8. Interpretation choices, what is not done, risks

- **Counting rules.**
  - I counted an in-place NBT round trip (R) as a restart test, because the TASK allows "a GameTest
    that saves and reloads". Section 4 marks those rows so that Root can raise the bar.
  - "Machine" means a delivered v1.8 block that runs a process, holds resources or acts on the
    world. Doors, torches, lamps and rocket parts are listed separately.

    finished; nothing had to be redone.

    class B.
  - Hosted run logs were not downloaded (`gh` is not available here); hosted results come from
    `CURRENT_VERSION.md`.
