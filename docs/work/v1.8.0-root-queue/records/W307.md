### Where the passenger landed before the fix

`RocketReleaseBoardingGameTests` builds a 3-by-3 stone floor for its returning passenger at the batch's top plus 8,
in the cleared space of its `rocket_test` structure, which stands at about y -60, and then lets the passenger rejoin. `RocketRejoinWorld.choose`
takes each candidate's height from the Overworld `MOTION_BLOCKING_NO_LEAVES` heightmap, so that floor is invisible:
the natural surface above the structure decides, and where all of it is unsafe the placement falls back to the ring
around the world spawn. The test does depend on the terrain.

- In a filtered run of the batch at the base (`before` below), the recorded footprint was the single column (3, 3).
  All 32 pad-ring columns had their feet at y 63 on the sea and none was safe, so the passenger was placed on the spawn
  ring (`target=OVERWORLD_SPAWN`) at (4.5, 68.0, -3.5), on grass: the one dry spawn-ring column that W304 also found.
- In W304's full run at `d99d7a459` (`D:/GitHub/ARCE-Task-Evidence/root-queue/W304/full/full-latest.log`, line
  10077), the same test placed its passenger with `target=PAD`, that is on the natural terrain above its structure at
  that run's position, which no test restores.

So the landing spot was either unrestored natural terrain or the shared spawn-ring column, depending on where the
batch's structure stood.

### The fix

- Just before the passenger rejoins, the fixture builds `RocketRejoinFixturePad.around(level, ...)` over the batch's
  recorded footprint (`batch.minimum()` to `batch.maximum()` in x and z, the same footprint `choose` uses). The pad is
  W304's class, reused unchanged from `rocket/rejoin`: it was already public and already used from `rocket/server` by
  the Admission scenarios, so it was not moved.
- `close()` closes the pad last, after the passenger has left the server. The fixture's `close()` already runs on
  success and when its own tick fails.
- A new `@AfterBatch(batch = "rocket_release_boarding")` hook calls `RocketRejoinFixturePad.closeAbandoned()`, so a
  pad is restored when the test fails or times out without reaching `close()`. The batch had no hook before.
- The floor inside the structure, the batch record and every assertion and timeout are unchanged. The pad loads no
  chunk (it refuses to start if one of its columns is not loaded) and replaces no block entity.

## The experiment

`W307FloodExperiment` (only on the two experiment branches, in `rocket/rejoin`) is called by the boarding fixture just
before the passenger rejoins and, on the after branch, before the pad is built. It logs the production-safe candidate
columns of the batch's pad ring and of the spawn ring, as `RocketRejoinWorld.safe` sees them (`W307_FLOOD`). With
`-Darce.w307.flood=true`, it then puts a water source on the feet of every safe candidate, on its sturdy support, with
stone on each of its four sides that holds no fluid, so the water cannot flow, and repeats until no candidate is safe.
On the after branch a second line (`W307_CENSUS stage=pad`) counts the candidates once the pad is built. Once the guard
ends, `W307_LANDING` logs where the passenger stands. Each case ran only `rocket_release_boarding` in a fresh filtered
GameTest server, so the structure stood at the same position in every case.

## Choices where the task was open

- The pad is built from the batch record that the placement itself uses (`batch.minimum()` and `batch.maximum()`),
  read just before the passenger rejoins, rather than from the rocket snapshot at setup as the Admission scenarios do,
  because the batch record is the exact input of `choose`.
- The fixture's floor inside the structure was kept, as W304 kept its fixtures' floors. It never decides the
  placement, but removing it is not needed for this task.
- `RocketRejoinFixturePad` was reused as it is. Moving it to a shared GameTest package would only rename an import for
  the two packages that use it, so it stays in `rocket/rejoin`.
- The experiment floods every production-safe candidate, not only fluid-free columns as W304's did, because the
  placement's own `safe` check is what decides the landing spot.

## Not done

- The hosted sharded run has not been run. Root's push decides it.
- The native release cases were not run; they use their own disposable worlds and none of their code changed.

## Known risks

- The pad lies at y 299 to 304 above the boarding structure, as W304's pads do above theirs. A future test that builds
  there in the same batch, or a world whose surface reaches y 299, would conflict.
- Vanilla allows one AfterBatch method per batch, so a later hook on `rocket_release_boarding` must call
  `RocketRejoinFixturePad.closeAbandoned()` too.
- If the pad's restore finds a changed cell it throws; on the failure path that exception would replace the test's own
  failure message. No run saw an unrestored cell.
- This does not satisfy or approve any v1.8.0 Required Gate.
