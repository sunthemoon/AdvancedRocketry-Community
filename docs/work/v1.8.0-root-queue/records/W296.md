## Step 1: the cause

I read the bytecode of the patched, official-mapped Minecraft jar that this build compiles against
(`forge-1.20.1-47.4.10_mapped_official_1.20.1.jar`, SHA-256 `95EECC5985233D83A6571299F89F02DE034267646DA171F7B36A5BE2D394D71E`)
with `javap -p -c -constants`, and the Forge patch files and Forge classes in `forge-1.20.1-47.4.10-sources.jar`
(SHA-256 `918A11BDFCEACE2752D4C29BDDBDF327981E1F6A1E1F0675F23E5FBF01E226C0`). No decompiler was available, and none was needed.
The reporter's guess is right. The exact condition is in `WorldDimensions.bake`:

1. **The dimension count.** `bake` merges the level stems from the data packs with those already in the world settings,
   then builds a new `LEVEL_STEM` registry. It gives that registry the stable lifecycle only when it holds exactly
   `VANILLA_DIMENSION_COUNT` entries. That constant is the size of the built-in order set (Overworld, Nether, End), so 3.
   The mod ships six level stems (`space`, `moon`, `mars`, `venus`, `tau_ceti_f`, `tau_ceti_g`; the older generated copies of
   `moon`, `mars` and `venus` are excluded in `build.gradle`), so the registry has 9 entries and is experimental.
2. **Each extra key.** Every entry is registered with `checkStability(key, stem)`. That returns stable only for the three
   vanilla keys with vanilla-like settings (`isVanillaLike`); every other key is experimental. Even one added dimension
   would therefore be enough.

Neither check reads the data. The mod's JSON files are not themselves experimental: Forge builds each mod's server data
pack as a `PathPackResources` with `isBuiltin = true` (`ResourcePackLoader.createPackForMod`), and
`RegistryDataLoader` registers entries from built-in packs as stable. The mod's dimension types, noise settings and
biomes therefore add nothing; only the rebuilt level-stem registry is experimental.

**The creation warning (`p11`).** `CreateWorldScreen.onCreate` bakes the dimensions and takes the lifecycle of all
registries, now including the level stems. It skips the warning only when the world is not a re-creation and that
lifecycle is stable. Otherwise `WorldOpenFlows.confirmWorldCreation` opens a `ConfirmScreen` with
`selectWorld.warning.experimental.title` and `.question` (Yes/No; No returns to the create-world screen). The
experimental feature flags (the Experiments tab) are added to the lifecycle that is stored, but the skip test looks only
at the registries, so the level stems alone trigger this screen; the reporter enabled no experiments.

**The first-reopen warning (`h5`).** Opening a saved world runs `LevelStorageSource`'s level-data reader, which bakes the
stored dimensions again and passes `bake(...).lifecycle()` combined with the data-pack registry lifecycle to
`PrimaryLevelData.parse` as `worldGenSettingsLifecycle`. Forge 47 patches `WorldOpenFlows.doLoadLevel`: when that
lifecycle is not stable and the world is not an old customised world, it calls `ForgeHooksClient.createWorldConfirmationScreen`
instead of vanilla's backup screen. That screen shows `selectWorld.backupQuestion.experimental`,
`selectWorld.backupWarning.experimental` and Forge's own `forge.selectWorld.backupWarning.experimental.additional`
("This message will not show again for this world."), with Proceed and Cancel. Cancel opens the title screen.
Proceed reloads with `confirmExperimentalWarning = true`, which calls `PrimaryLevelData.withConfirmedWarning(true)`.
Forge's `PrimaryLevelData` patch writes that flag to `level.dat` as `confirmedExperimentalSettings` on every save, and
reads it back only while the lifecycle is still not stable. Creating a world does not set the flag, which is why the
reporter saw the second screen on the first reopen and never again.

Two side facts: a dedicated server shows no screen (it only computes the lifecycle in `net.minecraft.server.Main` and
lists it in the system report), and Forge's experimental icon in the world list does not appear for these worlds,
because it reads Forge's separate `forgeLifecycle` setting, which nothing sets to experimental in Forge 47.4.10.

## Step 2: is there a supported way to mark the dimensions stable?

No. I found no supported way that fits AGENTS.md section 3.3:

- **A lifecycle field in the data.** None exists. `bake` decides from the key identity and the count only, and the
  data-pack entries are already stable.
- **A Forge option.** None. `ForgeConfig` in 47.4.10 has no such key. Forge's only mechanism is the per-world
  `confirmedExperimentalSettings` flag above.
- **Registering the levels another way.** Creating the six `ServerLevel`s at run time instead of shipping level stems
  would need non-public `MinecraftServer` state (the level map, the storage access and the executor) and a client-side
  update of the known level keys, so an access transformer or reflection. It would replace the fixed-dimension design of
  [ADR-001](../../../decisions/ADR-001-FIXED-DIMENSIONS.md). It would also not help existing worlds: their `level.dat`
  already lists the six stems under `WorldGenSettings.dimensions`, so vanilla would keep creating those levels and keep the
  lifecycle experimental. Rejected.
- **Hiding the screens on the client** (a `ScreenEvent.Opening` handler that presses Yes or Proceed). It uses public
  events only, but it would answer a vanilla safety prompt for the player and would also hide the warning when another mod
  or a real experiment is the cause. Rejected.

**The one narrow option (proposal, not implemented; Root decides).** The second screen could be avoided for new worlds
only. On an integrated server, in `ServerAboutToStartEvent`, when `server.getWorldData()` is a `PrimaryLevelData` that is
not yet initialised (`isInitialized()` is false, so the world was just created and the player has just answered Yes to
the creation warning), the mod would call Forge's public `withConfirmedWarning(true)`. The order holds in 47.4.10:
`IntegratedServer.initServer` fires the event before `loadLevel`, and `createLevels` sets the flag to initialised.

- Trade-offs: the creation warning stays. `withConfirmedWarning` is public but is a Forge patch, not documented API, and
  could change in a later Forge build. It would also hide Forge's reopen warning when the world is experimental for another
  reason. To narrow that, the mod would apply it only when every non-vanilla level stem is in the
  `advancedrocketrycommunity` namespace and `FeatureFlags.isExperimental(enabledFeatures)` is false. Even then, vanilla's
  checks of the three vanilla stems are private, so a world with a customised Overworld generator would also be
  suppressed. The player loses the "Here be dragons!" text, which they would otherwise see once.
- Saved-world compatibility: the change writes only `confirmedExperimentalSettings: 1b` into `level.dat`, the same tag
  Forge writes after the player's first Proceed. No dimension data, region file or SavedData changes. Existing worlds are
  not touched: they have either confirmed already or will ask once. Removing the mod or the change leaves a harmless tag,
  and Forge drops it by itself if the world ever becomes stable. Because it writes `level.dat`, AGENTS.md section 13
  would ask for a one-page design note and a read-only review before merging.
- My recommendation: keep the documentation only for v1.8. The warnings are harmless, appear twice per world, and the
  only workaround that fits section 3.3 removes just one of them at the cost of hiding a prompt that can be valid for
  other reasons.

## Step 3: the player documentation

The repository has no separate player guide for installing or first worlds, so the section went into `README.md`,
which holds "Install the published Beta". It says, in plain words, why the warnings appear (six added dimensions), when
each one shows, which button continues, that confirming changes or damages nothing, that no Experiments toggle is
needed, what "This message will not show again for this world" means (the answer is stored per world in `level.dat` at
the next save, and each new world asks again), what No and Cancel do, that dedicated servers and joining players see
nothing, and that backups are still the player's job.

Chinese: the project keeps no Chinese player documentation; `README.md` and the player guides under `docs/` are English,
and Chinese appears only in governance and developer documents. I did not create a new Chinese document. So that players
who run the game in Simplified Chinese can recognise the screens, the README table gives both titles and the
button names exactly as the 1.20.1 `zh_cn` language file and Forge 47.4.10's `zh_cn` file show them. If Root wants a full
Chinese version of the section, it needs a place for Chinese player documentation first.
