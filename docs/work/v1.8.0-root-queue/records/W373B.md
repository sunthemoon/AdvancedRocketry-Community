### 1.1 Terms and common rules

- A **cut** is one forced stop of a disposable native server (the Java process is killed while a gated probe holds
  the server at a named point), followed by **two restarts** that each end with an ordinary `stop`.
- The **ledger** is the escrow SavedData file. **Root 3** is its schema with the `fluid_accounts` list.
- An **account row** has a baseline (`b`) and, after the operator's O1, a frozen part (`f`). In a row entry, `s` and
  `t` are the source and destination amounts, `x` and `y` the planned deltas, and `a` the signed adjustment
  (positive is a loss, negative is a gain). Knowledge code 1 is KNOWN and 3 is UNKNOWN_ENDPOINT.
- The fixtures are the existing ones. Cargo: one rocket with one pressurized tank at `(68,100,64)` and one fluid
  cargo device at `(64,100,64)`, 5,000 mB of water in total, and one transfer of 1,000 mB. Unload starts with 5,000
  in the rocket and 0 in the device; load starts with 0 and 5,000. Fuel loader: the existing loader fixture, one
  fill of 1,000 mB of rocket fuel from a tank that holds 5,000.
- Every case runs on a locally built JAR of this branch's head, under the heavy-JVM lock, with the release-test
  hooks. Nothing here is X01 power loss or X02 fault injection.

**The oracle** is new: `scripts/accounting_cut_oracle.py`. It works only on files decoded independently of the
server (the ledger, the region file and the entity file). At the cut and after each restart it checks:

1. The ledger is root 3 with the root-3 epoch, and `escrow_accounting.check(root, fresh_fluid=True)` passes, so a
   fresh fluid operation or receipt that took the legacy UNKNOWN branch fails the case.
2. **Exact rows.** The set of row operation IDs equals the expected set. Each baseline entry equals the expected
   `(fluid, key digest, s, t, x, y)`, and the key digest is recomputed from the fluid ID with an absent tag. Each
   frozen entry equals the expected `(fluid, key digest, mask, s, t, a, owner)`, with the expected knowledge code
   and member list.
3. **Signed residual.** For every key, `r = (S - S0) + (D - D0)` is recomputed from the raw endpoint stores, not
   from the row, wherever the plan says both stores are durable. A KNOWN row must satisfy `r + a = 0`. Before O1,
   the raw stores must satisfy `dS + dD + q * (aS - aD) = 0`, where `aS` and `aD` are the endpoints' saved epochs.
4. **Knowledge.** A receipt's `accounting_status` equals the expected KNOWN or UNKNOWN, the row has an adjustment
   only when it is KNOWN, and a missing endpoint is never KNOWN.
5. **Epochs and markers.** Each endpoint's `resource_epoch` and marker count, and the ledger's `issued_through`,
   equal the expected values.
6. **No resource created or lost.** For every fluid, the raw amounts equal the baseline total minus the approved
   loss. More than the total may exist only as raw mixed stores while a record still locks both endpoints.
7. **Progress between starts.** A baseline is never replaced. A frozen row is byte-equal after every later start.
   An ordinary L2 deletes its row with its operation and leaves no receipt. A receipt-backed row is never removed,
   including after pruning.

The oracle has unit tests with negative controls (a changed amount, a missing row, an orphan row, a legacy-branch
operation, a wrong sign, a changed frozen row, a wrong epoch). No existing oracle or runner changes.

**The runners** are new: `scripts/run_v180_accounting_cuts.py` (sections 1.2 and 1.3) and
`scripts/run_v180_accounting_format.py` (section 1.4). For the fuel loader cases the first one calls the existing
`run_v180_loader_cuts.run_cut`, so those cases also keep that runner's unchanged oracle.

**Java.** Most cut points already exist in the gated probes and are reused unchanged. The only Java change is in
the gated probe `EscrowCargoSettlementCuts` (cases with the existing `FS_` prefix, so the dispatch in
`EscrowRuntime` does not change): three acknowledgement boundaries and four scenarios, listed below. No production
behaviour, ceiling, limit or log-manifest allowance changes.

Open points decided conservatively, as WORKER-RULES asks:

- The substitution uses the device tank only, because a tank holds one fluid. The adjusted amounts are therefore the
  whole device amount, not 100 mB.
- The readback case needs a state where the stored bytes differ from the live observation. Without storage fault
  injection that state exists only if the endpoint changes between the live check and the store, so the gated
  probe makes exactly that change at `BARRIER_STORE_BEFORE`. The reason string the settlement reports is recorded
  from the run, not assumed here.
- If any outcome case shows a production defect, the case stops there and the evidence is recorded. Production is
  not changed.

### 1.4 Format boundaries (TASK item 4)

The root-2 reader and writer is C3's pinned candidate JAR, SHA-256
`459669bf802ea7ca0ca88bf5a84902eb69274f4a3313305319843c6d8f81744b`
([C3-SWITCH-REPORT](C3-SWITCH-REPORT.md), section 2.1). The runner refuses any other file. "Activated JAR" is the
local build of this branch.

**The root-2 world.** The C3 JAR runs the existing case `FC_LOAD_L1_ACK` to its pause and is killed. The world then
has a root-2 ledger with one open PREPARED fluid operation, both stores BEFORE. A whole-world copy is taken here
(every file except `session.lock`, with SHA-256 per file). This copy is the pre-upgrade backup.

| Case | Steps | Checked |
|---|---|---|
| `UPGRADE_AFTER` | Start the root-2 world on the activated JAR with no probe. Wait until the server is ready, then kill it. Restart twice with an ordinary stop. | The migration report line names one migrated file and a backup. The ledger is root 3 with an empty `fluid_accounts`. The open operation is still schema 2 and **byte-equal** to its root-2 encoding (same canonical digest). It has no row: it is a legacy UNKNOWN_BASELINE hold, so it is neither applied nor retired, both stores still hold BEFORE with epoch 0, on the cut and on both restarts. The migrator's backup holds the root-2 file byte-equal. |
| `UPGRADE_DURING_BACKUP` | As above, but the runner kills the process as soon as the migrator's backup directory appears. | The observed state is recorded and must be one of: (a) ledger still root 2 and byte-equal, (b) ledger root 3 and valid. A torn or unreadable ledger fails the case. Then two restarts must end in the same state as `UPGRADE_AFTER`. Leftover staging files and the number of backup directories are recorded. |
| `UPGRADE_DURING_COMMIT` | As above, but the kill follows the first sight of the staged `.migrating-` file. | As the previous row. |
| `OLD_JAR_REFUSAL` | 1. Upgrade a copy of the root-2 world on the activated JAR and stop it. 2. Copy that root-3 world; start the copy on the C3 JAR, three times. 3. Restore the pre-upgrade backup into a fresh directory and start it on the C3 JAR. 4. Start the copy that the C3 JAR refused on the activated JAR, twice. | Step 2: the start is refused, and the refusal line and its reason are recorded; the ledger is byte-equal afterwards (no downgraded ledger); **every changed, added and removed file is listed** by comparing SHA-256 of the whole world before and after each start. Step 3: the server starts and the ledger is the original root-2 file, byte-equal at the first tick boundary the runner can observe, with the open operation still present. Step 4: the result of both starts is recorded with the ledger's state. |

The kill "during" the upgrade is timed by watching the file system, because the migration has no pause hook and
this task adds none to production. Where the kill lands is therefore observed, not chosen; the oracle classifies it.

`OLD_JAR_REFUSAL` is the evidence for R-044's sign-off text. Its verdict follows the existing downgrade family: if
the old JAR changes any world file before it refuses, the case reports FAILED with the list of files, exactly as
`w336-downgrade` does. Nothing is waived or fixed here.
