### 1.1 Terms and common rules

- A **cut** is one forced stop of a disposable native server (the Java process is killed while a gated probe holds
  the server at a named point), followed by **two restarts** that each end with an ordinary `stop`.
- The **ledger** is the escrow SavedData file. **Root 3** is its schema with the `fluid_accounts` list.
- An **account row** has a baseline (`b`) and, after the operator's O1, a frozen part (`f`). In a row entry, `s` and
  `t` are the source and destination amounts, `x` and `y` the planned deltas, and `a` the signed adjustment
  (positive is a loss, negative is a gain). Knowledge code 1 is KNOWN and 3 is UNKNOWN_ENDPOINT.
- The fixtures are the existing ones. Cargo: one rocket with one pressurized tank at `(68,100,64)` and one fluid
  cargo device at `(64,100,64)`, 5,000 mB of water in total, and one transfer of 1,000 mB. Unload starts with 5,000
  in the rocket and 0 in the device; load starts with 0 and 5,000. Fuel loader: the existing loader fixture, one
  fill of 1,000 mB of rocket fuel from a tank that holds 5,000.
- Every case runs on a locally built JAR of this branch's head, under the heavy-JVM lock, with the release-test
  hooks. Nothing here is X01 power loss or X02 fault injection.

**The oracle** is new: `scripts/accounting_cut_oracle.py`. It works only on files decoded independently of the
server (the ledger, the region file and the entity file). At the cut and after each restart it checks:

1. The ledger is root 3 with the root-3 epoch, and `escrow_accounting.check(root, fresh_fluid=True)` passes, so a
   fresh fluid operation or receipt that took the legacy UNKNOWN branch fails the case.
2. **Exact rows.** The set of row operation IDs equals the expected set. Each baseline entry equals the expected
   `(fluid, key digest, s, t, x, y)`, and the key digest is recomputed from the fluid ID with an absent tag. Each
   frozen entry equals the expected `(fluid, key digest, mask, s, t, a, owner)`, with the expected knowledge code
   and member list.
3. **Signed residual.** For every key, `r = (S - S0) + (D - D0)` is recomputed from the raw endpoint stores, not
   from the row, wherever the plan says both stores are durable. A KNOWN row must satisfy `r + a = 0`. Before O1,
   the raw stores must satisfy `dS + dD + q * (aS - aD) = 0`, where `aS` and `aD` are the endpoints' saved epochs.
4. **Knowledge.** A receipt's `accounting_status` equals the expected KNOWN or UNKNOWN, the row has an adjustment
   only when it is KNOWN, and a missing endpoint is never KNOWN.
5. **Epochs and markers.** Each endpoint's `resource_epoch` and marker count, and the ledger's `issued_through`,
   equal the expected values.
6. **No resource created or lost.** For every fluid, the raw amounts equal the baseline total minus the approved
   loss. More than the total may exist only as raw mixed stores while a record still locks both endpoints.
7. **Progress between starts.** A baseline is never replaced. A frozen row is byte-equal after every later start.
   An ordinary L2 deletes its row with its operation and leaves no receipt. A receipt-backed row is never removed,
   including after pruning.

The oracle has unit tests with negative controls (a changed amount, a missing row, an orphan row, a legacy-branch
operation, a wrong sign, a changed frozen row, a wrong epoch). No existing oracle or runner changes.

**The runners** are new: `scripts/run_v180_accounting_cuts.py` (sections 1.2 and 1.3) and
`scripts/run_v180_accounting_format.py` (section 1.4). For the fuel loader cases the first one calls the existing
`run_v180_loader_cuts.run_cut`, so those cases also keep that runner's unchanged oracle.

**Java.** Most cut points already exist in the gated probes and are reused unchanged. The only Java change is in
the gated probe `EscrowCargoSettlementCuts` (cases with the existing `FS_` prefix, so the dispatch in
`EscrowRuntime` does not change): three acknowledgement boundaries and four scenarios, listed below. No production
behaviour, ceiling, limit or log-manifest allowance changes.

## 4. Changes to the plan, and choices where the design was open

1. **How the probe changes a held device.** The plan said the probe would change the device tank. The first run showed
   that a live protected device refuses a replaced root (`ARCE_FLUID_CARGO_LIVE_REPLACEMENT_REFUSED`, one WARN), so the
   tank stayed as it was and the loss, substitution and readback cases failed in the harness, not in production. The
   probe now replaces the stored block entity as a whole, with the same device identity, binding and escrow section
   and only another tank. This models an edit outside the game, the only way a locked device's content can differ.
   The refused first attempt is kept in `chain1/`.
2. **What the readback case shows, and what it does not.** The typed per-fluid check (`EscrowCargoReadback`) refuses
   the changed device when the O2 store captures the slot, and the settlement reports `ACCOUNTING_MISMATCH`. Nothing
   is released, on the cut and on both restarts; after a restart the hold is reported by the live check as
   `Frozen settlement endpoint changed`. This is the validator that the stable readback also applies, but here it acts
   at the capture, before the bytes are forced. A read from disk that differs from the capture under an unchanged save
   generation cannot be produced by a process stop or by a probe that changes live state: a later save is answered by
   `SUPERSEDING_SAVE`, and anything else needs storage fault injection. That part is **NOT_COVERED** here and belongs
   to X02.
3. **Stops during the upgrade.** The migration has no pause hook and none was added. The runner kills the process
   when it first sees the migrator's backup directory or its staged file. Where the kill lands is observed and
   recorded. In all four runs (two shake-out runs and two campaign runs) it landed before the commit. A stop after
   the atomic replacement is the `UPGRADE_AFTER` case; a stop between the replacement and the end of the data check
   was never observed.
4. **The legacy hold is exercised, not assumed.** A plain start has no probe that loads the fixture chunk, and the
   hold itself logs nothing. Each upgrade start therefore force-loads both endpoints for at least 200 ticks
   (reconciliation retries a held operation every 20 ticks) and asks the server with
   `arce escrow inspect <operation>`; the answer must contain `accounting=UNKNOWN_BASELINE`. The control is the
   restored root-2 world on the root-2 JAR, where the same open operation completes.
5. **Verdict of the old-JAR case.** It follows the existing downgrade family: any world file changed by a refused
   start fails the case, and the campaign reports the family FAILED. It is not an expected-failure pass.
6. **One line in another task's test.** `tests/test_run_v180_x03_repair.py` looked up the X03 family as the last
   family. The six new families are appended after it, so the test now reads row 71, where X03 stays. Its assertions
   are unchanged.
7. **Re-pinned inventory counts.** These follow from added cases only: the settlement probe's cases 40 to 54 (the 40
   earlier cases are also pinned separately, unchanged), the probe-case inventory 677 to 692 tokens, its direct
   producers 24 to 25 and its related tests 42 to 44, and the campaign's families 72 to 78. A full campaign now also
   needs `--root2-jar` and `--root2-jar-sha256`; the two existing tests that build a full plan supply them.
8. **Independent families.** In the existing driver a failed family stops the later families of the same runner. The
   six accounting families are marked independent, because the TASK asks that a finding stops its own case only.
9. **Loader sessions.** In the first campaign the loader family failed before any server start: nested under the
   campaign's long session name, the copied Forge libraries exceeded Windows' 260-character path limit
   (`WinError 3`). The runner now puts the loader runner's sessions in a short sibling directory and removes it when
   it is empty. The family then passed. The shorter shake-out paths had not shown this.
10. **Fuel loader scope.** The loader cases of W373B cover L1, L2, the chained bank and the ambiguous replacement.

  operator archives older backups, as design section 4.2 documents. This is a refusal of the whole world start, not
  a hold of one object. An upgraded world is not refused: the migration returns before the backup step when no
  managed file needs migration, however many backup directories exist. A stale staged file is never removed: a
  killed process cannot run its cleanup, and a later start cleans only the files it staged itself. A staged file is
  not a backup slot. This follow-up does not change the limit and deletes no backup.

### 9.4 Changes to the TASK's plan, and choices where it was open

1. **How the probe changes a held loader.** A live protected loader refuses a replaced root
   (`ARCE_FLUID_FUEL_LOADER_LIVE_REPLACEMENT_REFUSED`), as the cargo device does. The probe therefore replaces the
   stored block entity as a whole, with the same device identity, binding and escrow section and only another tank
   amount, as W373B's cargo cases do. This models an edit outside the game.
2. **No loader substitution or bank change.** The TASK asks for a known loss and a known gain. The probe changes the
   loader's tank, as the cargo cases change the device and not the rocket. A substitution of the loader's fluid and a
   discrepancy on the rocket's bank were not attempted and stay not done (section 9.7).
3. **Pruning "before" and "after".** The loader's pruning has no checkpoint of its own. As in W373B's cargo cases,
   "before" is the tick on which the probe first sees both survivors pruned in memory, and "after" follows a full
   save. Neither is a stop inside the pruning step.
4. **The earlier cases' result line is unchanged.** The probe's result line gained `accounting=<status>` only for the
   `LF_S6_AC_` cases, because the S6 oracle compares the earlier cases' line to its end.
5. **Re-pinned counts** follow from added cases only: the loader family 6 to 23 cases, the runner's cases 58 to 75,
   the probe-case inventory 692 to 696 tokens (the thirteen reused cases only gain this runner as an origin), and the
   campaign's case counts `[17, 17, 6, 18, 3, 1]` to `[17, 17, 23, 18, 3, 1]`. Direct producers (25) and related
   tests (44) are unchanged.
6. **Campaign stopped and restarted once.** The first campaign (`followup/campaign1`) ran the loader family. While it
   waited for the lock before the upgrade family, another worker's family of about 98 cases took the lock, and the
   driver refuses to wait for a lock that is more than three hours old. I stopped my own waiting driver (its summary

   `tools/campaign_when_free.py`, which only waits until the lock directory is absent. No lock was removed or touched.
