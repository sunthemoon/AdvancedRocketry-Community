`IOWorkerPendingReadMixin` targets `net.minecraft.world.level.chunk.storage.IOWorker`.
It has one `@ModifyArg` on the argument of `Optional.ofNullable` in the `loadAsync`
lambda. A slice starts the search at the `GETFIELD IOWorker$PendingStore.data`, so the
injection matches only the pending-write branch; `require = 1` and `allow = 1` make it
fail loudly if it matches nothing or more than one call. The handler returns
`data == null ? null : data.copy()`. The disk branch and the store path are unchanged.
A comment in the class cites ADR-073.

The target was checked by bytecode in the SRG jar
`forge-1.20.1-47.4.10-srg.jar`. `loadAsync` (`m_156587_`) dispatches to the lambda
`m_223494_`, which reads `IOWorker$PendingStore.f_63565_` at offset 19 and passes it
to the first `Optional.ofNullable` at offset 22. The disk branch makes the second call
at offset 39. In the mapped development jar, the lambda is `lambda$loadAsync$4`.

## Tests

`IOWorkerPendingReadGameTests.readOfAPendingWriteIsACopy` gets the level's `ChunkMap`
worker through `chunkScanner()`.

1. It stores a gate chunk, then starts a scan of that chunk. The scan holds the IO
   thread inside its visitor.
2. It queues a store and a read of the probe chunk behind the scan, then releases the
   scan. The worker runs these foreground tasks in order, before any background disk
   write, so the read always finds the write pending.
3. It asserts that the read equals the stored tag and is not the same object.
4. It changes the read, as `upgradeChunkTag` does with `__context`, and asserts that
   the pending tag is unchanged.
5. It waits for the write, flushes the worker and reads again from disk. The written
   chunk does not contain the change.

Both chunks are at x = 1,000,000 and 1,000,001, z = 1,000,000. That is region
`r.31250.31250`, inside the world border and far from every test structure. A `finally`
block writes null to both chunks, which clears them again. Without the Mixin, the
"not the same object" assertion fails.

`MixinPackagingTest` opens the reobfuscated jar named by the existing `arce.runtimeJar`
test property. It checks:

- the `MixinConfigs` manifest entry;
- every field of the configuration, and the Mixin class file;
- that the refmap maps the lambda to `m_223494_` and `PendingStore.data` to
  `f_63565_`, in both its `mappings` and its `data.searge` sections.

## Log checker: one WARN needs a manifest entry from Root

Each development run (`runGameTestServer`, `runData`) logs this WARN once at startup:

```text
[main/WARN] [mixin/]: Reference map 'advancedrocketrycommunity.refmap.json' for advancedrocketrycommunity.mixins.json could not be read. If this is a development environment you can ignore this message
```

The annotation processor writes the refmap into the built jar only. The development
run loads `build/classes` with mapped names, which need no refmap, so Mixin cannot
read it there and says so. The passing GameTest shows that the injection still
applies in development, and the jar contains the refmap.

The TASK puts the log manifest out of scope, so I did not change
`scripts/gametest_expected_log.json`. Hosted CI will fail its log check until Root adds
this entry to `expectations`:

```json
{
  "id": "w08-mixin-development-refmap-unread",
  "level": "WARN",
  "logger": "mixin/",
  "message": "Reference map 'advancedrocketrycommunity\\.refmap\\.json' for advancedrocketrycommunity\\.mixins\\.json could not be read\\. If this is a development environment you can ignore this message",
  "counts": {"<startup>": 1},
  "test": "environment: ADR-073 Mixin configuration loaded by the ForgeGradle development run",
  "reason": "ADR-073 adds one Mixin configuration with a refmap. The annotation processor writes the refmap into the built jar only, so the development run, which loads build/classes with mapped names, cannot read it and Mixin logs this warning once at startup. The mapped names need no refmap there; the built jar contains it."
}
```

I chose an exact count of one at `<startup>` rather than a `max`, because the
warning appears once in every development run.

## Choices where the ADR or TASK was open

- Injection: `@ModifyArg` with a slice from the pending `GETFIELD`, at the first
  `Optional.ofNullable`, with `require = 1` and `allow = 1`. The method is named with its
  descriptor, so the processor writes a refmap entry for the synthetic lambda.
  `@SuppressWarnings("target")` silences only the processor's lookup warning for that
  lambda; a missing target still fails at load.
- The handler takes and returns `Object`, the parameter type of `Optional.ofNullable`.
- The GameTest calls the `IOWorker` directly through `chunkScanner()` instead of
  `ChunkMap.read`, because only the worker lets the test hold the queue and so
  guarantee that the read happens while the write is pending.
- MixinGradle 0.7.38 from the Forge Maven, with the Mixin 0.8.5 processor. The
  GameTest log shows that Forge 47.4.10 runs Mixin 0.8.5.

## Known risks

- Until Root adds the entry above, the hosted log check fails on the refmap WARN.
- The mod now depends on Mixin. Another mod that injects into the same lambda call
  could conflict. `allow = 1` makes a doubled match fail at load instead of applying
  twice.
- The SRG names are tied to Forge 47.4.10 mappings. A Forge or Minecraft upgrade must
  recheck them, and drop the Mixin if the target already copies pending data.
- The GameTest leaves an empty region file `r.31250.31250.mca` in the GameTest world,
  with both chunks cleared.
- The single run-2 failure of `catalogServiceSharesReopenBudgetAndRecoversLatestGeneration`
  is unexplained; it did not recur in the 13:39 or 15:29 runs.
