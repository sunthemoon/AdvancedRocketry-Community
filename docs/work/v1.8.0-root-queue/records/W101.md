## 3. Choices where the TASK was open

- **Where the version lives.** `ApiVersions.CURRENT = new ApiVersion(1, 9)` in
  `src/main/java/.../api/version/ApiVersions.java`. The fixture logs `ApiVersions.current()` (the host's value at
  run time) in every registration line. The helper reads that Java definition when it is imported, instead of
  keeping a second Python literal, so an API release changes only the Java constant. Its test also checks the
  value against the JUnit pin in `ApiVersionsTest` and refuses a missing, repeated or unusual definition. As
  before, a smoke must run from a checkout of the commit that built the JAR.
- **The acknowledged result.** None of the other v1.8 native runners waits for the acknowledgement line. They
  accept `JOURNAL_PENDING` or `SUCCESS` and then wait for `landed_reservation_retained`. For a release-test launch,
  v1.8 reports the acknowledgement only as `ARCE_TRANSFER_PREPARE ... code=SUCCESS`, which `RocketTransferService`
  logs inside the journal acknowledgement callback (governed path line 138, ordinary path line 205). An admin
  launch has no player report. The smoke requires exactly `JOURNAL_PENDING`, because v1.8's `prepareLaunch` never
  answers `SUCCESS` for a launch. The bounded wait is the existing 30-second flight budget, now measured once from
  the receipt across both waits, so the total limit is unchanged.
- **The startup hold.** This follows the GameTest manifest's `w44-first-moon-landing-startup-baseline` and
  `run_v180_satellite_bay_smoke.py`. The audit is stricter than both, because it also requires the clearing INFO
  line.
- **The catalog receipt.** The bundled counts come from the JAR, not a literal (11 bodies and 12 routes today), so
  the receipt still binds the unchanged bundled catalog.

## 5. Finding: the satellite fixture's `create` sends two intents in one tick

`arce_sat_fixture create` (`src/adapterTest/.../SatellitePayloadFixture.java`, lines 60 to 64) places the
terminal, fills it, and then calls `act(terminal, OWNER, 2)` (assemble) and `act(terminal, OWNER, 3)` (launch) in
the same tick. On v1.8, `SatelliteTerminalMenu.clickMenuButton` refuses a player's second state-changing intent
within `satellites.intentIntervalTicks` (ADR-049 section 10, C8a; at least 10 ticks). `act` then throws, and the
console shows only "An unexpected error occurred trying to execute that command". This cause is inferred from the
code; no log line shows the refusal, because the dispatcher hides the exception and the refusal only messages the
fake player. The inference is strong:

- The adapter GameTest uses the same `create()` helper and the same assemble click.
- It spaces the launch by 10 ticks ("ADR-049 section 10 (C8a)").
- It passes in the full GameTest runs.

This is a stale v1.3 expectation in the fixture, not a product defect, but fixing it is a Java change, which this
TASK excludes. The minimum interval cannot be configured below 10, so no script-side fix exists. For Root:

- The fixture's `create` should assemble only, with the launch as a later separate `launch` action at least 10
  ticks on.
- The smoke's reinstalled phase would then also need a 10-tick gap between its `claim` and replayed `claim`, which
  are back-to-back today.
- Until then the satellite smoke stays failing.
