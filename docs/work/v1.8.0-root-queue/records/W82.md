**B3-A, the device.** Everything sits in `rocket/fuel/loader` next to W81's codecs, except the screen
(`client/FluidFuelLoaderScreen`).
- `FluidFuelLoaderBlockEntity` holds one `LoaderRoot` exactly as loaded or last written, so an unsupported
  root (future, invalid, oversized or naming an unregistered Fluid) is saved unchanged; an over-bound root
  is kept by reference. `onlyOpCanSetNbt()` returns true.
- **Port.** One `FLUID_HANDLER` port, the same object for every side and the null side, bound to an epoch
  that every lifecycle event (removal, chunk unload, `invalidateCaps`, a data replacement) advances. Fill
  and drain need a claimed, supported, unlocked, unique device on the server thread with no call in
  progress; anything else returns zero or empty. Simulation writes nothing. There is no capability on the
  client or for an unsupported root.
- **Intake refusal (Root's decision).** `LoaderTank.escrowCarriable()` is the payload bound that
  `EscrowOperation` enforces (8,192 bytes, depth 12, 384 nodes). The port, `isFluidValid` and local
  container use refuse a Fluid outside it. The tank codec's bounds are unchanged, so such stored data still
  loads and can be drained.
- **Menu.** No slots and no buttons; six scalar values (amount, capacity, the low and high halves of the
  session's numeric Fluid ID, the status ordinal, and whether a binding is held). Only the owner within 8
  blocks opens it; operators and an unclaimed device get nothing. `stillValid` checks the exact block
  entity, its load state, the owner and the device UUID it opened on. There is no new packet or channel.
- **Carrier.** The loader item is the carrier (`stacksTo(1)`); it holds `arce_fluid_fuel_loader_carrier`
  and refuses any `BlockEntityTag`. A break or an explosion of an unprotected device drops exactly one
  carrier with the owner and the tank. Placement takes a fresh device UUID, no binding and the owner rule:
  the placer when the carrier has no owner or theirs, the carried owner for an operator, and an unclaimed
  device for a non-operator with another player's carrier.
- **Protection.** An escrow-locked device (a marker in its section, or a durable ledger record naming it)
  or an unsupported root refuses player break before loot, leaves explosions, drops nothing, refuses a
  live `/data` replacement, and logs one line when `/setblock` or another raw replacement removes it.
- **Status.** The ticker runs one attempt per 20 ticks through W81's `RefillPacer`, which is not saved, so
  a loaded device waits a full interval. An attempt checks the binding, the rocket, both resource layers
  (`RocketEscrowGate.idle`, `RocketRuntime.resourceMutationAllowed`) and `BankSelection`, and where a fill
  would start it gives `ADMISSION_DISABLED`. It never captures, reserves or moves anything.
- **Linker.** Use on a loaded loader the player owns selects it (`arce_linker`). Use on a rocket goes
  through Forge's `EntityInteract` event, before the rocket's own interaction, and binds the selection on
  the server: the logical rocket UUID, the Level, the physical UUID, the origin as locator and the
  station, if any. Sneak-use on a loader clears its idle binding; sneak-use in the air clears the
  selection. Every change starts a 10-tick item cooldown.

**B3-D, the data.** `V180FluidFuelLoaderData` writes the blockstate, block and item models, the loot
table, the two recipes and their unlock advancements, and draws four original 16 x 16 textures with the
existing `V180MaterialArt` encoder: the loader's tank side, port top and base, and the linker icon. The
loader recipe is shapeless: `advancedrocketrycommunity:empty_pressurized_tank`, a `liquid_io_board`, a
`control_board` and a `machine_casing`. The linker recipe is a `tracking_circuit`, an iron ingot and
redstone. English and Chinese text covers both items, all twenty `FluidFuelLoaderStatus` members, and the
menu, carrier and linker messages (43 keys in each language).

## Choices where the design was open

- **Status order.** The TASK asks for `ADMISSION_DISABLED` "where a fill would start". An attempt therefore
  runs the device, binding, rocket, resource-layer and bank checks first, so the owner sees `UNBOUND`,
  `OUT_OF_RANGE`, `BANK_FULL` and the like, and shows `ADMISSION_DISABLED` where `READY` would be. Taking the
  design's first eligibility item (escrow storage enabled) literally would show `ADMISSION_DISABLED` always.
  `RocketEscrowGate.idle` false maps to `ESCROW_PENDING`, and `RocketRuntime.resourceMutationAllowed` false to
  `TRANSFER_JOURNAL_UNPROVED`. Before the first paced attempt the menu shows the device refusal, if any, and
  otherwise `ADMISSION_DISABLED`, which is true of this build in every case.
- **Escrow-locked.** A marker in the section, or a durable record of an existing ledger whose source or
  destination identity is the device UUID. Reading never creates a ledger. Because
  `ResourceEscrowSavedData.existing` touches the disk when no ledger exists, the ledger half is cached for one
  game tick. Queued, captured and UNKNOWN operations and tombstones need the loader's endpoint key, which
  B3-E defines; B3-E must extend the check.
- **No new save refusal.** An unsupported root is saved verbatim (by reference when over its envelope).
  Section 6's proposed R-035 text also routes observed native incompatibility through `GuardedChunkSaves`;
  that is a save refusal, which AGENTS.md section 3.3 ties to a risk-register entry and an ADR note, so it is
  left to Root and B3-E.
- **Duplicate device IDs.** A transient per-Level index (a Level capability, as `TankTransfers` uses) maps
  device UUIDs to loaded loaders. The first loaded holder keeps a UUID; a second copy reports `INVALID_DATA`
  and refuses its port, menu and linker until the first leaves. It is disabled, not protected, so it can be
  broken normally. Copies in different Levels are not detected.
- **Duplicate rockets.** Another loaded rocket entity with the same logical ID inside the device's 6-block box
  or the bound rocket's box makes the binding `STALE_BINDING`.
- **Distances.** The rocket's bounding box must be within 6 blocks of the device centre; the actor must be
  within 8 blocks of the device centre and of the rocket's bounding box.
- **Rate limit.** One change per 10 ticks uses the linker's vanilla item cooldown, which is per player, ends
  with the player and needs no static map. A refused request starts no cooldown. A request that would write
  the binding the device already holds is refused as a replay (`ALREADY_BOUND`).
- **Entity use.** The binding runs in Forge's `PlayerInteractEvent.EntityInteract`, which fires before
  `RocketEntity.interact`, so `RocketEntity` (which W11b2 changes heavily) is untouched; a linker used on a
  rocket never opens the rocket's menu or exchanges fuel.
- **Placement and breaking.** Placement by anything but a connected, non-fake player leaves the device
  unclaimed; a bare block (`/setblock`) has no root and breaks into an empty, ownerless carrier. Breaking an
  unprotected device is not restricted to its owner (as for vanilla containers); the carrier keeps the owner
  and the owner rule decides on placement. The loot table has no explosion condition, so an explosion never
  destroys the carrier at random.
- **Local container use.** Block use with a Fluid container goes through the existing
  `TankContainerExchange` (whole 1,000 mB units), for the owner only and never while locked; other held items
  pass, so blocks can be placed against the loader.
- **Menu.** The binding is shown as a flag; no coordinates are sent.
- **Ingredient.** `{"type": "advancedrocketrycommunity:empty_pressurized_tank"}` takes no parameters, so a
  recipe cannot widen it; both recipes are shapeless.
- **Class size.** `FluidFuelLoaderBlockEntity` has 576 lines (51 of them comments). It has one
  responsibility, adapting one root and its surfaces to the block-entity lifecycle, and stays under the
  800-line ADR threshold; the port, eligibility, index, menu and linker logic are already separate classes.

## Known risks

- The intake bound repeats `EscrowOperation`'s payload literals (depth 12, 384 nodes); if W11b2 changes them,
  `LoaderEscrowPayloadBoundTest` fails, which is intended.
- Within one game tick, a new durable ledger record does not yet lock the device (the per-tick cache). B3-E's
  admission must check under its own owner-thread action rather than rely on this read.
- The rocket structure scan floods through all six neighbours, so a loader touching a rocket's blocks is
  captured and refused for want of an adapter, as the item fuel loader is. Players must leave a gap; a scan
  exclusion would be a separate change.
- The duplicate-ID index is per Level and transient; an operator's NBT copy in another Level is not detected.
- Early in this session I started two read-only Explore subagents for code search and stopped them within a
  minute, before they returned anything, when I noticed that WORKER-RULES forbids subagents for a Claude
  implementer. Nothing they produced was used, and they wrote nothing.
