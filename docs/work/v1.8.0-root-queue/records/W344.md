### Cause

The supplied shard log starts `bay_exit_delayed_one_box` at 00:07:21.558917 and reports
the 400-tick timeout at 00:07:23.164073, about 1.6 seconds later. There is no area-install
marker for this test. Its setup's only early return precedes player/flight creation and
requires `areEntitiesLoaded` and `isPositionEntityTicking` for every column in a 3x3
square. Thus the missing prerequisite was fixture readiness, not exit arbitration.
The historical log does not identify the particular column or which of those two
predicates was false; it would be unsupported to identify only entity loading as fact.

The local bay runs directly observed both forms: loaded-but-not-ticking columns, and
columns with neither predicate ready. The new `ARCE_BAY_EXIT_READINESS` line records
each initially missing column, both predicates, elapsed milliseconds and the test tick.
For example, the first bay run's HISTORY case began with both predicates false in five
columns and finished loading in 28 ms at test tick 0.

W122 and the earlier GameTest pacing handoff explain the scheduling: GameTest's
`waitUntilNextTick` runs queued tasks without sleeping, while native entity loading
requires IO, server-task deserialization and entity-manager integration. The local
mapped-jar `javap` outputs confirm these mechanisms. Four hundred accelerated ticks
therefore do not provide the twenty seconds they would on a 20 TPS server.

### Implementation and files

- `gametest/EntitySections.java` exposes a setup-only `awaitReady` using W122's existing
  managed-block algorithm. The original single-chunk `loadNow` delegates to it with
  its unchanged condition. Server tasks, at most 256 chunk tasks per poll, and the
  Level's entity-manager tick can progress without advancing the GameTest clock.
- `rocket/server/BayPassengerExitGameTestReadiness.java` holds exactly the same nine
  columns, tracks only newly forced columns for the existing cleanup, and awaits the
  original loaded-and-ticking condition. It uses W122's 600-second wall-clock setup
  bound and asserts that no measured test ticks elapsed. It runs before any player,
  transfer, exit or ticket/chunk audit exists.
- `rocket/server/BayPassengerExitGameTestFixture.java` delegates only its initial
  readiness phase. An optional fixture-local predicate supports the regression.
- `rocket/server/BayPassengerExitReadinessGameTests.java` adds one isolated batch,
  `bay_exit_late_readiness`, with its own leftover-fixture cleanup hook.
- This record is the only documentation change. All Java paths above are relative to
  `src/main/java/io/github/sunthemoon/advancedrocketrycommunity/`.

The original 400-tick annotations, 70-tick rider wait, measured exit, exact winner/loser
results, work limits, authority assertions, ticket census and loaded-chunk audits are
unchanged. No ADR decision or exemption was introduced.

### Siblings and regression

All **51** ordinary and **8** connection-ticked bay exit GameTests use this fixture,
so all 59 receive the same setup fix. Both bay-only runs also included the three
existing area tests and the new regression: 63 tests per run.

The comparable preflight loops in `RocketLogoutGravityGameTests.ready`,
`RocketLogoutSaveGameTests.Scenario` and `RocketResourceRecoveryGameTests.whenReady`
already pace their readiness waits. The paired checks in `EscrowCargoGameTestWorld`
and `FluidFuelLoaderEscrowFixtures.Area` are called by paced scenario frames. They
were inspected and left unchanged. Production-phase and deliberately cold/unloaded
checks were not converted to setup waits; unrelated fixtures were not rewritten.

The new regression holds an additional fixture-only readiness predicate false for
450 checks. It first releases at check 451, asserts that the test clock has not advanced,
and then executes the existing DELAYED_ONE_BOX scenario and all its original assertions.
The fixed runs log `checks=451 test_tick=0`, including the full suite.

The negative control reinstated the original once-per-tick setup loop, with the same
injected predicate. It failed exactly at the unchanged 400-tick timeout, with no exit
area installed. The external `negative-control.patch` reproduces this development-only
control against `3b87767ae`. It was removed before all final bay/full runs;
`git diff --exit-code` confirmed exact restoration. It is not delivered source.

### Runner incidents

Two initial launch attempts aborted because Windows PowerShell treated native stderr
as a terminating error: first the expected busy-lock `mkdir` error, then the JVM's
`JAVA_TOOL_OPTIONS` banner. The runner was corrected to use exit codes; the successful
four-test run is in `focused-verified-runner/`, not either aborted folder. Bare `javap`
was absent from PATH; the explicit JAVA_HOME executable succeeded.

After the successful build, the runner's default-encoding XML summary reader failed
on UTF-8 output in GroundSurveyCodecTest. Gradle had already written exit 0 and BUILD
SUCCESSFUL, and the lock was released in `finally`. Reading the same XML with
`[IO.File]::ReadAllText` recovered 6,454 tests and zero failures/errors/skips. Both the
failure and recovery are retained; `run-heavy-executed.ps1` preserves the executed
runner, while `run-heavy.ps1` contains the corrected reader. No product/test fix or
second build was needed for this postprocessing error.

push and hosted regression remain. v1.8.0's G0-G9 are not all satisfied or approved by
this slice; version/Gate status files are untouched.

that cannot establish readiness within 600 seconds fails explicitly at setup. The old
shard's exact missing column/predicate cannot be reconstructed from its logging.

by the hosted v1.8.0 regression. The change can be reverted as one test-only source
