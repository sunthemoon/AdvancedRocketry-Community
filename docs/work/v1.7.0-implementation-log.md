# v1.7.0 implementation log

## Goal and scope

Deliver [Endgame Systems](../versions/V1.7.0-ENDGAME-SYSTEMS.md): representative
vertical slices of the orbital laser drill, the railgun cargo launcher with its
targeting, black-hole power, the area gravity controller and space-elevator
logistics, each with its own permission, protection, rate, energy, audit and
recovery boundaries. Development evidence does not approve a release or remove
inherited Required Gates.

The v1.6 handoff is a development baseline, not a passed prerequisite. ADR-053
must separately authorize this version before any runtime change. Root is the
sole tracked writer. Independent review uses read-only repository access and
fresh Temp outputs. The untracked user documentation bundle stays excluded from
reads and writes. No upstream code or asset is imported.

Implementation decisions for the C11 review:

  quarantines the whole root. A block entity without a root gets a new ID;
  a root that exists but lacks an ID is quarantined (§2 read as: "without

- The drill's structure is 3 × 3 × 3 Endgame Casing with the controller in
  the middle of the front face (community-authored). Nothing operates

### C11c progress (2026-10-02)

Committed in parts: `df344db` (shaft geometry, classification, counter
steps, codes), `36afa15` (endpoint registration, removal and freeze, the
`laser_target`, tags, beam renderer) and `3006637` (link, selection,
confirmation, layers, debt and credit, GameTests).

Implementation decisions for the C11 review:
- Layer classification order: the first cell, in cell order, that is immune
  or a fluid stops the layer (`BLOCKED_IMMUNE` or `BLOCKED_FLUID`); break
  events are posted only when no cell is immune or fluid.
- Contacts settle a debt whatever the switches and whether the drill runs
  (ADR-054 §1 settlement); credit layers and new layers need every breaking
  condition. A stopped layer takes no payment.
- **Link identity (refinement of §3, for the review).** Each link has a
  `link_id`, stored by the controller and by the marker next to
  `controller_id`. A marker accepts only the link it adopted. Without it, a
  controller relinking a marker it served before would count that marker's
  old `ops_done` as a debt of the new link. A reset remembers the last 8
  link IDs it dropped, so their controllers see `LINK_LOST` (as §3 requires)
  (replaced after the C11 review by the marker generation, C11R-M1, below)
  instead of adopting the marker again with a free credit; a marker that a
  crash returned unlinked still adopts its link and settles it as credit.
- Mode, link and unlink stop a running drill, so physical work always
  restarts through the 200-tick confirmation. A new link counts as settled
  until its first contact.
- Selection lists only `ACTIVE` targets whose footprint is inside the chunk,
  owned by the drill's owner (any owner for operators), in ID order.
- One audit line per physical layer (marker, y, cells, items), as ADR-055 §6
  lists it, plus `DEBT_SETTLED`, `CREDIT_USED`, `LINK_ABANDONED`,
  `MARKER_RESET` and a protection notice at most once per 1,200 ticks.
- Endpoint registration is in its own class (`EndpointRegistrations`);
  candidates are an immutable snapshot read by chunk-load threads.
- Tag files omit `"replace"`, which means `false`.
- The controller block entity is 577 lines (587 after the C11 review
  fixes) with a single responsibility (the controller's lifecycle bridge);
  storage, physical engine, link and button effects are separate classes.
- GameTest fixtures post the `ChunkDataEvent.Save` a save would post, because
  vanilla throttles real saves of one chunk to one per 10 s of wall time.
- A GameTest found a crash in the first link (abandoning a link that did not
  exist); fixed before the commit.

### C11 review fixes (2026-10-02)

The independent review of C11a–C11d (at `8d52d7f`) accepted C11a with
required changes and C11d, and rejected C11b and C11c until their findings
are fixed. Each finding is fixed in its own commit. Rounds 2 and 3 accepted
all four slices; the [C11 review packet](v1.7.0-c11-review/VERIFICATION.md)
holds the dispositions, the tests, the evidence run at `6ace111` (1,304
JUnit tests, 321 GameTests) and the three reports.

- **C11R-C1** (partial shift-click not persisted): device menu slots are
  `EndgameItemSlot`s, which forward `setChanged()` to the owning block
  entity. Forge's `SlotItemHandler` returns the handler's live stack and its
  `setChanged()` reaches only a dummy container, so a partial move out of a
  slot or a merge into a non-empty slot changed the stack without marking
  the chunk. Covers the drill's lens and output, the laser target buffer
  and the generator's fuel; GameTests save a chunk after a partial move.
- **C11R-C1, older menus**: the review asked to check the repository's other
  `SlotItemHandler` menus. The satellite terminal and builder (v1.5/v1.6)
  hold up to 64 redstone in their charge slots and had the same defect; their
  slots now mark the block entity changed too (separate commit, GameTest for
  both). The machine menus write moved stacks back with `set` and the
  microwave receiver's slots hold one item, so neither was affected.
- **C11R-M1** (8 revoked links): the marker keeps a `generation` that every
  reset raises and never lowers, in place of the bounded revoked list; the
  controller's link records the generation of its first contact (`-1`
  before). An unlinked marker adopts only a link that never touched it or one
  recorded at its current generation, so no number of later links and resets
  brings an old link's credit back, while a marker a crash returned unlinked
  still settles its link. The marker root and the drill's link gain a
  required `generation` and the marker loses `revoked`; no world with the
  earlier development format exists outside test runs (v1.7 is unreleased).
- **C11R-H2** (slots ignored `WITHDRAW`): device menu slots take only with
  `WITHDRAW` and put only with `CONFIGURE`, decided on the server for the
  menu's viewer at every click (and in shift-clicks); a data slot shows the
  decision to the client. A viewer with public `VIEW` (a stranger outside
  stations, a station member) sees the slots and changes nothing. Putting
  a lens or fuel counts as `CONFIGURE`; automation is unchanged.
- **C11R-H1** (attached blocks counted twice): a physical layer removes
  cells without a full collision shape (torches, ladders, buttons, levers,
  cocoa, amethyst buds) first, then the rest, each group in cell order, so
  hanging blocks are removed before their supports. A cell whose block an
  earlier removal of the same layer already destroyed through a vanilla
  neighbour reaction is skipped with its planned drops (vanilla dropped or
  kept them), so no drop is counted twice. This refines the ADR-055 §3
  removal step for the C11 re-review; events and the whole-layer check are
  unchanged.
- **C11R-M2** (`device owner` left the index): for a registered endpoint
  the command first moves its record with `reassign` as a barrier, within
  the new owner's endpoint limit (`ENDPOINT_LIMIT` refuses it), then
  changes the block entity; a laser target given to another owner resets
  its link (generation + 1), so the old owner's drill sees `LINK_LOST`.
  A quarantined device and an unavailable root are refused first.
- **C11R-M3** (refused forget wrote the root): `endpoint forget` decides
  every refusal on the read view, so a refusal neither changes nor writes
  the root and adds no audit line (ADR-054 §13 audits state changes and
  operator commands); a record of another player is reported as
  `ENDPOINT_NOT_FOUND`, so the command reveals nothing. A successful forget
  is a coalesced mutation, not a barrier.
- **C11R-M4** (`WITHDRAW` unreachable): a device menu opens and stays open
  with `VIEW`, or with `WITHDRAW` alone where `VIEW` is refused (the owner or
  an operator at a device in an unavailable station). Such a withdraw-only
  menu takes items, puts none, refuses every button through the intent
  guard, and its view carries only the refusal code.
- **C11R-L1** (events twice per layer): the layer grant is taken before the
  layer is planned, so the effect event and the break events are posted once,
  in the tick that may run the layer; a grant used by a stopped plan is spent.
- **C11R-M5** (index rebuilt per mutation, housekeeping per tick): the root
  records the IDs each mutation touched, and the service moves only those
  IDs between chunk entries of its index (a concurrent map of immutable
  sets, read entry by entry from chunk threads); the full build runs only
  when the root loads. Housekeeping runs at most once per 200 ticks and
  counts tombstones without copying them. The reviewer's benchmark, rerun
  on the fix: 1,024 endpoints with 3,840 settled tombstones, idle tick
  0.001 ms and a no-op call 0.002 ms (were 0.033 and 0.98 ms); with 8,192,
  0.008 and 0.001 ms (were 1.26 and 0.95 ms). A unit test checks the index
  against a full rebuild after every kind of mutation.
- **C11R-L3** (crash paths from unbounded IDs): `register` refuses a kind
  over 64 or a Level key over 128 characters with `TARGET_OUT_OF_BOUNDS`
  (the code a marker shows for a place the endgame cannot record) instead
  of throwing in the server tick; laser table and black-hole data file IDs
  over 128 characters fail the reload with the other read errors; a text
  line of a device view is cut to its byte bound (never between the halves
  of a surrogate pair) instead of failing the view.
- **C11R-L6** (trust list without a schema): the consent list is stored as
  `{schema_version: 1, owners: [...]}`; the bare list of the C11 development
  format still reads and is rewritten with its schema on the next change.
- **C11R-L4** (32-bit Level hash): the service indexes ACTIVE records and
  young tombstones by the full Level key; only settled tombstones, which
  keep just the hash, stay keyed by it (housekeeping read-back only), and
  candidates wait under the full key. A save in one Level is never read as
  an absence in another whose key has the same hash (unit test with two
  colliding keys).
- **C11R-L5** (registration relied on incidental saves): a marker waiting
  for registration marks its chunk changed at every status check, so the
  next autosave or the unload save registers it; vanilla writes the unload
  save before it removes block entities, so the candidate is still waiting
  then. The GameTest runs one status check in its own tick, because vanilla
  saves dirty chunks eagerly between ticks.
- **C11R-L8** (per-session map, unpaged lists): a registration result is
  kept only while it explains a refusal and is dropped when the endpoint
  registers, unloads or is removed; `zone list [page]` and
  `endpoint list [player] [page]` page through 16 lines at a time.
- **C11R-I7** (quarantine line): the `ARCE_ENDGAME_DEVICE_QUARANTINED` line
  carries a reason cut to 256 characters on one line. It stays a server log
  line as ADR-054 §2 names it; the device package does not depend on the
  service that owns the audit ring.
- **C11R-L2** (tests proved a model the engine did not use): the physical
  engine takes every counter step from `LaserLinkCounters.next` and every
  contact decision from the new `LaserLinkCounters.accepts`, which the
  marker uses too; the model test covers resets, relinks and a
  crash-restored marker. A GameTest drives the debt cut (a marker two layers
  ahead: `ENERGY_DEBT`, one payment per layer as energy arrives, nothing dug
  meanwhile) and the credit cut (a controller two layers ahead: two layers
  dug without payment, then `INSUFFICIENT_ENERGY`) on the real engine,
  through test-only counter setters.
- **C11R-I8** (`endpoint forget` from `/execute as`): the command acts only
  for the player's own, connected, non-silent source, through the helper
  `field trust` already used (now shared as `EndgameCommandSources`).
- **C11R-L7** (missing tests): besides the tests named above, a GameTest
  unloads a linked marker's chunk and finds the drill stopped with
  `TARGET_UNLOADED`, the chunk still unloaded 60 ticks later, nothing paid
  and the record ACTIVE; the physical-shaft and gravity-field GameTests
  count chunk tickets by type around the system's chunks before and after
  (player, transient, fixture and rocket-flight tickets of other tests are
  left out of the count).
- **C11R2-L1** (round 2; an owner change before registration registered the
  old owner): a laser target given to another owner waits again under the
  new owner in the same tick, so a save right after the command registers
  the new owner, and a request queued from an earlier save no longer
  matches the waiting candidate and is skipped. GameTest.
- **C11R2-L2** (round 2; `EndgameService` over 500 lines without a
  responsibility check): the chunk index moved to `EndpointChunkIndex`
  (with its `ChunkKey`), leaving the service at 444 lines for the root's
  lifecycle and write policy, observations, housekeeping and diagnostics.
  The drill block entity is now 587 lines after the review fixes, still a
  single responsibility (its controller lifecycle bridge).
- **C11R2-I4** (round 2; test-file hygiene): a duplicate import removed and
  a helper's Javadoc moved back above its method.
- Round 2 Info items recorded without a change: C11R2-I1 (the skip rule can
  leave a block a same-layer reaction transformed, and blocks vanilla drops
  then lie in the shaft; the C13 operator guide says so), C11R2-I2
  (`TARGET_OUT_OF_BOUNDS` also covers a key too long to record), C11R2-I3
  (C11 development-format roots quarantine; never released) and C11R2-I5
  (a v1.3 rocket GameTest,
  `assemblyRollbackExceptionRetainsSnapshotForLaterRestoration`, failed once

   live state, redirects, the registration freeze and resolve.
2. The root section: `TransitTable` (at most 256 records in key order),
   the strict `TransitCodec`, and `EndgameRoot` integration (registration
   sets `dispatched_through`, pins, accounting, restore checks).
3. Endpoint state: `TransitSourceState` (`next_seq`, outbox of 4),
   `TransitDestinationState` (incoming, receipts of 64, frozen conflicts),
   `TransitTags` (what a chunk tag shows of them) and `TransitLedgerView`
   (what their reconciliation asks of the ledger).
4. The server side: `TransitLedger` (END-tick passes, observations,
   admission, removal settlement, retirement), its wiring into
   `EndgameService`, the transit codes and two COMMON limits.
5. Operator and owner actions: `TransitOperations` (redirect, purge,
   resettle, resolve, list, inspect) and `TransitCommands`
   (`/arce endgame transfer list|inspect|purge|resettle|redirect` and
   `/arce endgame endpoint resolve`).

Implementation decisions for the C12 review:
- The three C10 reference models (`Transit`, `Delivery`, `Redirect` in
  `check_examples.py`) are ported to JUnit with every protocol decision
  taken from `TransitRules`; the ports reach the pinned state counts of
  `examples.json` exactly (72,618; 24,011; 27,578; 1,385 and 33,057;
  1,622; 4,011; 8,122) and the same outcome classes, named cuts and
  reproduced findings (F02, R2-H1, R3-H1). Three mutations of the rules
  (registration without the aged observation, receipts dropped before the
  acknowledgement is durable, registration despite held contents) each
  fail the tests.
- Registration waits for the source's lowest outbox entry overall, as the
  reference model does, so an entry whose record is not yet durable holds
  the later ones back; the ADR's "lowest entry above `dispatched_through`"
  delivers the same payloads, only earlier.
- A payload is checked against the vanilla item registry view, which Forge
  fills with every mod item, so decoding needs no Forge bootstrap in tests.
- `EndgameNbt` moved to `endgame.model`, so the root depends on the transit
  package and never the reverse.
- A tombstone that any transit record names (source, destination or paid
  endpoint) is pinned: the caps, housekeeping and `tombstone evict` skip
  it. A decoded root must show every named ID as an endpoint or tombstone,
  every record at or below its source's `dispatched_through`, and no epoch
  above the root's save epoch.
- `EndgameRoot` is 524 lines after the transit section: it stays the §10
  container (sections, their accounting and cross-checks); record logic
  lives in `TransitTable` and encoding in the two codecs.
- An endpoint keeps its transit state under the device-root key `transit`:
  `next_seq`, `outbox`, `incoming` (key and raw payload), `receipts` and
  `conflicts`. Observation ticks (when a chunk tag showed an item) are
  runtime state; an item counts as persisted and aged 40 ticks after the
  first tag that showed it.
- Destination rows run in a fixed order per record (recover, claim,
  acknowledge, rematerialize), then the incoming gate, then receipts, all
  decided by `TransitRules`. A claim or rematerialization needs room for
  the whole payload beyond what incoming payloads already reserve, and a
  free receipt slot.
- An incoming payload or receipt whose record names another endpoint
  (only an operator's file restore can cause it) is frozen with
  `REDIRECT_CONFLICT` (`REDIRECT_DOUBLE_PAY` for a claim paid elsewhere)
  until an operator resolve. An incoming payload that no longer decodes is
  frozen too (`INCOMING_QUARANTINED`), and a record whose payload no longer
  decodes is quarantined instead of claimed.
- The ledger passes run in the END handler after observations, absence
  settlements and housekeeping: arrival (at most 64 records, in `arrive_at`
  order), payload drops of durably acknowledged records (stubs), then the
  reconciliation of the loaded ledger endpoints in ID order, round-robin
  from the last one served, within 64 records and 32 registrations per
  tick. A source also reconciles right before each escrow.
- An observation of an endpoint that is not loaded yet is kept (at most
  1,024 endpoints, oldest dropped) and applied when it loads, because a
  chunk's Load tag is drained before its block entities load.
- A stub is pruned when a tag of its paid endpoint's chunk, at least 40
  ticks after the acknowledgement, holds no incoming payload for it; an
  unreadable endgame block entity at the endpoint's position counts as
  holding it. Acknowledgement ticks are runtime state, so a record
  acknowledged before a restart counts as old.
- Escrow admission: the source's registration is durable (else
  `AWAITING_WORLD_SAVE`), the server's records, stubs and known outbox
  entries stay under `endgame.transitRecords` (≤ 256) and the owner's live
  records and known outbox entries under `endgame.transitPerOwner` (≤ 32)
  (else `TRANSIT_LIMIT`), and the accounted root stays within 3 MiB (else
  `ROOT_FULL`). "Known" means the outbox entries of loaded sources without
  a record. A registration is admitted up to 256 records and 4 MiB and
  otherwise waits with `ROOT_FULL`.
- Removal settlement runs one barrier flush when it settles a record or a
  registered entry's record is not durable yet, else a coalesced change; a
  failed barrier logs `REMOVAL_SETTLEMENT_PENDING` once and the status shows
  it until a write succeeds. `MISSING` returns unacknowledged claims paid at
  the endpoint to `ARRIVED`; `endpoint retire` also prunes its stubs.
- The registration freeze reads the tag's transit section: an unregistered
  copy carrying outbox entries, incoming payloads or receipts is frozen.
- A redirect needs a record that is not claimed, a destination that is no
  longer ACTIVE, an ACTIVE target with a durable registration, the same
  owner for a non-operator, and the system's route rule (registered by
  ADR-056 and ADR-059; without one every redirect is `ROUTE_REFUSED`). A
  pending root is written first, so the destination's removal is durable
  before the redirect; it stays `ROOT_BUSY` if that write fails. Owners
  redirect only from their own connected player source, within the shared
  20-tick player barrier spacing.
- `transfer purge` removes a record (its payload is destroyed, and
  `dispatched_through` stays) or a quarantined outbox entry of a loaded
  source that has no record. `transfer resettle incoming|moved` applies the
  logged outcome of a lost removal settlement to a claimed, unacknowledged
  record whose paid endpoint is no longer ACTIVE.
- `endpoint resolve` settles a frozen (retired) endpoint item by item: an
  outbox entry returns to the input buffer only when the tombstone proves
  it unregistered (seq above `dispatched_through`), an incoming payload
  joins the receive buffer only when its record is claimed here (and is then
  acknowledged), everything else is destroyed with an audit line and the
  payload hash, and receipts are dropped. An item that does not fit stays
  frozen and counts as `left`. A registered endpoint resolves only its
  frozen conflicts. Breaking a frozen endpoint runs the same resolve with
  every returned or moved payload dropped with the block.
- The destination state's `incoming`, `receipts` and `conflicts` views are
  copies in key order, so settlements and resolves process payloads in the
  same order on every run.

The ADR-056 railgun on the C12b ledger: `RailgunRoute`, `RailgunLaunch` and
`RailgunSettings` (pure), `RailgunLauncher`, `RailgunStorage`,
`RailgunBlockEntity`, `RailgunBlock`, `RailgunMenu`, `RailgunRedirectRule`,

Implementation decisions for the C12 review:
- The pattern is 3 × 6 × 3: a casing base with the controller in the middle
  of its front edge, an iron-block barrel four high in the middle and a casing
  muzzle; the 32 cells around the barrel are air or casing (`optional`).
- An endpoint's body is the ADR-014 resolver over one captured catalog, with
  the station-region resolver first, and its star system the catalog's root
  for that body (`EndgameStations.body`). It reads the station registry and
  the catalog, never a chunk.
- The distance is the integer square root corrected by division, so no
  product overflows even at the ends of the 64-bit range; the C10 vectors
  match exactly. Class, cost and travel are fixed in the outbox entry.
- A launch intent (`OPERATE`) runs a dry check and reports a refusal with its
  code at once; an accepted launch waits for the railgun's 20-tick cadence and
  a grant of the server's per-tick cap (round-robin in railgun ID order,
  `endgame.railgun.launchesPerTick` ≤ 4), then the check runs again after the
  source reconciliation and the escrow takes the stack and the cost in one
  tick. Neither the cadence nor the cap is a refusal: work waits (ADR-054 §7).
- Refusal order: ADR-056 §4's order, with the framework's conditions where
  they are first known: `ROOT_UNAVAILABLE` first; the railgun's own state
  (`UNOWNED`, `ENDPOINT_RETIRED`, its endpoint status, its structure) after
  authority; `PAYLOAD_TOO_LARGE` after `NO_PAYLOAD`; `AWAITING_WORLD_SAVE`
  for a destination whose registration is not durable yet after the route
  codes; `ROOT_BUSY` for a source rollback before `OUTBOX_FULL`; the ledger's
  admission (`AWAITING_WORLD_SAVE` for the source, `TRANSIT_LIMIT`,
  `ROOT_FULL`) last. The ADR's `NOT_AUTHORIZED` is the framework's
  `UNAUTHORIZED`.
- With `auto` and the redstone mode satisfied, a railgun asks for a cap slot
  only when it has a payload and a destination; a refused automatic attempt
  waits one cadence and is audited only when its code changes.
- An operator may select another owner's railgun; the root records
  `operator_target`, which lets the route rule's owner check pass at launch,
  and the next selection by anyone else clears it. An owner change clears the
  destination and `auto`.
- Claims, moves and acknowledgements run in the ledger pass whatever the
  structure or the switch, so a disabled railgun still receives. A frozen
  railgun exposes no capabilities, and its break resolves it.
- A player who is not an operator cannot break a railgun that holds outbox
  entries, incoming payloads, receipts or conflicts (`ENDPOINT_BUSY`).
- A copy whose registered ID stands at another position (operator copy tools)
  is never attached to the ledger, and breaking it settles nothing, so it
  cannot replace or retire the registered railgun. An unloading railgun
  detaches only itself.
- The redirect rule allows another of the owner's `ACTIVE` railguns in the
  source's star system, or the source itself. The source's system comes from
  its index record, so cargo whose source is gone as well needs an operator
  purge (`BODY_UNAVAILABLE`).
- Visuals are block events: a flash and an `END_ROD` streak rising from the
  muzzle at a launch, a flash when a claim adds a receipt while loaded. At
  most 8 run at once per client Level (`RailgunEffects`, eight slots reset
  when the client Level changes). No entity is spawned.
- The menu keeps its destination list for 100 ticks and refreshes it on a
  selection button, so a view does not resolve every candidate's body.
- `RailgunBlockEntity` is 510 lines: it holds the device root (buffers,
  transit state, settings), the lifecycle (registration status, ledger
  attachment, structure) and the `TransitEndpoint` adapter. Launch decisions
  live in `RailgunLauncher`, `RailgunLaunch` and `RailgunRoute`, buffers in
  `RailgunStorage`, effects in `RailgunEffects`.
- `NO_TARGET` now reads "No target selected" for the drill and the railgun.
- The railgun GameTests run one per batch, because the tests of a batch stand
  closer together than two railguns; each build clears its volume, since
  earlier batches may leave blocks around the shared test origin. Vanilla also
  saves dirty chunks on its own, so the 40-tick checks compare against every
  save of the watched chunks, real or posted.

  top of the endpoint block.

  up from the anchor and down from the terminal while the update tag's

### C12 review fixes (2026-10-02)

The independent review of C12a–C12d (at `616b9fd`)
accepted C12a and C12c, and accepted C12b and C12d with required changes
(C12R-H1, C12R-M1 to C12R-M3, C12R-L1 to C12R-L7, C12R-I1 to C12R-I6). Each
finding is fixed in its own commit, with its test.

- **C12R-H1** (a registration names an evicted destination): the root's
  restore checks only the source and the paid endpoint of a transfer
  against the index; a destination may be unknown (its record was settled
  and evicted before the entry registered), and redirect or resolve handle
  such a record. Service test: escrow, removal, eviction, registration, and
  the written root loads again.
- **C12R-M1** (one busy endpoint starves reconciliation): a record that no
  destination row applies to (a stub, a record still in transit, an
  acknowledged claim) costs no reconciliation; a pass the 64-record budget
  cuts short stops at that record and the endpoint's next pass starts there,
  while its incoming gate and receipts still run; and the round robin moves
  past an endpoint once it had its turn. Three service tests, each killed by
  reverting its part of the fix.
- **C12R-M2** (the ride's protection owner): the commit's protection batch
  names the departing endpoint's owner, as ADR-054 §5.1 says for
  `TELEPORT`. GameTest: a zone allowing only the arrival's owner refuses a
  ride down from the station owner's terminal, and one allowing the
  terminal's owner lets it commit.
- **C12R-M3** (binds were not spaced): `BarrierSpacing` holds the ADR-054 §7
  rules. A player's bind, owner redirect or owner resolve is admitted only
  20 ticks after the last one or the last unbind; a bind, and an owner
  redirect to an endpoint in a pair, also only 100 ticks after the last one
  for that station. A refusal answers `ROOT_BUSY` before anything changes.
  Unbinds are never refused and count toward the spacing of the next
  request. Every other barrier flush (unbinds, removal settlements,
  operator actions) is exempt and counted as `exempt_barriers` in
  `/arce endgame status`. Unit tests of the rules and of an elevator-like
  redirect route; a GameTest of bind, unbind and rebind in one tick, inside
  the cooldown and after it. The validity GameTest's rebind after an unbind
  is now an operator's.
- **C12R-I6** (flaky rocket GameTests): the cause is a GameTest world kept
  between runs in `build/gametest/world`. Rockets an earlier run saved can
  load after a later test cleared its area, so the rocket fuel test saw two
  rockets; each failure saved another one, so it failed on every following
  run. `runGameTestServer` now deletes that world before it starts. With
  the world deleted, the suite passed (331) where three runs on the kept
  world had failed it.
- **C12R-L2** (resolve of a returning `MISSING` endpoint): a resolve returns
  a frozen outbox entry above `dispatched_through` whenever the ID is
  retired, which includes a `MISSING` index record (it keeps its
  `dispatched_through`), not only a tombstone. Service test.
- **C12R-L3** (a same-ID copy fed observations to the original): a chunk
  tag's transit sections carry their block entity's position, and the
  ledger applies one only when it stands at the ID's recorded position (its
  index record or tombstone) in that chunk; a copy elsewhere stays inert, as
  ADR-054 §9 says. Service test: a copy's chunk save in another indexed
  chunk does not register the source's entry; the source's own save does.
- **C12R-L4** (a refused `endpoint retire` still pruned stubs): the
  command's operation is `TransitLedger.retire`, which refuses an ID without
  an index record with `ENDPOINT_NOT_FOUND` before it returns claims or
  prunes stubs. Service test: a retire of a just-removed endpoint (a young
  tombstone) keeps the stub paid there; an indexed endpoint retires.
- **C12R-I1** (a dead `pinned` predicate): `EndgameService.pinned`, which
  pinned nothing, is gone; every settle, forget, retire, housekeeping and
  eviction passes the root's own `pinned` (a transit record or a pair names
  the ID). The root still checks its own pins as well, which the existing
  codec test covers with a predicate that pins nothing.
- **C12R-L6** (a package cycle between the root and the elevator):
  `ElevatorPair`, `ElevatorPairTable` and `ElevatorPairCodec` move to
  `endgame.elevator.model`, which depends only on `endgame.model`, Java and
  vanilla NBT and resource types; `endgame.root` imports that package and
  never `endgame.elevator`, which keeps its Forge adapters.
- **C12R-L1** (the elevator redirect rule was wider than the contract):
  apart from the source itself, a redirect target must be the endpoint of
  the original destination's kind in the current valid pair of the station
  whose region holds the transfer's terminal side (its source or its
  destination, from the index or a tombstone, as the station guard reads
  it). When neither is known any more, only the source is a target.
  GameTest: two bound stations; cargo whose destination was a terminal of
  the first is refused at the second's terminal (`ROUTE_REFUSED`) and
  redirected to the first's.
- **C12R-L5** (a constant ride-ticket count): the service status no longer
  prints `ride_tickets=0`; the device status prints `ride_tickets=` with the
  arrival tickets held, one per pending ride (ADR-054 §13). The rides
  GameTest checks both lines during a pending ride.
- **C12R-L7** (automation inherited the owner's operator exemption): only a
  launch with a player actor asks whether that player is an online operator;
  an automatic launch is checked as its owner without the exemption.
  GameTest: an online operator owns an anchor bound to a station they are
  not a member of; the automatic launch is refused and their own launch
  intent passes the access rule.
- **C12R-I5** (a bind whose write failed was live): when the bind's barrier
  write fails, the pair is removed from memory again, audited with
  `write=failed`, and the bind answers `ROOT_BUSY`, so no ride, shipment or
  warp check uses a pair that is not durable. Not covered by an automatic
  test: a GameTest has no way to make the root write fail.
- **C12R-I2** (class sizes, checked again after these fixes; none exceeds
  800 lines, and no common class imports `net.minecraft.client`):
  `TransitLedger` (554 lines) is the server side of the ADR-054 §11 ledger
  only: the END-tick passes (arrival, stub payload drops, reconciliation),
  observation routing and stub pruning, escrow admission and registration,
  removal settlement and retirement without live state. The rows are
  `TransitRules`, the per-endpoint states `TransitSourceState` and
  `TransitDestinationState`, operator and owner actions `TransitOperations`.
  `EndgameRoot` (551) stays the §10 container with the pair table;
  `EndgameService` (524) the root's lifecycle, write policy (barrier,
  coalesced, spacing), observations, housekeeping and diagnostics;
  `BlackHoleGeneratorBlockEntity` (552) the generator's one device root
  (fuel, burn, buffer), its lifecycle and capabilities; the laser drill
  block entity (593) its controller lifecycle bridge. `RailgunBlockEntity`
  is 245 lines since `CargoEndpointBlockEntity` (434) took the shared cargo
  endpoint (the 510 above is from before that).
